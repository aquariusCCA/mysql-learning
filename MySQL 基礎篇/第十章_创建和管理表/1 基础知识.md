# 1 基礎知識

返回章節：[第十章_创建和管理表](./README.md)

## 本節導讀

這一節的重點不是馬上背 `CREATE TABLE` 語法，而是先建立「建表前要想清楚什麼」的基礎觀念。

建立資料表之前，至少要先回答三個問題：

1. **這筆資料代表什麼業務概念？**  
   例如：使用者、員工、部門、訂單、訂單明細、商品、付款紀錄。

2. **這些資料應該放在哪一層、哪一張表？**  
   MySQL 的基本層級可以理解成：資料庫伺服器 → 資料庫 → 資料表 → 欄位與資料列。

3. **每個欄位應該使用什麼名稱與資料型別？**  
   例如：金額用 `DECIMAL`，文字名稱用 `VARCHAR`，建立時間用 `DATETIME`，是否啟用可以用 `TINYINT` 或 `BOOLEAN`。

這一節的目的，是讓你在進入後面的「建立資料庫、建立表、修改表、刪除表」之前，先理解資料如何被組織、命名與選型。

## 關鍵字

- 主題：MySQL 建表前置知識、資料儲存流程、資料庫層級、標識符命名規則、MySQL 資料型別
- 英文：identifier, schema, database, table, column, row, data type, DDL, DML
- 常見搜尋：MySQL 建表前要先知道什麼、MySQL 表名欄位名怎麼命名、MySQL 常用資料型別、VARCHAR 和 CHAR 差異、DECIMAL 和 DOUBLE 差異
- 容易混淆：資料庫 vs 資料表、欄位 vs 資料列、`CHAR` vs `VARCHAR`、`FLOAT` / `DOUBLE` vs `DECIMAL`、`TEXT` vs `LONGTEXT`、`BLOB` vs `LONGBLOB`

## 建議回查情境

- 看到一個業務需求，但還不知道要怎麼拆成資料庫與資料表時。
- 準備寫 `CREATE TABLE`，但不確定欄位名稱和資料型別該怎麼設計時。
- 忘記 MySQL 物件名稱的長度限制、命名規則、保留字處理方式時。
- 想快速判斷「這個欄位應該用 `VARCHAR`、`INT`、`DECIMAL`、`DATETIME` 還是 `TEXT`」時。
- 想區分 DDL、DML 這類 SQL 操作分類時。

## 30 秒複習入口

- MySQL 的資料組織層級：**資料庫伺服器 → 資料庫 → 資料表 → 欄位與資料列**。
- 建表前要先想清楚：**存什麼資料、放在哪張表、欄位如何命名、欄位用什麼型別**。
- 資料庫、資料表、欄位等名稱屬於 **identifier**，多數物件名稱上限是 **64 個字元**。
- 實務命名建議：小寫英文 + 數字 + 底線，例如 `user_order`、`order_detail`。
- 金額、利率、精確小數優先用 `DECIMAL`；`FLOAT` / `DOUBLE` 是近似值，不適合財務金額。
- 一般文字用 `VARCHAR`；固定長度代碼可用 `CHAR`；大量文字再考慮 `TEXT` / `LONGTEXT`。
- 圖片、PDF、壓縮檔等二進位內容才考慮 `BLOB` / `LONGBLOB`，但實務上常改存檔案路徑或物件儲存網址。

## 速查區

### 資料儲存流程

簡化流程：

```text
釐清業務資料
    ↓
建立資料庫
    ↓
設計資料表與欄位
    ↓
選擇資料型別與約束
    ↓
建立資料表
    ↓
寫入資料
```

常見 SQL 分類：

| 分類 | 作用 | 常見語句 |
| --- | --- | --- |
| DDL | 定義或修改資料庫結構 | `CREATE`、`ALTER`、`DROP`、`TRUNCATE` |
| DML | 新增、修改、刪除資料 | `INSERT`、`UPDATE`、`DELETE` |
| DQL | 查詢資料 | `SELECT` |
| DCL | 權限控制 | `GRANT`、`REVOKE` |

> 本章「創建和管理表」主要會碰到 DDL；後續插入、更新、刪除資料時會碰到 DML。

### MySQL 物件層級

| 層級 | 說明 | 例子 |
| --- | --- | --- |
| 資料庫伺服器 | 安裝並執行的 MySQL Server / MySQL Instance | 本機 MySQL、測試機 MySQL、正式機 MySQL |
| 資料庫 | 一組相關資料表的集合，在 MySQL 中也常稱為 schema | `shop_db`、`bank_db` |
| 資料表 | 用來存放同一類資料 | `users`、`orders`、`order_items` |
| 欄位 | 描述一筆資料有哪些屬性 | `id`、`username`、`created_at` |
| 資料列 | 表中的一筆完整資料 | 一個使用者、一筆訂單 |

### 標識符命名規則

| 項目 | MySQL 規則 / 實務建議 |
| --- | --- |
| 長度限制 | 資料庫名、表名、欄位名、索引名、約束名通常最多 **64 個字元** |
| 建議格式 | 小寫英文、數字、底線 `_` |
| 避免格式 | 空格、中文、特殊符號、大小寫混用 |
| 保留字 | 避免使用 `select`、`order`、`group` 等保留字 |
| 必須使用保留字時 | 用反引號包起來，例如 `` `order` `` |
| 大小寫 | 為了跨 Windows / Linux / macOS，建議一律小寫 |
| 一致性 | 同一業務概念在不同表中，欄位名與資料型別應盡量一致 |

推薦命名：

```sql
user_id
user_name
order_id
created_at
updated_at
is_deleted
```

不推薦命名：

```sql
UserName       -- 大小寫混用
user name      -- 中間有空格
使用者名稱      -- 不利於團隊維護與跨系統整合
select         -- 保留字
order          -- 常見關鍵字，容易混淆
```

### 常見資料型別

| 類型 | 常見型別 | 適合場景 |
| --- | --- | --- |
| 整數 | `TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT`、`BIGINT` | 主鍵 ID、數量、狀態碼、年齡 |
| 精確小數 | `DECIMAL(M,D)` | 金額、利率、財務數字 |
| 近似小數 | `FLOAT`、`DOUBLE` | 科學計算、測量值、座標等可接受誤差的數字 |
| 日期時間 | `DATE`、`TIME`、`DATETIME`、`TIMESTAMP`、`YEAR` | 生日、建立時間、更新時間、登入時間 |
| 字串 | `CHAR`、`VARCHAR`、`TEXT` | 姓名、帳號、Email、描述、文章內容 |
| 二進位 | `BINARY`、`VARBINARY`、`BLOB` | 圖片、檔案、加密後的二進位資料 |
| 枚舉 / 集合 | `ENUM`、`SET` | 固定選項，但實務上大型系統常改用字典表或代碼表 |
| JSON | `JSON` | 半結構化資料、彈性欄位、外部 API 原始內容 |
| 空間型別 | `GEOMETRY`、`POINT` 等 | 地理位置、座標、GIS 應用 |

## 1.1 一筆資料儲存到 MySQL 的過程

`儲存資料是處理資料的第一步`。資料如果沒有被有規則地存起來，後續就很難查詢、統計、分析與維護。

以「訂單系統」為例，業務上可能會出現這些資料：

- 使用者資料：姓名、手機、Email
- 商品資料：商品名稱、價格、庫存
- 訂單資料：訂單編號、下單時間、付款狀態
- 訂單明細：哪一張訂單買了哪些商品、數量是多少、單價是多少

這些資料不能全部塞進同一張表，否則會出現重複、難查詢、難維護的問題。比較合理的做法，是先把業務概念拆開：

```text
users          使用者表
products       商品表
orders         訂單表
order_items    訂單明細表
```

接著才開始思考每張表有哪些欄位，例如 `users` 表可能有：

```text
id
username
email
phone
created_at
updated_at
```

然後再替每個欄位選擇資料型別：

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100),
    phone VARCHAR(20),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

所以，從業務資料到 MySQL 資料表，大致可以理解成：

```text
業務需求
  → 找出資料對象
  → 拆成資料表
  → 設計欄位
  → 選擇資料型別與約束
  → 建立資料表
  → 寫入資料
```

## 1.2 MySQL 的資料庫層級

MySQL 中的資料不是直接散落在伺服器裡，而是有層級的。

可以先用下面這個結構理解：

```text
MySQL Server / MySQL Instance
└── database / schema
    └── table
        ├── column
        └── row
```

例如：

```text
MySQL Server
└── shop_db
    ├── users
    │   ├── id
    │   ├── username
    │   └── created_at
    └── orders
        ├── id
        ├── user_id
        └── total_amount
```

這個層級很重要，因為後面的語法都會圍繞這個結構：

```sql
CREATE DATABASE shop_db;
USE shop_db;

CREATE TABLE users (...);
INSERT INTO users (...) VALUES (...);
SELECT * FROM users;
```

也就是說：

- `CREATE DATABASE`：先建立一個資料庫。
- `USE database_name`：指定接下來操作哪個資料庫。
- `CREATE TABLE`：在目前資料庫中建立資料表。
- `INSERT INTO`：往資料表中新增資料。
- `SELECT`：從資料表中查詢資料。

## 1.3 標識符命名規則

在 MySQL 中，資料庫名、表名、欄位名、索引名、別名等，都可以稱為 **identifier**，中文常翻成「標識符」或「識別符」。

### 1.3.1 官方限制與實務建議要分開看

原則上，MySQL 對 identifier 有自己的語法規則，例如：

- 資料庫名、表名、欄位名、索引名、約束名等，多數上限是 **64 個字元**。
- 欄位別名通常可以到 **256 個字元**。
- 未加引號的 identifier 可以包含英文字母、數字、底線 `_`、美元符號 `$`，也允許部分 Unicode 字元。
- identifier 可以數字開頭，但未加引號時不能全部都是數字。
- 如果名稱包含特殊字元，或剛好是保留字，引用時要用反引號 `` ` `` 包起來。

但是實務開發時，不建議把「MySQL 允許」直接當成「專案應該這樣寫」。

比較推薦的團隊規範是：

```text
小寫英文 + 數字 + 底線
```

例如：

```sql
user_id
order_id
order_amount
created_at
updated_at
is_deleted
```

這樣做的好處是：

- 跨平台比較安全，避免 Windows / Linux 對表名大小寫處理不同造成問題。
- SQL 可讀性比較高。
- Java、Vue、後端 API、Excel 匯出欄位對應時比較一致。
- 團隊協作時不容易出現同一概念多種命名。

### 1.3.2 同一層級不能重名

命名時要注意「同一層級不能重名」：

| 範圍 | 是否可重名 |
| --- | --- |
| 同一個 MySQL Server 中的資料庫 | 不可重名 |
| 同一個資料庫中的資料表 | 不可重名 |
| 同一張資料表中的欄位 | 不可重名 |
| 不同資料表中的欄位 | 可以同名 |

例如，不同表中都可以有 `id`、`created_at`、`updated_at`：

```text
users.id
orders.id
products.id
```

這沒有問題，因為它們分別屬於不同資料表。

但是同一張表中不能有兩個 `id` 欄位。

### 1.3.3 避免使用保留字與容易混淆的名稱

不推薦：

```sql
CREATE TABLE order (
    select VARCHAR(50),
    group VARCHAR(50)
);
```

因為 `order`、`select`、`group` 都容易和 SQL 關鍵字混淆。

如果真的使用了保留字，必須用反引號：

```sql
CREATE TABLE `order` (
    `select` VARCHAR(50),
    `group` VARCHAR(50)
);
```

但實務上更推薦直接避開：

```sql
CREATE TABLE orders (
    order_no VARCHAR(50),
    group_name VARCHAR(50)
);
```

### 1.3.4 保持同一業務概念的命名一致

如果同一個概念在多張表中出現，命名與型別應盡量一致。

推薦：

```text
users.id              BIGINT
orders.user_id        BIGINT
order_items.order_id  BIGINT
```

不推薦：

```text
users.id              BIGINT
orders.uid            VARCHAR(20)
order_items.orderNo   INT
```

原因是：

- 關聯查詢比較難讀。
- 寫 Java 實體類、DTO、Mapper 時容易混亂。
- 後續維護者不容易判斷欄位是否代表同一個概念。
- 資料型別不一致時，可能造成查詢效能或轉型問題。

## 1.4 MySQL 中的常見資料型別

MySQL 的資料型別很多，但初學建表時，不需要一次背完全部型別。比較重要的是先知道：「這個欄位是數字、文字、時間、二進位資料，還是特殊結構？」

### 1.4.1 整數型別

| 型別 | 儲存空間 | 適合場景 |
| --- | --- | --- |
| `TINYINT` | 1 byte | 狀態碼、布林值、很小的數字 |
| `SMALLINT` | 2 bytes | 較小範圍的整數 |
| `MEDIUMINT` | 3 bytes | 中等範圍整數，較少用 |
| `INT` / `INTEGER` | 4 bytes | 一般整數、數量、普通流水號 |
| `BIGINT` | 8 bytes | 大型系統主鍵、大數量資料 ID |

常見選擇：

```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT,
age INT,
status TINYINT
```

補充：

- `BOOLEAN` / `BOOL` 在 MySQL 中通常可理解為 `TINYINT(1)` 的同義用法。
- 主鍵 ID 如果資料量可能很大，實務上常直接用 `BIGINT`。
- 狀態欄位可用 `TINYINT`，再搭配程式中的 enum 或字典表解釋含義。

### 1.4.2 小數型別：`FLOAT`、`DOUBLE`、`DECIMAL`

| 型別 | 特性 | 適合場景 |
| --- | --- | --- |
| `FLOAT` | 單精度近似值 | 科學計算、測量值，可接受誤差 |
| `DOUBLE` | 雙精度近似值 | 比 `FLOAT` 精度高，但仍是近似值 |
| `DECIMAL(M,D)` | 精確小數 | 金額、利率、財務數字 |

最重要的判斷：

> **需要精確計算時，用 `DECIMAL`；可以接受誤差時，才考慮 `FLOAT` / `DOUBLE`。**

例如金額欄位：

```sql
total_amount DECIMAL(15,2)
```

代表最多 15 位數，其中 2 位是小數。

例如：

```text
9999999999999.99
```

不建議用：

```sql
total_amount DOUBLE
```

因為 `DOUBLE` 是近似值，可能在比較、加總、計算時出現誤差，不適合銀行、訂單、會計、財務相關資料。

另外，舊教材常見的 `FLOAT(M,D)`、`DOUBLE(M,D)` 寫法，現在不建議當作新專案重點使用；建議直接使用 `FLOAT`、`DOUBLE`，或在需要精確小數時改用 `DECIMAL(M,D)`。

### 1.4.3 日期時間型別

| 型別 | 說明 | 適合場景 |
| --- | --- | --- |
| `YEAR` | 年份 | 年度資料 |
| `DATE` | 日期，格式通常是 `YYYY-MM-DD` | 生日、交易日期 |
| `TIME` | 時間 | 時分秒、持續時間 |
| `DATETIME` | 日期 + 時間 | 建立時間、更新時間、業務事件時間 |
| `TIMESTAMP` | 日期 + 時間，通常與時區轉換、系統時間戳較相關 | 記錄系統事件時間 |

常見寫法：

```sql
created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

實務上，初學者可以先這樣記：

- 只需要日期：用 `DATE`。
- 需要日期 + 時間：多數業務欄位可先用 `DATETIME`。
- 需要處理跨時區或系統時間戳，再進一步理解 `TIMESTAMP`。

### 1.4.4 字串型別：`CHAR`、`VARCHAR`、`TEXT`

| 型別 | 特性 | 適合場景 |
| --- | --- | --- |
| `CHAR(M)` | 固定長度 | 固定代碼，例如性別、幣別、國家代碼 |
| `VARCHAR(M)` | 可變長度 | 姓名、帳號、Email、標題 |
| `TEXT` | 較長文字 | 文章內容、備註、描述 |
| `MEDIUMTEXT` / `LONGTEXT` | 更大文字 | 很長的文章、文件內容、JSON 原文備份 |

`CHAR` 和 `VARCHAR` 的差異：

```text
CHAR(10)     固定長度，比較適合長度固定的資料
VARCHAR(10)  可變長度，比較適合長度不固定的資料
```

常見選擇：

```sql
username VARCHAR(50),
email VARCHAR(100),
currency_code CHAR(3),
description TEXT
```

注意：

- `VARCHAR(M)` 的 `M` 是最多可存幾個字元，不是一定會佔滿這麼多字元。
- `TEXT` 不是最大 4GB；接近 4GB 的是 `LONGTEXT`。
- 一般欄位不要一開始就全部用 `TEXT`，因為查詢、索引、排序與維護上都可能更麻煩。

### 1.4.5 二進位型別：`BINARY`、`VARBINARY`、`BLOB`

| 型別 | 特性 | 適合場景 |
| --- | --- | --- |
| `BINARY(M)` | 固定長度二進位資料 | 固定長度 byte 資料 |
| `VARBINARY(M)` | 可變長度二進位資料 | 加密結果、雜湊值等 |
| `BLOB` | 二進位大物件 | 圖片、檔案、小型二進位內容 |
| `MEDIUMBLOB` / `LONGBLOB` | 更大的二進位資料 | 大型圖片、文件、影音檔案 |

注意：

- `BLOB` 不是文字型別，而是二進位資料。
- `BLOB` 也不是最大 4GB；接近 4GB 的是 `LONGBLOB`。
- 實務上，大型檔案常不直接塞進 MySQL，而是存到檔案系統、NAS、MinIO、S3 等物件儲存，再於資料表保存檔案路徑或 URL。

例如：

```sql
file_name VARCHAR(255),
file_url VARCHAR(500),
file_size BIGINT,
content_type VARCHAR(100)
```

這種設計通常比直接把大檔案存進資料庫更容易維護。

### 1.4.6 JSON、ENUM、SET、空間型別

這些型別不用一開始背很細，但要知道它們存在。

| 型別 | 說明 | 備註 |
| --- | --- | --- |
| `JSON` | 儲存 JSON 文件 | 適合半結構化資料，但不要濫用成萬用欄位 |
| `ENUM` | 單選固定值 | 小型固定選項可用，大型系統常改用代碼表 |
| `SET` | 多選固定值 | 較少用，維護成本較高 |
| 空間型別 | 儲存地理位置或幾何資料 | GIS 或地圖功能會用到 |

例如：

```sql
extra_info JSON
```

可以保存彈性資料，但如果某個 JSON 欄位經常需要查詢、排序、統計，就應該考慮拆成正式欄位。

## 1.5 建表前的選型思路

建表不是單純把欄位列出來，而是要根據資料的性質做選擇。

可以用下面這個順序判斷：

```text
這個欄位是什麼？
    ↓
是數字、文字、日期、二進位，還是 JSON？
    ↓
是否需要精確計算？
    ↓
長度是否固定？
    ↓
是否經常查詢、排序、關聯？
    ↓
是否需要 NOT NULL、DEFAULT、PRIMARY KEY、UNIQUE 等約束？
```

範例：會員表欄位設計

| 欄位 | 型別 | 原因 |
| --- | --- | --- |
| `id` | `BIGINT` | 主鍵，資料量可能成長 |
| `username` | `VARCHAR(50)` | 使用者名稱長度不固定 |
| `email` | `VARCHAR(100)` | Email 長度不固定 |
| `status` | `TINYINT` | 狀態碼，例如 0 停用、1 啟用 |
| `balance` | `DECIMAL(15,2)` | 金額需要精確保存 |
| `created_at` | `DATETIME` | 建立時間 |
| `updated_at` | `DATETIME` | 更新時間 |

對應 SQL：

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE,
    status TINYINT NOT NULL DEFAULT 1,
    balance DECIMAL(15,2) NOT NULL DEFAULT 0.00,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

這個例子可以作為後面學 `CREATE TABLE` 時的基本模板。

## 本節小結

這一節可以濃縮成三句話：

1. MySQL 的資料有層級：**資料庫伺服器 → 資料庫 → 資料表 → 欄位與資料列**。
2. 建表前要先設計：**業務資料、資料表、欄位名稱、資料型別、約束條件**。
3. 選型時要避免兩個常見錯誤：**金額用 `FLOAT/DOUBLE`、所有文字都用 `TEXT`**。

你真正要記住的不是所有型別細節，而是下面這幾個判斷：

| 需求 | 優先考慮 |
| --- | --- |
| 主鍵 ID | `BIGINT` |
| 狀態碼 | `TINYINT` |
| 金額 / 利率 | `DECIMAL(M,D)` |
| 姓名 / 帳號 / Email | `VARCHAR(M)` |
| 固定長度代碼 | `CHAR(M)` |
| 建立時間 / 更新時間 | `DATETIME` |
| 長文章 / 備註 | `TEXT` / `MEDIUMTEXT` / `LONGTEXT` |
| 圖片 / 檔案二進位 | `BLOB` / `MEDIUMBLOB` / `LONGBLOB`，或改存檔案 URL |
