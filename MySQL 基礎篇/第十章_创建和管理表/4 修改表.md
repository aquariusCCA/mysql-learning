# 4 修改表

返回章節：[第十章_创建和管理表](./README.md)

## 本節導讀

這一節處理的是：**表已經建好了，後面還想調整表結構時，應該怎麼做。**

在真實專案中，資料表結構很少一次設計完就永遠不變。需求一變，表結構就可能跟著調整，例如：

- 使用者資料表要新增 `phone` 手機欄位；
- 商品資料表的 `price` 要從整數改成 `DECIMAL(12,2)`；
- 原本的 `name` 欄位想改成語意更清楚的 `username`；
- 某個舊欄位已經不再使用，需要刪除；
- 欄位預設值、是否可為 `NULL`、註解、位置需要調整；
- 需要新增或刪除索引、唯一約束、外鍵、檢查約束。

這些動作大多會使用：

```sql
ALTER TABLE 表名 ...;
```

不過，`ALTER TABLE` 不是普通查詢，它屬於 **DDL，Data Definition Language，資料定義語言**。它修改的是資料表結構，而不是單純修改某幾筆資料。

所以這一篇不只要背語法，還要建立一個很重要的觀念：

> 修改表結構前，要先確認影響範圍；正式環境中的 `ALTER TABLE` 不能隨便執行。

如果是小表、測試表，修改欄位通常很快；但如果是正式環境的大表，某些 `ALTER TABLE` 可能會：

- 重建整張表；
- 複製大量資料；
- 產生 metadata lock；
- 阻塞其他 SQL；
- 造成欄位資料被轉換、截斷或遺失；
- 讓應用程式、報表、View、Stored Procedure、批次程式一起壞掉。

這一篇學完後，你應該要能做到：

1. 看懂 `ALTER TABLE` 的常見語法；
2. 正確區分 `ADD COLUMN`、`MODIFY COLUMN`、`CHANGE COLUMN`、`RENAME COLUMN`、`DROP COLUMN`；
3. 知道修改欄位時要重新寫完整欄位定義；
4. 知道新增 `NOT NULL` 欄位、縮短欄位長度、刪除欄位前要檢查什麼；
5. 知道正式環境修改表結構前的基本安全流程。

## 關鍵字

- 主題：修改表、修改欄位、新增欄位、刪除欄位、修改欄位型別、修改預設值、欄位重命名、調整欄位位置、表結構演進
- 英文：alter table, add column, modify column, change column, rename column, drop column, set default, drop default, online DDL, metadata lock
- 常見搜尋：MySQL 修改表、MySQL ALTER TABLE、MySQL 新增欄位、MySQL 修改欄位型別、MySQL 改欄位名稱、MySQL 刪除欄位、MySQL MODIFY CHANGE 差異
- 容易混淆：`MODIFY` vs `CHANGE`、`CHANGE` vs `RENAME COLUMN`、修改預設值 vs 更新既有資料、調整欄位位置 vs 調整查詢結果順序、刪除欄位 vs 刪除表

## 建議回查情境

- 表已經存在，現在要補新欄位時。
- 要修改欄位型別、長度、是否可為 `NULL`、預設值、註解時。
- 想改欄位名稱，但不確定該用 `CHANGE` 還是 `RENAME COLUMN` 時。
- 想刪除欄位，但不確定它有沒有被索引、外鍵、程式碼或報表使用時。
- 想調整欄位順序，但不確定這樣做是否有必要時。
- 正式環境要執行 `ALTER TABLE`，需要先做風險檢查時。

## 30 秒複習入口

- 修改既有表結構，核心命令是 `ALTER TABLE`。
- `ADD COLUMN`：新增欄位。
- `MODIFY COLUMN`：修改欄位定義，但不改欄位名稱。
- `CHANGE COLUMN`：可以同時改欄位名稱和欄位定義。
- `RENAME COLUMN`：只改欄位名稱，不改欄位定義，MySQL 8.0+ 很常用。
- `DROP COLUMN`：刪除欄位，會移除該欄位的資料。
- `ALTER COLUMN ... SET DEFAULT`：只修改欄位預設值。
- `ALTER COLUMN ... DROP DEFAULT`：移除欄位預設值。
- 使用 `MODIFY` 或 `CHANGE` 修改欄位時，要把希望保留的型別屬性完整寫出來，例如 `UNSIGNED`、`NOT NULL`、`DEFAULT`、`COMMENT`。
- 修改欄位預設值只影響之後新增資料時的預設值，不會自動更新既有資料。
- 縮短字串欄位、改數值型別、改 `NULL` 為 `NOT NULL`，都要先檢查既有資料是否符合新規則。
- 刪除欄位前，要先確認索引、外鍵、View、Stored Procedure、排程、報表、應用程式是否還依賴它。
- 正式環境的大表不要直接隨手 `ALTER TABLE`，要先評估資料量、鎖表風險、備份、回滾方案與低峰時段。

## 速查區

### 常見 `ALTER TABLE` 操作總表

| 需求 | 建議語法 | 用途 |
| --- | --- | --- |
| 新增欄位 | `ALTER TABLE t ADD COLUMN c type;` | 在既有表加入新欄位 |
| 一次新增多欄位 | `ALTER TABLE t ADD COLUMN (...);` | 同時新增多個欄位 |
| 修改欄位定義 | `ALTER TABLE t MODIFY COLUMN c new_definition;` | 改型別、長度、`NULL`、預設值、註解、位置 |
| 同時改欄位名與定義 | `ALTER TABLE t CHANGE COLUMN old_c new_c new_definition;` | 舊版常用的欄位改名方式，也可順便改定義 |
| 只改欄位名 | `ALTER TABLE t RENAME COLUMN old_c TO new_c;` | MySQL 8.0+ 推薦用於單純改欄位名 |
| 修改預設值 | `ALTER TABLE t ALTER COLUMN c SET DEFAULT value;` | 只改欄位預設值 |
| 移除預設值 | `ALTER TABLE t ALTER COLUMN c DROP DEFAULT;` | 移除欄位預設值 |
| 刪除欄位 | `ALTER TABLE t DROP COLUMN c;` | 刪除欄位與該欄位資料 |
| 一次刪多欄位 | `ALTER TABLE t DROP COLUMN c1, DROP COLUMN c2;` | 同一條 SQL 刪多個欄位 |
| 調整欄位位置 | `MODIFY ... FIRST / AFTER ...` | 改變欄位在表結構中的顯示順序 |
| 修改表註解 | `ALTER TABLE t COMMENT = '...';` | 修改資料表註解 |
| 修改表預設字元集 | `ALTER TABLE t DEFAULT CHARSET = utf8mb4;` | 影響後續新增欄位的預設字元集 |
| 轉換表字元集 | `ALTER TABLE t CONVERT TO CHARACTER SET utf8mb4;` | 嘗試轉換既有文字欄位內容 |

### `MODIFY`、`CHANGE`、`RENAME COLUMN` 差異

| 語法 | 是否可改欄位名 | 是否可改欄位定義 | 是否需要重寫資料型別 | 適合場景 |
| --- | --- | --- | --- | --- |
| `MODIFY COLUMN c definition` | 否 | 是 | 要 | 只改型別、長度、預設值、是否可空、註解、位置 |
| `CHANGE COLUMN old_c new_c definition` | 是 | 是 | 要 | 同時改欄位名與欄位定義，或相容舊寫法 |
| `RENAME COLUMN old_c TO new_c` | 是 | 否 | 不用 | 只改欄位名，語意最清楚 |

簡單記法：

```text
只改欄位定義：MODIFY
只改欄位名稱：RENAME COLUMN
改欄位名稱 + 改欄位定義：CHANGE
```

### 正式環境修改表前檢查清單

執行 `ALTER TABLE` 前，建議先做這幾件事：

```sql
-- 1. 確認目前資料庫
SELECT DATABASE();

-- 2. 查看完整建表語句
SHOW CREATE TABLE app_user;

-- 3. 查看欄位資訊
SHOW FULL COLUMNS FROM app_user;

-- 4. 查看索引
SHOW INDEX FROM app_user;

-- 5. 查看目標欄位是否存在
SELECT COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT, COLUMN_COMMENT
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'app_user'
  AND COLUMN_NAME = 'phone';
```

正式環境還要額外確認：

- 是否已備份；
- 是否已在測試環境演練；
- 是否有回滾方案；
- 是否會影響線上 API、批次程式、報表、View、Stored Procedure；
- 是否需要低峰時段執行；
- 是否要加上 `ALGORITHM`、`LOCK` 控制執行方式；
- 是否需要 DBA 或資深工程師審查。

## 4.1 `ALTER TABLE` 的基本概念

`ALTER TABLE` 是用來修改既有表結構的語句。

基本骨架如下：

```sql
ALTER TABLE 表名
    修改動作1,
    修改動作2,
    修改動作3;
```

例如：

```sql
ALTER TABLE app_user
    ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼' AFTER email,
    ADD COLUMN last_login_at DATETIME NULL COMMENT '最後登入時間' AFTER updated_at;
```

這代表對 `app_user` 這張表同時做兩件事：

1. 新增 `phone` 欄位；
2. 新增 `last_login_at` 欄位。

MySQL 允許在同一條 `ALTER TABLE` 中放多個修改動作，用逗號分隔。這在需要一次完成多個結構調整時很常見。

### 4.1.1 修改表前先看原始結構

修改表以前，第一步不是直接寫 `ALTER TABLE`，而是先看原表長什麼樣子。

最重要的是：

```sql
SHOW CREATE TABLE app_user;
```

它會顯示完整建表語句，包含：

- 欄位名稱；
- 欄位型別；
- `NULL` / `NOT NULL`；
- `DEFAULT`；
- `COMMENT`；
- 主鍵；
- 索引；
- 唯一約束；
- 外鍵；
- `CHECK` 約束；
- 儲存引擎；
- 字元集；
- 排序規則。

如果只是快速看欄位，可以用：

```sql
DESC app_user;
```

或：

```sql
SHOW FULL COLUMNS FROM app_user;
```

`SHOW FULL COLUMNS` 會比 `DESC` 多看到欄位註解、collation 等資訊。

## 4.2 新增欄位：`ADD COLUMN`

### 4.2.1 基本語法

```sql
ALTER TABLE 表名
ADD [COLUMN] 欄位名 欄位定義 [FIRST | AFTER 某欄位];
```

其中：

| 部分 | 說明 |
| --- | --- |
| `ADD COLUMN` | 新增欄位 |
| `欄位名` | 新欄位名稱 |
| `欄位定義` | 型別、是否可空、預設值、註解等 |
| `FIRST` | 放到第一個欄位 |
| `AFTER 某欄位` | 放在某欄位後面 |

`COLUMN` 通常可以省略，但筆記與實務上建議保留，語意比較清楚。

### 4.2.2 新增普通欄位

假設有一張使用者表：

```sql
CREATE TABLE app_user (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '使用者ID',
    username VARCHAR(50) NOT NULL COMMENT '帳號',
    email VARCHAR(100) NOT NULL COMMENT '電子信箱',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    PRIMARY KEY (id),
    UNIQUE KEY uk_app_user_username (username),
    UNIQUE KEY uk_app_user_email (email)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '使用者表';
```

現在想新增手機欄位：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼' AFTER email;
```

說明：

| 寫法 | 意義 |
| --- | --- |
| `phone` | 新欄位名稱 |
| `VARCHAR(20)` | 字串型別，最多 20 個字元 |
| `NULL` | 允許沒有手機號碼 |
| `COMMENT '手機號碼'` | 欄位註解 |
| `AFTER email` | 放在 `email` 欄位後面 |

### 4.2.3 新增帶預設值的欄位

例如新增會員狀態欄位：

```sql
ALTER TABLE app_user
ADD COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '狀態：1啟用，0停用' AFTER phone;
```

這樣之後新增資料時，如果沒有指定 `status`，MySQL 會使用預設值 `1`。

注意：

> 預設值主要影響「之後新增資料」時的欄位值；對於既有資料，實際結果會受到 MySQL 版本、欄位定義、執行方式與資料表狀態影響。正式環境中，不要只靠猜測，應先在測試環境驗證。

比較安全、可控的做法是分三步：

```sql
-- 1. 先新增可為 NULL 的欄位，降低既有資料不符合規則的風險
ALTER TABLE app_user
ADD COLUMN status TINYINT NULL COMMENT '狀態：1啟用，0停用' AFTER phone;

-- 2. 回填既有資料
UPDATE app_user
SET status = 1
WHERE status IS NULL;

-- 3. 確認沒有 NULL 後，再改成 NOT NULL + DEFAULT
ALTER TABLE app_user
MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '狀態：1啟用，0停用' AFTER phone;
```

這種流程比一次新增 `NOT NULL` 欄位更適合正式環境，因為每一步都可以檢查。

### 4.2.4 新增欄位到第一個位置

```sql
ALTER TABLE app_user
ADD COLUMN tenant_id BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '租戶ID' FIRST;
```

這會把 `tenant_id` 放在表結構的第一個欄位。

不過實務上要注意：

> 欄位順序通常不應該影響程式邏輯。查詢時應該明確寫欄位名稱，不要依賴 `SELECT *` 的欄位順序。

例如不要這樣依賴順序：

```sql
SELECT * FROM app_user;
```

正式程式建議明確寫：

```sql
SELECT id, username, email, phone, status
FROM app_user;
```

### 4.2.5 一次新增多個欄位

MySQL 支援一條 `ALTER TABLE` 新增多個欄位。

寫法一：重複多個 `ADD COLUMN`：

```sql
ALTER TABLE app_user
ADD COLUMN nickname VARCHAR(50) NULL COMMENT '暱稱' AFTER username,
ADD COLUMN last_login_at DATETIME NULL COMMENT '最後登入時間' AFTER updated_at;
```

寫法二：使用括號新增多個欄位：

```sql
ALTER TABLE app_user
ADD COLUMN (
    avatar_url VARCHAR(500) NULL COMMENT '頭像URL',
    bio VARCHAR(500) NULL COMMENT '個人簡介'
);
```

實務上我比較建議第一種，因為每個欄位可以清楚控制 `FIRST` / `AFTER`。

## 4.3 修改欄位定義：`MODIFY COLUMN`

### 4.3.1 基本語法

```sql
ALTER TABLE 表名
MODIFY [COLUMN] 欄位名 新欄位定義 [FIRST | AFTER 某欄位];
```

`MODIFY COLUMN` 用於修改欄位定義，但不修改欄位名稱。

可以修改的內容包括：

- 資料型別；
- 長度；
- `NULL` / `NOT NULL`；
- `DEFAULT`；
- `COMMENT`；
- `VISIBLE` / `INVISIBLE`；
- 欄位位置。

### 4.3.2 修改欄位長度

例如把 `username` 從 `VARCHAR(50)` 改成 `VARCHAR(80)`：

```sql
ALTER TABLE app_user
MODIFY COLUMN username VARCHAR(80) NOT NULL COMMENT '帳號';
```

注意，這裡不是只寫：

```sql
ALTER TABLE app_user
MODIFY COLUMN username VARCHAR(80);
```

因為這樣可能會讓原本的 `NOT NULL`、`DEFAULT`、`COMMENT` 等屬性沒有被保留下來。

`MODIFY` / `CHANGE` 的重要原則是：

> 你希望修改後欄位擁有哪些屬性，就要在新的欄位定義中完整寫出來。

### 4.3.3 錯誤示範：少寫屬性造成欄位規則被改掉

假設原欄位是：

```sql
balance DECIMAL(12, 2) UNSIGNED NOT NULL DEFAULT 0.00 COMMENT '帳戶餘額'
```

你只是想把精度改成 `DECIMAL(14,2)`，但寫成：

```sql
ALTER TABLE app_user
MODIFY COLUMN balance DECIMAL(14, 2);
```

這樣很危險，因為你沒有重新寫出：

- `UNSIGNED`；
- `NOT NULL`；
- `DEFAULT 0.00`；
- `COMMENT '帳戶餘額'`。

比較正確的寫法是：

```sql
ALTER TABLE app_user
MODIFY COLUMN balance DECIMAL(14, 2) UNSIGNED NOT NULL DEFAULT 0.00 COMMENT '帳戶餘額';
```

這是 `ALTER TABLE` 很重要的細節，不能只記「`MODIFY` 可以改型別」。

### 4.3.4 修改欄位為 `NOT NULL`

假設 `phone` 原本允許 `NULL`，現在想改成不可為空：

```sql
ALTER TABLE app_user
MODIFY COLUMN phone VARCHAR(20) NOT NULL COMMENT '手機號碼';
```

但在執行之前，應該先檢查是否有既有資料是 `NULL`：

```sql
SELECT COUNT(*) AS null_phone_count
FROM app_user
WHERE phone IS NULL;
```

如果有資料是 `NULL`，應先補值：

```sql
UPDATE app_user
SET phone = ''
WHERE phone IS NULL;
```

然後再改欄位：

```sql
ALTER TABLE app_user
MODIFY COLUMN phone VARCHAR(20) NOT NULL COMMENT '手機號碼';
```

不過，如果手機號碼真的可能沒有資料，硬改成 `NOT NULL` 不一定合理。應該回到業務規則判斷：

> 這個欄位到底是不是業務上必填？

### 4.3.5 縮短欄位長度前先檢查資料

假設 `email` 原本是 `VARCHAR(100)`，你想縮短成 `VARCHAR(60)`。

不要直接做：

```sql
ALTER TABLE app_user
MODIFY COLUMN email VARCHAR(60) NOT NULL COMMENT '電子信箱';
```

應先檢查是否有超過 60 字元的資料：

```sql
SELECT id, email, CHAR_LENGTH(email) AS email_length
FROM app_user
WHERE CHAR_LENGTH(email) > 60;
```

如果查得出資料，代表直接縮短可能造成資料截斷或失敗。應先處理資料，再修改欄位。

### 4.3.6 修改欄位註解

如果只是修改欄位註解，也要重新寫完整欄位定義：

```sql
ALTER TABLE app_user
MODIFY COLUMN email VARCHAR(100) NOT NULL COMMENT '使用者電子信箱';
```

注意：

> `COMMENT` 不是附加在原欄位上的獨立操作；你通常需要在欄位定義中重新寫出型別與其他屬性。

### 4.3.7 調整欄位位置

例如把 `phone` 移到 `email` 後面：

```sql
ALTER TABLE app_user
MODIFY COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼' AFTER email;
```

或者移到第一個欄位：

```sql
ALTER TABLE app_user
MODIFY COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼' FIRST;
```

實務提醒：

- 調整欄位位置通常只是讓 `DESC` 或 `SELECT *` 看起來比較順；
- 正式程式不應該依賴欄位順序；
- 對大表來說，調整欄位位置可能是昂貴操作；
- 如果只是查詢結果想改順序，應該改 `SELECT` 欄位順序，不一定要改表結構。

例如：

```sql
SELECT id, username, email, phone, created_at
FROM app_user;
```

## 4.4 修改欄位預設值：`ALTER COLUMN SET DEFAULT / DROP DEFAULT`

如果只是修改欄位預設值，不一定要用 `MODIFY COLUMN`。

### 4.4.1 設定預設值

```sql
ALTER TABLE app_user
ALTER COLUMN status SET DEFAULT 1;
```

這代表之後新增資料時，如果沒有指定 `status`，預設使用 `1`。

### 4.4.2 移除預設值

```sql
ALTER TABLE app_user
ALTER COLUMN status DROP DEFAULT;
```

### 4.4.3 預設值不會自動更新既有資料

假設原本資料裡有：

```text
id | username | status
---+----------+-------
1  | tom      | NULL
2  | mary     | NULL
```

你執行：

```sql
ALTER TABLE app_user
ALTER COLUMN status SET DEFAULT 1;
```

這不代表既有資料中的 `NULL` 會自動變成 `1`。

若要更新既有資料，要另外執行 `UPDATE`：

```sql
UPDATE app_user
SET status = 1
WHERE status IS NULL;
```

所以要清楚區分：

| 操作 | 影響對象 |
| --- | --- |
| `ALTER COLUMN ... SET DEFAULT` | 之後新增資料時的預設值 |
| `UPDATE ... SET ...` | 既有資料內容 |

## 4.5 重命名欄位：`RENAME COLUMN` 與 `CHANGE COLUMN`

### 4.5.1 MySQL 8.0+：只改名建議用 `RENAME COLUMN`

如果只是把 `username` 改成 `login_name`，且不修改欄位型別與其他屬性，建議用：

```sql
ALTER TABLE app_user
RENAME COLUMN username TO login_name;
```

優點是語意非常清楚：

```text
rename column：只改欄位名稱
```

不需要重新寫資料型別，因此比較不容易漏掉 `NOT NULL`、`DEFAULT`、`COMMENT` 等欄位屬性。

### 4.5.2 同時改名與改定義：用 `CHANGE COLUMN`

基本語法：

```sql
ALTER TABLE 表名
CHANGE [COLUMN] 舊欄位名 新欄位名 新欄位定義 [FIRST | AFTER 某欄位];
```

例如把 `login_name` 改成 `account_name`，同時把長度改成 `VARCHAR(80)`：

```sql
ALTER TABLE app_user
CHANGE COLUMN login_name account_name VARCHAR(80) NOT NULL COMMENT '登入帳號';
```

`CHANGE COLUMN` 有一個很重要的特性：

> 它必須寫「舊欄位名、新欄位名、新欄位定義」。

即使不改欄位名，也要寫兩次欄位名。

例如你想用 `CHANGE` 修改 `account_name` 的型別但不改名：

```sql
ALTER TABLE app_user
CHANGE COLUMN account_name account_name VARCHAR(100) NOT NULL COMMENT '登入帳號';
```

但這種情況其實用 `MODIFY` 更清楚：

```sql
ALTER TABLE app_user
MODIFY COLUMN account_name VARCHAR(100) NOT NULL COMMENT '登入帳號';
```

### 4.5.3 改名後仍要檢查依賴關係

欄位改名不只是資料庫內部的事情，還可能影響：

- Java Entity；
- MyBatis XML；
- JPA / Hibernate mapping；
- SQL 查詢；
- View；
- Stored Procedure；
- Trigger；
- 報表；
- 批次程式；
- 前端欄位名稱；
- API JSON 欄位；
- Excel 匯出欄位。

資料庫可能可以幫你更新部分索引或外鍵引用，但不代表會自動修正應用程式、View、Stored Procedure 或報表中的 SQL。

所以欄位改名前要先搜尋專案：

```text
username
login_name
account_name
```

如果是 MyBatis 專案，至少要找：

```text
resultMap
column="username"
username
#{username}
${username}
```

## 4.6 刪除欄位：`DROP COLUMN`

### 4.6.1 基本語法

```sql
ALTER TABLE 表名
DROP [COLUMN] 欄位名;
```

例如刪除 `bio` 欄位：

```sql
ALTER TABLE app_user
DROP COLUMN bio;
```

這會從表中移除 `bio` 欄位，該欄位保存的資料也會一起消失。

### 4.6.2 一次刪除多個欄位

```sql
ALTER TABLE app_user
DROP COLUMN avatar_url,
DROP COLUMN bio;
```

注意：

- 每個欄位都要寫一次 `DROP COLUMN`；
- 不要寫成 `DROP COLUMN avatar_url, bio`；
- 刪除欄位前最好先確認備份與依賴關係。

### 4.6.3 MySQL 不支援 `DROP COLUMN IF EXISTS`

在 MySQL 的 `ALTER TABLE` 語法中，刪欄位通常不能直接寫：

```sql
ALTER TABLE app_user
DROP COLUMN IF EXISTS bio;
```

比較穩妥的做法是先查欄位是否存在：

```sql
SELECT COLUMN_NAME
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'app_user'
  AND COLUMN_NAME = 'bio';
```

確認存在後再執行：

```sql
ALTER TABLE app_user
DROP COLUMN bio;
```

### 4.6.4 刪除被索引使用的欄位

刪欄位前先看索引：

```sql
SHOW INDEX FROM app_user;
```

如果欄位在索引裡，刪除時可能需要先調整或刪除相關索引。

例如：

```sql
ALTER TABLE app_user
DROP INDEX idx_app_user_phone;

ALTER TABLE app_user
DROP COLUMN phone;
```

如果欄位是唯一索引的一部分，刪除前更要小心，因為那可能代表一條重要業務規則。

### 4.6.5 刪除被外鍵使用的欄位

假設有一張訂單表：

```sql
CREATE TABLE user_order (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '訂單ID',
    user_id BIGINT UNSIGNED NOT NULL COMMENT '使用者ID',
    order_no VARCHAR(50) NOT NULL COMMENT '訂單編號',
    PRIMARY KEY (id),
    CONSTRAINT fk_user_order_user
        FOREIGN KEY (user_id) REFERENCES app_user(id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '訂單表';
```

如果你想刪除 `user_order.user_id`，需要先刪除外鍵：

```sql
ALTER TABLE user_order
DROP FOREIGN KEY fk_user_order_user;

ALTER TABLE user_order
DROP COLUMN user_id;
```

外鍵名稱可以用：

```sql
SHOW CREATE TABLE user_order;
```

或查詢：

```sql
SELECT CONSTRAINT_NAME, TABLE_NAME, COLUMN_NAME, REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'user_order'
  AND COLUMN_NAME = 'user_id';
```

### 4.6.6 正式環境刪欄位的建議流程

刪欄位是高風險操作，因為它會移除資料，且通常不容易回復。

比較安全的流程是：

```text
1. 確認欄位真的不再使用
2. 搜尋程式碼、SQL、報表、View、Stored Procedure
3. 先停止寫入該欄位，或讓程式不再依賴該欄位
4. 觀察一段時間
5. 備份資料
6. 在測試環境演練 DROP COLUMN
7. 低峰時段正式刪除
8. 刪除後檢查應用程式與錯誤日誌
```

如果你不確定欄位是否還有用，可以先不要刪，而是採用「停用欄位」策略：

```text
先不再寫入 → 不再讀取 → 觀察 → 備份 → 最後刪除
```

## 4.7 修改表註解、表選項與字元集

`ALTER TABLE` 不只可以修改欄位，也可以修改表本身的選項。

### 4.7.1 修改表註解

```sql
ALTER TABLE app_user
COMMENT = '系統使用者資料表';
```

### 4.7.2 修改表的預設字元集

```sql
ALTER TABLE app_user
DEFAULT CHARACTER SET = utf8mb4
COLLATE = utf8mb4_0900_ai_ci;
```

這個語句主要是在說：

> 以後這張表如果新增文字欄位，且沒有特別指定字元集，就預設使用 `utf8mb4` 和 `utf8mb4_0900_ai_ci`。

例如原本有：

```sql
CREATE TABLE app_user (
  username VARCHAR(50) CHARACTER SET latin1 COLLATE latin1_swedish_ci
);
```

你執行：

```sql
ALTER TABLE app_user
DEFAULT CHARACTER SET = utf8mb4
COLLATE = utf8mb4_0900_ai_ci;
```

之後，原本的 `username` **不會自動變成 utf8mb4**。

但是你之後新增：

```sql
ALTER TABLE app_user
ADD COLUMN nickname VARCHAR(50);
```

這個 `nickname` 沒有明確指定字元集，所以它會吃表的預設，也就是 `utf8mb4 / utf8mb4_0900_ai_ci`。

### 4.7.3 轉換既有文字欄位的字元集

如果要嘗試轉換既有文字欄位，可以使用：

```sql
ALTER TABLE app_user
CONVERT TO CHARACTER SET utf8mb4
COLLATE utf8mb4_0900_ai_ci;
```

這個語句是在說：

> 把這張表的既有文字欄位，例如 `CHAR`、`VARCHAR`、`TEXT`，轉成指定的字元集與排序規則。

例如原本：

```sql
CREATE TABLE app_user (
  username VARCHAR(50) CHARACTER SET latin1 COLLATE latin1_swedish_ci,
  email VARCHAR(100) CHARACTER SET latin1 COLLATE latin1_swedish_ci
) DEFAULT CHARSET = latin1;
```

執行：

```sql
ALTER TABLE app_user
CONVERT TO CHARACTER SET utf8mb4
COLLATE utf8mb4_0900_ai_ci;
```

之後大致會變成：

```sql
CREATE TABLE app_user (
  username VARCHAR(50) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci,
  email VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci
) DEFAULT CHARSET = utf8mb4;
```

也就是：

```text
表預設字元集改了
既有文字欄位也改了
既有資料也會被 MySQL 嘗試轉換
```

## 4.8 控制執行方式：`ALGORITHM` 與 `LOCK`

前面學到的 `ALTER TABLE`，重點是：

> 我要修改資料表的哪一部分？

例如：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼';
```

這句話表面上是在說：

```text
我要在 app_user 表新增 phone 欄位。
```

但是在正式環境中，還要多想一層：

> MySQL 會用什麼方式完成這個修改？
> 修改過程中，其他 SQL 還能不能查詢、寫入這張表？
> 這次修改會不會掃描、轉換、複製既有資料？

這就是 `ALGORITHM` 與 `LOCK` 要處理的問題。

簡單記：

```text
ALTER TABLE：控制「要改什麼」
ALGORITHM：控制「MySQL 用什麼方式改」
LOCK：控制「修改期間別人能不能讀寫」
```

MySQL 官方文件也說明，`ALTER TABLE` 可以新增或刪除欄位、建立或刪除索引、改變既有欄位型別、重新命名欄位或表，也可以改變儲存引擎、表註解等表特性。也就是說，`ALTER TABLE` 修改的是表結構，但這個結構會直接影響資料的儲存、讀取與驗證方式。

---

### 4.8.1 先理解：為什麼「修改表」會牽涉到資料？

你可能會疑惑：

> 我只是修改表結構，為什麼會和資料有關？

原因是：

> **資料不是隨便存在資料庫裡，而是按照表結構的規則被存進去。**

資料表不是只有欄位名稱而已，表結構還包含：

```text
欄位名稱
欄位順序
資料型別
資料長度
是否允許 NULL
預設值
字元集
排序規則
索引
唯一約束
外鍵約束
CHECK 約束
```

所以當你修改表結構時，可能會改到：

```text
資料要怎麼存
資料要怎麼讀
資料是否合法
資料需不需要重新轉換
索引資料需不需要重建
資料列需不需要重新排列
```

例如：

```sql
CREATE TABLE app_user (
    id BIGINT NOT NULL,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL
);
```

這代表每一筆資料都必須符合：

```text
id 必須是 BIGINT
username 最多 50 字元，而且不能是 NULL
email 最多 100 字元，而且不能是 NULL
```

所以一旦你改這些規則，既有資料可能就會受到影響。

---

#### 4.8.1.1 最簡單例子：縮短欄位長度

假設原本是：

```sql
username VARCHAR(50)
```

資料裡有一筆：

```text
username = 'very_long_username_超過20個字元...'
```

現在你改成：

```sql
ALTER TABLE app_user
MODIFY COLUMN username VARCHAR(20);
```

表面上你是在「修改表結構」。

但問題是：

```text
既有資料如果超過 20 字元，怎麼辦？
```

MySQL 必須處理這件事：

```text
要不要截斷？
要不要報錯？
要不要檢查每一筆資料？
要不要重新儲存這個欄位？
```

所以這種 `ALTER TABLE` 就和資料有關。

---

#### 4.8.1.2 再看一個例子：改資料型別

原本：

```sql
age VARCHAR(10)
```

資料可能是：

```text
'18'
'25'
'abc'
'unknown'
```

現在你改成：

```sql
ALTER TABLE app_user
MODIFY COLUMN age INT;
```

這看起來也是改表。

但實際上 MySQL 要面對：

```text
'18' 可以轉成 18
'25' 可以轉成 25
'abc' 怎麼轉？
'unknown' 怎麼轉？
```

所以它不是只改一個欄位定義而已，而是可能要把既有資料重新轉換。

這就是為什麼「修改表」會牽涉到「資料」。

---

#### 4.8.1.3 新增欄位為什麼也可能跟資料有關？

假設原本有三個欄位：

```text
id, username, email
```

現在你新增：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL;
```

邏輯上，表變成：

```text
id, username, email, phone
```

問題是：

```text
舊資料原本沒有 phone 這個欄位，那舊資料的 phone 是什麼？
```

如果 `phone` 可以是 `NULL`，那很好處理：

```text
舊資料的 phone 就當作 NULL
```

所以這種情況可能很輕，甚至可以 `ALGORITHM=INSTANT`。

但是如果你新增的是：

```sql
ALTER TABLE app_user
ADD COLUMN status TINYINT NOT NULL;
```

那就麻煩了。

因為舊資料沒有 `status`，但你又說：

```text
status 不能是 NULL
```

那 MySQL 就要思考：

```text
舊資料的 status 要放什麼？
有沒有 DEFAULT？
需不需要回填？
需不需要改每一筆資料？
```

所以新增欄位也可能跟資料有關。

---

#### 4.8.1.4 刪除欄位更明顯

假設你執行：

```sql
ALTER TABLE app_user
DROP COLUMN email;
```

你表面上是在刪欄位。

但實際上：

```text
所有資料裡的 email 值都會消失。
```

例如原本：

```text
id | username | email
1  | tom      | tom@gmail.com
2  | mary     | mary@gmail.com
```

刪除後變成：

```text
id | username
1  | tom
2  | mary
```

`email` 這些既有資料就沒了。

所以 `DROP COLUMN` 當然和資料有關。

---

#### 4.8.1.5 加索引也和資料有關

這個也很重要。

假設你執行：

```sql
ALTER TABLE app_user
ADD INDEX idx_email (email);
```

你可能會覺得：

```text
我只是加索引，又沒有改資料。
```

沒錯，表裡的原始資料沒變。

但是 MySQL 要建立一份新的索引結構。

它必須掃描既有資料：

```text
tom@gmail.com
mary@gmail.com
jack@gmail.com
...
```

然後建立類似這樣的索引：

```text
email value        -> 對應資料位置
jack@gmail.com    -> 第 3 筆
mary@gmail.com    -> 第 2 筆
tom@gmail.com     -> 第 1 筆
```

所以加索引也是 `ALTER TABLE`，而且也跟既有資料有關，因為索引是根據既有資料建立出來的。

---


### 4.8.2 `ALGORITHM` 是什麼？

`ALGORITHM` 可以理解成：

> **MySQL 修改表結構時採用的施工方式。**

常見值有三個：

```text
ALGORITHM = INSTANT
ALGORITHM = INPLACE
ALGORITHM = COPY
```

你可以先用下面這句話理解：

```text
ALGORITHM 不是控制「你要改什麼」；
ALGORITHM 是控制「MySQL 可以用什麼方式幫你改」。
```

三種方式的感覺如下：

| `ALGORITHM` | 白話理解             | 是否大量動到既有資料 | 成本    |
| ----------- | ---------------- | ---------- | ----- |
| `INSTANT`   | 只改表結構說明，不搬資料     | 幾乎不動       | 最輕    |
| `INPLACE`   | 在原表上施工，可能掃描或整理資料 | 可能會動       | 中等到偏重 |
| `COPY`      | 建新表，把舊資料複製過去     | 會大量處理資料    | 最重    |

MySQL 官方文件把 `ALTER TABLE` 的處理方式分成 `COPY`、`INPLACE`、`INSTANT`：`COPY` 會在原表的副本上操作並逐列複製資料；`INPLACE` 避免複製整張表資料，但仍可能在原地重建表；`INSTANT` 則只修改 data dictionary 中的 metadata，表資料不受影響。

---

### 4.8.3 `ALGORITHM=INSTANT`：只改 metadata，最輕

`INSTANT` 是最輕的方式。

可以把它理解成：

```text
只改表的說明書，不重寫既有資料。
```

例如：

```sql
ALTER TABLE app_user
ADD COLUMN last_login_ip VARCHAR(45) NULL COMMENT '最後登入IP',
ALGORITHM = INSTANT;
```

這句話的意思不是單純：

```text
新增 last_login_ip 欄位。
```

而是更精準地說：

```text
我要新增 last_login_ip 欄位，
而且要求 MySQL 用 INSTANT 的方式新增。
如果不能 INSTANT，就報錯，不要偷偷改用比較重的方式。
```

`INSTANT` 的核心是：

```text
只修改表結構的 metadata。
不重新整理既有資料。
不重建整張表。
```

例如原本表中有三個欄位：

```text
id, username, email
```

現在新增一個可為 `NULL` 的欄位：

```text
phone
```

對既有資料來說，它原本沒有 `phone`。如果這個欄位允許 `NULL`，MySQL 可以把舊資料的 `phone` 視為 `NULL`，不一定需要真的把每一筆舊資料都重新寫一遍。

所以你可以把 `INSTANT ADD COLUMN` 想成：

```text
表結構說明書多了一欄。
舊資料本身不用搬。
讀出舊資料時，新增欄位就依規則顯示為 NULL 或預設值。
```

MySQL 文件列出的 `INSTANT` 類操作包含新增欄位、刪除欄位、新增或刪除 virtual column、新增或刪除欄位預設值等，但仍然有版本與操作限制。

#### 直覺比喻

假設你有一份 Excel：

```text
員工編號 | 姓名 | Email
```

現在你在最右邊多加一個標題：

```text
手機號碼
```

如果不用去改每一列舊資料，只是在表頭多一欄，這就很像 `INSTANT`。

所以：

```text
INSTANT = 只改表結構說明，不搬舊資料。
```

---

### 4.8.4 `ALGORITHM=INPLACE`：在原表上施工，但不代表完全不動資料

`INPLACE` 很容易被誤解。

很多人看到 `INPLACE` 會以為：

```text
完全不重建表
完全不掃描資料
完全不影響線上系統
```

這是不準確的。

比較正確的理解是：

```text
MySQL 盡量不要使用「建立新表再整表複製」的方式，
而是盡量在原本的表上處理。
但它仍然可能需要掃描資料、建立索引、整理資料，甚至原地重建表。
```

例如：

```sql
ALTER TABLE app_user
ADD INDEX idx_app_user_email (email),
ALGORITHM = INPLACE;
```

這個操作表面上只是「新增索引」，沒有修改原本的 email 值。

但是 MySQL 要建立索引，就必須根據既有資料產生一份新的索引結構。

例如既有資料有：

```text
tom@gmail.com
mary@gmail.com
jack@gmail.com
```

MySQL 要建立類似這樣的索引資料：

```text
email value      -> 對應資料位置
jack@gmail.com   -> 第 3 筆
mary@gmail.com   -> 第 2 筆
tom@gmail.com    -> 第 1 筆
```

所以加索引雖然不是修改原始欄位資料，但仍然要處理既有資料。

MySQL 官方文件說，`INPLACE` 操作會避免複製表資料，但仍可能在原地重建表，並且在準備與執行階段可能短暫取得 exclusive metadata lock；通常支援併發 DML，但不是所有操作都一樣。

#### 直覺比喻

`INPLACE` 像是：

```text
不搬家，在原本房子裡施工。
```

但施工有大有小：

```text
小施工：換門牌
中施工：加隔間
大施工：重新整理整層樓
```

所以：

```text
INPLACE 不是「一定很輕」。
INPLACE 只是「不是用最傳統的整表 COPY 方式」。
```

---

### 4.8.5 `ALGORITHM=COPY`：建新表、搬資料，最重

`COPY` 是最重的方式。

它的概念大致是：

```text
1. 建立一張新表，結構是修改後的樣子
2. 從舊表讀出資料
3. 按照新表結構把資料寫進新表
4. 用新表取代舊表
5. 刪除舊表
```

例如：

```sql
ALTER TABLE app_user
MODIFY COLUMN age BIGINT NULL COMMENT '年齡',
ALGORITHM = COPY;
```

如果原本 `age` 是 `INT`，現在改成 `BIGINT`，MySQL 可能需要重新處理既有資料的儲存格式。

`COPY` 的成本通常比較高，因為它可能需要：

```text
讀取整張表
複製整張表
建立新索引
消耗額外磁碟空間
等待其他修改操作完成
阻擋後續寫入
```

MySQL 官方文件說明，`COPY` 會在原表副本上操作，將資料從原表逐列複製到新表；使用 `COPY` 的 `ALTER TABLE` 不允許併發 DML，且寫入會被延後到新表準備好之後。([MySQL 主管區域][1])

#### 直覺比喻

`COPY` 像是：

```text
原本房子不直接改。
旁邊蓋一棟新房子。
把所有家具、住戶、資料搬過去。
最後用新房子取代舊房子。
```

所以：

```text
COPY = 最重，因為它真的會大量處理既有資料。
```

---

### 4.8.6 三種 `ALGORITHM` 的對比

| 項目       | `INSTANT`       | `INPLACE`              | `COPY`                |
| -------- | --------------- | ---------------------- | --------------------- |
| 核心概念     | 只改 metadata     | 在原表上施工                 | 建新表並複製資料              |
| 是否重寫既有資料 | 通常不會            | 可能會                    | 會                     |
| 是否可能重建表  | 通常不會            | 可能會                    | 等同重建                  |
| 是否需要額外空間 | 很少              | 視操作而定                  | 通常需要較多                |
| 成本       | 最低              | 中等到偏高                  | 最高                    |
| 常見感覺     | 改說明書            | 原地施工                   | 搬家重蓋                  |
| 適合理解成    | 表結構 metadata 修改 | 避免整表 copy 的 online DDL | offline / copying DDL |

簡單記：

```text
INSTANT：只改表的說明書。
INPLACE：在原本的表上施工。
COPY：做一張新表，把舊資料搬過去。
```

---

### 4.8.7 指定 `ALGORITHM` 的真正目的

指定 `ALGORITHM` 不是單純為了「加速」。

它真正的目的通常是：

> **限制 MySQL 只能用你接受的方式執行。**

例如：

```sql
ALTER TABLE app_user
ADD COLUMN last_login_ip VARCHAR(45) NULL COMMENT '最後登入IP',
ALGORITHM = INSTANT;
```

這句話的真正意思是：

```text
我只接受 INSTANT 這種低影響方式。
如果 MySQL 不能用 INSTANT 完成，就請直接失敗。
不要偷偷改用 INPLACE 或 COPY。
```

這在正式環境很重要。

因為你最怕的是：

```text
你以為只是新增欄位，很快；
結果 MySQL 實際上選了比較重的方式，導致大表長時間修改。
```

MySQL 文件說明，如果省略 `ALGORITHM`，MySQL 會優先使用支援的 `INSTANT`，否則使用 `INPLACE`，再不支援才使用 `COPY`；但如果你明確指定某個 `ALGORITHM`，MySQL 必須使用該方式，否則會報錯。([MySQL 主管區域][1])

所以指定：

```sql
ALGORITHM = INSTANT
```

不是在說：

```text
請幫我加速。
```

而是在說：

```text
只能用最輕的方式做。
做不到就不要做。
```

指定：

```sql
ALGORITHM = INPLACE
```

是在說：

```text
不要用 COPY 那種整表複製方式。
請盡量在原表上處理。
如果不能 INPLACE，就報錯。
```

指定：

```sql
ALGORITHM = COPY
```

是在說：

```text
我允許你使用建新表、搬資料的重型方式。
```

---

### 4.8.8 `LOCK` 是什麼？

`LOCK` 控制的是：

> `ALTER TABLE` 執行期間，其他 SQL 能不能讀、能不能寫這張表。

常見值有：

```text
LOCK = NONE
LOCK = SHARED
LOCK = EXCLUSIVE
LOCK = DEFAULT
```

對照表如下：

| `LOCK`           | 讀取 `SELECT` | 寫入 `INSERT/UPDATE/DELETE` | 白話          |
| ---------------- | ----------- | ------------------------- | ----------- |
| `LOCK=NONE`      | 盡量允許        | 盡量允許                      | 希望讀寫都不要擋    |
| `LOCK=SHARED`    | 允許          | 阻擋或限制                     | 可以查，但不要寫    |
| `LOCK=EXCLUSIVE` | 阻擋或限制       | 阻擋或限制                     | 我要獨占這張表     |
| `LOCK=DEFAULT`   | MySQL 自己選   | MySQL 自己選                 | 交給 MySQL 判斷 |

MySQL 官方文件說明，對於支援的 `ALTER TABLE` 操作，可以使用 `LOCK` 控制修改期間的併發讀寫程度；`LOCK=NONE` 要求允許併發讀寫，不支援則報錯；`LOCK=SHARED` 允許讀但阻擋寫；`LOCK=EXCLUSIVE` 則要求排他存取。([MySQL 主管區域][1])

---

### 4.8.9 `ALGORITHM` 與 `LOCK` 的差別

`ALGORITHM` 和 `LOCK` 不要混在一起。

它們控制的是不同層面的事情：

```text
ALGORITHM：MySQL 怎麼施工
LOCK：施工期間別人能不能使用這張表
```

例如：

```sql
ALTER TABLE app_user
ADD INDEX idx_app_user_email (email),
ALGORITHM = INPLACE,
LOCK = NONE;
```

這句話可以翻譯成：

```text
我要新增 email 索引。
請用 INPLACE 的方式做，不要用 COPY。
而且執行期間，希望其他 SQL 還可以繼續讀寫 app_user。
如果做不到，就報錯。
```

所以：

```text
ALGORITHM = INPLACE
```

關心的是：

```text
是不是用原地施工方式？
有沒有避免整表 COPY？
```

而：

```text
LOCK = NONE
```

關心的是：

```text
施工期間能不能讓其他 SQL 繼續讀寫？
```

---

### 4.8.10 基本語法

常見語法如下：

```sql
ALTER TABLE 表名
    修改動作,
    ALGORITHM = 演算法,
    LOCK = 鎖定方式;
```

例如新增欄位，希望使用 `INSTANT`：

```sql
ALTER TABLE app_user
ADD COLUMN last_login_ip VARCHAR(45) NULL COMMENT '最後登入IP',
ALGORITHM = INSTANT;
```

例如新增索引，希望使用 `INPLACE` 且允許線上讀寫：

```sql
ALTER TABLE app_user
ADD INDEX idx_app_user_email (email),
ALGORITHM = INPLACE,
LOCK = NONE;
```

例如你明確允許使用較重的 `COPY`：

```sql
ALTER TABLE app_user
MODIFY COLUMN age BIGINT NULL COMMENT '年齡',
ALGORITHM = COPY;
```

注意，`ALGORITHM=INSTANT` 的操作在 MySQL 中只允許搭配 `LOCK=DEFAULT`，其他 `LOCK` 參數不適用。([MySQL 主管區域][1])

所以一般寫：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼',
ALGORITHM = INSTANT;
```

即可，不需要再加：

```sql
LOCK = NONE
```

### 4.8.11 常見情境一：新增可為 `NULL` 欄位

假設原本有表：

```sql
CREATE TABLE app_user (
    id BIGINT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL
);
```

現在新增手機欄位：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼',
ALGORITHM = INSTANT;
```

這個操作可能很輕，因為舊資料原本沒有 `phone`，而 `phone` 又允許 `NULL`。

可以理解成：

```text
舊資料不用真的每一筆都補一個 phone。
MySQL 只要記住：這張表現在多了一個 phone 欄位。
舊資料讀出來時，phone 視為 NULL。
```

所以這類操作在支援條件下可能適合使用：

```sql
ALGORITHM = INSTANT
```

但要注意：

```text
不是所有版本、所有表、所有欄位位置、所有資料型別都一定支援 INSTANT。
正式環境仍應先在測試環境驗證。
```

---

### 4.8.12 常見情境二：新增 `NOT NULL` 欄位

假設你新增：

```sql
ALTER TABLE app_user
ADD COLUMN status TINYINT NOT NULL COMMENT '狀態';
```

這就比新增可為 `NULL` 欄位更敏感。

因為舊資料原本沒有 `status`，但你現在規定：

```text
status 不可以是 NULL
```

MySQL 就要面對：

```text
舊資料的 status 要放什麼？
有沒有 DEFAULT？
需不需要回填？
會不會違反 NOT NULL？
```

所以正式環境中，比較安全的流程通常是：

```sql
-- 1. 先新增可為 NULL 的欄位
ALTER TABLE app_user
ADD COLUMN status TINYINT NULL COMMENT '狀態：1啟用，0停用',
ALGORITHM = INSTANT;

-- 2. 回填既有資料
UPDATE app_user
SET status = 1
WHERE status IS NULL;

-- 3. 確認沒有 NULL
SELECT COUNT(*) AS null_status_count
FROM app_user
WHERE status IS NULL;

-- 4. 再改成 NOT NULL + DEFAULT
ALTER TABLE app_user
MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '狀態：1啟用，0停用';
```

這樣做的好處是：

```text
新增欄位、回填資料、加上 NOT NULL 規則分開處理。
每一步都可以檢查與回滾。
```

---

### 4.8.13 常見情境三：修改欄位型別

假設原本：

```sql
age VARCHAR(10)
```

資料裡可能有：

```text
'18'
'25'
'abc'
'unknown'
```

現在你改成：

```sql
ALTER TABLE app_user
MODIFY COLUMN age INT;
```

這表面上是修改欄位型別，但實際上 MySQL 必須處理既有資料：

```text
'18' 可以轉成 18
'25' 可以轉成 25
'abc' 怎麼轉？
'unknown' 怎麼轉？
```

所以這類操作通常不只是改 metadata，而是可能需要掃描、檢查、轉換甚至重建資料。

正式環境中，執行前應先檢查：

```sql
SELECT id, age
FROM app_user
WHERE age REGEXP '[^0-9]';
```

如果有不合法資料，應先清理，再修改欄位型別。

MySQL 文件也說，`CHANGE` 或 `MODIFY` 改變欄位資料型別時，MySQL 會嘗試轉換既有欄位值，這種轉換可能造成資料變化，例如縮短字串欄位可能導致截斷。([MySQL 主管區域][1])

---

### 4.8.14 常見情境四：新增索引

假設你執行：

```sql
ALTER TABLE app_user
ADD INDEX idx_app_user_email (email),
ALGORITHM = INPLACE,
LOCK = NONE;
```

這代表：

```text
我要新增 email 索引。
希望使用 INPLACE。
希望執行期間仍允許其他 SQL 讀寫。
```

新增索引雖然不會改變原本欄位值，但它要根據既有資料建立索引結構。

所以它仍然和資料有關：

```text
必須掃描既有 email
必須排序或建立索引結構
必須產生新的索引頁
```

MySQL 文件列出，對 InnoDB 來說，新增或刪除 secondary index 屬於支援 `INPLACE` 的 `ALTER TABLE` 操作類型之一。([MySQL 主管區域][1])

---

### 4.8.15 常見情境五：刪除欄位

假設你執行：

```sql
ALTER TABLE app_user
DROP COLUMN email;
```

這當然和資料有關，因為：

```text
所有既有資料中的 email 值都會消失。
```

例如原本：

```text
id | username | email
1  | tom      | tom@gmail.com
2  | mary     | mary@gmail.com
```

刪除後：

```text
id | username
1  | tom
2  | mary
```

所以刪除欄位前，要確認：

```text
是否還有程式使用這個欄位
是否還有報表使用這個欄位
是否還有 View / Stored Procedure / Trigger 使用這個欄位
是否有索引或外鍵依賴這個欄位
是否已備份
```

MySQL 文件也提到，如果刪除的欄位是某個索引的一部分，該欄位也會從索引中移除；如果索引的所有欄位都被刪除，索引也會被刪除。([MySQL 主管區域][1])

---

### 4.8.16 `LOCK=NONE` 不代表完全沒有鎖

`LOCK=NONE` 很容易被誤解成：

```text
完全沒有鎖
完全不會等待
完全不會影響線上系統
```

這不準確。

比較正確的理解是：

```text
如果這個操作支援，就允許其他 SQL 繼續讀寫。
如果不支援，就報錯。
```

即使是 online DDL，MySQL 仍可能在開始或結束階段短暫取得 metadata lock。

所以正式環境中，如果剛好有長交易或長查詢佔著表，`ALTER TABLE` 可能會等待；而等待中的 DDL 又可能影響後續 SQL。

可以先檢查：

```sql
SHOW PROCESSLIST;
```

或查詢 metadata lock 狀況：

```sql
SELECT *
FROM performance_schema.metadata_locks
WHERE OBJECT_NAME = 'app_user';
```

重點是：

```text
LOCK=NONE 是要求「允許併發讀寫」，
不是保證「完全沒有鎖」。
```

---

### 4.8.17 如果不寫 `ALGORITHM`，MySQL 會怎麼做？

如果你寫：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼';
```

沒有指定：

```sql
ALGORITHM = ...
```

那 MySQL 會自己選擇執行方式。

MySQL 文件說明，如果省略 `ALGORITHM`，MySQL 會對支援的操作優先使用 `INSTANT`，否則使用 `INPLACE`，如果 `INPLACE` 也不支援，才使用 `COPY`。([MySQL 主管區域][1])

這雖然方便，但在正式環境有一個問題：

```text
你不一定清楚 MySQL 最後選了哪種方式。
```

所以正式環境的大表，常會明確指定：

```sql
ALGORITHM = INSTANT
```

或：

```sql
ALGORITHM = INPLACE,
LOCK = NONE
```

這樣做的目的不是炫技，而是：

```text
我只接受低風險做法。
如果 MySQL 做不到，就直接失敗。
```

### 4.8.18 實務上怎麼選？

可以先用下面這個判斷方式。

#### 只改 metadata，優先考慮 `INSTANT`

例如：

```text
新增可為 NULL 的欄位
修改欄位預設值
刪除欄位預設值
某些欄位改名
```

可以嘗試：

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼',
ALGORITHM = INSTANT;
```

意思是：

```text
只能用 metadata 修改方式。
做不到就報錯。
```

---

#### 需要掃描資料或建立索引，可能考慮 `INPLACE + LOCK=NONE`

例如：

```text
新增二級索引
刪除二級索引
某些不需要整表 COPY 的修改
```

可以嘗試：

```sql
ALTER TABLE app_user
ADD INDEX idx_app_user_email (email),
ALGORITHM = INPLACE,
LOCK = NONE;
```

意思是：

```text
不要用 COPY。
希望修改期間仍允許讀寫。
做不到就報錯。
```

---

#### 會改變資料儲存格式，要非常小心

例如：

```text
VARCHAR 改 INT
INT 改 BIGINT
縮短 VARCHAR 長度
改字元集
改欄位順序
修改主鍵
修改外鍵欄位
```

這些操作可能需要重建表或轉換資料，不應直接在正式環境的大表上隨手執行。

執行前應先做：

```text
測試環境演練
檢查資料是否合法
評估表大小
評估索引與外鍵
確認備份
確認回滾方案
安排低峰時段
必要時請 DBA 審查
```

---

### 4.8.19 正式環境建議流程

正式環境執行 `ALTER TABLE` 前，建議先做這些檢查：

```sql
-- 1. 確認目前資料庫
SELECT DATABASE();

-- 2. 查看表結構
SHOW CREATE TABLE app_user;

-- 3. 查看欄位
SHOW FULL COLUMNS FROM app_user;

-- 4. 查看索引
SHOW INDEX FROM app_user;

-- 5. 估算資料量
SELECT COUNT(*) FROM app_user;
```

如果是修改欄位型別或縮短長度，先查不符合新規則的資料：

```sql
SELECT id, username, CHAR_LENGTH(username) AS username_length
FROM app_user
WHERE CHAR_LENGTH(username) > 20;
```

如果是改 `NULL` 為 `NOT NULL`：

```sql
SELECT COUNT(*) AS null_count
FROM app_user
WHERE phone IS NULL;
```

如果是新增索引，要確認是否已有重複或不適合的索引：

```sql
SHOW INDEX FROM app_user;
```

如果要避免重型操作，可以先嘗試指定低風險方式：

```sql
ALTER TABLE app_user
ADD COLUMN last_login_ip VARCHAR(45) NULL COMMENT '最後登入IP',
ALGORITHM = INSTANT;
```

或：

```sql
ALTER TABLE app_user
ADD INDEX idx_app_user_email (email),
ALGORITHM = INPLACE,
LOCK = NONE;
```

### 4.8.20 常見誤解整理

#### 誤解一：`ALTER TABLE` 只是改表，跟資料無關

錯。

因為資料是按照表結構存的。

```text
改欄位型別，可能要轉換既有資料。
縮短欄位長度，可能造成資料截斷。
新增 NOT NULL 欄位，舊資料必須有合法值。
新增索引，要掃描既有資料建立索引。
刪除欄位，既有資料會消失。
```

---

#### 誤解二：`INSTANT` 是讓 SQL 跑比較快

不精確。

`INSTANT` 的重點是：

```text
只改 metadata，不重寫既有資料。
```

它之所以快，是因為不需要大量處理既有資料。

---

#### 誤解三：`INPLACE` 就是不重建表

不一定。

`INPLACE` 的意思是：

```text
避免使用 COPY 那種整表複製方式。
```

但它仍然可能：

```text
掃描資料
建立索引
整理資料
原地重建表
短暫取得 metadata lock
```

MySQL 官方文件也明確說，`INPLACE` 避免複製表資料，但可能在原地重建表。([MySQL 主管區域][1])

---

#### 誤解四：`COPY` 一定不能用

不是。

`COPY` 不是錯誤，它只是成本高。

如果你明確知道：

```text
表不大
可以停機
可以接受寫入阻塞
已經備份
已經演練
```

那 `COPY` 也可以使用。

真正危險的是：

```text
你不知道 MySQL 實際上用了 COPY，
卻在正式環境大表上直接執行。
```

---

#### 誤解五：`LOCK=NONE` 完全沒有鎖

不精確。

`LOCK=NONE` 的意思是：

```text
如果支援，就允許併發讀寫。
如果不支援，就報錯。
```

它不代表完全沒有 metadata lock，也不代表不會等待長交易或長查詢。

### 4.8.21 一句話總結

```text
ALTER TABLE 是改表結構；
但表結構是資料的儲存規則、讀取規則與驗證規則。
所以改表結構，常常會牽涉既有資料。
```

```text
ALGORITHM 管「MySQL 用什麼方式改表」。
LOCK 管「改表期間其他 SQL 能不能讀寫」。
```

```text
INSTANT：只改 metadata，最輕。
INPLACE：在原表上施工，不等於完全不重建。
COPY：建新表並搬資料，最重。
```

```text
指定 ALGORITHM / LOCK 的目的，
不是保證 ALTER TABLE 一定更快，
而是限制 MySQL 只能用你能接受的風險等級執行。
```

最重要的實務觀念是：

> 正式環境的大表，不要只問「這個 ALTER TABLE 語法對不對」，還要問「MySQL 會用什麼方式執行，以及執行期間會不會影響線上讀寫」。

## 4.9 綜合範例：使用者表演進

假設一開始有這張表：

```sql
CREATE TABLE app_user (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '使用者ID',
    username VARCHAR(50) NOT NULL COMMENT '帳號',
    email VARCHAR(100) NOT NULL COMMENT '電子信箱',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    PRIMARY KEY (id),
    UNIQUE KEY uk_app_user_username (username),
    UNIQUE KEY uk_app_user_email (email)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '使用者表';
```

現在需求變更：

1. 新增手機欄位 `phone`；
2. 新增狀態欄位 `status`，預設啟用；
3. 把 `username` 改名為 `login_name`；
4. 把 `email` 註解改得更清楚；
5. 新增最後登入時間 `last_login_at`；
6. 刪除不再使用的 `nickname` 欄位。

### 4.9.1 先檢查原表

```sql
SHOW CREATE TABLE app_user;
SHOW FULL COLUMNS FROM app_user;
SHOW INDEX FROM app_user;
```

### 4.9.2 新增欄位

```sql
ALTER TABLE app_user
ADD COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼' AFTER email,
ADD COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '狀態：1啟用，0停用' AFTER phone,
ADD COLUMN last_login_at DATETIME NULL COMMENT '最後登入時間' AFTER updated_at;
```

### 4.9.3 改欄位名

```sql
ALTER TABLE app_user
RENAME COLUMN username TO login_name;
```

如果你的 MySQL 版本較舊，不支援 `RENAME COLUMN`，可以使用 `CHANGE COLUMN`：

```sql
ALTER TABLE app_user
CHANGE COLUMN username login_name VARCHAR(50) NOT NULL COMMENT '登入帳號';
```

### 4.9.4 修改欄位註解

```sql
ALTER TABLE app_user
MODIFY COLUMN email VARCHAR(100) NOT NULL COMMENT '使用者電子信箱';
```

### 4.9.5 刪除欄位前先確認

```sql
SELECT COLUMN_NAME
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'app_user'
  AND COLUMN_NAME = 'nickname';
```

確認存在且不再使用後：

```sql
ALTER TABLE app_user
DROP COLUMN nickname;
```

### 4.9.6 修改後再檢查

```sql
SHOW CREATE TABLE app_user;
SHOW FULL COLUMNS FROM app_user;
```

## 4.10 常見錯誤整理

### 錯誤 1：`MODIFY` 時忘記保留原本屬性

錯誤寫法：

```sql
ALTER TABLE app_user
MODIFY COLUMN email VARCHAR(150);
```

可能問題：

- 原本 `NOT NULL` 消失；
- 原本 `COMMENT` 消失；
- 原本 `DEFAULT` 消失；
- 原本字元集或其他屬性可能被改變。

較好寫法：

```sql
ALTER TABLE app_user
MODIFY COLUMN email VARCHAR(150) NOT NULL COMMENT '使用者電子信箱';
```

### 錯誤 2：改欄位名後只改資料庫，忘記改程式

```sql
ALTER TABLE app_user
RENAME COLUMN username TO login_name;
```

如果 Java Entity、MyBatis XML、SQL、前端欄位仍然使用 `username`，程式就可能報錯。

改欄位名通常要搭配程式碼一起改。

### 錯誤 3：直接刪除欄位，沒有確認依賴

```sql
ALTER TABLE app_user
DROP COLUMN phone;
```

刪除前應至少確認：

```sql
SHOW INDEX FROM app_user;
SHOW CREATE TABLE app_user;
```

並搜尋專案中是否還使用：

```text
phone
getPhone
setPhone
phone)
phone,
column="phone"
#{phone}
```

### 錯誤 4：以為修改預設值會更新既有資料

```sql
ALTER TABLE app_user
ALTER COLUMN status SET DEFAULT 1;
```

這不會自動把既有的 `NULL` 改成 `1`。

要更新既有資料，需要：

```sql
UPDATE app_user
SET status = 1
WHERE status IS NULL;
```

### 錯誤 5：為了欄位順序頻繁改表

```sql
ALTER TABLE app_user
MODIFY COLUMN phone VARCHAR(20) NULL COMMENT '手機號碼' AFTER email;
```

如果只是查詢時想讓欄位順序更好看，不一定要改表。

可以改查詢：

```sql
SELECT id, login_name, email, phone, status, created_at
FROM app_user;
```

## 一句話對比

- `ADD COLUMN`：新增欄位。
- `MODIFY COLUMN`：修改欄位定義，不改欄位名。
- `CHANGE COLUMN`：可以同時改欄位名與欄位定義。
- `RENAME COLUMN`：只改欄位名。
- `ALTER COLUMN ... SET DEFAULT`：修改預設值。
- `ALTER COLUMN ... DROP DEFAULT`：移除預設值。
- `DROP COLUMN`：刪除欄位與欄位資料。
- `FIRST` / `AFTER`：調整欄位在表結構中的位置。
- `ALGORITHM` / `LOCK`：控制部分 DDL 的執行方式與併發影響。
