# 7 清空表

返回章节：[第十章_创建和管理表](./README.md)

## 本节导读

这一节处理的是“表还要留着，但里面的数据想清掉”的情境。

这类题目最容易混淆的，不是语法本身，而是该选哪一种操作：

- `TRUNCATE TABLE`：清空整张表的数据，但保留结构；
- `DELETE FROM`：删除表内数据，可以整表删，也可以条件删；
- `DROP TABLE`：连表结构一起删除。

所以这一篇的重点不是只记一条命令，而是先分清“要保留什么、要不要回滚、要不要重置自增、会不会影响结构”，再决定该用 `TRUNCATE`、`DELETE` 还是 `DROP`。

## 关键字

- 主题：清空表、`TRUNCATE TABLE`、`DELETE FROM`、`DROP TABLE`
- 英文：truncate table, delete from, drop table
# 7 清空表

返回章節：[第十章_创建和管理表](./README.md)

## 本節導讀

這一節處理的是：**表結構還要保留，但表內資料想全部清掉時，應該怎麼做。**

「清空表」看起來只是一句 SQL：

```sql
TRUNCATE TABLE table_name;
```

但在真實專案中，這一題很容易出事故，因為很多人會把下面三件事混在一起：

```text
DELETE FROM：刪除資料列
TRUNCATE TABLE：快速清空整張表
DROP TABLE：刪掉整張表物件
```

這三個指令都可能讓資料消失，但它們的本質完全不同：

- `DELETE FROM` 是 DML，刪的是資料列，可以加 `WHERE`，通常可以受交易控制。
- `TRUNCATE TABLE` 是 DDL，清空的是整張表資料，不能加 `WHERE`，會造成 implicit commit，不能像一般 DML 一樣靠 `ROLLBACK` 救回。
- `DROP TABLE` 是 DDL，刪的是整張表，連表結構都不保留。

所以這一篇的重點不是背「清空表 = `TRUNCATE`」，而是要能判斷：

1. 我是要刪部分資料，還是清空全部資料？
2. 我還要不要保留表結構？
3. 我需不需要 `ROLLBACK` 能力？
4. 我要不要重置 `AUTO_INCREMENT`？
5. 這張表是否被外鍵引用？
6. 有沒有 Trigger、報表、批次、程式碼依賴這些資料？
7. 在正式環境中，清空前要做哪些檢查？

這一篇學完後，你應該要能做到：

- 正確使用 `TRUNCATE TABLE` 清空整張表；
- 正確使用 `DELETE FROM` 刪除全部或部分資料；
- 分清楚 `DELETE`、`TRUNCATE`、`DROP` 的差異；
- 知道 `TRUNCATE` 為什麼通常比整表 `DELETE` 快；
- 知道 `TRUNCATE` 為什麼不能期待用 `ROLLBACK` 復原；
- 知道 `TRUNCATE` 會重置 `AUTO_INCREMENT`；
- 知道 `TRUNCATE` 不會觸發 `ON DELETE` Trigger；
- 知道有外鍵引用時，`TRUNCATE` 可能失敗；
- 能在正式環境中寫出清空資料前的檢查清單。

- 想清空測試資料，但表結構還要保留時。
- 想重置測試表的 `AUTO_INCREMENT` 編號時。
- 想刪除某段時間以前的歷史資料時。
- 想知道 `DELETE FROM table_name;` 和 `TRUNCATE TABLE table_name;` 差在哪裡時。
- 想確認某個操作能不能用 `ROLLBACK` 救回時。
- 正式環境要清理大量資料，需要設計安全流程時。
- 有外鍵、Trigger、報表或批次依賴，不確定能不能直接清空表時。

## 30 秒複習入口

- 只刪部分資料：用 `DELETE FROM table_name WHERE 條件;`。
- 刪全部資料但想保留回滾能力：優先用 `DELETE FROM`，並放在交易中測試。
- 快速清空整張表且要重置 `AUTO_INCREMENT`：用 `TRUNCATE TABLE`。
- 表本身不要了：用 `DROP TABLE`，這不是清空表，而是刪除表。
- `TRUNCATE TABLE` 是 DDL，不是 DML。
- `TRUNCATE TABLE` 會造成 implicit commit，不能像 `DELETE` 一樣靠 `ROLLBACK` 復原。
- `TRUNCATE TABLE` 不能加 `WHERE`，只能清空整張表。
- `TRUNCATE TABLE` 通常會重置 `AUTO_INCREMENT`。
- `TRUNCATE TABLE` 不會觸發 `ON DELETE` Trigger。
- 如果其他表用外鍵引用這張表，`TRUNCATE TABLE` 可能直接失敗。
- `DELETE FROM table_name;` 沒有 `WHERE` 時會刪除整張表的所有資料列，但表結構還在。
- `DELETE` 可以用 `ORDER BY`、`LIMIT` 做分批刪除，適合正式環境清理大量歷史資料。

## 速查區

### 1. 三個指令的核心差異

| 指令 | 刪除對象 | 表結構是否保留 | 是否可加 `WHERE` | 是否重置 `AUTO_INCREMENT` | 是否通常可回滾 | 操作類型 |
| --- | --- | --- | --- | --- | --- | --- |
| `DELETE FROM` | 資料列 | 保留 | 可以 | 通常不重置 | 可以，前提是交易型表與正確交易控制 | DML |
| `TRUNCATE TABLE` | 整張表的全部資料 | 保留 | 不可以 | 會重置 | 不可以像 DML 一樣回滾 | DDL |
| `DROP TABLE` | 整張表物件 | 不保留 | 不可以 | 不適用，表已刪除 | 通常不能靠 `ROLLBACK` 救回 | DDL |

---

### 2. 常用語法

| 需求 | 語法 | 說明 |
| --- | --- | --- |
| 快速清空整張表 | `TRUNCATE TABLE table_name;` | 保留表結構，清空全部資料 |
| 刪除整張表全部資料 | `DELETE FROM table_name;` | 保留表結構，可受交易控制 |
| 刪除部分資料 | `DELETE FROM table_name WHERE 條件;` | 最常見、最安全的刪除方式 |
| 分批刪除資料 | `DELETE FROM table_name WHERE 條件 ORDER BY id LIMIT 1000;` | 降低長時間鎖定與大量 undo 壓力 |
| 刪除整張表 | `DROP TABLE table_name;` | 表結構和資料都消失 |

---

### 3. 一句話選擇

```text
只刪部分資料：DELETE + WHERE
清空全部資料但要可回滾：交易中的 DELETE
清空全部資料且要重置自增：TRUNCATE
連表都不要：DROP TABLE
```

## 7.1 清空表的核心觀念

清空表的意思是：

> 表還要繼續存在，但表裡面的資料全部不要了。

也就是：

- 欄位還在；
- 主鍵還在；
- 索引還在；
- 約束還在；
- 表註解還在；
- 表名還在；
- 只是資料列被清掉。

可以把資料表想成 Excel 工作表：

```text
DELETE FROM：刪除工作表中的某些列或全部列
TRUNCATE TABLE：把工作表內容全部清空，但工作表格式還在
DROP TABLE：把整個工作表分頁刪掉
```

所以「清空表」通常會在兩個指令中選擇：

```sql
TRUNCATE TABLE table_name;
```

或：

```sql
DELETE FROM table_name;
```

真正的判斷點是：

- 是否需要 `WHERE`？
- 是否需要交易回滾？
- 是否需要重置自增？
- 資料量是否很大？
- 是否存在外鍵與 Trigger？

---

## 7.2 `TRUNCATE TABLE`

### 7.2.1 基本語法

MySQL 的語法是：

```sql
TRUNCATE [TABLE] table_name;
```

實務上建議完整寫成：

```sql
TRUNCATE TABLE table_name;
```

例如：

```sql
TRUNCATE TABLE employees;
```

執行後：

- `employees` 表仍然存在；
- 表結構仍然存在；
- 表內所有資料列被清空；
- 若有 `AUTO_INCREMENT`，通常會重置為起始值；
- 不會回傳有意義的刪除筆數。

---

### 7.2.2 `TRUNCATE TABLE` 的本質

`TRUNCATE TABLE` 很像：

```sql
DELETE FROM table_name;
```

因為兩者都可以讓表變空。

但它的本質不是逐行刪除資料，而是接近：

```text
刪掉原本的資料儲存空間
重新建立一個空的表資料空間
保留原本的表定義
```

因此它有幾個重要特性：

1. 速度通常比整表 `DELETE` 快；
2. 會造成 implicit commit；
3. 不能像 DML 一樣靠 `ROLLBACK` 復原；
4. 會重置 `AUTO_INCREMENT`；
5. 不會觸發 `ON DELETE` Trigger；
6. 有其他表外鍵引用時可能失敗；
7. 需要 `DROP` 權限，而不是單純 `DELETE` 權限。

---

### 7.2.3 `TRUNCATE` 為什麼通常比較快

`DELETE FROM table_name;` 的語意是：

```text
把表內每一列資料刪掉
```

而 `TRUNCATE TABLE table_name;` 的語意更接近：

```text
直接把整張表清空，重新得到一張空表
```

所以資料量很大時，`TRUNCATE` 通常比整表 `DELETE` 快。

但是「比較快」不代表「比較安全」。

正式環境中，速度不是唯一考量，還要考慮：

- 能不能回滾；
- 是否誤清空正式資料；
- 是否被外鍵引用；
- 是否需要觸發 Trigger；
- 是否會影響複製、備份、報表、批次；
- 是否需要保留自增序號。

---

### 7.2.4 `TRUNCATE` 會重置 `AUTO_INCREMENT`

假設有一張表：

```sql
CREATE TABLE truncate_demo (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

INSERT INTO truncate_demo (name) VALUES ('A'), ('B'), ('C');

SELECT * FROM truncate_demo;
```

可能得到：

```text
id | name
---+-----
1  | A
2  | B
3  | C
```

執行：

```sql
TRUNCATE TABLE truncate_demo;

INSERT INTO truncate_demo (name) VALUES ('D');

SELECT * FROM truncate_demo;
```

通常會得到：

```text
id | name
---+-----
1  | D
```

這表示 `AUTO_INCREMENT` 已經被重置。

這在測試資料表中很方便，但在正式環境中要小心，因為有些系統雖然不應該依賴自增 ID 的連續性，但實務上報表、匯出檔、人工查詢、外部系統對帳可能會間接受影響。

---

### 7.2.5 `TRUNCATE` 不會觸發 `ON DELETE` Trigger

假設有一個 Trigger：

```sql
CREATE TRIGGER trg_employee_delete
AFTER DELETE ON employee
FOR EACH ROW
INSERT INTO employee_delete_log(employee_id, deleted_at)
VALUES (OLD.id, NOW());
```

執行：

```sql
DELETE FROM employee WHERE id = 1;
```

會觸發 `AFTER DELETE` Trigger。

但執行：

```sql
TRUNCATE TABLE employee;
```

不會觸發 `ON DELETE` Trigger。

這一點非常重要。

如果系統依賴 Trigger 做：

- 刪除紀錄；
- 稽核日誌；
- 同步資料；
- 統計表更新；
- 歷史資料備份；
- 關聯資料清理；

那麼用 `TRUNCATE` 就可能繞過這些邏輯。

---

### 7.2.6 `TRUNCATE` 遇到外鍵可能失敗

假設有兩張表：

```sql
CREATE TABLE department (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    dept_name VARCHAR(50) NOT NULL
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

CREATE TABLE employee (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    dept_id BIGINT NOT NULL,
    emp_name VARCHAR(50) NOT NULL,
    CONSTRAINT fk_employee_department
        FOREIGN KEY (dept_id) REFERENCES department(id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

這裡 `employee.dept_id` 引用 `department.id`。

如果你執行：

```sql
TRUNCATE TABLE department;
```

可能會失敗，因為 `department` 被其他表的外鍵引用。

這時候不要直覺使用：

```sql
SET foreign_key_checks = 0;
TRUNCATE TABLE department;
SET foreign_key_checks = 1;
```

這種寫法在正式環境很危險，因為它可能造成資料不一致。

比較正確的思考順序是：

1. 先確認是否真的要清空父表；
2. 查出哪些子表引用它；
3. 判斷是否應該先刪子表資料；
4. 判斷是否應該改用 `DELETE` 搭配正確順序；
5. 必要時先備份資料；
6. 正式環境需經過審核。

查詢哪些表引用目前表，可以使用：

```sql
SELECT
    TABLE_SCHEMA,
    TABLE_NAME,
    COLUMN_NAME,
    CONSTRAINT_NAME,
    REFERENCED_TABLE_SCHEMA,
    REFERENCED_TABLE_NAME,
    REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE REFERENCED_TABLE_SCHEMA = DATABASE()
  AND REFERENCED_TABLE_NAME = 'department';
```

## 7.3 `DELETE FROM`

### 7.3.1 基本語法

刪除部分資料：

```sql
DELETE FROM table_name
WHERE 條件;
```

刪除全部資料：

```sql
DELETE FROM table_name;
```

注意：

```sql
DELETE FROM table_name;
```

沒有 `WHERE`，代表刪除表內所有資料列。

這一點非常危險。

---

### 7.3.2 `DELETE` 的特性

`DELETE` 是 DML，特性如下：

- 可以加 `WHERE`；
- 可以只刪部分資料；
- 可以放在交易中；
- 對 InnoDB 這種交易型表，通常可以透過 `ROLLBACK` 復原尚未提交的刪除；
- 會回傳刪除筆數；
- 會觸發 `DELETE` Trigger；
- 通常不會重置 `AUTO_INCREMENT`；
- 大量刪除時可能產生大量 undo / redo / binlog，並造成長時間鎖定。

範例：

```sql
DELETE FROM orders
WHERE order_date < '2025-01-01';
```

這代表刪除 `2025-01-01` 以前的訂單資料。

---

### 7.3.3 大量刪除建議使用分批刪除

如果正式環境要刪除大量歷史資料，不建議直接：

```sql
DELETE FROM audit_log
WHERE created_at < '2025-01-01';
```

因為一次刪太多可能造成：

- 交易時間太長；
- 鎖持有太久；
- undo log 壓力過大；
- binlog 很大；
- replication 延遲；
- 線上查詢變慢；
- 回滾成本很高。

比較安全的做法是分批刪除：

```sql
DELETE FROM audit_log
WHERE created_at < '2025-01-01'
ORDER BY id
LIMIT 1000;

SELECT ROW_COUNT();
```

重複執行，直到 `ROW_COUNT()` 小於 `1000` 或等於 `0`。

如果你要在程式或批次中處理，可以設計成：

```text
每次刪 1000 筆
刪完 sleep 幾百毫秒
記錄刪除筆數
如果 ROW_COUNT() = 0 就停止
```

這樣會比一次刪幾十萬、幾百萬筆更穩定。

---

### 7.3.4 `DELETE`、`ORDER BY`、`LIMIT`

MySQL 的單表 `DELETE` 可以搭配：

```sql
DELETE FROM table_name
WHERE 條件
ORDER BY 欄位
LIMIT 筆數;
```

例如：

```sql
DELETE FROM login_log
WHERE created_at < '2025-01-01'
ORDER BY id
LIMIT 5000;
```

這種寫法適合做「分批清理」。

但要注意：

- `ORDER BY` + `LIMIT` 主要適用於單表 `DELETE`；
- 多表 `DELETE` 不支援 `ORDER BY`、`LIMIT`；
- 分批刪除最好搭配索引欄位，例如 `id`、`created_at`；
- 刪除條件沒有索引時，仍可能掃描大量資料。

---

## 7.4 `TRUNCATE` 與 `DELETE` 的交易差異

### 7.4.1 `DELETE` 可以被交易控制

建立測試表：

```sql
DROP TABLE IF EXISTS tx_delete_demo;

CREATE TABLE tx_delete_demo (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

INSERT INTO tx_delete_demo (name) VALUES ('A'), ('B'), ('C');
```

測試 `DELETE`：

```sql
START TRANSACTION;

DELETE FROM tx_delete_demo;

SELECT * FROM tx_delete_demo;

ROLLBACK;

SELECT * FROM tx_delete_demo;
```

結果概念：

```text
DELETE 後：表內暫時看不到資料
ROLLBACK 後：資料恢復
```

原因是：

```text
DELETE 是 DML
InnoDB 支援交易
尚未 COMMIT 前可以 ROLLBACK
```

---

### 7.4.2 `TRUNCATE` 不能像 DML 一樣被回滾

建立測試表：

```sql
DROP TABLE IF EXISTS tx_truncate_demo;

CREATE TABLE tx_truncate_demo (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

INSERT INTO tx_truncate_demo (name) VALUES ('A'), ('B'), ('C');
```

測試 `TRUNCATE`：

```sql
START TRANSACTION;

TRUNCATE TABLE tx_truncate_demo;

ROLLBACK;

SELECT * FROM tx_truncate_demo;
```

結果概念：

```text
ROLLBACK 後，資料不會恢復。
```

原因是：

```text
TRUNCATE TABLE 是 DDL
執行時會造成 implicit commit
不能像 DELETE 一樣靠 ROLLBACK 救回
```

所以原本常見的範例：

```sql
SET autocommit = FALSE;

DELETE FROM emp2;
-- TRUNCATE TABLE emp2;

ROLLBACK;
```

應該理解成：

- 如果執行的是 `DELETE FROM emp2;`，`ROLLBACK` 可以恢復尚未提交的資料；
- 如果執行的是 `TRUNCATE TABLE emp2;`，即使 `autocommit = FALSE`，也不能期待 `ROLLBACK` 把資料救回。

**重點：`SET autocommit = FALSE` 不會讓 `TRUNCATE` 變成可回滾的 DML。**

## 7.5 `DROP`、`TRUNCATE`、`DELETE` 對比

| 比較項目 | `DELETE FROM table_name` | `TRUNCATE TABLE table_name` | `DROP TABLE table_name` |
| --- | --- | --- | --- |
| 核心意思 | 刪資料列 | 清空整張表資料 | 刪掉整張表 |
| 表結構是否存在 | 存在 | 存在 | 不存在 |
| 是否可加 `WHERE` | 可以 | 不可以 | 不可以 |
| 是否可刪部分資料 | 可以 | 不可以 | 不可以 |
| 是否刪全部資料 | 沒有 `WHERE` 時是 | 是 | 是，連結構也刪 |
| 是否重置 `AUTO_INCREMENT` | 通常不重置 | 會重置 | 不適用 |
| 是否觸發 `DELETE` Trigger | 會 | 不會 | 不適用 |
| 是否回傳刪除筆數 | 會 | 不回傳有意義刪除筆數 | 不適用 |
| 是否通常可回滾 | 可，視交易與儲存引擎而定 | 不可像 DML 回滾 | 通常不可 |
| 操作類型 | DML | DDL | DDL |
| 速度 | 大量刪除較慢 | 通常較快 | 快，但表也消失 |
| 常見用途 | 刪部分資料、正式環境清理 | 測試表快速重置 | 表已廢棄 |
| 風險 | 條件寫錯會誤刪 | 一次清空且難救回 | 最高，表直接消失 |

## 7.6 正式環境清空資料前檢查清單

正式環境不要看到 `TRUNCATE` 就直接執行。

至少先檢查以下項目。

---

### 7.6.1 確認目前所在 database

```sql
SELECT DATABASE();
```

避免連錯環境、選錯 schema。

更安全一點可以：

```sql
SELECT @@hostname, @@port, DATABASE();
```

用來確認目前連到哪一台資料庫。

## 7.7 實務選擇建議

### 7.7.1 測試環境重置資料

如果是測試表，例如：

```text
測試帳號資料
測試訂單資料
測試匯入暫存表
測試報表暫存表
```

且你明確知道資料可以全部丟掉，通常可以使用：

```sql
TRUNCATE TABLE test_import_temp;
```

適合情境：

- 表資料全部不要；
- 表結構還要；
- 想重置 `AUTO_INCREMENT`；
- 不需要 Trigger；
- 沒有其他表引用；
- 不需要回滾。

---

### 7.7.2 正式環境清理歷史資料

如果是正式環境的歷史資料，例如：

```text
登入紀錄
操作紀錄
排程紀錄
介接紀錄
通知紀錄
```

通常不建議直接 `TRUNCATE`。

比較常見是：

```sql
DELETE FROM login_log
WHERE created_at < '2025-01-01'
ORDER BY id
LIMIT 5000;
```

並且分批執行。

這樣的好處是：

- 可以控制每次刪除量；
- 可以保留較新的資料；
- 可以降低鎖定時間；
- 可以觀察刪除速度；
- 可以中途停止；
- 可以在交易中測試小批量操作。

---

### 7.7.3 正式環境整表資料都不要

如果正式環境真的要整表清空，建議流程至少是：

```text
1. 確認需求單或主管核准
2. 確認目前 database 和 server
3. 查 COUNT(*)
4. 查 SHOW CREATE TABLE
5. 查外鍵依賴
6. 查 Trigger
7. 查 View / Procedure / Function / Event
8. 確認程式碼、報表、批次不再依賴舊資料
9. 備份資料
10. 在測試環境演練
11. 安排維護時段
12. 正式執行
13. 執行後驗證
```

如果無法接受資料不可回復，就不要用 `TRUNCATE`。

## 7.8 常見錯誤觀念

### 錯誤觀念 1：`TRUNCATE` 和 `DELETE FROM` 完全一樣

錯。

它們都可以讓表變空，但本質不同：

```text
DELETE：DML，逐行刪除資料，可加 WHERE，通常可受交易控制
TRUNCATE：DDL，清空整張表，不可加 WHERE，會 implicit commit
```

---

### 錯誤觀念 2：`SET autocommit = FALSE` 後，`TRUNCATE` 就可以回滾

錯。

`TRUNCATE TABLE` 會造成 implicit commit，不能像 `DELETE` 一樣靠 `ROLLBACK` 救回。

---

### 錯誤觀念 3：`TRUNCATE` 會觸發 `DELETE` Trigger

錯。

`TRUNCATE` 不會觸發 `ON DELETE` Trigger。

如果你需要 `DELETE` Trigger 裡面的稽核或同步邏輯，應該使用 `DELETE`。

---

### 錯誤觀念 4：`DELETE FROM table_name;` 比較安全

不一定。

如果沒有 `WHERE`：

```sql
DELETE FROM table_name;
```

它一樣會刪掉全部資料。

差別是它可能可以回滾，但如果已經 `COMMIT`，一樣不能簡單救回。

---

### 錯誤觀念 5：`TRUNCATE` 只是刪資料，不會影響其他東西

不完整。

`TRUNCATE` 不只清空資料，還會：

- 重置 `AUTO_INCREMENT`；
- 不觸發 `DELETE` Trigger；
- 受到外鍵限制；
- 造成 implicit commit；
- 不回傳有意義刪除筆數。

---

## 7.10 面試與考試常問

### 問題 1：`DELETE`、`TRUNCATE`、`DROP` 差異是什麼？

答：

```text
DELETE 是刪除資料列，表結構保留，可以加 WHERE，屬於 DML，通常可受交易控制。
TRUNCATE 是清空整張表資料，表結構保留，不可加 WHERE，屬於 DDL，會重置 AUTO_INCREMENT，通常不能回滾。
DROP 是刪除整張表物件，表結構和資料都不保留，屬於 DDL。
```

---

### 問題 2：`TRUNCATE TABLE` 能不能回滾？

答：

```text
不能像一般 DML 一樣回滾。
```

原因是 `TRUNCATE TABLE` 是 DDL，會造成 implicit commit。

---

### 問題 3：`TRUNCATE` 會不會重置自增 ID？

答：

```text
會，AUTO_INCREMENT 會被重置為起始值。
```

---

### 問題 4：`TRUNCATE` 會不會觸發 `DELETE` Trigger？

答：

```text
不會。
```

如果你需要 `DELETE` Trigger 裡的邏輯，應該用 `DELETE`。

---

### 問題 5：正式環境要刪大量歷史資料，應該用 `TRUNCATE` 嗎？

答：

```text
通常不應該直接用 TRUNCATE。
```

如果只是刪除部分歷史資料，應使用 `DELETE + WHERE`，並視資料量採取分批刪除。

- 常见搜寻：MySQL 清空表、MySQL truncate、MySQL delete from 全删、MySQL truncate 和 delete 区别、MySQL 清空表重置自增
- 易混淆：`TRUNCATE` vs `DELETE`、清空表 vs 删除表、是否可回滚、是否重置 `AUTO_INCREMENT`

## 建议回查情境

- 想清空测试数据，但表结构还要保留时。
- 想删除全部资料，但又不确定要不要保留自增计数时。
- 想比较 `TRUNCATE` 和 `DELETE` 的速度、事务行为与风险时。
- 想确认自己该用 `DELETE`、`TRUNCATE` 还是 `DROP TABLE` 时。

## 30 秒复习入口

- 想清空资料但保留表结构，先考虑 `TRUNCATE TABLE` 或 `DELETE FROM`。
- 想保留事务回滚能力，优先看 `DELETE FROM`。
- 想快速清空并重置 `AUTO_INCREMENT`，优先看 `TRUNCATE TABLE`。
- 想把表和结构一起移除，那不是“清空表”，而是 `DROP TABLE`。

## 速查区

### `TRUNCATE TABLE`

- 作用：清空整张表的数据，保留表结构
- 特点：通常不能回滚
- 自增：会重置 `AUTO_INCREMENT`
- 速度：通常比整表 `DELETE` 快

### `DELETE FROM`

- 作用：删除表内资料，可整表删，也可搭配 `WHERE` 条件删
- 特点：属于 DML，通常可受事务控制
- 自增：通常不会重置 `AUTO_INCREMENT`
- 速度：整表删除时通常比 `TRUNCATE` 慢

### `DROP TABLE`

- 作用：删除整张表与结构
- 适合：表本身已不再需要
- 不是“清空资料”，而是“删除对象”

### 选择建议

- 只清空资料且想保留回滚：`DELETE FROM`
- 只清空资料且想重置自增、追求更快：`TRUNCATE TABLE`
- 连表定义都不要了：`DROP TABLE`

## 7.1 基本概念

### 7.1.1 語法

```sql
TRUNCATE TABLE table_name;
```

### 7.1.2 特性

- **僅刪除數據，不刪除表結構**：`TRUNCATE` 會清空表內所有數據，但表的結構、索引、約束仍然存在。
- **不可回滾**：`TRUNCATE` 通常**不能被回滾**（因為它是 DDL 操作，而不是 DML 操作），而使用 DELETE 语句删除数据，可以回滚。
- **重置 `AUTO_INCREMENT` 計數**：如果表有 `AUTO_INCREMENT` 的主鍵，`TRUNCATE` 會將計數**重置為 1**。
- **執行速度比 `DELETE` 快**：因為 `TRUNCATE` **不會逐行刪除數據，而是直接釋放存儲空間**，所以通常比 `DELETE FROM table_name;` 更快。

### 7.1.3 示例

```sql
TRUNCATE TABLE employees;
```

**結果：**

- `employees` 表內的**所有數據被清空**，但表結構仍然存在。
- 若有 `AUTO_INCREMENT` 主鍵，則計數會被重置。

## 7.2 DELETE FROM（刪除表內數據）

> `DELETE` 也經常用來刪除資料，所以這裡一併比較。

### 7.2.1 語法

```sql
DELETE FROM table_name;
```

### 7.2.2 特性

- **僅刪除數據，不刪除表結構**：`DELETE` 只刪除行數據，表的結構、索引、約束仍然存在。
- **可以回滾（受事務控制）**：`DELETE` 是 DML（Data Manipulation Language），如果在 `BEGIN TRANSACTION` 內執行，可以用 `ROLLBACK` 還原。
- **不會重置 `AUTO_INCREMENT`**：如果表有 `AUTO_INCREMENT`，刪除數據後插入新數據時，自增主鍵**不會重置**。
- **執行速度比 `TRUNCATE` 慢**：因為 `DELETE` 會**逐行刪除數據**，並觸發 `DELETE` 觸發器（如果有的話）。

### 7.2.3 示例

```sql
DELETE FROM employees;
```

**結果：**

- `employees` 表內的數據**被刪除**，但表結構還在。
- 若有 `AUTO_INCREMENT` 主鍵，數據刪除後，自增計數**不會重置**。

## 7.3 DELETE 和 TRUNCATE 的对比

```sql
SET autocommit = FALSE;

DELETE FROM emp2;
#TRUNCATE TABLE emp2;

SELECT * FROM emp2;

ROLLBACK;

SELECT * FROM emp2;
```

### 7.3.1 代碼解析

1. **關閉自動提交**
    
    ```sql
    SET autocommit = FALSE;
    ```
    
    - MySQL 默認會自動提交每條 SQL 語句的更改 (`autocommit = TRUE`)。
    - `SET autocommit = FALSE;` 會將當前會話的自動提交關閉，使 `DELETE` 和 `TRUNCATE` 操作成為**可回滾的事務**的一部分。
2. **刪除 `emp2` 表的所有數據**
    
    ```sql
    DELETE FROM emp2;
    ```
    
    - `DELETE` 會逐行刪除 `emp2` 表中的數據，但**不會重置自增 ID** (如果 `emp2` 有 `AUTO_INCREMENT` 的主鍵)。
    - `DELETE` 是一個 DML (Data Manipulation Language) 操作，受事務 (`ROLLBACK`) 影響，可以被回滾。
3. **（被註解的 `TRUNCATE`）**
    
    ```sql
    #TRUNCATE TABLE emp2;
    ```
    
    - 如果取消註解並執行 `TRUNCATE TABLE emp2;`，則 `emp2` 會**完全清空**，並且會**重置 `AUTO_INCREMENT`**。
    - `TRUNCATE` 是 DDL (Data Definition Language) 操作，通常**無法回滾**，即使 `autocommit = FALSE`。
4. **查看 `emp2` 表的數據**
    
    ```sql
    SELECT * FROM emp2;
    ```
    
    - 在 `DELETE FROM emp2;` 執行後，這裡會顯示 `emp2` 表是空的。
5. **回滾 (`ROLLBACK`)**
    
    ```sql
    ROLLBACK;
    ```
    
    - 由於 `DELETE` 是可回滾的 DML 操作，`ROLLBACK` 會將 `emp2` 中的數據恢復。
6. **再次查看 `emp2`**
    
    ```sql
    SELECT * FROM emp2;
    ```
    
    - 如果用的是 `DELETE FROM emp2;`，這時候 `emp2` 的數據會被恢復。
    - 但如果用的是 `TRUNCATE TABLE emp2;`，那麼 `ROLLBACK` **無法恢復數據**，`emp2` 仍然是空的，因為 `TRUNCATE` 屬於 DDL，不受事務控制。

### 7.3.2 結論

| 操作 | 可回滾 (`ROLLBACK`) | 影響 `AUTO_INCREMENT` | 操作類型 |
| --- | --- | --- | --- |
| `DELETE FROM emp2;` | ✅ 可以回滾 | ❌ 不會重置 | DML（數據操作語言） |
| `TRUNCATE TABLE emp2;` | ❌ 不能回滾 | ✅ 會重置 | DDL（數據定義語言） |

如果你執行 `DELETE FROM emp2;`，然後 `ROLLBACK;`，數據會被恢復。

但如果你執行 `TRUNCATE TABLE emp2;`，然後 `ROLLBACK;`，數據不會恢復，因為 `TRUNCATE` 直接影響表結構，通常不受事務控制。

### 7.3.3 阿里开发规范

> 阿里开发规范：
>
> - 【参考】`TRUNCATE TABLE` 比 `DELETE` 速度快，且使用的系统和事务日志资源少，但 `TRUNCATE` 无事务且不触发 `TRIGGER`，有可能造成事故，故不建议在开发代码中使用此语句。
> - 说明：`TRUNCATE TABLE` 在功能上与不带 `WHERE` 子句的 `DELETE` 语句相同。

## 7.4 DROP vs. TRUNCATE vs. DELETE 對比

| 操作 | 是否刪除表結構 | 是否刪除數據 | 是否可回滾（ROLLBACK） | 是否重置 `AUTO_INCREMENT` | 速度 |
| --- | --- | --- | --- | --- | --- |
| `DROP TABLE` | ✅ 是 | ✅ 是 | ❌ 否 | ✅ 是（表刪除後重建才會生效） | 🚀 非常快（直接刪除整個表） |
| `TRUNCATE TABLE` | ❌ 否 | ✅ 是 | ❌ 否 | ✅ 是 | 🚀 非常快（直接釋放空間） |
| `DELETE FROM` | ❌ 否 | ✅ 是 | ✅ 是（若有事務） | ❌ 否 | 🐢 慢（逐行刪除數據） |

## 7.5 何時使用？

1. **使用 `DROP TABLE`**
    - 當**確定不再需要該表**時，或者想要重新創建一個新的表。
    - 例如：
        
        ```sql
        DROP TABLE logs;
        ```
        
2. **使用 `TRUNCATE TABLE`**
    - 當**只想清空表內數據，但保留表結構**時，特別是當有 `AUTO_INCREMENT` 需要重置時。
    - 例如：
        
        ```sql
        TRUNCATE TABLE users;
        ```
        
3. **使用 `DELETE FROM`**
    - 當**想刪除部分數據**，或者**希望保留 `AUTO_INCREMENT` 計數**時。
    - 例如：
        
        ```sql
        DELETE FROM orders WHERE order_date < '2023-01-01';
        ```

## 一句话对比

- `DELETE FROM`：删资料，可回滚，通常不重置自增
- `TRUNCATE TABLE`：清空资料，不回滚，通常会重置自增
- `DROP TABLE`：连表结构一起删掉
