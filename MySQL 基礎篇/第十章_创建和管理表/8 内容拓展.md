# 8 內容拓展

返回章節：[第十章_创建和管理表](./README.md)

## 本節導讀

這一節不是再補一堆新的 SQL 語法，而是把前面 1～7 節整理成一套更接近實務開發的判斷方式。

前面幾節你已經學過：

```text
建立資料庫：CREATE DATABASE
建立表：CREATE TABLE
修改表：ALTER TABLE
重命名表：RENAME TABLE / ALTER TABLE ... RENAME
刪除表：DROP TABLE
清空表：TRUNCATE TABLE / DELETE FROM
```

但真正做專案時，重點不只是「語法會不會寫」，而是：

1. 表名、欄位名怎麼命名，未來才不會難維護？
2. 為什麼資料庫物件命名要盡量穩定？
3. 為什麼正式環境不能隨便 `DROP`、`ALTER`、`TRUNCATE`？
4. 為什麼 MySQL 8 的 atomic DDL 可以降低「做到一半」的風險？
5. 為什麼 atomic DDL 不等於你可以用 `ROLLBACK` 救回 DDL？
6. 為什麼大小寫、字元集、排序規則、儲存引擎會影響表設計？
7. 真正改表、刪表、清空表之前，應該先檢查什麼？

所以這一篇的定位是：

> 把「第十章：創建和管理表」從語法筆記，提升成正式專案可用的資料表管理觀念。

學完這一節後，你應該要能做到：

- 分清楚 MySQL 的硬性語法規則與團隊命名規範；
- 知道為什麼建議資料庫名、表名、欄位名使用小寫英文與底線；
- 知道大小寫敏感性會受作業系統與 `lower_case_table_names` 影響；
- 知道 `utf8mb4`、`COLLATE`、`ENGINE = InnoDB` 為什麼常出現在建表語句中；
- 知道 `DROP TABLE`、`ALTER TABLE`、`TRUNCATE TABLE` 的共同風險；
- 知道 MySQL 8 atomic DDL 解決的是「DDL 執行中失敗後的中間狀態」問題；
- 知道 atomic DDL 不等於一般交易中的 `ROLLBACK`；
- 能整理出正式環境變更資料表前的檢查清單。

## 關鍵字

- 主題：命名規範、大小寫敏感、字元集、排序規則、儲存引擎、DDL 風險、atomic DDL、metadata lock
- 英文：naming convention, identifier, character set, collation, storage engine, implicit commit, atomic DDL, metadata lock
- 常見搜尋：MySQL 表名命名規範、MySQL 欄位命名規範、MySQL lower_case_table_names、MySQL utf8mb4、MySQL InnoDB、MySQL DDL implicit commit、MySQL atomic DDL、MySQL metadata lock
- 容易混淆：MySQL 語法限制 vs 團隊規範、atomic DDL vs transaction rollback、清空表 vs 刪除表、字元集 vs 排序規則、表名大小寫 vs 欄位名大小寫

## 建議回查情境

- 想整理自己的 MySQL 表名與欄位命名習慣時。
- 不確定為什麼資料庫命名通常建議用小寫英文與底線時。
- 想知道 `user`、`order`、`desc` 這類名稱為什麼不建議直接拿來當表名或欄位名時。
- 想知道 `utf8mb4`、`utf8mb4_0900_ai_ci`、`utf8mb4_unicode_ci` 這些設定在做什麼時。
- 想知道正式環境為什麼不能直接 `ALTER TABLE`、`DROP TABLE`、`TRUNCATE TABLE` 時。
- 想理解 MySQL 8 的 atomic DDL 和一般交易 `ROLLBACK` 有什麼差別時。
- 想把第十章學過的語法整理成一份「上線前檢查清單」時。

## 30 秒複習入口

- MySQL 允許的命名範圍和專案實務建議不是同一件事。
- 官方允許不代表專案應該亂命名；實務上建議使用小寫英文、數字、底線 `_`。
- 表名與資料庫名的大小寫敏感性會受到作業系統與 `lower_case_table_names` 影響，所以跨平台專案最好統一小寫。
- `CHARACTER SET` 決定字元如何儲存；`COLLATE` 決定字串如何比較與排序。
- 新專案通常優先使用 `utf8mb4`，不要把舊式 `utf8` 當成完整 UTF-8。
- 一般業務表通常優先使用 `InnoDB`，因為它支援交易、外鍵、行級鎖等常用能力。
- `ALTER TABLE`、`DROP TABLE`、`TRUNCATE TABLE` 都是高風險 DDL，正式環境操作前要先檢查與備份。
- 很多 DDL 會造成 implicit commit，不能期待用一般交易 `ROLLBACK` 救回。
- MySQL 8 的 atomic DDL 是指 DDL 本身要嘛完整成功、要嘛回滾到未完成前的狀態。
- atomic DDL 不等於 transactional DDL；它不能讓你把 DDL 包在 `START TRANSACTION` 中隨意 `ROLLBACK`。
- 正式環境改表前，要先查表結構、資料量、外鍵、索引、Trigger、View、Procedure、Event、應用程式依賴與備份。

## 速查區

### 1. 命名建議速查

| 對象 | 建議 | 範例 | 不建議 |
| --- | --- | --- | --- |
| database | 小寫英文 + 底線 | `bank_core` | `BankCore` |
| table | 小寫英文 + 底線，表達業務對象 | `customer_account` | `CustomerAccount`、`table1` |
| column | 小寫英文 + 底線，表達欄位含義 | `customer_id`、`created_at` | `customerId`、`c_id` |
| primary key | 常見用 `id` | `id BIGINT UNSIGNED` | `ID`、`pk` |
| foreign key column | 常見用 `xxx_id` | `department_id` | `deptNo`、`did` |
| time column | 常見用 `_at` 表示時間點 | `created_at`、`updated_at` | `create_time_1` |
| status column | 建議配合註解或字典表 | `status TINYINT` | `s`、`flag1` |

---

### 2. DDL 風險速查

| 操作 | 風險 | 操作前要確認 |
| --- | --- | --- |
| `ALTER TABLE ADD COLUMN` | 大表可能耗時、可能鎖表 | 資料量、MySQL 版本、是否支援 online / instant DDL |
| `ALTER TABLE MODIFY COLUMN` | 可能資料截斷、屬性遺失 | 原欄位完整定義、最大長度、NULL、DEFAULT、COMMENT |
| `ALTER TABLE DROP COLUMN` | 欄位與資料永久消失 | 程式碼、報表、View、Procedure、備份 |
| `RENAME TABLE` | 程式碼可能找不到舊表名 | Mapper、SQL、View、Procedure、批次、權限 |
| `DROP TABLE` | 表結構與資料一起刪除 | 是否真的不用、是否被外鍵引用、是否已備份 |
| `TRUNCATE TABLE` | 整表資料清空、通常重置自增 | 是否要回滾、是否有外鍵、是否有 Trigger |

---

### 3. atomic DDL 速查

| 觀念 | 正確理解 |
| --- | --- |
| atomic DDL | DDL 本身要嘛完整成功，要嘛回到未完成前狀態 |
| transactional DDL | 能不能由使用者放進交易中自行 `ROLLBACK` |
| MySQL 8 atomic DDL | 主要由 InnoDB 與 MySQL data dictionary 支援 |
| 容易誤解 | atomic DDL 不代表你可以 `START TRANSACTION; ALTER TABLE ...; ROLLBACK;` 救回 |
| 實務價值 | 降低 DDL 執行中斷、失敗、當機後留下半套結果的風險 |

## 8.1 這一章真正要建立的觀念

第十章表面上是在學「創建和管理表」，但核心其實是三個能力。

### 能力 1：會建立結構

例如：

```sql
CREATE TABLE app_user (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT COMMENT '主鍵 ID',
    username VARCHAR(50) NOT NULL COMMENT '使用者名稱',
    email VARCHAR(100) NOT NULL COMMENT '電子信箱',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '狀態：1啟用，0停用',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    UNIQUE KEY uk_app_user_username (username),
    UNIQUE KEY uk_app_user_email (email)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '使用者表';
```

這是「建表能力」。

---

### 能力 2：會維護結構

例如：

```sql
ALTER TABLE app_user
ADD COLUMN last_login_at DATETIME NULL COMMENT '最後登入時間';
```

或：

```sql
ALTER TABLE app_user
MODIFY COLUMN username VARCHAR(80) NOT NULL COMMENT '使用者名稱';
```

這是「改表能力」。

但改表不只是語法問題，還要知道：

- 這張表有多少資料？
- 這個欄位是否有索引？
- 這個欄位是否被程式使用？
- 這個欄位是否被報表使用？
- 這個操作會不會鎖表？
- 失敗後怎麼復原？

---

### 能力 3：會控制風險

例如刪表前，不應該直接寫：

```sql
DROP TABLE app_user;
```

而應該先確認：

```sql
SELECT DATABASE();

SHOW TABLES LIKE 'app_user';

SHOW CREATE TABLE app_user;

SELECT COUNT(*) FROM app_user;

SELECT *
FROM information_schema.KEY_COLUMN_USAGE
WHERE table_schema = DATABASE()
  AND referenced_table_name = 'app_user';
```

也就是說，真正成熟的資料庫操作能力，不只是「我會寫 SQL」，而是：

> 我知道這句 SQL 會影響什麼，知道怎麼檢查，也知道出錯時怎麼復原。

---

## 8.2 命名規範：MySQL 規則與團隊規範要分開

很多筆記會直接寫：

```text
表名、欄位名必須使用小寫英文、數字、底線。
```

這句話作為「團隊規範」可以，但作為「MySQL 官方語法規則」就不精確。

更準確的說法是：

```text
MySQL 允許的 identifier 範圍比較寬，
但正式專案為了可讀性、可維護性與跨平台一致性，
通常會制定更嚴格的命名規範。
```

也就是要分成兩層：

| 層次 | 意義 | 例子 |
| --- | --- | --- |
| MySQL 語法允許 | 資料庫本身允許你這樣命名 | 可以使用反引號包住特殊名稱 |
| 團隊工程規範 | 團隊為了維護方便，規定應該怎麼命名 | 統一小寫、底線、避免保留字 |

---

### 8.2.1 為什麼資料庫命名比一般變數命名更要慎重？

因為資料庫欄位一旦進入系統，會被很多地方依賴。

例如一個欄位：

```sql
customer_id
```

可能會出現在：

- Java Entity；
- MyBatis XML；
- SQL 查詢；
- View；
- Stored Procedure；
- 報表；
- Excel 匯出；
- 批次排程；
- API 回傳欄位；
- 前端頁面欄位；
- 權限控管條件；
- 測試資料；
- 文件說明。

所以欄位名不像普通區域變數，想改就改。

在 Java 裡你改一個區域變數名稱，IDE 可以幫你 refactor；但資料庫欄位名一旦被多個系統、報表、批次、外部介面依賴，修改成本就會很高。

因此命名要盡量：

- 穩定；
- 清楚；
- 不依賴個人習慣；
- 不使用過度縮寫；
- 不使用模糊詞；
- 不使用容易撞保留字的名稱；
- 不使用大小寫混合造成跨平台問題。

---

## 8.3 建議命名規範

以下不是 MySQL 強制規定，而是實務上常見、也比較適合長期維護的命名方式。

### 8.3.1 資料庫名

建議：

```text
小寫英文 + 底線
```

範例：

```sql
CREATE DATABASE bank_core
DEFAULT CHARACTER SET utf8mb4
DEFAULT COLLATE utf8mb4_0900_ai_ci;
```

較不建議：

```text
BankCore
bankCore
BANK_CORE
bank-core
銀行核心系統
```

原因：

- 大小寫可能有跨平台差異；
- `-` 需要額外處理；
- 中文命名雖然某些情況可行，但不利於跨工具、跨環境維護；
- 全大寫在 SQL 中可讀性較差，也不符合多數 MySQL 專案慣例。

---

### 8.3.2 表名

建議：

```text
業務名稱_業務對象
```

或：

```text
模組名稱_表用途
```

範例：

```text
customer_account
loan_contract
credit_card_application
system_user
system_role
system_user_role
order_item
payment_record
audit_log
```

較不建議：

```text
user
order
table1
data_info
customerData
CustomerAccount
t_customer_account
```

說明：

- `user`、`order` 容易和關鍵字、內建概念或業務通用詞混淆；
- `table1` 完全看不出業務含義；
- `data_info` 太空泛；
- `customerData` 混入 camelCase，和 MySQL 慣例不一致；
- `t_` 前綴有些公司會用，但如果團隊沒有統一規範，不建議自己亂加。

---

### 8.3.3 欄位名

建議：

```text
小寫英文 + 底線 + 明確業務含義
```

範例：

```text
id
customer_id
account_no
contract_no
apply_amount
approved_amount
interest_rate
status
created_at
updated_at
created_by
updated_by
```

較不建議：

```text
c_id
custId
amount1
amount2
flag
flag1
kind
type1
```

不是說這些一定不能用，而是要看團隊是否有清楚規範。

例如 `status_cd` 在某些金融系統中可能代表 `status code`，如果全公司都這樣寫，那可以接受；但如果只有你自己這樣寫，其他人就會看不懂。

---

### 8.3.4 主鍵欄位

常見寫法：

```sql
id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT COMMENT '主鍵 ID'
```

這種寫法的優點：

- 簡單；
- 好理解；
- ORM 或後端程式容易對應；
- 適合單表自增主鍵場景。

但要注意：

```text
id 一定要自增嗎？不一定。
id 一定要 BIGINT UNSIGNED 嗎？不一定。
id 一定是業務主鍵嗎？不一定。
```

實務上要分清楚兩種概念：

| 類型 | 說明 | 範例 |
| --- | --- | --- |
| 技術主鍵 | 系統內部用來唯一識別資料列 | `id` |
| 業務唯一鍵 | 業務上不能重複的值 | `account_no`、`contract_no`、`email` |

例如：

```sql
CREATE TABLE bank_account (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT COMMENT '技術主鍵',
    account_no VARCHAR(30) NOT NULL COMMENT '帳號',
    customer_id BIGINT UNSIGNED NOT NULL COMMENT '客戶 ID',
    balance DECIMAL(18, 2) NOT NULL DEFAULT 0 COMMENT '餘額',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    UNIQUE KEY uk_bank_account_account_no (account_no),
    KEY idx_bank_account_customer_id (customer_id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '銀行帳戶表';
```

這裡：

- `id` 是技術主鍵；
- `account_no` 是業務唯一鍵；
- 兩者不要混在一起理解。

---

### 8.3.5 外鍵欄位

如果某個欄位引用另一張表的主鍵，常見命名方式是：

```text
被引用業務對象_id
```

範例：

```text
customer_id
department_id
role_id
order_id
product_id
```

例如：

```sql
CREATE TABLE employee (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT COMMENT '員工 ID',
    department_id BIGINT UNSIGNED NOT NULL COMMENT '部門 ID',
    employee_name VARCHAR(50) NOT NULL COMMENT '員工姓名',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    KEY idx_employee_department_id (department_id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '員工表';
```

即使你沒有建立實體外鍵約束，也建議欄位命名清楚表達引用關係。

---

### 8.3.6 時間欄位

常見命名：

```text
created_at
updated_at
deleted_at
submitted_at
approved_at
expired_at
last_login_at
```

`_at` 通常表示某個事件發生的時間點。

例如：

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間'
```

如果欄位表示日期，而不是時間點，可以用 `_date`：

```text
birth_date
settlement_date
payment_date
```

如果欄位表示年月，可以用：

```text
statement_month
salary_month
```

重點不是哪一種絕對正確，而是整個專案要一致。

---

### 8.3.7 狀態欄位

狀態欄位常見命名：

```text
status
review_status
payment_status
approval_status
```

不建議只寫：

```text
flag
flag1
kind
type1
```

因為這些名稱太模糊。

較好的寫法：

```sql
review_status TINYINT NOT NULL DEFAULT 0 COMMENT '審查狀態：0待審查，1同意，2不同意，3補件'
```

如果狀態值很多、會被多張表共用，則可以考慮用字典表或 enum-like 設計，而不是把所有狀態都塞在欄位註解中。

## 8.4 關鍵字與保留字：不是不能用，而是不該輕易用

MySQL 中有一些關鍵字或保留字，例如：

```text
SELECT
ORDER
GROUP
DESC
RANGE
MATCH
USER
```

如果你真的要使用，可能需要用反引號：

```sql
CREATE TABLE `order` (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    `desc` VARCHAR(255)
);
```

但實務上不建議這樣做。

比較好的命名：

```sql
CREATE TABLE customer_order (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    order_description VARCHAR(255)
);
```

原因：

- 反引號會讓 SQL 可讀性變差；
- 容易讓不同工具、ORM、SQL 產生器出問題；
- 新版本可能新增保留字，導致舊命名未來變麻煩；
- 團隊協作時容易有人忘記加反引號。

所以規則可以簡化成：

```text
能不用保留字，就不要用。
能用更明確的業務名稱，就不要用過短的通用詞。
```

## 8.5 大小寫問題：為什麼建議統一小寫？

MySQL 的大小寫問題比較特殊，因為資料庫名、表名在底層可能和作業系統檔案系統有關。

簡化理解：

| 環境 | 常見情況 |
| --- | --- |
| Windows | 表名、資料庫名通常不區分大小寫 |
| Linux / Unix | 表名、資料庫名通常區分大小寫 |
| macOS | 受檔案系統設定影響 |

這會導致一個問題：

```sql
SELECT * FROM UserAccount;
```

在某些環境可能可以查到：

```sql
CREATE TABLE useraccount (...);
```

但換到另一個環境就可能失敗。

所以實務建議是：

```text
資料庫名、表名一律小寫。
SQL 中引用時也一律小寫。
不要一下 user_account，一下 User_Account，一下 USER_ACCOUNT。
```

---

### 8.5.1 `lower_case_table_names`

`lower_case_table_names` 會影響 MySQL 如何儲存與比較資料庫名、表名。

常見值可以簡化理解為：

| 值 | 簡化理解 |
| --- | --- |
| `0` | 依建立時大小寫儲存，比較時區分大小寫，常見於 Unix/Linux |
| `1` | 儲存成小寫，比較時不區分大小寫，常見於 Windows |
| `2` | 依建立時大小寫儲存，但查找時轉小寫，常見於部分 macOS 情境 |

注意：

```text
這個設定通常必須在 MySQL 初始化時決定。
不要期待系統跑一段時間後才隨便修改它。
```

對你寫專案來說，最穩的做法仍然是：

```text
所有 database name、table name 都用小寫英文與底線。
```

---

## 8.6 字元集與排序規則：`CHARACTER SET` 和 `COLLATE`

建表時常看到：

```sql
ENGINE = InnoDB
DEFAULT CHARSET = utf8mb4
COLLATE = utf8mb4_0900_ai_ci;
```

這三個設定分別處理不同問題。

---

### 8.6.1 `CHARACTER SET`

`CHARACTER SET` 決定字元如何儲存。

例如：

```sql
DEFAULT CHARSET = utf8mb4
```

代表表中的字串欄位，若沒有另外指定字元集，預設使用 `utf8mb4`。

新專案通常建議使用：

```sql
utf8mb4
```

原因是：

- 可以支援完整 Unicode；
- 可以儲存 emoji；
- 比舊式 `utf8` / `utf8mb3` 更適合作為新系統預設。

---

### 8.6.2 `COLLATE`

`COLLATE` 決定字串如何比較與排序。

例如：

```sql
COLLATE = utf8mb4_0900_ai_ci
```

可以拆開理解：

| 片段 | 簡化理解 |
| --- | --- |
| `utf8mb4` | 使用的字元集 |
| `0900` | Unicode Collation Algorithm 版本相關 |
| `ai` | accent-insensitive，重音不敏感 |
| `ci` | case-insensitive，大小寫不敏感 |

也就是說，collation 會影響：

- `ORDER BY` 排序；
- `WHERE name = 'abc'` 比較；
- `LIKE` 查詢；
- 唯一索引判斷是否重複；
- 大小寫是否視為相同。

例如在 case-insensitive 的 collation 下，下面兩個值可能被視為相同：

```text
abc
ABC
```

如果欄位有唯一索引，這就會影響是否能同時存在。

---

### 8.6.3 字元集設定的層級

字元集與排序規則可以出現在多個層級：

```text
server 層級
  ↓
database 層級
  ↓
table 層級
  ↓
column 層級
  ↓
connection / client 層級
```

例如 database：

```sql
CREATE DATABASE demo_db
DEFAULT CHARACTER SET utf8mb4
DEFAULT COLLATE utf8mb4_0900_ai_ci;
```

例如 table：

```sql
CREATE TABLE demo_user (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

例如 column：

```sql
username VARCHAR(50)
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci
    NOT NULL
```

一般開發中，不需要每個欄位都寫一次，只要 database / table 層級統一即可。

## 8.7 儲存引擎：為什麼建表常寫 `ENGINE = InnoDB`？

MySQL 有不同儲存引擎，例如：

```text
InnoDB
MyISAM
Memory
CSV
Archive
```

但一般業務系統中，最常用的是：

```sql
ENGINE = InnoDB
```

原因是 InnoDB 支援很多正式業務系統需要的能力：

- 交易；
- 行級鎖；
- 外鍵；
- crash recovery；
- MVCC；
- 較完整的併發控制；
- MySQL 8 atomic DDL 支援。

所以新建正式業務表時，通常會明確寫：

```sql
ENGINE = InnoDB
```

例如：

```sql
CREATE TABLE payment_record (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT COMMENT '主鍵 ID',
    order_id BIGINT UNSIGNED NOT NULL COMMENT '訂單 ID',
    amount DECIMAL(18, 2) NOT NULL COMMENT '付款金額',
    status TINYINT NOT NULL DEFAULT 0 COMMENT '付款狀態',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    KEY idx_payment_record_order_id (order_id)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '付款紀錄表';
```

## 8.8 DDL 風險：為什麼改表、刪表、清空表要特別小心？

DDL 是 Data Definition Language，也就是資料定義語言。

常見 DDL：

```sql
CREATE DATABASE
DROP DATABASE
CREATE TABLE
ALTER TABLE
RENAME TABLE
DROP TABLE
TRUNCATE TABLE
CREATE INDEX
DROP INDEX
CREATE VIEW
DROP VIEW
```

DDL 的特點是：

```text
它操作的是資料庫物件與結構，不只是資料列。
```

所以一旦出錯，影響通常比一般查詢或單筆資料更新更大。

---

### 8.8.1 `DROP TABLE` 的風險

```sql
DROP TABLE customer_account;
```

這不是刪除幾筆資料，而是：

```text
整張表物件消失。
```

包含：

- 表結構；
- 表資料；
- 索引；
- 表上的 Trigger；
- 和這張表直接相關的物件。

所以刪表前至少要確認：

```sql
SELECT DATABASE();

SHOW TABLES LIKE 'customer_account';

SHOW CREATE TABLE customer_account;

SELECT COUNT(*) FROM customer_account;
```

並且確認是否有外鍵依賴：

```sql
SELECT
    table_schema,
    table_name,
    column_name,
    constraint_name,
    referenced_table_schema,
    referenced_table_name,
    referenced_column_name
FROM information_schema.KEY_COLUMN_USAGE
WHERE referenced_table_schema = DATABASE()
  AND referenced_table_name = 'customer_account';
```

---

### 8.8.2 `ALTER TABLE` 的風險

```sql
ALTER TABLE customer_account
MODIFY COLUMN account_no VARCHAR(10) NOT NULL COMMENT '帳號';
```

如果原本 `account_no` 有超過 10 個字元的資料，就可能出現資料截斷或修改失敗。

所以縮短欄位前要先查：

```sql
SELECT MAX(CHAR_LENGTH(account_no)) AS max_len
FROM customer_account;
```

如果要把欄位改成 `NOT NULL`，要先查是否有 `NULL`：

```sql
SELECT COUNT(*) AS null_count
FROM customer_account
WHERE account_no IS NULL;
```

如果要刪欄位，要先查程式與資料庫物件依賴：

```sql
ALTER TABLE customer_account
DROP COLUMN old_column;
```

這種操作會讓欄位資料消失，不是單純把欄位「隱藏」。

---

### 8.8.3 `TRUNCATE TABLE` 的風險

```sql
TRUNCATE TABLE customer_account;
```

這會清空整張表資料，且不能加 `WHERE`。

要特別注意：

- 不能只清一部分；
- 通常會重置 `AUTO_INCREMENT`；
- 不會觸發 `ON DELETE` Trigger；
- 不能像 `DELETE` 一樣靠一般交易 `ROLLBACK` 救回；
- 若其他表有外鍵引用，可能失敗。

如果你只是想刪部分資料，應該用：

```sql
DELETE FROM customer_account
WHERE created_at < '2025-01-01';
```

如果資料很多，正式環境通常要分批：

```sql
DELETE FROM customer_account
WHERE created_at < '2025-01-01'
ORDER BY id
LIMIT 1000;
```

---

## 8.9 implicit commit：為什麼 DDL 不能當成普通 DML？

很多人會以為：

```sql
START TRANSACTION;

ALTER TABLE app_user ADD COLUMN remark VARCHAR(255);

ROLLBACK;
```

這樣就可以把 `ALTER TABLE` 回滾。

這個理解是錯的。

MySQL 中很多 DDL 會造成 implicit commit，也就是：

```text
DDL 執行前或執行後，MySQL 會自動提交目前交易。
```

常見會造成 implicit commit 的語句包括：

```text
CREATE DATABASE
DROP DATABASE
CREATE TABLE
ALTER TABLE
DROP TABLE
RENAME TABLE
TRUNCATE TABLE
CREATE INDEX
DROP INDEX
CREATE VIEW
DROP VIEW
```

所以你不能把 DDL 當成一般 DML 來期待：

```sql
ROLLBACK;
```

能救回。

### 錯誤期待

```sql
START TRANSACTION;

DROP TABLE test_table;

ROLLBACK;
```

你不應該期待 `ROLLBACK` 讓 `test_table` 回來。

### 正確做法

DDL 前要有：

- 備份；
- 還原方案；
- 變更腳本；
- 回復腳本；
- 影響範圍確認；
- 測試環境驗證；
- 正式環境操作窗口；
- 操作人與覆核人。

---

## 8.10 MySQL 8 atomic DDL：解決的是什麼問題？

MySQL 8 的 atomic DDL 可以簡化理解為：

```text
一個 DDL 操作，要嘛完整成功，要嘛回到未完成前的狀態。
```

它把 DDL 過程中的幾件事整合成一個原子操作：

- data dictionary 更新；
- storage engine 操作；
- binary log 寫入；
- 必要時的 DDL redo / rollback 機制。

它的目的不是讓你手動 `ROLLBACK` DDL，而是降低這種問題：

```text
DDL 執行到一半失敗，資料字典、儲存引擎、binlog 狀態不一致。
```

---

### 8.10.1 atomic DDL 不等於 transactional DDL

這一點非常重要。

| 觀念 | 說明 |
| --- | --- |
| atomic DDL | DDL 自己執行時，要嘛完整成功，要嘛完整失敗 |
| transactional DDL | 使用者可以把 DDL 放入交易中，自己決定 `COMMIT` 或 `ROLLBACK` |

MySQL 8 的 atomic DDL 是前者，不是後者。

所以不要這樣理解：

```text
MySQL 8 支援 atomic DDL，所以我可以隨便 ALTER，錯了再 ROLLBACK。
```

正確理解是：

```text
MySQL 8 的 InnoDB DDL 在執行失敗或當機恢復時，更能避免留下半套結果；
但它仍然不是讓你手動控制 DDL 回滾的一般交易。
```

---

### 8.10.2 例子：多表 `DROP TABLE`

假設有一張表存在：

```sql
CREATE DATABASE mytest;
USE mytest;

CREATE TABLE book1 (
    book_id INT,
    book_name VARCHAR(255)
) ENGINE = InnoDB;
```

但 `book2` 不存在。

執行：

```sql
DROP TABLE book1, book2;
```

在支援 atomic DDL 的 MySQL 8 + InnoDB 場景下，重點是：

```text
如果其中一個命名表不存在，整個 DROP TABLE 會失敗，而且不會先刪掉 book1。
```

也就是避免出現：

```text
book1 被刪了，但整句 SQL 又報錯。
```

這就是 atomic DDL 的價值之一。

---

### 8.10.3 atomic DDL 的限制

不要把 atomic DDL 神化。

它仍然有前提與限制：

- 主要針對支援 atomic DDL 的儲存引擎，例如 InnoDB；
- 不是所有儲存引擎都支援；
- 不是所有 DDL 都能用一樣方式理解；
- 不是讓你手動 `ROLLBACK` DDL；
- DDL 仍可能造成 implicit commit；
- DDL 仍可能鎖表或等待 metadata lock；
- DDL 成功後，業務影響仍然要自己負責。

所以 atomic DDL 降低的是：

```text
資料庫內部結構變更做到一半的風險。
```

它不會替你解決：

```text
你下錯 SQL、刪錯表、改錯欄位、清空錯資料。
```

---

## 8.11 Metadata Lock：為什麼改表可能卡住？

在 MySQL 中，當你對表做 DDL 時，MySQL 需要保護表的 metadata，也就是表結構資訊。

例如：

```sql
ALTER TABLE app_user ADD COLUMN remark VARCHAR(255);
```

這個操作可能需要等待其他正在使用 `app_user` 的交易結束。

反過來，DDL 持有 metadata lock 時，也可能阻塞後續查詢或更新。

常見情境：

```text
Session A：開了一個交易，查了 app_user，但一直沒有 commit。
Session B：想 ALTER TABLE app_user，結果一直等待 metadata lock。
Session C：後續查詢 app_user，也可能被堵住。
```

所以正式環境改表時，要注意：

- 是否有長交易；
- 是否有慢查詢；
- 是否有批次正在跑；
- 是否有線上流量高峰；
- 是否需要維護窗口；
- 是否需要先在測試環境測 DDL 時間。

可以用以下方向排查：

```sql
SHOW PROCESSLIST;
```

或查詢 Performance Schema 中的 lock 相關資訊。

這部分不用現在深入背，但要先建立觀念：

> DDL 不是只有「執行成功或失敗」的問題，還可能造成等待、阻塞與線上服務延遲。

## 8.12 正式環境 DDL 操作前檢查清單

這一段是整篇最實用的部分。

以後你在正式環境要改表、刪表、清空表時，可以照這個順序檢查。

---

### 8.12.1 確認目前資料庫與目標表

```sql
SELECT DATABASE();

SHOW TABLES LIKE 'target_table';
```

避免在錯誤 database 操作。

---

### 8.12.2 查看完整建表語句

```sql
SHOW CREATE TABLE target_table\G
```

確認：

- 欄位；
- 型別；
- NULL / NOT NULL；
- DEFAULT；
- COMMENT；
- PRIMARY KEY；
- UNIQUE KEY；
- INDEX；
- FOREIGN KEY；
- ENGINE；
- CHARSET；
- COLLATE。

---

### 8.12.3 查看欄位資訊

```sql
SHOW FULL COLUMNS FROM target_table;
```

或：

```sql
SELECT
    column_name,
    column_type,
    is_nullable,
    column_default,
    column_key,
    extra,
    column_comment
FROM information_schema.COLUMNS
WHERE table_schema = DATABASE()
  AND table_name = 'target_table'
ORDER BY ordinal_position;
```

---

### 8.12.4 查看索引

```sql
SHOW INDEX FROM target_table;
```

改欄位前要確認欄位是否在索引中。

例如你要修改 `account_no`，要先知道它是不是：

- 主鍵；
- 唯一索引；
- 普通索引；
- 複合索引的一部分。

---

### 8.12.5 查看資料量

```sql
SELECT COUNT(*) FROM target_table;
```

如果資料量很大，`ALTER TABLE`、`DELETE`、`TRUNCATE` 的風險都會增加。

---

### 8.12.6 修改欄位前先檢查資料是否符合新規則

如果要縮短欄位：

```sql
SELECT MAX(CHAR_LENGTH(column_name)) AS max_len
FROM target_table;
```

如果要改成 `NOT NULL`：

```sql
SELECT COUNT(*) AS null_count
FROM target_table
WHERE column_name IS NULL;
```

如果要加唯一索引：

```sql
SELECT column_name, COUNT(*) AS cnt
FROM target_table
GROUP BY column_name
HAVING COUNT(*) > 1;
```

如果要加外鍵：

```sql
SELECT t.child_id
FROM child_table t
LEFT JOIN parent_table p ON t.child_id = p.id
WHERE p.id IS NULL;
```

---

### 8.12.7 檢查外鍵依賴

查「這張表引用了誰」：

```sql
SELECT
    constraint_name,
    table_name,
    column_name,
    referenced_table_name,
    referenced_column_name
FROM information_schema.KEY_COLUMN_USAGE
WHERE table_schema = DATABASE()
  AND table_name = 'target_table'
  AND referenced_table_name IS NOT NULL;
```

查「誰引用了這張表」：

```sql
SELECT
    constraint_name,
    table_name,
    column_name,
    referenced_table_name,
    referenced_column_name
FROM information_schema.KEY_COLUMN_USAGE
WHERE referenced_table_schema = DATABASE()
  AND referenced_table_name = 'target_table';
```

---

### 8.12.8 檢查 Trigger

```sql
SELECT
    trigger_name,
    event_manipulation,
    action_timing,
    event_object_table
FROM information_schema.TRIGGERS
WHERE trigger_schema = DATABASE()
  AND event_object_table = 'target_table';
```

如果要 `DROP TABLE`，要知道相關 Trigger 也會受到影響。

如果要 `TRUNCATE TABLE`，要知道它不會像 `DELETE` 一樣觸發 `ON DELETE` Trigger。

---

### 8.12.9 檢查 View

```sql
SELECT
    table_name AS view_name,
    view_definition
FROM information_schema.VIEWS
WHERE table_schema = DATABASE()
  AND view_definition LIKE '%target_table%';
```

注意：`LIKE '%target_table%'` 只是粗略搜尋，仍要人工判斷是否真的依賴。

---

### 8.12.10 檢查 Stored Procedure / Function

```sql
SELECT
    routine_name,
    routine_type,
    routine_definition
FROM information_schema.ROUTINES
WHERE routine_schema = DATABASE()
  AND routine_definition LIKE '%target_table%';
```

一樣，這只是粗略搜尋。

如果公司有使用版本控管，還要搜尋 Git 專案中的 SQL、Mapper XML、Repository、DAO、Service、報表設定。

---

### 8.12.11 檢查 Event

```sql
SELECT
    event_name,
    event_definition
FROM information_schema.EVENTS
WHERE event_schema = DATABASE()
  AND event_definition LIKE '%target_table%';
```

如果有排程事件依賴該表，改表或刪表可能會造成排程失敗。

---

### 8.12.12 備份與回復方案

正式環境操作前至少要回答：

```text
1. 有沒有備份？
2. 備份在哪裡？
3. 備份能不能還原？
4. 還原需要多久？
5. 如果只要還原單表，做得到嗎？
6. 如果 DDL 成功但應用程式壞掉，怎麼回復？
7. 是否需要先停用排程或切維護模式？
```

不要只說「有備份」，要確認「可以還原」。

## 8.13 常見錯誤觀念整理

### 錯誤 1：MySQL 8 atomic DDL 可以讓我手動 rollback DDL

錯。

atomic DDL 是 MySQL 內部確保 DDL 本身不要留下半套狀態，不是讓使用者把 DDL 當普通 DML 一樣手動回滾。

---

### 錯誤 2：`DROP TABLE IF EXISTS` 很安全

錯。

`IF EXISTS` 只是避免表不存在時報錯，不是防呆。

下面這句仍然會刪除存在的表：

```sql
DROP TABLE IF EXISTS important_table;
```

---

### 錯誤 3：`TRUNCATE TABLE` 和 `DELETE FROM table_name` 差不多

錯。

差異很大：

- `DELETE` 是 DML；
- `TRUNCATE` 是 DDL；
- `DELETE` 可以加 `WHERE`；
- `TRUNCATE` 不能加 `WHERE`；
- `DELETE` 通常可以受交易控制；
- `TRUNCATE` 不能像普通 DML 一樣回滾；
- `TRUNCATE` 通常會重置 `AUTO_INCREMENT`；
- `TRUNCATE` 不會觸發 `ON DELETE` Trigger。

---

### 錯誤 4：欄位名稱改一下很簡單

不一定。

欄位名可能被下面地方使用：

- 後端 Entity；
- DTO；
- Mapper XML；
- SQL 字串；
- 前端欄位；
- 匯出 Excel；
- 報表；
- 批次；
- Stored Procedure；
- View；
- Event；
- 權限條件；
- 第三方介面。

所以資料庫命名要一開始就慎重。

---

### 錯誤 5：`MODIFY COLUMN` 只要寫新型別就好

危險。

例如原本欄位是：

```sql
amount DECIMAL(18, 2) NOT NULL DEFAULT 0 COMMENT '金額'
```

如果你只寫：

```sql
ALTER TABLE payment_record
MODIFY COLUMN amount DECIMAL(20, 2);
```

可能導致原本的 `NOT NULL`、`DEFAULT`、`COMMENT` 沒有照你預期保留。

較安全的寫法是重新寫出完整欄位定義：

```sql
ALTER TABLE payment_record
MODIFY COLUMN amount DECIMAL(20, 2) NOT NULL DEFAULT 0 COMMENT '金額';
```

## 8.14 建議你自己的建表模板

你之後練習 MySQL，可以先用這個模板。

```sql
CREATE TABLE table_name (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT COMMENT '主鍵 ID',

    -- 業務欄位
    business_code VARCHAR(50) NOT NULL COMMENT '業務編號',
    business_name VARCHAR(100) NOT NULL COMMENT '業務名稱',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '狀態：1啟用，0停用',

    -- 審計欄位
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '建立時間',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新時間',
    created_by VARCHAR(50) NULL COMMENT '建立人員',
    updated_by VARCHAR(50) NULL COMMENT '更新人員',

    -- 索引
    UNIQUE KEY uk_table_name_business_code (business_code),
    KEY idx_table_name_status (status)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci
  COMMENT = '表說明';
```

使用時要根據真實業務調整，不要機械套用。

## 8.15 第十章總結：你應該帶走的能力

學完第十章，你不只是要記住：

```sql
CREATE TABLE
ALTER TABLE
DROP TABLE
TRUNCATE TABLE
```

你更應該建立下面這張圖的思維：

```text
需求
 ↓
資料庫 / 表 / 欄位設計
 ↓
命名規範
 ↓
資料型別選擇
 ↓
約束與索引設計
 ↓
CREATE TABLE 建表
 ↓
ALTER TABLE 維護
 ↓
RENAME / DROP / TRUNCATE 管理
 ↓
正式環境檢查、備份、回復
```

如果你能做到下面這些，就代表這一章已經學得很扎實：

- 看到需求時，能拆出基本資料表；
- 能為表和欄位取出清楚、穩定、可維護的名稱；
- 能選擇合理的資料型別；
- 能知道什麼時候要加 `NOT NULL`、`DEFAULT`、`UNIQUE`、`CHECK`；
- 能分清楚 `CREATE TABLE ... LIKE` 和 `CREATE TABLE ... AS SELECT`；
- 能安全使用 `ALTER TABLE`；
- 能分清楚 `RENAME TABLE` 和 `ALTER TABLE ... RENAME`；
- 能分清楚 `DROP TABLE`、`TRUNCATE TABLE`、`DELETE FROM`；
- 能知道 DDL 的 implicit commit 風險；
- 能理解 MySQL 8 atomic DDL 的價值與限制；
- 能在正式環境操作前列出檢查清單。

## 自測問題

### 題目 1

為什麼資料庫欄位命名比一般 Java 區域變數命名更需要慎重？

<details>
<summary>答案</summary>

因為資料庫欄位可能被後端 Entity、Mapper XML、SQL、View、Stored Procedure、報表、批次、前端頁面、匯出功能、外部介面等多個地方依賴。

一旦欄位名稱進入系統，修改成本通常比一般程式變數高很多。

</details>

---

### 題目 2

MySQL 官方允許的 identifier 命名規則，和團隊命名規範是同一件事嗎？

<details>
<summary>答案</summary>

不是。

MySQL 官方允許的命名範圍比較寬，但團隊通常會制定更嚴格的工程規範，例如小寫英文、數字、底線、避免保留字、避免大小寫混用。

</details>

---

### 題目 3

為什麼資料庫名、表名建議統一小寫？

<details>
<summary>答案</summary>

因為資料庫名、表名的大小寫敏感性會受到作業系統與 `lower_case_table_names` 影響。

為了跨 Windows、Linux、macOS 與不同部署環境時更穩定，實務上建議資料庫名、表名都使用小寫英文與底線。

</details>

---

### 題目 4

`CHARACTER SET` 和 `COLLATE` 差在哪裡？

<details>
<summary>答案</summary>

`CHARACTER SET` 決定字元如何儲存，例如是否使用 `utf8mb4`。

`COLLATE` 決定字串如何比較與排序，例如大小寫是否敏感、重音是否敏感、排序結果如何。

</details>

---

### 題目 5

MySQL 8 的 atomic DDL 是否代表下面操作可以靠 `ROLLBACK` 救回？

```sql
START TRANSACTION;
DROP TABLE app_user;
ROLLBACK;
```

<details>
<summary>答案</summary>

不代表。

atomic DDL 是指 DDL 本身要嘛完整成功、要嘛完整失敗；它不是 transactional DDL，不代表使用者可以把 DDL 放進一般交易中自行 `ROLLBACK`。

</details>

---

### 題目 6

`DROP TABLE IF EXISTS table_name;` 為什麼不是安全防呆？

<details>
<summary>答案</summary>

因為 `IF EXISTS` 只是在表不存在時避免報錯。

如果表真的存在，這句仍然會刪除該表，所以不能把它當作防止誤刪的保護機制。

</details>

---

### 題目 7

正式環境 `ALTER TABLE` 前，至少要檢查哪些事情？

<details>
<summary>答案</summary>

至少要確認：

- 目前 database；
- 目標表是否正確；
- `SHOW CREATE TABLE`；
- 欄位完整定義；
- 索引；
- 資料量；
- 是否有外鍵；
- 是否有 Trigger；
- 是否有 View、Procedure、Function、Event 依賴；
- 程式碼、Mapper XML、報表、批次是否使用該欄位或表；
- 是否已備份；
- 是否有回復方案。

</details>
