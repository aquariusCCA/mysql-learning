# 6 刪除表

返回章節：[第十章_创建和管理表](./README.md)

## 本節導讀

這一節處理的是：**資料表已經不需要了，想把整張表從資料庫中移除時，應該怎麼做。**

刪除表看起來只有一句：

```sql
DROP TABLE table_name;
```

但在真實專案中，`DROP TABLE` 是非常高風險的 DDL 操作，因為它刪掉的不是某幾筆資料，而是整個資料庫物件。

一旦執行成功，通常會一起消失：

- 表結構；
- 表內資料；
- 索引；
- 主鍵、唯一約束、檢查約束；
- 這張表上定義的外鍵約束；
- 這張表上的 Trigger。

所以這一篇不是只背語法，而是要學會：

1. `DROP TABLE` 會刪掉什麼；
2. `DROP TABLE` 和 `DELETE`、`TRUNCATE` 差在哪裡；
3. `IF EXISTS` 什麼時候適合使用；
4. `TEMPORARY` 關鍵字有什麼特殊效果；
5. 有外鍵依賴時為什麼可能刪不掉；
6. 為什麼 `DROP TABLE` 不能期待用 `ROLLBACK` 救回；
7. 正式環境刪表前要檢查什麼。

這一篇學完後，你應該要能做到：

- 正確使用 `DROP TABLE` 刪除單張表；
- 正確使用 `DROP TABLE IF EXISTS` 避免表不存在時中斷腳本；
- 正確理解 `DROP TABLE`、`DELETE`、`TRUNCATE` 的差異；
- 知道 `DROP TEMPORARY TABLE` 只會刪除暫時表；
- 知道有外鍵引用時，刪除父表可能會失敗；
- 知道正式環境刪表前需要先查依賴、備份與權限。

## 建議回查情境

- 想刪除測試表、備份表、臨時表、過期表時。
- 寫初始化 SQL 腳本，希望表存在就刪除，不存在也不要報錯時。
- 不確定 `DROP TABLE` 會刪表結構還是只刪資料時。
- 想知道刪表後能不能用 `ROLLBACK` 救回時。
- 準備刪表，但擔心有外鍵、View、Procedure、Trigger、程式碼仍然引用這張表時。
- 在正式環境中要刪除舊表，需要建立刪表前檢查清單時。

## 30 秒複習入口

- 刪除整張表的核心語法是：`DROP TABLE table_name;`。
- 想避免表不存在時報錯，可以用：`DROP TABLE IF EXISTS table_name;`。
- `DROP TABLE` 刪的是整張表，不是只刪表內資料。
- `DROP TABLE` 會刪除表結構、資料、索引、約束，以及該表上的 Trigger。
- `DROP TABLE` 是 DDL，普通表的 `DROP TABLE` 會造成 implicit commit，通常不能靠 `ROLLBACK` 救回。
- `DROP TEMPORARY TABLE` 只刪暫時表，不會刪到同名的普通表，也不會造成 implicit commit。
- 即使 `DROP TEMPORARY TABLE` 不造成 implicit commit，它本身也不能靠 `ROLLBACK` 復原。
- `DROP TABLE IF EXISTS` 不代表更安全，它只是避免「表不存在」報錯。
- 如果其他表用外鍵引用這張表，直接刪除父表可能會失敗。
- MySQL 的 `DROP TABLE ... RESTRICT` 和 `DROP TABLE ... CASCADE` 只是為了相容其他資料庫語法而保留，在 MySQL 中不會真正執行級聯刪表。
- 正式環境刪表前，至少要確認：目前 database、表是否存在、資料筆數、建表語句、外鍵、Trigger、View、Procedure、Function、Event、程式碼、報表、備份。

## 速查區

### 1. 常用語法

| 需求 | 語法 | 說明 |
| --- | --- | --- |
| 刪除單張表 | `DROP TABLE table_name;` | 表必須存在，否則報錯 |
| 表存在才刪 | `DROP TABLE IF EXISTS table_name;` | 表不存在不報錯，但會產生 warning/note |
| 一次刪多張表 | `DROP TABLE t1, t2, t3;` | 多張表一起刪除 |
| 一次刪多張表，允許不存在 | `DROP TABLE IF EXISTS t1, t2, t3;` | 常見於初始化腳本 |
| 只刪暫時表 | `DROP TEMPORARY TABLE temp_table;` | 不會刪到同名普通表 |
| 只刪暫時表，允許不存在 | `DROP TEMPORARY TABLE IF EXISTS temp_table;` | 適合清理 session 內暫時表 |

---

### 2. `DROP TABLE` 會刪掉什麼

假設有一張表：

```sql
CREATE TABLE employee (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    emp_no VARCHAR(30) NOT NULL UNIQUE,
    emp_name VARCHAR(50) NOT NULL,
    salary DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

執行：

```sql
DROP TABLE employee;
```

會刪掉：

- `employee` 這張表本身；
- 表內所有資料；
- 欄位定義；
- 主鍵；
- 唯一索引；
- 普通索引；
- 約束；
- 這張表上的 Trigger。

刪除後再執行：

```sql
SELECT * FROM employee;
```

會出現類似錯誤：

```text
Table 'xxx.employee' doesn't exist
```

---

### 3. `DROP TABLE`、`DELETE`、`TRUNCATE` 差異

| 比較項目 | `DROP TABLE` | `DELETE FROM` | `TRUNCATE TABLE` |
| --- | --- | --- | --- |
| 刪除對象 | 整張表 | 表內符合條件的資料列 | 表內全部資料列 |
| 表結構是否保留 | 不保留 | 保留 | 保留 |
| 資料是否保留 | 不保留 | 視 `WHERE` 而定 | 不保留 |
| 是否可以加 `WHERE` | 不可以 | 可以 | 不可以 |
| 是否保留索引與約束定義 | 不保留 | 保留 | 保留 |
| 是否重置 `AUTO_INCREMENT` | 表都被刪了，不適用 | 通常不重置 | 通常會重置 |
| 操作類型 | DDL | DML | DDL |
| 常見用途 | 廢棄整張表 | 刪除部分或全部資料 | 快速清空整張表 |
| 風險等級 | 最高 | 視條件而定 | 高 |

簡單記法：

```text
DROP TABLE：表不要了
DELETE：資料不要了，但表還要
TRUNCATE：資料全部不要了，但表還要
```

---

### 4. `DROP TABLE` vs `ALTER TABLE DROP COLUMN`

這兩個也很容易混淆。

| 比較項目 | `DROP TABLE` | `ALTER TABLE ... DROP COLUMN` |
| --- | --- | --- |
| 刪除對象 | 整張表 | 表中的某個欄位 |
| 表是否存在 | 刪完後表不存在 | 表仍然存在 |
| 其他欄位是否保留 | 不保留 | 保留 |
| 適合場景 | 整張表已廢棄 | 某個欄位已廢棄 |

範例：

```sql
-- 刪掉整張 employee 表
DROP TABLE employee;

-- 只刪掉 employee 表中的 remark 欄位
ALTER TABLE employee DROP COLUMN remark;
```

## 6.1 刪除表的核心觀念

刪除表的本質是：**從資料庫中移除一個表物件。**

它不是把表內資料改成空，也不是把某幾筆資料刪掉，而是直接讓這張表不存在。

可以把資料表想成一個 Excel 工作表：

```text
DELETE：刪除工作表裡的某些列
TRUNCATE：清空工作表裡所有列，但工作表還在
DROP TABLE：整個工作表分頁都刪掉
```

所以 `DROP TABLE` 的風險比 `DELETE` 更高。

如果你的需求是：

> 我只是不想要某些資料。

通常應該先考慮：

```sql
DELETE FROM table_name
WHERE 條件;
```

如果你的需求是：

> 我想清空整張表，之後還會繼續使用這張表。

通常考慮：

```sql
TRUNCATE TABLE table_name;
```

如果你的需求是：

> 這張表已經廢棄，以後不再使用。

才考慮：

```sql
DROP TABLE table_name;
```

## 6.2 基本語法

### 6.2.1 刪除單張表

```sql
DROP TABLE employee;
```

意思是：刪除目前 database 中的 `employee` 表。

如果這張表不存在，會報錯。

正式操作前，建議先確認目前所在 database：

```sql
SELECT DATABASE();
```

再確認表是否存在：

```sql
SHOW TABLES LIKE 'employee';
```

也可以使用完整限定名稱，避免刪錯 database：

```sql
DROP TABLE demo_db.employee;
```

正式環境中，推薦使用完整限定名稱：

```sql
DROP TABLE database_name.table_name;
```

這樣比只寫：

```sql
DROP TABLE table_name;
```

更不容易因為目前選錯 database 而刪錯表。

---

### 6.2.2 表存在才刪除：`IF EXISTS`

```sql
DROP TABLE IF EXISTS employee;
```

意思是：

```text
如果 employee 存在，就刪除。
如果 employee 不存在，不要直接報錯中斷。
```

常見用法：

```sql
DROP TABLE IF EXISTS test_employee;

CREATE TABLE test_employee (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    emp_name VARCHAR(50) NOT NULL
);
```

這種寫法常用在：

- 練習 SQL；
- 測試腳本；
- 初始化資料庫腳本；
- 單元測試資料庫準備；
- 開發環境重建資料表。

但是要注意：

> `IF EXISTS` 不是防呆保護，它只是避免「表不存在」時報錯。

例如你寫錯表名：

```sql
DROP TABLE IF EXISTS emplyoee;
```

如果 `emplyoee` 不存在，SQL 不會直接失敗，但你真正想刪的 `employee` 也不會被刪掉。

所以正式環境不應該因為有 `IF EXISTS` 就降低警覺。

執行後可以查看 warning/note：

```sql
SHOW WARNINGS;
```

---

### 6.2.3 一次刪除多張表

```sql
DROP TABLE employee_backup, employee_temp, employee_old;
```

也可以搭配 `IF EXISTS`：

```sql
DROP TABLE IF EXISTS employee_backup, employee_temp, employee_old;
```

適合用於清理多張測試表或備份表。

但正式環境中不建議隨便一次刪太多張表，因為：

- 風險集中；
- 影響範圍難以確認；
- 回復成本高；
- 審核與紀錄不易追蹤。

正式環境較好的做法是：

1. 一張一張列出要刪的表；
2. 每張表說明刪除原因；
3. 附上資料筆數與依賴檢查結果；
4. 先備份或保留歸檔表；
5. 確認沒有程式、報表、排程仍在使用。

## 6.3 `DROP TEMPORARY TABLE`

`TEMPORARY` 是 `DROP TABLE` 中很重要但容易忽略的關鍵字。

語法：

```sql
DROP TEMPORARY TABLE temp_employee;
```

意思是：**只刪除暫時表。**

如果目前 session 中沒有這張暫時表，即使同名普通表存在，也不會刪到普通表。

例如：

```sql
CREATE TABLE employee (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TEMPORARY TABLE employee (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

DROP TEMPORARY TABLE employee;
```

這裡刪除的是 session 內的 temporary `employee`，不是普通表 `employee`。

### 6.3.1 為什麼 `TEMPORARY` 有保護效果

`DROP TEMPORARY TABLE` 有幾個特點：

- 只會刪除 `TEMPORARY` table；
- 不會刪到同名普通表；
- 不會造成 implicit commit；
- temporary table 只在建立它的 session 中可見。

因此，如果你的目標本來就是清理暫時表，建議明確寫：

```sql
DROP TEMPORARY TABLE IF EXISTS temp_report_data;
```

不要偷懶寫成：

```sql
DROP TABLE IF EXISTS temp_report_data;
```

因為後者如果真的有一張普通表叫 `temp_report_data`，就可能刪到普通表。

---

## 6.4 `DROP TABLE` 與交易：為什麼不能靠 `ROLLBACK`

很多初學者會以為：

```sql
START TRANSACTION;

DROP TABLE employee;

ROLLBACK;
```

這樣就可以把表救回來。

這個理解是錯的。

`DROP TABLE` 是 DDL。對普通表而言，`DROP TABLE` 會造成 implicit commit，也就是它會隱含提交交易。

所以你不能把它當成下面這種 DML 操作：

```sql
START TRANSACTION;

DELETE FROM employee
WHERE id = 1;

ROLLBACK;
```

`DELETE` 在交易中通常可以回滾；但普通表的 `DROP TABLE` 不應該期待用 `ROLLBACK` 復原。

### 6.4.1 `TEMPORARY` 表的特殊情況

`DROP TEMPORARY TABLE` 不會造成 implicit commit。

但這不代表它可以被 `ROLLBACK` 復原。

也就是說：

```sql
START TRANSACTION;

DROP TEMPORARY TABLE temp_employee;

ROLLBACK;
```

即使執行 `ROLLBACK`，也不代表暫時表會回來。

你可以這樣記：

```text
普通表 DROP TABLE：會 implicit commit，不能靠 ROLLBACK 救回。
暫時表 DROP TEMPORARY TABLE：不會 implicit commit，但本身也不能靠 ROLLBACK 救回。
```

## 6.5 外鍵依賴與刪表

如果其他表透過外鍵引用你要刪的表，直接 `DROP TABLE` 可能會失敗。

例如：

```sql
CREATE TABLE department (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    dept_name VARCHAR(50) NOT NULL
) ENGINE = InnoDB;

CREATE TABLE employee (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    dept_id BIGINT NOT NULL,
    emp_name VARCHAR(50) NOT NULL,
    CONSTRAINT fk_employee_department
        FOREIGN KEY (dept_id)
        REFERENCES department(id)
) ENGINE = InnoDB;
```

這裡：

```text
department 是父表
employee 是子表
employee.dept_id 參照 department.id
```

如果直接刪父表：

```sql
DROP TABLE department;
```

可能會因為 `employee` 還依賴它而失敗。

### 6.5.1 刪表前檢查誰引用它

可以用 `INFORMATION_SCHEMA.KEY_COLUMN_USAGE` 查外鍵關係：

```sql
SELECT
    TABLE_NAME,
    COLUMN_NAME,
    CONSTRAINT_NAME,
    REFERENCED_TABLE_NAME,
    REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
  AND (
        TABLE_NAME = 'department'
        OR REFERENCED_TABLE_NAME = 'department'
      );
```

結果中要注意兩種方向：

| 情況 | 意思 |
| --- | --- |
| `TABLE_NAME = 'department'` | `department` 這張表本身有外鍵指向別人 |
| `REFERENCED_TABLE_NAME = 'department'` | 其他表有外鍵指向 `department` |

刪表前最需要注意的是第二種：

```text
其他表有外鍵指向我要刪的表。
```

因為這代表你要刪的是父表。

---

### 6.5.2 正常處理方式：先處理依賴

比較安全的做法通常是：

1. 確認哪些子表依賴父表；
2. 確認這些子表是否仍在使用；
3. 如果整組表都廢棄，先評估一起下線；
4. 如果只刪父表，要先移除子表上的外鍵；
5. 刪除前備份；
6. 刪除後驗證程式、報表、排程沒有錯誤。

移除外鍵的語法：

```sql
ALTER TABLE employee DROP FOREIGN KEY fk_employee_department;
```

但不要看到外鍵擋住就急著刪外鍵。

外鍵存在通常代表資料之間有業務關係，例如：

```text
員工一定屬於某個部門。
```

如果你刪掉外鍵，資料庫就不再保護這個關係。

所以正式環境刪外鍵前，要先確認：

- 這個關係是否真的廢棄；
- 應用程式是否還依賴這個關係；
- 是否有報表或統計 SQL 使用這個關聯；
- 是否有資料一致性風險。

---

### 6.5.3 不建議隨便使用 `SET foreign_key_checks = 0`

你可能會看到有人這樣寫：

```sql
SET foreign_key_checks = 0;

DROP TABLE department;

SET foreign_key_checks = 1;
```

這種方式可以暫時關閉外鍵檢查，但不建議在正式環境中隨便使用。

原因是：

- 它可能讓你繞過資料庫原本的參照完整性保護；
- 你可能留下引用不存在父表的子表；
- 重新開啟 `foreign_key_checks` 時，不代表 MySQL 會完整掃描既有資料並幫你修正不一致；
- 後續重建表、修改表或新增外鍵時可能遇到更難理解的錯誤。

比較適合使用 `foreign_key_checks = 0` 的情境通常是：

- 匯入資料；
- 還原備份；
- 按照 dump 檔重建多張有外鍵依賴的表；
- 經過審核的維護腳本。

如果真的要用，至少要做到：

```sql
-- 1. 確認目前 session 的設定
SELECT @@SESSION.foreign_key_checks;

-- 2. 暫時關閉
SET SESSION foreign_key_checks = 0;

-- 3. 執行經過審核的維護操作
-- DROP TABLE ...

-- 4. 立刻打開
SET SESSION foreign_key_checks = 1;

-- 5. 再確認一次
SELECT @@SESSION.foreign_key_checks;
```

重點：

```text
能先理解依賴並正常處理，就不要直接關掉 foreign_key_checks 硬刪。
```

## 6.6 `RESTRICT` 和 `CASCADE` 在 MySQL 中的意義

有些資料庫支援類似：

```sql
DROP TABLE table_name CASCADE;
```

意思可能是刪表時連依賴物件一起處理。

但在 MySQL 的 `DROP TABLE` 中，`RESTRICT` 和 `CASCADE` 關鍵字沒有實際效果，只是為了讓其他資料庫系統的語法比較容易移植。

也就是說，下面這種寫法不要當成真正的級聯刪除保證：

```sql
DROP TABLE department CASCADE;
```

在 MySQL 中，不能把它理解成：

```text
幫我自動把依賴 department 的東西全部刪掉。
```

如果有外鍵、View、Procedure、Trigger、程式碼依賴，你仍然要自己檢查與處理。

## 6.7 權限與 Trigger 的注意事項

### 6.7.1 表上的 Trigger 會一起被刪除

如果一張表上有 Trigger，例如：

```sql
CREATE TRIGGER trg_employee_before_insert
BEFORE INSERT ON employee
FOR EACH ROW
SET NEW.created_at = CURRENT_TIMESTAMP;
```

執行：

```sql
DROP TABLE employee;
```

這張表上的 Trigger 也會一起消失。

所以刪表前要先查：

```sql
SELECT
    TRIGGER_NAME,
    EVENT_MANIPULATION,
    ACTION_TIMING,
    ACTION_STATEMENT
FROM INFORMATION_SCHEMA.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE()
  AND EVENT_OBJECT_TABLE = 'employee';
```

如果查到 Trigger，代表這張表可能有額外業務邏輯，例如：

- 寫入時自動補欄位；
- 更新時記錄異動紀錄；
- 刪除時寫 audit log；
- 同步其他表。

不能只看表本身有沒有資料。

---

### 6.7.2 表專屬權限不一定會自動清乾淨

MySQL 官方文件特別提醒：刪表時，針對該表授予的專屬權限不會自動刪除，必要時要手動處理。

所以正式環境刪表後，若該表曾經有特別授權，還要檢查權限設定。

可用：

```sql
SHOW GRANTS FOR 'some_user'@'%';
```

如果系統有使用專門的 DBA 權限管理流程，通常要交由 DBA 或權限管理流程處理。

---

## 6.8 正式環境刪表前檢查清單

正式環境刪表前，建議至少做以下檢查。

### 6.8.1 確認目前 database

```sql
SELECT DATABASE();
```

如果結果不是你預期的 database，不要繼續操作。

也可以直接使用完整名稱：

```sql
DROP TABLE production_db.old_table;
```

---

### 6.8.2 確認表是否存在

```sql
SHOW TABLES LIKE 'old_table';
```

或：

```sql
SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_TYPE, ENGINE
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'old_table';
```

---

### 6.8.3 查看建表語句

```sql
SHOW CREATE TABLE old_table\G
```

要確認：

- 欄位；
- 主鍵；
- 索引；
- 外鍵；
- 約束；
- engine；
- charset；
- collation；
- comment。

這個結果也可以保存起來，作為日後重建表的依據。

---

### 6.8.4 查看資料筆數

```sql
SELECT COUNT(*) FROM old_table;
```

大表執行 `COUNT(*)` 可能有成本，正式環境要注意執行時間。

也可以先看估算值：

```sql
SELECT TABLE_ROWS
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'old_table';
```

注意：`TABLE_ROWS` 對 InnoDB 常常是估算值，不一定精準。

---

### 6.8.5 檢查外鍵依賴

```sql
SELECT
    TABLE_NAME,
    COLUMN_NAME,
    CONSTRAINT_NAME,
    REFERENCED_TABLE_NAME,
    REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
  AND (
        TABLE_NAME = 'old_table'
        OR REFERENCED_TABLE_NAME = 'old_table'
      );
```

重點看：

```sql
REFERENCED_TABLE_NAME = 'old_table'
```

這代表其他表正在引用你要刪的表。

---

### 6.8.6 檢查 Trigger

```sql
SELECT
    TRIGGER_NAME,
    EVENT_MANIPULATION,
    ACTION_TIMING
FROM INFORMATION_SCHEMA.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE()
  AND EVENT_OBJECT_TABLE = 'old_table';
```

---

### 6.8.7 檢查 View 是否引用這張表

```sql
SELECT TABLE_NAME
FROM INFORMATION_SCHEMA.VIEWS
WHERE TABLE_SCHEMA = DATABASE()
  AND VIEW_DEFINITION LIKE '%old_table%';
```

注意：

- `LIKE '%old_table%'` 只是輔助搜尋；
- 如果表名很短，可能有誤判；
- 如果 View 定義被格式化或使用別名，也可能漏掉。

---

### 6.8.8 檢查 Stored Procedure / Function

```sql
SELECT ROUTINE_NAME, ROUTINE_TYPE
FROM INFORMATION_SCHEMA.ROUTINES
WHERE ROUTINE_SCHEMA = DATABASE()
  AND ROUTINE_DEFINITION LIKE '%old_table%';
```

注意：

- 這只能搜尋目前使用者有權限看到的 routine 定義；
- 如果 SQL 是動態拼字串，可能搜不到；
- 還是要搭配程式碼搜尋。

---

### 6.8.9 檢查 Event Scheduler

```sql
SELECT EVENT_NAME
FROM INFORMATION_SCHEMA.EVENTS
WHERE EVENT_SCHEMA = DATABASE()
  AND EVENT_DEFINITION LIKE '%old_table%';
```

---

### 6.8.10 檢查程式碼與外部依賴

資料庫內部查完後，還要查外部依賴：

- Java 程式碼；
- Mapper XML；
- Repository / DAO；
- MyBatis XML；
- JPA Entity；
- 報表 SQL；
- 批次程式；
- ETL 腳本；
- 排程任務；
- Excel 匯出 SQL；
- BI 工具；
- 權限設定；
- 監控 SQL；
- 備份腳本。

對你目前接觸的銀行舊系統來說，尤其要注意：

- XML 裡面寫死的 SQL；
- 很舊的 DAO / Service；
- stored procedure；
- 批次報表；
- 排程產檔；
- 一些看起來沒人用，但其實每月或每季才跑一次的程式。

---

## 6.9 正式環境建議流程

正式環境不建議一上來就直接：

```sql
DROP TABLE old_table;
```

比較安全的流程是：

```text
第一步：確認表是否真的廢棄
第二步：確認沒有程式、報表、排程依賴
第三步：查外鍵、Trigger、View、Procedure、Function、Event
第四步：匯出或備份表結構與資料
第五步：先改名觀察，而不是立刻刪除
第六步：觀察一段時間沒有錯誤後，再正式刪除
```

### 6.9.1 先改名觀察

正式環境中，如果不確定表是否真的沒人用，有時候可以先改名：

```sql
RENAME TABLE old_table TO old_table_deprecated_20260501;
```

觀察一段時間：

- 應用程式是否報錯；
- 排程是否報錯；
- 報表是否報錯；
- 監控是否報錯；
- 使用者是否回報異常。

確認沒問題後，再刪除：

```sql
DROP TABLE old_table_deprecated_20260501;
```

這種做法比直接刪除安全，但也不是萬無一失，因為有些程式可能一個月、一季或一年才執行一次。

---

### 6.9.2 先備份再刪除

如果表內資料可能還有歷史價值，刪除前至少保留備份。

常見方式一：建立備份表。

```sql
CREATE TABLE old_table_backup_20260501 LIKE old_table;

INSERT INTO old_table_backup_20260501
SELECT * FROM old_table;
```

常見方式二：用 `mysqldump` 匯出。

```bash
mysqldump -u user -p database_name old_table > old_table_20260501.sql
```

正式環境通常不只要備份，還要確認備份可以還原。

只備份但沒有驗證還原，風險仍然很高。

---

## 6.10 範例：刪除測試表

### 6.10.1 建立測試表

```sql
CREATE TABLE test_employee (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    emp_name VARCHAR(50) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

確認存在：

```sql
SHOW TABLES LIKE 'test_employee';
```

查看結構：

```sql
SHOW CREATE TABLE test_employee\G
```

---

### 6.10.2 刪除測試表

```sql
DROP TABLE test_employee;
```

再查一次：

```sql
SHOW TABLES LIKE 'test_employee';
```

若沒有結果，代表表已被刪除。

---

## 6.11 範例：初始化腳本常見寫法

開發或測試環境中，經常會看到：

```sql
DROP TABLE IF EXISTS test_order_item;
DROP TABLE IF EXISTS test_order;

CREATE TABLE test_order (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no VARCHAR(50) NOT NULL UNIQUE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

CREATE TABLE test_order_item (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    quantity INT NOT NULL DEFAULT 1,
    CONSTRAINT fk_test_order_item_order
        FOREIGN KEY (order_id)
        REFERENCES test_order(id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

這種寫法的目的通常是：

```text
每次執行腳本前，先刪掉舊測試表，再重建一份乾淨結構。
```

但要注意外鍵順序。

上面先刪 `test_order_item`，再刪 `test_order`，是因為：

```text
test_order_item 是子表
test_order 是父表
```

通常要先刪子表，再刪父表。

---

## 6.12 範例：清理暫時表

如果你建立的是 temporary table：

```sql
CREATE TEMPORARY TABLE temp_report_data (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    report_name VARCHAR(100) NOT NULL
);
```

清理時建議寫：

```sql
DROP TEMPORARY TABLE IF EXISTS temp_report_data;
```

不要寫成：

```sql
DROP TABLE IF EXISTS temp_report_data;
```

因為你真正想清的是暫時表，就應該明確使用 `TEMPORARY`。

這樣可以降低誤刪普通表的風險。

## 6.13 常見錯誤與反模式

### 錯誤 1：以為 `DROP TABLE` 可以靠 `ROLLBACK` 救回

錯誤理解：

```sql
START TRANSACTION;
DROP TABLE employee;
ROLLBACK;
```

以為表會回來。

正確理解：

```text
普通表 DROP TABLE 是 DDL，會造成 implicit commit，不能靠 ROLLBACK 復原。
```

---

### 錯誤 2：把 `DROP TABLE` 當成清空資料

錯誤：

```sql
DROP TABLE employee;
```

原本只是想清資料，結果整張表不見了。

如果只是要刪資料，應該考慮：

```sql
DELETE FROM employee;
```

或：

```sql
TRUNCATE TABLE employee;
```

---

### 錯誤 3：正式環境直接 `DROP TABLE IF EXISTS`

錯誤心態：

```text
有 IF EXISTS 就比較安全。
```

正確理解：

```text
IF EXISTS 只是不讓「表不存在」變成錯誤，不是刪表防呆機制。
```

正式環境更重要的是：

- 刪除前檢查；
- 審核；
- 備份；
- 依賴分析；
- 操作紀錄；
- 回復方案。

---

### 錯誤 4：忽略外鍵依賴

錯誤：

```sql
DROP TABLE department;
```

結果因為 `employee` 仍引用 `department` 而失敗。

正確做法：

```sql
SELECT
    TABLE_NAME,
    CONSTRAINT_NAME,
    REFERENCED_TABLE_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
  AND REFERENCED_TABLE_NAME = 'department';
```

先查出誰依賴它，再決定怎麼處理。

---

### 錯誤 5：隨便關閉 `foreign_key_checks`

錯誤：

```sql
SET foreign_key_checks = 0;
DROP TABLE department;
SET foreign_key_checks = 1;
```

正確理解：

```text
這是維護手段，不是日常刪表手段。
```

如果還沒搞清楚資料關係，就直接關掉外鍵檢查，可能留下更大的資料一致性問題。

---

### 錯誤 6：刪表前沒有保存 `SHOW CREATE TABLE`

錯誤：刪完表之後才發現不知道原本欄位、索引、約束怎麼建。

刪除前至少保存：

```sql
SHOW CREATE TABLE old_table\G
```

必要時也要保存資料：

```bash
mysqldump -u user -p database_name old_table > old_table_backup.sql
```

---

## 6.14 一句話對比

- `DROP TABLE`：整張表不要了，表結構和資料都刪掉。
- `DELETE`：表還要，只刪表裡的資料。
- `TRUNCATE`：表還要，但資料全部清空。
- `ALTER TABLE DROP COLUMN`：表還要，只刪某個欄位。
- `DROP TEMPORARY TABLE`：只刪目前 session 的暫時表。
- `DROP TABLE IF EXISTS`：表存在就刪，不存在就不要因為這件事報錯。

## 6.15 面試 / 實務問答

### Q1：`DROP TABLE` 和 `DELETE` 有什麼差別？

`DROP TABLE` 是 DDL，會刪除整張表，包括表結構與資料；`DELETE` 是 DML，只刪除表內資料，表結構仍然保留。

---

### Q2：`DROP TABLE IF EXISTS` 比 `DROP TABLE` 安全嗎？

不完全是。

`IF EXISTS` 只是不讓「表不存在」造成錯誤，它不會防止你刪錯表。

正式環境安全不安全，主要取決於是否有：

- 依賴檢查；
- 備份；
- 審核；
- 回復方案；
- 正確的 database 與表名確認。

---

### Q3：`DROP TABLE` 可以 `ROLLBACK` 嗎？

普通表的 `DROP TABLE` 不應期待用 `ROLLBACK` 復原。

它是 DDL，會造成 implicit commit。

`DROP TEMPORARY TABLE` 雖然不會造成 implicit commit，但這個操作本身也不能靠 `ROLLBACK` 復原。

---

### Q4：有外鍵引用時，為什麼刪表會失敗？

因為其他表可能還依賴你要刪的表。

例如 `employee.dept_id` 參照 `department.id`，此時 `department` 是父表。如果直接刪掉父表，子表中的資料就可能失去參照對象，因此資料庫會阻止這種破壞參照完整性的操作。

---

### Q5：能不能用 `DROP TABLE table_name CASCADE` 讓 MySQL 自動刪依賴？

不要這樣理解。

MySQL 的 `DROP TABLE` 語法雖然允許 `RESTRICT`、`CASCADE` 關鍵字，但它們沒有實際作用，只是為了相容其他資料庫系統。

## 6.17 本節總結

這一節的核心不是背 `DROP TABLE` 語法，而是建立刪表時的風險意識。

你可以這樣記：

```text
DROP TABLE 是把整張表從資料庫中移除。
它不是清資料，而是刪物件。
```

實務上要掌握五個重點：

1. `DROP TABLE` 刪除表結構與資料；
2. `DROP TABLE IF EXISTS` 只避免表不存在時報錯，不是防呆；
3. 普通表 `DROP TABLE` 是 DDL，會 implicit commit，不能靠 `ROLLBACK` 救回；
4. 有外鍵依賴時，刪表前要先處理依賴；
5. 正式環境刪表前一定要檢查、備份、審核、保留回復方案。

在開發環境中，`DROP TABLE IF EXISTS` 是很常見的初始化寫法。

但在正式環境中，刪表永遠不是「語法問題」，而是「風險控制問題」。
