# 4 生成列 / 计算列

返回章节：[第十一章_数据处理之增删改](./README.md)

## 本节导读

这一节学习 MySQL 中一个很实用的表结构功能：**生成列**。

生成列也常被称为：

- 计算列
- 派生列
- Generated Column
- Computed Column

它的核心思想是：

> 某个字段的值，不需要手动插入或更新，  
> 而是根据其他字段自动计算出来。

例如，有一张表 `tb1`：

| a | b | c |
|---|---|---|
| 100 | 200 | 300 |

其中 `c` 不需要手动维护，而是永远等于：

```text
a + b
```

这时就可以把 `c` 定义成生成列：

```sql
c INT GENERATED ALWAYS AS (a + b)
```

以后只要 `a` 或 `b` 发生变化，`c` 就会根据表达式自动得到对应结果。

---

## 学习目标

学完本节后，应能掌握：

1. 什么是生成列 / 计算列。
2. 为什么生成列不需要手动插入值。
3. `GENERATED ALWAYS AS` 的基本语法。
4. `VIRTUAL` 和 `STORED` 的差异。
5. 为什么更新基础字段后，生成列会自动变化。
6. 生成列适合解决什么问题。
7. 生成列不适合解决什么问题。
8. 生成列表达式有哪些限制。
9. 插入或更新生成列时为什么不能随便指定值。
10. 生成列和普通字段、视图、触发器的差异。

## 30 秒复习入口

- 生成列是由表达式自动计算出来的字段。
- 基本语法是：

```sql
字段名 数据类型 GENERATED ALWAYS AS (表达式) [VIRTUAL | STORED]
```

- 生成列的值通常不需要手动插入。
- 生成列会根据其他字段自动计算。
- `VIRTUAL` 表示不真正储存计算结果，读取时计算。
- `STORED` 表示把计算结果存起来，插入或更新时计算。
- 如果没有指定 `VIRTUAL` 或 `STORED`，MySQL 默认是 `VIRTUAL`。
- 生成列适合处理稳定、可重复、由同一张表字段推导出来的值。
- 生成列不适合处理复杂业务流程，也不适合依赖子查询、变量、随机值或当前时间。

## 4.1 实际问题

假设现在有一张表，里面有三个字段：

```text
a
b
c
```

其中 `c` 永远等于：

```text
a + b
```

如果使用普通字段，就可能这样设计：

```sql
CREATE TABLE tb1 (
    id INT,
    a INT,
    b INT,
    c INT
);
```

插入时要手动算好 `c`：

```sql
INSERT INTO tb1(id, a, b, c)
VALUES (1, 100, 200, 300);
```

问题是：

如果以后把 `a` 改成 `500`：

```sql
UPDATE tb1
SET a = 500
WHERE id = 1;
```

这时 `c` 不会自动变化。

如果忘记同步更新 `c`，数据就会变成：

| id | a | b | c |
|---|---:|---:|---:|
| 1 | 500 | 200 | 300 |

但实际上 `c` 应该是：

```text
500 + 200 = 700
```

这就造成数据不一致。

---

## 4.2 生成列要解决的问题

生成列主要是为了解决这种问题：

> 某个字段的值可以由其他字段计算出来，  
> 不希望人工维护，也不希望应用程序每次都重复计算。

例如：

| 场景 | 基础字段 | 生成列 |
|---|---|---|
| 商品小计 | 单价、数量 | 小计 |
| 姓名显示 | 姓、名 | 全名 |
| 订单金额 | 数量、单价、折扣 | 应付金额 |
| 文字处理 | 姓名、编号 | 拼接后的显示名称 |
| JSON 资料 | JSON 字段 | JSON 中抽出的某个值 |
| 几何计算 | 长、宽 | 面积 |

---

## 4.3 什么是生成列

生成列就是：

> 由数据库根据表达式自动计算出来的字段。

它不是由使用者手动维护，而是由 MySQL 根据定义好的表达式计算。

例如：

```sql
c INT GENERATED ALWAYS AS (a + b)
```

意思是：

> `c` 这个字段的值，永远根据 `a + b` 计算。

完整示例：

```sql
CREATE TABLE tb1 (
    id INT,
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b)
);
```

这里：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | 普通字段 | 手动插入 |
| `a` | 普通字段 | 手动插入 |
| `b` | 普通字段 | 手动插入 |
| `c` | 生成列 | 根据 `a + b` 自动计算 |

---

## 4.4 基本语法

### 标准语法

```sql
字段名 数据类型 [GENERATED ALWAYS] AS (表达式) [VIRTUAL | STORED]
```

例如：

```sql
c INT GENERATED ALWAYS AS (a + b) VIRTUAL
```

可以拆成：

| 部分 | 说明 |
|---|---|
| `c` | 生成列字段名 |
| `INT` | 生成列的数据类型 |
| `GENERATED ALWAYS` | 明确表示这是生成列 |
| `AS (a + b)` | 生成列的计算表达式 |
| `VIRTUAL` | 表示这是虚拟生成列 |

---

## 4.5 创建生成列

### 示例

```sql
CREATE TABLE tb1 (
    id INT,
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b) VIRTUAL
);
```

这张表中，`c` 是生成列。

它的值不是手动插入的，而是根据：

```text
a + b
```

自动计算出来。

---

### 插入数据

```sql
INSERT INTO tb1(id, a, b)
VALUES (1, 100, 200);
```

注意：

这里没有插入 `c`。

因为 `c` 是生成列，不需要手动维护。

---

### 查询数据

```sql
SELECT id, a, b, c
FROM tb1;
```

结果：

```text
id    a      b      c
1     100    200    300
```

`c` 的值来自：

```text
100 + 200 = 300
```

---

## 4.6 更新基础字段后，生成列会自动变化

生成列最大的特点是：

> 它会根据基础字段自动重新计算。

例如，原本资料是：

```text
id    a      b      c
1     100    200    300
```

现在更新 `a`：

```sql
UPDATE tb1
SET a = 500
WHERE id = 1;
```

再查询：

```sql
SELECT id, a, b, c
FROM tb1;
```

结果：

```text
id    a      b      c
1     500    200    700
```

因为：

```text
c = a + b = 500 + 200 = 700
```

---

## 4.7 生成列不能像普通字段一样随便插入

生成列的值由 MySQL 自动计算，通常不应该手动指定。

### 不推荐写法

```sql
INSERT INTO tb1(id, a, b, c)
VALUES (1, 100, 200, 999);
```

这里的问题是：

```text
c 应该由 a + b 自动计算，不应该手动写 999。
```

如果允许这样做，就会破坏生成列的意义。

---

### 推荐写法

```sql
INSERT INTO tb1(id, a, b)
VALUES (1, 100, 200);
```

让 MySQL 自动计算：

```text
c = 100 + 200 = 300
```

---

### 如果真的列出生成列，只能使用 `DEFAULT`

有些情况下，如果 SQL 语句中列出了生成列，应该使用：

```sql
INSERT INTO tb1(id, a, b, c)
VALUES (1, 100, 200, DEFAULT);
```

意思是：

> `c` 不由我手动指定，让 MySQL 根据生成列表达式产生默认计算结果。

不过实际开发中更建议直接省略生成列：

```sql
INSERT INTO tb1(id, a, b)
VALUES (1, 100, 200);
```

---

## 4.8 生成列也不能随便手动更新

同样，生成列通常也不应该被手动更新。

### 错误理解

```sql
UPDATE tb1
SET c = 999
WHERE id = 1;
```

这种写法违背生成列的意义。

因为 `c` 应该来自：

```text
a + b
```

而不是人为指定。

---

### 正确做法

如果想让 `c` 变化，应该更新它依赖的基础字段。

例如：

```sql
UPDATE tb1
SET a = 500
WHERE id = 1;
```

然后 `c` 会自动变成：

```text
500 + b
```

---

## 4.9 `VIRTUAL` 和 `STORED` 的差异

生成列有两种类型：

```text
VIRTUAL
STORED
```

这是本节最重要的概念之一。

---

### 4.9.1 `VIRTUAL`：虚拟生成列

```sql
CREATE TABLE tb_virtual (
    id INT,
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b) VIRTUAL
);
```

`VIRTUAL` 的意思是：

> 不真正储存计算结果，读取时才计算。

也就是说，表中实际存的是：

```text
id
a
b
```

`c` 是查询时根据 `a + b` 算出来的。

---

### `VIRTUAL` 的特点

| 特点 | 说明 |
|---|---|
| 是否储存结果 | 不储存 |
| 占用空间 | 较少 |
| 计算时机 | 读取时计算 |
| 适合场景 | 计算简单、节省空间 |
| 默认类型 | 如果没写 `VIRTUAL` 或 `STORED`，默认是 `VIRTUAL` |

---

### 4.9.2 `STORED`：存储生成列

```sql
CREATE TABLE tb_stored (
    id INT,
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b) STORED
);
```

`STORED` 的意思是：

> 计算结果会实际存进表中。

也就是说，插入或更新 `a`、`b` 时，MySQL 会计算 `c`，并把结果存起来。

---

### `STORED` 的特点

| 特点 | 说明 |
|---|---|
| 是否储存结果 | 会储存 |
| 占用空间 | 较多 |
| 计算时机 | 插入或更新时计算 |
| 适合场景 | 计算成本较高、查询频繁 |
| 查询效率 | 可能比每次读取时计算更稳定 |

---

### 4.9.3 `VIRTUAL` vs `STORED` 对比

| 比较项目 | `VIRTUAL` | `STORED` |
|---|---|---|
| 是否实际存值 | 不存 | 存 |
| 占用磁盘空间 | 较少 | 较多 |
| 计算时机 | 查询时计算 | 插入或更新时计算 |
| 适合场景 | 简单计算、节省空间 | 复杂计算、频繁查询 |
| 默认值 | 默认就是 `VIRTUAL` | 需要明确指定 |
| 直觉理解 | 像临时算出来的字段 | 像预先算好并存起来的字段 |

---

## 4.10 如果不写 `VIRTUAL` 或 `STORED`

例如：

```sql
CREATE TABLE tb1 (
    id INT,
    a INT,
    b INT,
    c INT GENERATED ALWAYS AS (a + b)
);
```

这里没有写：

```text
VIRTUAL
STORED
```

在 MySQL 中，默认会当成：

```sql
c INT GENERATED ALWAYS AS (a + b) VIRTUAL
```

所以为了让笔记和团队协作更清楚，建议初学阶段明确写出来：

```sql
c INT GENERATED ALWAYS AS (a + b) VIRTUAL
```

或：

```sql
c INT GENERATED ALWAYS AS (a + b) STORED
```

## 4.11 生成列表达式可以写什么

生成列的表达式应该是：

> 可以根据当前行中的字段稳定计算出来的表达式。

### 可以使用的常见内容

```sql
a + b
```

```sql
price * quantity
```

```sql
CONCAT(first_name, ' ', last_name)
```

```sql
LOWER(email)
```

```sql
YEAR(birth_date)
```

---

### 示例一：商品小计

```sql
CREATE TABLE order_items (
    id INT PRIMARY KEY AUTO_INCREMENT,
    price DECIMAL(10, 2) NOT NULL,
    quantity INT NOT NULL,
    amount DECIMAL(10, 2)
        GENERATED ALWAYS AS (price * quantity) STORED
);
```

插入数据：

```sql
INSERT INTO order_items(price, quantity)
VALUES (100.00, 3);
```

查询：

```sql
SELECT id, price, quantity, amount
FROM order_items;
```

结果：

```text
id    price    quantity    amount
1     100.00   3           300.00
```

---

### 示例二：全名

```sql
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    full_name VARCHAR(120)
        GENERATED ALWAYS AS (CONCAT(first_name, ' ', last_name)) VIRTUAL
);
```

插入：

```sql
INSERT INTO users(first_name, last_name)
VALUES ('Tom', 'Chen');
```

查询：

```sql
SELECT id, first_name, last_name, full_name
FROM users;
```

结果：

```text
id    first_name    last_name    full_name
1     Tom           Chen         Tom Chen
```

---

### 示例三：邮箱小写化

```sql
CREATE TABLE members (
    id INT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(100),
    email_lower VARCHAR(100)
        GENERATED ALWAYS AS (LOWER(email)) STORED
);
```

插入：

```sql
INSERT INTO members(email)
VALUES ('Tom.Chen@Example.COM');
```

查询：

```sql
SELECT email, email_lower
FROM members;
```

结果：

```text
email                 email_lower
Tom.Chen@Example.COM  tom.chen@example.com
```

---

## 4.12 生成列表达式不能随便写

生成列不是万能的。

它的表达式有一些限制。

### 不适合使用的内容

| 内容 | 原因 |
|---|---|
| 子查询 | 生成列通常只根据当前行计算 |
| 用户变量 | 结果不够稳定 |
| 存储过程参数 | 不属于表中固定资料 |
| 非确定性函数 | 每次执行结果可能不同 |
| `NOW()` | 当前时间会变化 |
| `RAND()` | 随机数不稳定 |
| `AUTO_INCREMENT` | 生成列本身不能是自增字段 |

---

### 错误示例一：使用当前时间

```sql
CREATE TABLE test_time (
    id INT,
    created_year INT GENERATED ALWAYS AS (YEAR(NOW()))
);
```

问题是：

```text
NOW() 会随着时间改变，不适合当成稳定的生成列表达式。
```

---

### 错误示例二：使用子查询

```sql
CREATE TABLE test_subquery (
    id INT,
    total INT GENERATED ALWAYS AS (
        (SELECT COUNT(*) FROM orders)
    )
);
```

问题是：

```text
生成列不适合依赖其他表的查询结果。
```

如果需要跨表统计，通常要考虑：

- 普通查询；
- 视图；
- 汇总表；
- 定时任务；
- 应用程序计算；
- 触发器或其他机制。

---

## 4.13 生成列和普通字段的差异

| 比较项目 | 普通字段 | 生成列 |
|---|---|---|
| 值从哪里来 | 手动插入或更新 | 根据表达式自动计算 |
| 是否能手动维护 | 可以 | 通常不应该 |
| 是否容易不一致 | 可能 | 比较不容易 |
| 适合内容 | 原始资料 | 可由原始资料推导的资料 |
| 例子 | `price`、`quantity` | `price * quantity` |

---

### 普通字段示例

```sql
CREATE TABLE order_items_normal (
    id INT PRIMARY KEY AUTO_INCREMENT,
    price DECIMAL(10, 2),
    quantity INT,
    amount DECIMAL(10, 2)
);
```

插入时要手动维护 `amount`：

```sql
INSERT INTO order_items_normal(price, quantity, amount)
VALUES (100.00, 3, 300.00);
```

如果以后 `quantity` 改成 5，却忘记改 `amount`：

```sql
UPDATE order_items_normal
SET quantity = 5
WHERE id = 1;
```

资料就可能不一致：

```text
price = 100
quantity = 5
amount = 300
```

但正确金额应该是：

```text
100 * 5 = 500
```

---

### 生成列示例

```sql
CREATE TABLE order_items_generated (
    id INT PRIMARY KEY AUTO_INCREMENT,
    price DECIMAL(10, 2),
    quantity INT,
    amount DECIMAL(10, 2)
        GENERATED ALWAYS AS (price * quantity) STORED
);
```

更新：

```sql
UPDATE order_items_generated
SET quantity = 5
WHERE id = 1;
```

`amount` 会根据 `price * quantity` 自动得到新结果。

## 4.14 生成列和视图的差异

有些场景也可以用视图解决。

例如：

```sql
CREATE VIEW v_order_items AS
SELECT id,
       price,
       quantity,
       price * quantity AS amount
FROM order_items;
```

这样查询视图时，也可以看到 `amount`。

---

### 对比

| 比较项目 | 生成列 | 视图 |
|---|---|---|
| 属于哪里 | 表结构的一部分 | 独立的查询对象 |
| 是否像字段一样存在 | 是 | 不是原表字段 |
| 是否可建立索引 | 可以视类型和限制而定 | 一般不直接对普通视图结果建索引 |
| 适合场景 | 某个计算结果本来就是表的派生属性 | 封装复杂查询 |
| 使用方式 | `SELECT amount FROM order_items` | `SELECT amount FROM v_order_items` |

---

### 简单判断

如果这个计算结果是某一张表中某一行的固定派生属性，可以考虑生成列。

如果这个计算结果涉及多表查询、聚合统计、复杂筛选，通常更适合用视图或查询。

---

## 4.15 生成列和触发器的差异

也可以用触发器来维护计算字段。

例如：

```text
插入或更新 price、quantity 时，自动修改 amount
```

但如果只是简单的行内计算：

```text
amount = price * quantity
```

使用生成列通常更直观。

---

### 对比

| 比较项目 | 生成列 | 触发器 |
|---|---|---|
| 适合逻辑 | 简单、稳定、行内计算 | 较复杂的自动处理 |
| 可读性 | 高 | 逻辑可能分散 |
| 维护成本 | 较低 | 较高 |
| 是否能跨表处理 | 不适合 | 可以处理更多场景 |
| 初学理解难度 | 较低 | 较高 |

---

### 简单判断

适合生成列：

```text
同一行内，根据 A 字段和 B 字段计算 C 字段
```

适合触发器或应用程序逻辑：

```text
根据其他表、复杂流程、业务状态去改变资料
```

---

## 4.16 生成列是否可以建立索引

生成列可以配合索引使用，但要注意不同类型和存储引擎的限制。

常见场景是：

> 某个查询条件经常使用表达式计算，  
> 可以把表达式做成生成列，再对生成列建立索引。

---

### 示例：邮箱小写索引

```sql
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(100),
    email_lower VARCHAR(100)
        GENERATED ALWAYS AS (LOWER(email)) STORED,
    INDEX idx_email_lower (email_lower)
);
```

这样以后可以查询：

```sql
SELECT *
FROM users
WHERE email_lower = LOWER('Tom.Chen@Example.COM');
```

---

### 示例：JSON 字段取值

假设有一个 JSON 字段：

```sql
CREATE TABLE products (
    id INT PRIMARY KEY AUTO_INCREMENT,
    attrs JSON,
    brand VARCHAR(50)
        GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(attrs, '$.brand'))) STORED,
    INDEX idx_brand (brand)
);
```

插入：

```sql
INSERT INTO products(attrs)
VALUES ('{"brand": "Apple", "color": "white"}');
```

查询：

```sql
SELECT id, brand
FROM products
WHERE brand = 'Apple';
```

这里 `brand` 是从 JSON 中抽出来的生成列。

---

## 4.17 生成列适合什么场景

生成列适合：

| 场景 | 示例 |
|---|---|
| 同一行字段计算 | `amount = price * quantity` |
| 字符串拼接 | `full_name = CONCAT(first_name, ' ', last_name)` |
| 格式标准化 | `email_lower = LOWER(email)` |
| 日期拆分 | `birth_year = YEAR(birth_date)` |
| JSON 字段提取 | 从 JSON 中提取 `brand`、`type` |
| 避免重复表达式 | 把常用计算集中在表结构中 |
| 降低数据不一致风险 | 不让应用程序手动维护派生值 |

---

## 4.18 生成列不适合什么场景

生成列不适合：

| 场景 | 原因 |
|---|---|
| 跨表统计 | 生成列主要依赖当前行 |
| 复杂业务流程 | 表达式不应承载太多业务逻辑 |
| 需要当前时间 | 当前时间不是稳定输入 |
| 需要随机数 | 随机结果不可预测 |
| 需要调用存储过程 | 不适合放入生成列表达式 |
| 需要人工修正值 | 生成列由表达式控制，不适合手动改 |
| 业务规则经常变化 | 频繁改表结构维护成本高 |

## 4.19 使用生成列的完整示例

### 建表

```sql
CREATE TABLE order_items (
    id INT PRIMARY KEY AUTO_INCREMENT,
    product_name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    quantity INT NOT NULL,
    amount DECIMAL(10, 2)
        GENERATED ALWAYS AS (price * quantity) STORED
);
```

---

### 插入数据

```sql
INSERT INTO order_items(product_name, price, quantity)
VALUES
    ('Keyboard', 1200.00, 2),
    ('Mouse', 500.00, 3);
```

---

### 查询数据

```sql
SELECT id, product_name, price, quantity, amount
FROM order_items;
```

结果：

```text
id    product_name    price     quantity    amount
1     Keyboard        1200.00   2           2400.00
2     Mouse           500.00    3           1500.00
```

---

### 更新数量

```sql
UPDATE order_items
SET quantity = 5
WHERE id = 1;
```

---

### 再次查询

```sql
SELECT id, product_name, price, quantity, amount
FROM order_items;
```

结果：

```text
id    product_name    price     quantity    amount
1     Keyboard        1200.00   5           6000.00
2     Mouse           500.00    3           1500.00
```

`amount` 自动从：

```text
1200.00 * 2 = 2400.00
```

变成：

```text
1200.00 * 5 = 6000.00
```

## 4.20 生成列和 DML 的关系

本章主题是：

```text
数据处理之增删改
```

也就是 DML。

严格来说，生成列本身属于表结构设计，主要通过 `CREATE TABLE` 或 `ALTER TABLE` 定义。

但是它和 DML 有密切关系。

---

### 插入时的关系

普通字段需要插入：

```sql
INSERT INTO order_items(product_name, price, quantity)
VALUES ('Keyboard', 1200.00, 2);
```

生成列 `amount` 不需要插入，它会自动计算。

---

### 更新时的关系

更新基础字段：

```sql
UPDATE order_items
SET quantity = 5
WHERE id = 1;
```

生成列会跟着变化。

---

### 删除时的关系

删除资料时，生成列和普通字段一样，都会随着该行资料一起被删除：

```sql
DELETE FROM order_items
WHERE id = 1;
```

---

## 4.21 通过 `ALTER TABLE` 添加生成列

如果表已经存在，也可以后续新增生成列。

### 示例

原本表结构：

```sql
CREATE TABLE order_items (
    id INT PRIMARY KEY AUTO_INCREMENT,
    price DECIMAL(10, 2),
    quantity INT
);
```

添加生成列：

```sql
ALTER TABLE order_items
ADD COLUMN amount DECIMAL(10, 2)
    GENERATED ALWAYS AS (price * quantity) STORED;
```

之后查询：

```sql
SELECT id, price, quantity, amount
FROM order_items;
```

就可以看到 `amount`。

---

### 注意

如果表中已经有很多资料，添加 `STORED` 生成列可能需要计算并保存每一行的结果。

所以在正式环境操作前，应该评估：

- 表的数据量；
- 是否会锁表；
- 是否会影响线上服务；
- 是否需要备份；
- 是否要在低峰时段执行；
- 是否需要先在测试环境验证。

## 4.22 常见错误整理

| 错误情况 | 可能原因 | 修正方式 |
|---|---|---|
| 手动插入生成列具体值 | 生成列由表达式计算，不应手动指定 | 省略生成列，或使用 `DEFAULT` |
| 手动更新生成列具体值 | 生成列不能像普通字段一样维护 | 更新它依赖的基础字段 |
| 表达式使用 `NOW()` | 当前时间会变化，不适合生成列 | 改用普通字段或应用程序维护 |
| 表达式使用子查询 | 生成列不适合跨表查询 | 改用视图、查询、汇总表 |
| `c` 没有如预期变化 | 可能更新的不是基础字段，或查询错资料 | 检查 `a`、`b` 是否变化 |
| 不知道 `VIRTUAL` 和 `STORED` 差异 | 一个读取时计算，一个存储结果 | 根据空间和查询频率选择 |
| 误以为生成列等于触发器 | 生成列只适合表达式计算 | 复杂逻辑用触发器或应用程序 |
| 添加生成列失败 | 表达式非法或类型不匹配 | 检查表达式、字段类型和 SQL mode |
| 查询性能不如预期 | 虚拟列未建立索引或计算成本高 | 考虑索引或改为 `STORED` |

## 4.23 写生成列时的建议习惯

### 建议一：表达式保持简单

推荐：

```sql
amount DECIMAL(10, 2)
    GENERATED ALWAYS AS (price * quantity) STORED
```

不建议把复杂业务规则都塞进去。

如果表达式太复杂，后续维护会很困难。

---

### 建议二：明确写出 `VIRTUAL` 或 `STORED`

虽然默认是 `VIRTUAL`，但建议写清楚：

```sql
c INT GENERATED ALWAYS AS (a + b) VIRTUAL
```

或：

```sql
c INT GENERATED ALWAYS AS (a + b) STORED
```

这样别人读表结构时比较清楚。

---

### 建议三：生成列名称要表达业务意义

不推荐：

```sql
c INT GENERATED ALWAYS AS (a + b)
```

如果是正式业务表，建议写成：

```sql
amount DECIMAL(10, 2)
    GENERATED ALWAYS AS (price * quantity) STORED
```

字段名应该让人一看就知道用途。

---

### 建议四：不要把所有计算都做成生成列

生成列适合稳定、简单、行内计算。

如果是以下情况，应该谨慎：

- 业务规则经常变化；
- 涉及多表；
- 涉及权限；
- 涉及流程状态；
- 涉及人工判断；
- 涉及复杂条件分支。

---

### 建议五：正式环境修改表结构前先测试

生成列属于表结构设计。

如果要对正式表执行：

```sql
ALTER TABLE ...
ADD COLUMN ... GENERATED ALWAYS AS ...
```

建议先在测试环境确认：

- 表结构是否正确；
- 旧数据是否能成功计算；
- 是否有类型转换问题；
- 查询结果是否符合预期；
- 执行时间是否可接受。

---

## 4.24 一句话对比

| 写法 / 概念 | 作用 |
|---|---|
| 普通字段 | 手动插入、手动更新 |
| 生成列 | 根据表达式自动计算 |
| `VIRTUAL` | 不存结果，读取时计算 |
| `STORED` | 存结果，插入或更新时计算 |
| `GENERATED ALWAYS AS` | 定义字段由表达式生成 |
| `DEFAULT` | 明确让生成列走自动计算 |
| 视图 | 封装查询结果 |
| 触发器 | 自动执行较复杂的数据处理逻辑 |

## 4.25 本节重点总结

本节核心是掌握生成列的三个重点。

---

### 重点一：生成列不是手动维护的字段

```sql
c INT GENERATED ALWAYS AS (a + b)
```

表示：

```text
c 的值由 a + b 自动计算
```

插入时应该写：

```sql
INSERT INTO tb1(id, a, b)
VALUES (1, 100, 200);
```

不要手动写：

```sql
INSERT INTO tb1(id, a, b, c)
VALUES (1, 100, 200, 999);
```

---

### 重点二：基础字段变化，生成列跟着变化

```sql
UPDATE tb1
SET a = 500
WHERE id = 1;
```

如果 `c = a + b`，那么 `c` 会跟着重新计算。

---

### 重点三：要分清 `VIRTUAL` 和 `STORED`

| 类型 | 核心理解 |
|---|---|
| `VIRTUAL` | 读取时计算，不额外存结果 |
| `STORED` | 插入或更新时计算，并把结果存起来 |

选择原则：

```text
计算简单、想省空间 → VIRTUAL
查询频繁、计算较重 → STORED
```

## 自测答案提示

1. 生成列是根据表达式自动计算出来的字段。
2. 普通字段需要手动插入或更新，生成列由 MySQL 根据表达式计算。
3. 表示该字段的值由 `a + b` 自动产生。
4. 因为生成列的值由数据库自动计算，不应该手动维护。
5. 因为生成列依赖基础字段，基础字段变化后，生成列会重新计算。
6. `VIRTUAL` 表示不真正储存结果，读取时计算。
7. `STORED` 表示计算结果会储存起来，插入或更新时计算。
8. 默认是 `VIRTUAL`。
9. 因为生成列适合稳定、简单、行内计算，复杂业务逻辑会增加维护成本。
10. 因为这些函数结果不稳定，不适合定义成固定的派生字段。
11. 适合同一行内的金额计算、字符串拼接、格式标准化、JSON 字段提取等。
12. 不适合跨表统计、复杂业务流程、当前时间、随机数、人工判断等。
13. 生成列是表结构的一部分；视图是封装好的查询对象。
14. 生成列适合简单表达式计算；触发器适合更复杂的自动处理逻辑。
15. 应该更新基础字段，让生成列自动重新计算。
