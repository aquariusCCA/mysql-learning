# 6 日期与时间类型

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇要解决的问题是：

> MySQL 里 `YEAR`、`DATE`、`TIME`、`DATETIME`、`TIMESTAMP` 都和时间有关，建表时到底该怎么选？尤其是 `DATETIME` 和 `TIMESTAMP`，为什么看起来一样，却经常被说成语义不同？

日期时间字段几乎所有业务系统都会遇到，例如：

- 用户生日
- 注册时间
- 登录时间
- 订单创建时间
- 订单支付时间
- 商品上架时间
- 活动开始时间
- 会议预约时间
- 账单日期
- 合约起讫日期
- 日志产生时间

这些字段表面上都叫「时间」，但它们背后的语义并不一样。

建表时真正要先分清的是：

1. 只需要「年份」吗？
2. 只需要「日期」吗？
3. 只需要「一天中的时间」或「一段时长」吗？
4. 需要完整的「日期 + 时间」吗？
5. 这个时间是否要随着时区变化而转换显示？
6. 这个字段是业务约定时间，还是系统记录时间？
7. 未来是否可能超过 `2038` 年？
8. 是否需要毫秒、微秒精度？
9. 查询时是否经常按日期范围筛选、排序、建索引？

如果只把日期时间类型理解成「能不能存时间」，很容易选错。

这一篇的目标不是让你死背格式，而是建立一套实务选型判断：

> 先判断时间字段的业务语义，再选择对应的 MySQL 时间类型。

如果只能先记一句话：

> `DATE` 存日期，`TIME` 存时间或时长，`DATETIME` 存业务上的固定日期时间，`TIMESTAMP` 存会受时区转换影响的系统时间点。

## 30 秒复习入口

- MySQL 常见日期时间类型有：`YEAR`、`DATE`、`TIME`、`DATETIME`、`TIMESTAMP`。
- `YEAR`：只存年份，范围通常是 `1901 ~ 2155`，以及 `0000`。
- 新系统中写 `YEAR` 即可，不建议写已经过时的 `YEAR(4)`。
- `DATE`：只存日期，格式是 `YYYY-MM-DD`，范围是 `1000-01-01 ~ 9999-12-31`。
- `TIME`：可以表示一天中的时间，也可以表示时间间隔，范围是 `-838:59:59 ~ 838:59:59`。
- `DATETIME`：存完整日期时间，范围大，通常不随 session 时区自动转换。
- `TIMESTAMP`：存完整日期时间，但会按 session time zone 与 UTC 互相转换。
- `TIMESTAMP` 不是保存「时区名称」或「时区文本」，它保存的是会参与时区转换的时间点。
- `DATETIME` 更适合业务约定的固定日期时间，例如会议时间、预约时间、活动开始时间。
- `TIMESTAMP` 更适合系统记录的发生时刻，例如日志时间、创建时间、更新时间，但要注意 `2038` 年范围限制。
- 现代 MySQL 中，`TIMESTAMP` 和 `DATETIME` 都可以使用 `DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP`。
- `TIME`、`DATETIME`、`TIMESTAMP` 可以写成 `TIME(fsp)`、`DATETIME(fsp)`、`TIMESTAMP(fsp)`，`fsp` 是小数秒精度，范围 `0 ~ 6`。
- 如果省略 `fsp`，默认是 `0`，也就是不保存小数秒。
- 常见毫秒精度可以用 `DATETIME(3)` 或 `TIMESTAMP(3)`。
- 插入的小数秒位数超过字段定义时，MySQL 默认会四舍五入；如果开启 `TIME_TRUNCATE_FRACTIONAL`，则会截断。
- 不建议用字符串类型保存时间，除非有非常特殊的兼容性需求。
- 不建议用 `'0000-00-00'` 代表未知日期，新系统应优先使用 `NULL` 或明确的业务状态字段。
- 查询某一天的数据时，优先写范围条件，不建议直接 `WHERE DATE(created_at) = '2025-03-07'`。
- 更推荐：`created_at >= '2025-03-07 00:00:00' AND created_at < '2025-03-08 00:00:00'`。

## 一、先讲结论

MySQL 日期时间类型的选型，不能只看「能不能存时间」。

更合理的判断顺序是：

```text
先判断语义，再判断范围，再判断时区，再判断精度。
```

### 1.1 最重要的选型表

| 需求 | 推荐类型 | 说明 |
| --- | --- | --- |
| 只存年份 | `YEAR` | 例如毕业年份、生产年份 |
| 只存日期 | `DATE` | 例如生日、账单日期、签约日期 |
| 只存一天中的时间 | `TIME` | 例如上班时间、营业开始时间 |
| 存一段时长 | `TIME` / 整数秒数 | `TIME` 可超过 24 小时，也可为负 |
| 存业务上的固定日期时间 | `DATETIME` | 例如会议时间、预约时间、活动时间 |
| 存系统记录的发生时刻 | `TIMESTAMP` / `DATETIME` | 例如 `created_at`、`updated_at`、日志时间 |
| 需要跨时区统一时间点 | `TIMESTAMP` 或 UTC `DATETIME` | 关键是团队要统一规范 |
| 需要超过 2038 年 | `DATETIME` | `TIMESTAMP` 有 2038 年范围限制 |
| 需要毫秒精度 | `DATETIME(3)` / `TIMESTAMP(3)` | `fsp = 3` 表示毫秒 |
| 需要微秒精度 | `DATETIME(6)` / `TIMESTAMP(6)` | `fsp = 6` 表示微秒 |
| 日期可能未知 | `NULL` | 不建议用 `'0000-00-00'` 当未知日期 |
| 只想存 Unix 秒数 | `BIGINT` / `INT UNSIGNED` | 仅在兼容协议、日志系统等特殊场景考虑 |

### 1.2 一个简单选型流程

```text
这个字段只需要年份吗？
  └─ 是：YEAR

这个字段只需要日期，不需要时分秒吗？
  └─ 是：DATE

这个字段只需要时分秒，或表示一段时长吗？
  └─ 是：TIME 或整数秒数

这个字段需要日期 + 时间吗？
  └─ 是：继续问
        │
        ├─ 是否是业务约定的本地日期时间？
        │     └─ 是：优先 DATETIME
        │
        ├─ 是否是系统记录的真实发生时刻？
        │     └─ 是：TIMESTAMP 或 UTC DATETIME
        │
        ├─ 是否会超过 2038 年？
        │     └─ 是：优先 DATETIME
        │
        ├─ 是否要统一存 UTC？
        │     └─ 是：TIMESTAMP + 统一 time_zone，或 DATETIME + 应用层保证 UTC
        │
        └─ 是否不确定？
              └─ 先用 DATETIME，另外明确命名和时区规范
```

### 1.3 常见业务字段选型速查

| 字段 | 推荐类型示例 | 说明 |
| --- | --- | --- |
| `birth_date` | `DATE` | 生日通常只关心哪一天 |
| `graduate_year` | `YEAR` / `SMALLINT` | 只存年份可用 `YEAR`，也可用小整数表达业务年份 |
| `business_date` | `DATE` | 营业日、账务日通常是日期语义 |
| `contract_start_date` | `DATE` | 合约起日通常不需要时分秒 |
| `open_time` | `TIME` | 营业开始时间 |
| `close_time` | `TIME` | 营业结束时间 |
| `duration` | `TIME` / `INT` | 时长若要便于计算，整数秒数也很常见 |
| `meeting_at` | `DATETIME` | 会议预约时间通常是业务约定时间 |
| `booking_at` | `DATETIME` | 预约时间通常不希望随查询时区自动变化 |
| `activity_start_at` | `DATETIME` | 活动开始时间偏业务语义 |
| `published_at` | `DATETIME` / `TIMESTAMP` | 看是业务发布时间，还是系统发布时间点 |
| `created_at` | `TIMESTAMP(3)` / `DATETIME(3)` | 两者都可，关键是统一时区规范 |
| `updated_at` | `TIMESTAMP(3)` / `DATETIME(3)` | 常配合 `ON UPDATE CURRENT_TIMESTAMP(3)` |
| `deleted_at` | `DATETIME(3)` / `TIMESTAMP(3)` | 软删除时间，未删除时可为 `NULL` |
| `last_login_at` | `TIMESTAMP(3)` / `DATETIME(3)` | 系统记录时间点 |
| `log_created_at` | `TIMESTAMP(3)` / `DATETIME(3)` | 日志时间，常需要统一 UTC |
| `expires_at` | `DATETIME` / `TIMESTAMP` | 若可能跨 2038，注意 `TIMESTAMP` 范围 |

## 二、日期与时间类型总览

MySQL 常见的日期时间类型有五种：

```text
YEAR
DATE
TIME
DATETIME
TIMESTAMP
```

它们都属于 temporal types，也就是时间相关类型。

### 2.1 类型总览表

| 类型 | 存储内容 | 常见显示格式 | 典型语义 | 是否含日期 | 是否含时间 | 是否受时区转换影响 |
| --- | --- | --- | --- | --- | --- | --- |
| `YEAR` | 年份 | `YYYY` | 哪一年 | 是，只有年 | 否 | 否 |
| `DATE` | 日期 | `YYYY-MM-DD` | 哪一天 | 是 | 否 | 否 |
| `TIME` | 时间 / 时长 | `HH:MM:SS` | 几点几分几秒，或持续多久 | 否 | 是 | 否 |
| `DATETIME` | 日期 + 时间 | `YYYY-MM-DD HH:MM:SS` | 固定日期时间 | 是 | 是 | 通常否 |
| `TIMESTAMP` | 日期 + 时间 | `YYYY-MM-DD HH:MM:SS` | 真实时间点在当前时区下的显示 | 是 | 是 | 是 |

### 2.2 范围与存储空间速查

| 类型 | 范围 | 现代 MySQL 常见存储空间 |
| --- | --- | --- |
| `YEAR` | `1901 ~ 2155`，以及 `0000` | 1 byte |
| `DATE` | `1000-01-01 ~ 9999-12-31` | 3 bytes |
| `TIME` | `-838:59:59 ~ 838:59:59` | 3 bytes + 小数秒空间 |
| `DATETIME` | `1000-01-01 00:00:00 ~ 9999-12-31 23:59:59` | 5 bytes + 小数秒空间 |
| `TIMESTAMP` | `1970-01-01 00:00:01 UTC ~ 2038-01-19 03:14:07 UTC` | 4 bytes + 小数秒空间 |

注意：

- 这里的存储空间是现代 MySQL 版本中常见理解。
- `TIME`、`DATETIME`、`TIMESTAMP` 如果使用小数秒精度，会额外占用 `0 ~ 3` bytes。
- 实务选型时，不要只为了省 1 byte 就选错语义。

### 2.3 最容易误解的点

日期时间类型最容易误解的地方有五个：

1. `TIME` 不只是一天中的时间，也可以表示时长。
2. `TIMESTAMP` 不是 Unix timestamp 整数。
3. `TIMESTAMP` 不保存时区名称，但会根据 session `time_zone` 做转换。
4. `DATETIME` 和 `TIMESTAMP` 显示格式相同，不代表语义相同。
5. `created_at` / `updated_at` 不一定只能用 `TIMESTAMP`，现代 MySQL 中 `DATETIME` 也可以自动初始化和自动更新。

## 三、`YEAR`：只存年份

`YEAR` 用来保存年份。

常见写法：

```sql
graduate_year YEAR
```

### 3.1 核心规则

`YEAR` 的核心特点：

- 占用空间小，通常是 1 byte。
- 显示格式是 `YYYY`。
- 范围是 `1901 ~ 2155`，以及特殊值 `0000`。
- 新系统建议写 `YEAR`，不要写 `YEAR(4)`。
- 两位年份输入容易造成歧义，不建议依赖。

### 3.2 示例

```sql
CREATE TABLE product_model (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    model_year YEAR NOT NULL
);
```

```sql
INSERT INTO product_model (name, model_year)
VALUES
    ('A100', 2024),
    ('B200', 2025);
```

### 3.3 `YEAR(4)` 不建议继续写

旧资料中可能会看到：

```sql
model_year YEAR(4)
```

在现代 MySQL 中，新系统直接写：

```sql
model_year YEAR
```

`YEAR(4)` 这种显式 display width 写法已经不建议继续依赖。

### 3.4 两位年份的坑

旧系统里可能有人插入：

```sql
INSERT INTO product_model (name, model_year)
VALUES ('Old Product', '69');
```

MySQL 对两位年份有转换规则，例如：

- `'00' ~ '69'` 可能被解释为 `2000 ~ 2069`。
- `'70' ~ '99'` 可能被解释为 `1970 ~ 1999`。

这种规则很容易造成误会。

所以新系统建议：

```text
年份一律使用 4 位数。
```

不要让数据库帮你猜世纪。

### 3.5 什么时候适合用 `YEAR`

适合：

- 毕业年份
- 生产年份
- 车型年份
- 财年编号，如果真的只需要年份

不太适合：

- 生日：应该用 `DATE`。
- 入职日期：通常用 `DATE`。
- 商品上架时间：通常用 `DATETIME`。
- 需要超过 `2155` 年的长期日期：不要用 `YEAR`。

### 3.6 `YEAR` vs `SMALLINT`

有些团队不喜欢 `YEAR`，会用：

```sql
graduate_year SMALLINT UNSIGNED
```

这也是可以的，尤其当年份本质上只是一个业务数字时。

简单判断：

| 场景 | 可以考虑 |
| --- | --- |
| 希望数据库类型直接表达年份语义 | `YEAR` |
| 希望更像普通数字、范围更弹性 | `SMALLINT UNSIGNED` |
| 未来可能扩展到月日 | `DATE` |

## 四、`DATE`：只存日期

`DATE` 用来保存日期，不保存时分秒。

常见写法：

```sql
birth_date DATE
```

### 4.1 核心规则

`DATE` 的核心特点：

- 格式是 `YYYY-MM-DD`。
- 范围是 `1000-01-01 ~ 9999-12-31`。
- 不包含时分秒。
- 不做时区转换。
- 占用空间通常是 3 bytes。

### 4.2 示例

```sql
CREATE TABLE user_profile (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    birth_date DATE NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
);
```

```sql
INSERT INTO user_profile (username, birth_date)
VALUES ('Tom', '2000-05-20');
```

### 4.3 什么时候该选 `DATE`

如果业务只关心「哪一天」，就应该优先考虑 `DATE`。

适合：

- 生日
- 入职日期
- 离职日期
- 账单日期
- 交易日期
- 签约日期
- 合约开始日
- 合约结束日
- 营业日
- 统计日期

### 4.4 为什么生日通常不用 `DATETIME`

生日通常问的是：

```text
你是哪一天出生？
```

而不是：

```text
你在那一天的几点几分几秒出生？
```

所以：

```sql
birth_date DATE
```

通常比：

```sql
birth_at DATETIME
```

更清楚。

除非你的业务真的需要出生时刻，例如命理、医学记录、出生证明等场景，才需要考虑 `DATETIME`。

### 4.5 日期字段不要用字符串存

不推荐：

```sql
birth_date VARCHAR(10)
```

原因：

- 数据库不会严格按照日期语义处理。
- 容易出现不统一格式，例如 `2025/03/07`、`2025-3-7`、`07-03-2025`。
- 排序可能变成字符串排序。
- 日期函数使用麻烦。
- 范围查询和索引设计容易变差。

推荐：

```sql
birth_date DATE
```

### 4.6 未知日期不要随便用 `'0000-00-00'`

旧系统中可能看到：

```sql
birth_date DATE NOT NULL DEFAULT '0000-00-00'
```

新系统不建议这样设计。

更推荐：

```sql
birth_date DATE NULL
```

或根据业务再加状态字段：

```sql
birth_date DATE NULL,
birth_date_status TINYINT NOT NULL DEFAULT 0
```

例如：

| `birth_date_status` | 含义 |
| --- | --- |
| `0` | 未填写 |
| `1` | 已填写 |
| `2` | 不愿提供 |
| `3` | 资料待确认 |

这样比用 `'0000-00-00'` 更清楚。

## 五、`TIME`：时间或时长

`TIME` 表示时间值，但它不只表示「一天中的几点几分几秒」。

它也可以表示：

```text
经过多久、持续多久、相差多久。
```

### 5.1 核心规则

`TIME` 的核心特点：

- 常见显示格式是 `HH:MM:SS`。
- 大小时数可能显示为 `HHH:MM:SS`。
- 范围是 `-838:59:59 ~ 838:59:59`。
- 可以超过 24 小时。
- 可以是负数。
- 可以使用小数秒精度，例如 `TIME(3)`、`TIME(6)`。

### 5.2 为什么 `TIME` 可以超过 24 小时

因为 `TIME` 不只是表示钟表时间。

它也可以表示：

- 一段持续时间
- 两个事件之间的间隔
- 提前或延后的偏移量

所以：

```text
62:30:00
```

在 `TIME` 中是有意义的。

它可以表示：

```text
62 小时 30 分钟
```

而不是「一天中的 62 点」。

### 5.3 示例：一天中的营业时间

```sql
CREATE TABLE store_business_hours (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    store_id BIGINT UNSIGNED NOT NULL,
    weekday TINYINT UNSIGNED NOT NULL,
    open_time TIME NOT NULL,
    close_time TIME NOT NULL,
    CHECK (weekday BETWEEN 1 AND 7)
);
```

```sql
INSERT INTO store_business_hours (store_id, weekday, open_time, close_time)
VALUES (1, 1, '09:00:00', '18:00:00');
```

### 5.4 示例：持续时长

```sql
CREATE TABLE video_info (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    duration TIME NOT NULL
);
```

```sql
INSERT INTO video_info (title, duration)
VALUES ('MySQL Tutorial', '02:15:30');
```

如果视频可能非常长，或你更重视计算便利，也可以用整数秒数：

```sql
duration_seconds INT UNSIGNED NOT NULL
```

### 5.5 `TIME` vs 整数秒数

| 需求 | 推荐方向 |
| --- | --- |
| 希望直接看到 `HH:MM:SS` | `TIME` |
| 经常做加总、平均、比较、计算 | 整数秒数，如 `INT UNSIGNED` |
| 时长可能超过 `838:59:59` | 整数秒数 |
| 需要和 MySQL 时间函数配合 | `TIME` |
| 需要表达负时长 | `TIME` 或有符号整数 |

### 5.6 输入简写的坑

`TIME` 有些简写格式容易误会。

例如：

```sql
INSERT INTO t (duration) VALUES ('11:12');
```

带冒号时，可能被理解为：

```text
11:12:00
```

也就是 11 点 12 分 0 秒。

但如果写成：

```sql
INSERT INTO t (duration) VALUES ('1112');
```

MySQL 可能按「右边两位是秒」的思路解释成：

```text
00:11:12
```

所以实务上建议：

```text
TIME 值尽量写完整格式：HH:MM:SS。
```

不要让数据库帮你猜。

---

## 六、`DATETIME`：固定的日期时间

`DATETIME` 用来保存完整的日期时间。

常见格式：

```text
YYYY-MM-DD HH:MM:SS
```

例如：

```sql
'2025-03-07 14:30:00'
```

### 6.1 核心规则

`DATETIME` 的核心特点：

- 同时包含日期和时间。
- 范围很大：`1000-01-01 00:00:00 ~ 9999-12-31 23:59:59`。
- 通常不因为 session `time_zone` 改变而自动换算显示。
- 可以使用小数秒精度，例如 `DATETIME(3)`、`DATETIME(6)`。
- 现代 MySQL 中也可以使用 `DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP`。

### 6.2 怎么理解 `DATETIME`

可以把 `DATETIME` 理解成：

```text
保存一个日历上的日期时间值。
```

例如：

```text
2025-03-07 14:30:00
```

它更像是在说：

```text
业务上约定的时间就是 2025 年 3 月 7 日 14 点 30 分。
```

你写进去这个值，之后查询出来通常还是这个值本身。

### 6.3 适合场景

`DATETIME` 适合保存业务上的固定日期时间，例如：

- 会议开始时间
- 医院预约时间
- 餐厅订位时间
- 活动开始时间
- 活动结束时间
- 商品上架时间
- 商品下架时间
- 合约签署时间
- 业务系统中的计划执行时间

这些字段通常更像「业务约定的时间」，不一定希望因为数据库 session 时区不同而自动改变显示值。

### 6.4 示例：预约时间

```sql
CREATE TABLE appointment (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT UNSIGNED NOT NULL,
    appointment_at DATETIME NOT NULL,
    note VARCHAR(500),
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);
```

### 6.5 `DATETIME(3)` 是什么

`DATETIME(3)` 表示保留 3 位小数秒，也就是毫秒。

例如：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

可能保存：

```text
2025-03-07 14:30:00.123
```

常见选择：

| 写法 | 精度 | 示例 |
| --- | --- | --- |
| `DATETIME` / `DATETIME(0)` | 秒 | `2025-03-07 14:30:00` |
| `DATETIME(3)` | 毫秒 | `2025-03-07 14:30:00.123` |
| `DATETIME(6)` | 微秒 | `2025-03-07 14:30:00.123456` |

实务上：

- 普通业务系统：`DATETIME` 或 `DATETIME(3)` 常见。
- 需要和 Java、前端时间戳毫秒对齐：`DATETIME(3)` 常见。
- 日志、交易、追踪系统需要更细精度：可考虑 `DATETIME(6)`。

---

## 七、`TIMESTAMP`：会受时区转换影响的时间点

`TIMESTAMP` 也能保存完整的日期时间，显示格式看起来和 `DATETIME` 很像。

常见格式也是：

```text
YYYY-MM-DD HH:MM:SS
```

但它和 `DATETIME` 最大的不同在于：

```text
TIMESTAMP 会根据当前 session time_zone 与 UTC 做转换。
```

### 7.1 核心规则

`TIMESTAMP` 的核心特点：

- 同时包含日期和时间。
- 范围相对较小：`1970-01-01 00:00:01 UTC ~ 2038-01-19 03:14:07 UTC`。
- 存储时会从当前 session 时区转换成 UTC。
- 取出时会从 UTC 转换成当前 session 时区。
- 可以使用小数秒精度，例如 `TIMESTAMP(3)`、`TIMESTAMP(6)`。
- 常用于系统记录时间、日志时间、创建时间、更新时间。

### 7.2 `TIMESTAMP` 不是保存时区

这是非常重要的一点。

`TIMESTAMP` 不是保存下面这种东西：

```text
2025-03-07 14:30:00 Asia/Taipei
```

也不是保存：

```text
2025-03-07 14:30:00 +08:00
```

它更像是保存一个「真实发生时刻」，然后在不同 session `time_zone` 下显示成不同本地时间。

也就是说：

```text
TIMESTAMP 保存的不是时区名称，而是会参与时区转换的时间点。
```

### 7.3 示例：创建时间与更新时间

```sql
CREATE TABLE user_account (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);
```

这类写法常用于：

- 记录资料创建时间
- 记录资料最后修改时间
- 记录系统事件发生时间

### 7.4 `TIMESTAMP` 的 2038 年问题

`TIMESTAMP` 的范围到：

```text
2038-01-19 03:14:07 UTC
```

所以如果你的字段可能保存 `2038` 年之后的时间，例如：

- 长期合约到期时间
- 保险到期时间
- 未来预约时间
- 证件有效期限
- 长期任务排程

就要特别小心。

这种情况通常更适合：

```sql
expires_at DATETIME NOT NULL
```

而不是：

```sql
expires_at TIMESTAMP NOT NULL
```

### 7.5 什么时候适合 `TIMESTAMP`

适合：

- 系统日志时间
- 创建时间
- 更新时间
- 最后登录时间
- API 请求时间
- 事件发生时间
- 需要随着时区转换显示的时间点

不太适合：

- 生日
- 只需要日期的字段
- 2038 年之后的未来时间
- 不希望受 session 时区影响的业务预约时间
- 需要保留「原始本地时间」语义的字段

---

## 八、`DATETIME` vs `TIMESTAMP`

这是本篇最重要的部分。

两者显示格式很像，但语义不同。

### 8.1 核心比较表

| 对比项 | `DATETIME` | `TIMESTAMP` |
| --- | --- | --- |
| 保存内容 | 日期 + 时间 | 日期 + 时间 |
| 常见显示格式 | `YYYY-MM-DD HH:MM:SS` | `YYYY-MM-DD HH:MM:SS` |
| 范围 | `1000 ~ 9999` 年 | `1970 ~ 2038` 年 |
| 是否做时区转换 | 通常不做 | 会做 |
| 存储逻辑 | 保存日期时间值本身 | 存储时转 UTC，取出时转当前时区 |
| 是否保存时区名称 | 否 | 否 |
| 适合语义 | 业务固定时间 | 系统发生时刻 |
| 常见字段 | `meeting_at`、`booking_at`、`start_at` | `created_at`、`updated_at`、`log_at` |
| 跨 2038 年 | 适合 | 不适合 |
| 自动初始化 / 自动更新 | 支持 | 支持 |

### 8.2 用一句话区分

可以这样记：

```text
DATETIME：我就是这个日期时间。
TIMESTAMP：我是一个真实时间点，会按当前时区显示。
```

### 8.3 举例：会议时间

假设一个台湾本地系统预约会议：

```text
2025-03-07 14:30:00
```

业务人员通常希望看到的就是：

```text
2025 年 3 月 7 日下午 2:30
```

这种字段更像「业务约定时间」。

可以用：

```sql
meeting_at DATETIME NOT NULL
```

### 8.4 举例：系统日志时间

假设系统记录一次 API 请求发生时间。

这个时间更像：

```text
某个真实发生的瞬间。
```

如果系统要跨时区显示，或数据库统一按 UTC 管理，可以考虑：

```sql
request_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

### 8.5 `created_at` / `updated_at` 到底用哪个

这是实务上最常见的问题。

答案不是绝对的。

`created_at` / `updated_at` 可以用 `TIMESTAMP`，也可以用 `DATETIME`。

关键是团队要统一规范。

#### 方案 A：使用 `TIMESTAMP`

```sql
created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

优点：

- 适合表达系统发生时刻。
- 会参与时区转换。
- 存储空间较小。
- 和 `CURRENT_TIMESTAMP` 搭配自然。

注意：

- 有 2038 年限制。
- session `time_zone` 不一致时，显示值可能不同。
- 团队必须清楚它不是保存「原样日期时间」。

#### 方案 B：使用 `DATETIME`

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

优点：

- 范围大。
- 不会因为 session `time_zone` 改变而自动换算显示。
- 对业务人员和开发者比较直观。
- 也支持自动初始化和自动更新。

注意：

- 如果你想表达 UTC 时间，需要在应用层或连接层明确保证写入的是 UTC。
- 字段命名最好表达清楚，例如 `created_at_utc`。

### 8.6 我的实务建议

如果是普通后台管理系统、单一地区业务，例如台湾内部系统：

```text
业务时间：优先 DATETIME
系统记录时间：DATETIME(3) 或 TIMESTAMP(3) 都可以，但团队要统一
```

如果是跨地区、跨时区、多国家系统：

```text
真实发生时刻：统一 UTC 保存
展示时：再按用户时区转换
```

可以选择：

```sql
created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

并确保连接时区统一。

也可以选择：

```sql
created_at_utc DATETIME(3) NOT NULL
```

但要由应用层保证写入 UTC。

关键不是某个类型绝对正确，而是：

```text
类型语义 + 时区规范 + 应用层处理 必须一致。
```

## 九、小数秒精度：`TIME(fsp)`、`DATETIME(fsp)`、`TIMESTAMP(fsp)`

MySQL 支持时间类型的小数秒精度。

可使用的类型包括：

```sql
TIME(fsp)
DATETIME(fsp)
TIMESTAMP(fsp)
```

其中 `fsp` 表示 fractional seconds precision，也就是小数秒精度。

### 9.1 `fsp` 的范围

`fsp` 的范围是：

```text
0 ~ 6
```

含义：

| 写法 | 含义 | 示例 |
| --- | --- | --- |
| `DATETIME` | 等同 `DATETIME(0)`，不保存小数秒 | `2025-03-07 14:30:00` |
| `DATETIME(0)` | 不保存小数秒 | `2025-03-07 14:30:00` |
| `DATETIME(1)` | 保存 1 位小数秒 | `2025-03-07 14:30:00.1` |
| `DATETIME(2)` | 保存 2 位小数秒 | `2025-03-07 14:30:00.12` |
| `DATETIME(3)` | 保存毫秒 | `2025-03-07 14:30:00.123` |
| `DATETIME(6)` | 保存微秒 | `2025-03-07 14:30:00.123456` |

### 9.2 省略 `fsp` 时默认是 0

如果写：

```sql
created_at DATETIME
```

基本可以理解为：

```sql
created_at DATETIME(0)
```

也就是不保存小数秒。

如果你希望保存毫秒，应写：

```sql
created_at DATETIME(3)
```

或：

```sql
created_at TIMESTAMP(3)
```

同时默认值也要对应：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

不要只写：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP
```

虽然有些情况下可以工作，但表达不如 `CURRENT_TIMESTAMP(3)` 清楚。

### 9.3 小数秒超出时会怎样

例如字段是：

```sql
created_at DATETIME(2)
```

插入：

```sql
'2025-03-07 14:30:00.777'
```

MySQL 默认会进行四舍五入，可能保存为：

```text
2025-03-07 14:30:00.78
```

如果开启 `TIME_TRUNCATE_FRACTIONAL` SQL mode，则会改成截断，可能保存为：

```text
2025-03-07 14:30:00.77
```

所以如果业务对时间精度敏感，不要让数据库隐式处理得太随意。

建议：

```text
字段精度、应用层时间精度、接口输出精度要统一。
```

### 9.4 常见选择建议

| 场景 | 建议 |
| --- | --- |
| 普通业务日期时间 | `DATETIME` |
| 普通创建 / 更新时间 | `DATETIME(3)` 或 `TIMESTAMP(3)` |
| 和前端毫秒时间戳对齐 | `DATETIME(3)` / `TIMESTAMP(3)` |
| 日志追踪、交易流水 | `DATETIME(6)` / `TIMESTAMP(6)` |
| 不需要小数秒 | 不要随便用 `(6)` |

## 十、自动初始化与自动更新时间

在现代 MySQL 中，`TIMESTAMP` 和 `DATETIME` 都支持自动初始化和自动更新。

常见语法：

```sql
DEFAULT CURRENT_TIMESTAMP
ON UPDATE CURRENT_TIMESTAMP
```

也可以带小数秒：

```sql
DEFAULT CURRENT_TIMESTAMP(3)
ON UPDATE CURRENT_TIMESTAMP(3)
```

### 10.1 创建时间

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

含义：

```text
插入数据时，如果没有指定 created_at，就自动使用当前时间。
```

### 10.2 更新时间

```sql
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

含义：

```text
插入时给当前时间；之后这一行其他字段发生更新时，自动更新为当前时间。
```

### 10.3 完整示例

```sql
CREATE TABLE article (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    content TEXT NOT NULL,
    published_at DATETIME NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);
```

### 10.4 `CURRENT_TIMESTAMP`、`NOW()`、`LOCALTIME` 的关系

在字段定义中，下面这些通常可以视为同类写法：

```sql
CURRENT_TIMESTAMP
CURRENT_TIMESTAMP()
NOW()
LOCALTIME
LOCALTIME()
LOCALTIMESTAMP
LOCALTIMESTAMP()
```

不过为了可读性和习惯统一，建表时最推荐写：

```sql
CURRENT_TIMESTAMP
```

如果需要毫秒：

```sql
CURRENT_TIMESTAMP(3)
```

### 10.5 不要把自动更新时间滥用到业务时间

适合自动更新：

```sql
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

不适合随便自动更新：

```sql
paid_at DATETIME(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

为什么？

因为 `paid_at` 表示付款发生时间，不应该因为修改订单备注、收货地址、状态字段就自动改变。

所以：

| 字段 | 是否适合 `ON UPDATE CURRENT_TIMESTAMP` |
| --- | --- |
| `updated_at` | 适合 |
| `modified_at` | 适合 |
| `paid_at` | 不适合自动更新 |
| `shipped_at` | 不适合自动更新 |
| `cancelled_at` | 不适合自动更新 |
| `deleted_at` | 通常由业务逻辑显式设置 |

## 十一、时区设计：最容易踩坑的地方

日期时间字段真正复杂的地方，不是格式，而是时区。

### 11.1 先区分两种时间

时间字段可以粗略分成两种：

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 本地业务时间 | 业务上约定的某个当地日期时间 | 台湾门诊预约：2025-03-07 14:30 |
| 真实发生时刻 | 世界时间轴上的某个瞬间 | 某次 API 请求实际发生时刻 |

这两种时间的存法可能不同。

### 11.2 本地业务时间

例如台湾医院预约：

```text
2025-03-07 14:30:00
```

这通常表示：

```text
台湾当地时间 2025 年 3 月 7 日 14:30
```

这种字段可以用：

```sql
appointment_at DATETIME NOT NULL
```

如果业务跨国家，还可以额外保存时区：

```sql
appointment_at DATETIME NOT NULL,
appointment_timezone VARCHAR(64) NOT NULL
```

例如：

```text
appointment_at = 2025-03-07 14:30:00
appointment_timezone = Asia/Taipei
```

这样可以保留「原始预约地的当地时间」。

### 11.3 真实发生时刻

例如系统日志：

```text
用户在某个瞬间发起请求。
```

这种时间更适合统一成 UTC 管理。

可以选择：

```sql
request_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

也可以选择：

```sql
request_at_utc DATETIME(3) NOT NULL
```

但如果使用 `DATETIME` 保存 UTC，必须由应用层保证写入的是 UTC。

### 11.4 不要混用时区规范

最危险的是同一系统里混着来：

- 有些表用台湾时间写 `DATETIME`。
- 有些表用 UTC 写 `DATETIME`。
- 有些表用 `TIMESTAMP`，但连接时区不固定。
- Java 应用、数据库服务器、Linux 系统时区各不相同。
- 前端又传毫秒时间戳。

这种情况下，时间错 8 小时、错 1 天、跨日统计错误，都会很常见。

建议团队明确规定：

1. 数据库连接 `time_zone` 是什么？
2. 系统记录时间是否统一 UTC？
3. 业务预约时间是否保存当地时间？
4. API 输出给前端时是否带时区？
5. Java 后端使用 `LocalDateTime`、`OffsetDateTime`、`Instant` 的规则是什么？

## 十二、日期时间查询与索引写法

日期时间字段经常会参与查询。

例如：

- 查询今天订单
- 查询本月交易
- 查询最近 7 天日志
- 按创建时间排序
- 按日期统计数量

这里最重要的是：

```text
尽量让条件直接作用在字段本身，不要随便用函数包住字段。
```

### 12.1 不推荐写法

查询某一天的数据，很多初学者会写：

```sql
SELECT *
FROM orders
WHERE DATE(created_at) = '2025-03-07';
```

这看起来直观，但问题是：

```text
DATE(created_at) 对字段做了函数处理，可能影响索引使用。
```

### 12.2 推荐写法

更推荐写成范围查询：

```sql
SELECT *
FROM orders
WHERE created_at >= '2025-03-07 00:00:00'
  AND created_at <  '2025-03-08 00:00:00';
```

这样条件直接比较 `created_at` 字段本身，更利于索引。

### 12.3 查询某个月

不推荐：

```sql
SELECT *
FROM orders
WHERE DATE_FORMAT(created_at, '%Y-%m') = '2025-03';
```

推荐：

```sql
SELECT *
FROM orders
WHERE created_at >= '2025-03-01 00:00:00'
  AND created_at <  '2025-04-01 00:00:00';
```

### 12.4 半开区间更安全

推荐使用：

```sql
created_at >= start_time
AND created_at < end_time
```

而不是：

```sql
created_at BETWEEN start_time AND end_time
```

原因是 `BETWEEN` 包含右边界。

如果你写：

```sql
WHERE created_at BETWEEN '2025-03-07 00:00:00'
                     AND '2025-03-07 23:59:59'
```

可能会漏掉：

```text
2025-03-07 23:59:59.123
```

尤其是字段用了 `DATETIME(3)` 或 `TIMESTAMP(3)` 时。

所以更稳的是：

```sql
WHERE created_at >= '2025-03-07 00:00:00'
  AND created_at <  '2025-03-08 00:00:00'
```

### 12.5 常见索引设计

如果经常按创建时间查询：

```sql
CREATE INDEX idx_orders_created_at ON orders (created_at);
```

如果经常查某个用户的订单并按时间排序：

```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);
```

如果经常查某个状态下最近订单：

```sql
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
```

重点：

```text
索引字段顺序要跟查询条件匹配，不是看到时间字段就单独建一个索引。
```

## 十三、完整建表示例

下面用几个常见业务表串起来看。

### 13.1 用户表

```sql
CREATE TABLE user_account (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    birth_date DATE NULL,
    last_login_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_user_account_username (username),
    KEY idx_user_account_created_at (created_at)
);
```

说明：

- `birth_date`：生日只用 `DATE`。
- `last_login_at`：登录时间可以用 `DATETIME(3)`；如果团队统一 UTC，也可以用 `TIMESTAMP(3)`。
- `created_at` / `updated_at`：这里选择 `DATETIME(3)`，语义直观且范围大。

### 13.2 订单表

```sql
CREATE TABLE orders (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    order_no VARCHAR(32) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    status TINYINT UNSIGNED NOT NULL,
    paid_at DATETIME(3) NULL,
    shipped_at DATETIME(3) NULL,
    cancelled_at DATETIME(3) NULL,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_orders_order_no (order_no),
    KEY idx_orders_user_created (user_id, created_at),
    KEY idx_orders_status_created (status, created_at)
);
```

说明：

- `paid_at`：付款时间由付款成功事件写入，不应该自动更新。
- `shipped_at`：出货时间由出货业务写入。
- `cancelled_at`：取消时间由取消业务写入。
- `updated_at`：表示这一行资料最后更新时间，适合自动更新。

### 13.3 预约表

```sql
CREATE TABLE appointment (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT UNSIGNED NOT NULL,
    appointment_at DATETIME NOT NULL,
    appointment_timezone VARCHAR(64) NOT NULL DEFAULT 'Asia/Taipei',
    status TINYINT UNSIGNED NOT NULL DEFAULT 0,
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    KEY idx_appointment_user_time (user_id, appointment_at),
    KEY idx_appointment_time (appointment_at)
);
```

说明：

- `appointment_at` 保存预约地的本地日期时间。
- `appointment_timezone` 保存预约地时区。
- 对跨地区预约系统，这比只存一个没有语义说明的时间值更清楚。

### 13.4 日志表

```sql
CREATE TABLE api_request_log (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    request_id VARCHAR(64) NOT NULL,
    user_id BIGINT UNSIGNED NULL,
    path VARCHAR(255) NOT NULL,
    status_code SMALLINT UNSIGNED NOT NULL,
    request_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    KEY idx_api_request_log_request_at (request_at),
    KEY idx_api_request_log_user_request_at (user_id, request_at)
);
```

说明：

- 日志时间更像真实发生时刻。
- 使用 `TIMESTAMP(3)` 可以表达毫秒级系统事件时间。
- 但要注意连接时区设置，并确认 `2038` 范围是否可接受。

## 十四、Java 后端中的对应思路

如果你使用 Java，建议优先使用 `java.time` 包，而不是旧的 `java.util.Date`、`java.sql.Date` 作为业务层核心类型。

### 14.1 常见对应关系

| MySQL 类型 | Java 常见类型 | 说明 |
| --- | --- | --- |
| `DATE` | `LocalDate` | 只有日期，没有时间 |
| `TIME` | `LocalTime` / `Duration` | 一天中的时间可用 `LocalTime`；时长可考虑 `Duration` 或秒数 |
| `DATETIME` | `LocalDateTime` | 没有时区信息的日期时间 |
| `TIMESTAMP` | `Instant` / `OffsetDateTime` / `LocalDateTime` | 要看 JDBC、框架和时区策略 |
| `YEAR` | `Year` / `Integer` | 实务中常用 `Integer` 更简单 |

### 14.2 不要混淆 `LocalDateTime` 和真实时间点

`LocalDateTime` 本身不带时区。

它表示：

```text
某个本地日期时间
```

例如：

```text
2025-03-07 14:30:00
```

但它没有告诉你这是：

- 台湾时间
- 日本时间
- UTC 时间
- 美国纽约时间

所以如果你处理的是跨时区的真实时间点，最好在应用层明确使用：

- `Instant`
- `OffsetDateTime`
- `ZonedDateTime`

然后在数据库层配合统一的时区规范。

### 14.3 MyBatis / JPA 中的实务建议

普通业务系统可以这样思考：

```text
DATE       -> LocalDate
DATETIME   -> LocalDateTime
TIME       -> LocalTime
时间点 UTC -> Instant / OffsetDateTime，再按团队规范入库
```

如果数据库字段是 `TIMESTAMP`，一定要确认：

1. MySQL session `time_zone`。
2. JDBC 连接参数。
3. JVM 默认时区。
4. 应用层使用的 Java 时间类型。
5. API 输出给前端的格式。

否则很容易出现：

```text
数据库看是 10:00，Java 读出来变 18:00，前端又显示成另一个时间。
```

## 十五、常见混淆点

### 15.1 `TIMESTAMP` 是不是 Unix timestamp？

不是。

MySQL 的 `TIMESTAMP` 是日期时间类型，显示形式类似：

```text
2025-03-07 14:30:00
```

Unix timestamp 通常是整数，例如：

```text
1741329000
```

不要因为名字里都有 timestamp 就混为一谈。

### 15.2 `DATETIME` 有没有时区？

`DATETIME` 本身不保存时区，也通常不做自动时区转换。

它只是保存：

```text
YYYY-MM-DD HH:MM:SS
```

所以如果你把 UTC 时间写入 `DATETIME`，它不会自己知道那是 UTC。

你必须靠：

- 字段命名，例如 `created_at_utc`
- 团队规范
- 应用层转换
- API 文档

来保证语义清楚。

### 15.3 `TIMESTAMP` 会保存时区名称吗？

不会。

`TIMESTAMP` 不会保存 `Asia/Taipei`、`UTC`、`+08:00` 这类时区名称。

它会根据 session `time_zone` 做转换，但不是把时区本身存进去。

### 15.4 `DATETIME` 和 `TIMESTAMP` 谁更好？

没有绝对谁更好。

要看语义：

| 需求 | 更倾向 |
| --- | --- |
| 固定业务日期时间 | `DATETIME` |
| 真实发生时间点 | `TIMESTAMP` 或 UTC `DATETIME` |
| 需要超过 2038 年 | `DATETIME` |
| 不想受 session 时区影响 | `DATETIME` |
| 想利用时区转换机制 | `TIMESTAMP` |

### 15.5 `TIME` 只能表示一天中的时间吗？

不是。

`TIME` 可以表示：

- 一天中的时间，例如 `09:30:00`
- 持续时间，例如 `36:00:00`
- 时间差，例如 `-02:15:00`

所以它的范围才会超过 24 小时。

### 15.6 可以用 `VARCHAR` 存日期时间吗？

一般不建议。

除非你保存的是：

- 外部系统原始报文
- 用户输入的原始文本
- 不能解析的历史脏数据
- 特殊格式日志文本

否则业务字段应使用日期时间类型。

### 15.7 可以用 `INT` / `BIGINT` 存 Unix timestamp 吗？

可以，但不是默认首选。

适合场景：

- 与外部协议强绑定。
- 日志系统要求整数时间戳。
- 需要纳秒、毫秒等特殊精度且已有统一规范。
- 大数据链路或消息系统统一用 epoch milliseconds。

不适合普通业务表的原因：

- 可读性差。
- MySQL 日期函数使用不直观。
- 容易搞混秒、毫秒、微秒。
- 查询调试不方便。

普通业务表中，优先考虑 `DATE`、`DATETIME`、`TIMESTAMP`。

### 15.8 `BETWEEN` 查询日期范围安全吗？

要小心。

如果字段有小数秒，下面写法可能漏数据：

```sql
WHERE created_at BETWEEN '2025-03-07 00:00:00'
                     AND '2025-03-07 23:59:59'
```

更推荐半开区间：

```sql
WHERE created_at >= '2025-03-07 00:00:00'
  AND created_at <  '2025-03-08 00:00:00'
```

## 十六、常见错误写法与改法

### 16.1 用字符串保存生日

不推荐：

```sql
birth_date VARCHAR(10)
```

推荐：

```sql
birth_date DATE
```

### 16.2 用 `DATETIME` 保存只需要日期的字段

不推荐：

```sql
bill_date DATETIME
```

如果账单只关心哪一天，推荐：

```sql
bill_date DATE
```

### 16.3 用 `TIMESTAMP` 保存长期未来时间

不推荐：

```sql
contract_expire_at TIMESTAMP
```

如果可能超过 2038，推荐：

```sql
contract_expire_at DATETIME
```

### 16.4 付款时间自动更新

不推荐：

```sql
paid_at DATETIME ON UPDATE CURRENT_TIMESTAMP
```

推荐：

```sql
paid_at DATETIME(3) NULL
```

付款成功时由业务代码显式写入：

```sql
UPDATE orders
SET paid_at = CURRENT_TIMESTAMP(3),
    status = 2
WHERE id = ?;
```

### 16.5 用函数包住索引字段查询日期

不推荐：

```sql
WHERE DATE(created_at) = '2025-03-07'
```

推荐：

```sql
WHERE created_at >= '2025-03-07 00:00:00'
  AND created_at <  '2025-03-08 00:00:00'
```

### 16.6 用 `'0000-00-00'` 表示未知

不推荐：

```sql
birth_date DATE NOT NULL DEFAULT '0000-00-00'
```

推荐：

```sql
birth_date DATE NULL
```

或：

```sql
birth_date DATE NULL,
birth_date_status TINYINT NOT NULL DEFAULT 0
```

## 十八、一句话抓核心

日期时间类型的选择，不是看它们都能不能「存时间」，而是先分清：

```text
你存的是年份、日期、时长、业务固定时间，还是会参与时区转换的真实时间点。
```

最实用的记法是：

```text
YEAR：只存年份。
DATE：只存日期。
TIME：存时间或时长。
DATETIME：存固定的业务日期时间。
TIMESTAMP：存会按时区转换显示的系统时间点。
```

## 十九、本篇最终选型口诀

```text
只要年份，用 YEAR。
只要日期，用 DATE。
只要时间或时长，用 TIME。
业务约定时间，优先 DATETIME。
系统发生时刻，可用 TIMESTAMP 或 UTC DATETIME。
需要毫秒，加 (3)。
需要微秒，加 (6)。
超过 2038，避开 TIMESTAMP。
未知日期，用 NULL，不要用 0000-00-00。
日期范围查询，用半开区间，不要随便 DATE(column)。
```
