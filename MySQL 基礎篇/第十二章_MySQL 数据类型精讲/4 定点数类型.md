# 4 定点数类型

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇要解决的问题是：

> 建表时，遇到金额、余额、价格、汇率、税率这类「必须精确」的小数字段，为什么应该优先考虑 `DECIMAL`？`DECIMAL(M,D)` 里的 `M` 和 `D` 到底该怎么设计？

在第 3 篇「浮点类型」中，我们已经知道：

- `FLOAT` / `DOUBLE` 是近似值类型；
- `DOUBLE` 比 `FLOAT` 精度高，但仍然不是精确十进制；
- 金额、财务、交易、余额、税额通常不应该用浮点数。

这一篇就是第 3 篇的延伸：

> 如果不能用 `FLOAT` / `DOUBLE` 存金额，那应该怎么用 `DECIMAL` 正确建模？

很多初学者会以为：

- `DECIMAL(10,2)` 表示最多 10 位整数 + 2 位小数。
- `DECIMAL` 只是「能存小数」而已，和 `DOUBLE` 差不多。
- `DECIMAL` 会自动帮我处理所有金额问题。
- `DECIMAL(5,2)` 一定会把多余小数位四舍五入。
- `DECIMAL UNSIGNED` 是定义非负金额的最佳方式。

这些理解都不够准确。

这一篇的重点不是死背语法，而是建立一套建表判断：

1. 什么场景应该用 `DECIMAL`？
2. `DECIMAL(M,D)` 的 `M`、`D` 如何拆解？
3. 金额、汇率、税率、比例应该分别怎么设计精度？
4. 小数位超出、整数位超出时会发生什么？
5. 为什么 `DECIMAL` 也不是「万能金额方案」，仍需要业务层规则配合？

如果只能先记一句话：

> `DECIMAL` 适合保存「必须精确表示的十进制数值」；`M` 是总位数，`D` 是小数位数，整数部分最多 `M - D` 位。

## 30 秒复习入口

- `DECIMAL` 是定点数类型，属于 exact value，适合保存需要精确的十进制数值。
- `DECIMAL`、`DEC`、`NUMERIC` 在 MySQL 中基本可以视为同类，其中 `NUMERIC` 被实现为 `DECIMAL`。
- `DECIMAL(M,D)` 中，`M` 是 precision，总位数；`D` 是 scale，小数位数。
- 小数点和负号不计入 `M`。
- 整数部分最多有 `M - D` 位。
- `DECIMAL(5,2)` 的可表达范围通常理解为 `-999.99 ~ 999.99`。
- `DECIMAL` 不写 `M,D` 时，MySQL 默认 `M` 为 10、`D` 为 0，也就是近似等同 `DECIMAL(10,0)`。
- MySQL 中 `DECIMAL` 最大 precision 是 65，最大 scale 是 30。
- `DECIMAL` 不是字符串存储；MySQL 使用二进制格式保存 `DECIMAL` 值。
- 金额、余额、价格、税额、手续费、汇率通常优先考虑 `DECIMAL`，不要优先用 `FLOAT` / `DOUBLE`。
- `DECIMAL` 解决的是「十进制精确表示」问题，不自动解决「业务舍入规则」问题。
- 新系统中，不建议依赖 `DECIMAL UNSIGNED`；非负约束可优先考虑 `CHECK (amount >= 0)`。

## 一、先讲结论

定点数类型的核心是：

> 用固定的小数位来保存精确的十进制数值。

这和浮点数的思路完全不同。

浮点数关心的是：

```text
用有限空间表示非常大或非常小的近似值。
```

定点数关心的是：

```text
按业务规定的小数位，稳定、精确地保存十进制数值。
```

所以在实务中，`DECIMAL` 最常出现于：

- 商品价格
- 订单金额
- 账户余额
- 交易金额
- 税额
- 手续费
- 汇率
- 利率
- 折扣率
- 财务报表数值

### 1.1 最常用的判断原则

| 问题 | 如果答案是「是」 | 推荐方向 |
| --- | --- | --- |
| 这个数值是否涉及钱？ | 是 | 优先 `DECIMAL` |
| 这个数值是否要和账务、对账、报表一致？ | 是 | 优先 `DECIMAL` |
| 这个数值是否必须精确到固定小数位？ | 是 | 优先 `DECIMAL` |
| 这个数值是否只是测量值或统计值？ | 是 | 可考虑 `DOUBLE` / `FLOAT` |
| 这个数值是否允许极小误差？ | 是 | 可考虑浮点数 |
| 这个数值是否会被大量汇总、结算、比较？ | 是 | 优先 `DECIMAL` |

### 1.2 一个简单选型流程

```text
这个字段是数值吗？
  ├─ 不是：考虑 CHAR / VARCHAR / DATE / JSON 等类型
  └─ 是：继续问
        │
        ├─ 是否必须存整数？
        │     └─ 是：考虑 TINYINT / INT / BIGINT 等整数类型
        │
        ├─ 是否涉及金额、价格、余额、税额、汇率、会计、交易？
        │     └─ 是：优先 DECIMAL
        │
        ├─ 是否要求固定小数位且不能有近似误差？
        │     └─ 是：优先 DECIMAL
        │
        ├─ 是否只是测量值、统计值、科学计算值、模型分数？
        │     └─ 是：可以考虑 DOUBLE / FLOAT
        │
        └─ 仍不确定：先按 DECIMAL 设计，再回到业务规则确认精度
```

### 1.3 常见业务字段选型速查

| 字段 | 推荐类型示例 | 说明 |
| --- | --- | --- |
| 商品价格 | `DECIMAL(10,2)` | 常见商品金额，精确到分 |
| 订单总金额 | `DECIMAL(18,2)` | 订单金额可能更大，预留更多整数位 |
| 账户余额 | `DECIMAL(18,2)` / `DECIMAL(20,2)` | 余额类字段通常要保守预留范围 |
| 银行交易金额 | `DECIMAL(18,2)` / `DECIMAL(20,2)` | 依业务规模决定 |
| 手续费 | `DECIMAL(18,2)` / `DECIMAL(18,4)` | 看是否需要更细精度 |
| 税额 | `DECIMAL(18,2)` / `DECIMAL(18,4)` | 看税务计算规则 |
| 汇率 | `DECIMAL(18,6)` / `DECIMAL(20,8)` | 通常需要比金额更多小数位 |
| 利率 | `DECIMAL(7,6)` / `DECIMAL(9,6)` | 例如 0.035000 表示 3.5% |
| 折扣率 | `DECIMAL(5,4)` | 例如 0.8500 表示 85 折 |
| 百分比展示值 | `DECIMAL(5,2)` | 例如 99.99% |
| 温度、湿度 | `DOUBLE` / `DECIMAL` | 若只是测量近似值可用 `DOUBLE`；若业务要求固定小数位可用 `DECIMAL` |
| 机器学习模型分数 | `DOUBLE` | 通常是近似计算结果 |

## 二、什么是定点数类型

MySQL 中常见的定点数类型包括：

- `DECIMAL`
- `DEC`
- `NUMERIC`
- `FIXED`

其中，最常用的是：

```sql
DECIMAL(M,D)
```

`DECIMAL` 的重点是「exact fixed-point number」，也就是精确的定点数。

你可以先这样理解：

```text
DECIMAL = 以十进制语义保存的精确数值
FLOAT / DOUBLE = 以二进制浮点格式保存的近似数值
```

### 2.1 `DECIMAL` 不是浮点数

`DECIMAL` 和 `DOUBLE` 都可以存小数，但它们的设计目标不同：

| 类型 | 类型本质 | 是否精确十进制 | 典型场景 |
| --- | --- | --- | --- |
| `DECIMAL` | 定点数 / exact value | 是 | 金额、价格、税额、余额 |
| `FLOAT` | 单精度浮点 / approximate value | 否 | 测量值、误差可接受的统计值 |
| `DOUBLE` | 双精度浮点 / approximate value | 否 | 科学计算、模型分数、统计分析 |

所以不要只用「能不能存小数」判断类型。

真正的问题应该是：

```text
这个小数是否必须精确？
```

如果答案是「必须精确」，就应该优先考虑 `DECIMAL`。

### 2.2 `DECIMAL` 不是字符串

有些人会把 `DECIMAL` 误解成「用字符串存数字」。

这个理解也不准确。

MySQL 的 `DECIMAL` 值是用二进制格式保存的，不是简单把 `'123.45'` 当字符串放进去。

更准确的说法是：

```text
DECIMAL 用适合精确十进制计算的内部格式保存数值，而不是用二进制浮点近似格式保存小数。
```

所以 `DECIMAL` 的价值不是「看起来像字符串」，而是：

- 可以避免典型二进制浮点误差；
- 更适合十进制金额场景；
- 聚合、计算、比较时语义更接近业务要求。

## 三、`DECIMAL(M,D)` 怎么理解

`DECIMAL(M,D)` 是定点数类型最核心的语法。

```sql
amount DECIMAL(10,2)
```

其中：

- `M`：precision，总位数；
- `D`：scale，小数位数。

注意：

```text
M 不是整数位数，而是总位数。
```

### 3.1 `M` 是总位数

`M` 表示总共最多可以存多少位数字。

它不包含：

- 小数点；
- 负号。

例如：

```sql
DECIMAL(5,2)
```

表示：

```text
总数字位数：5
小数位数：2
整数位数：5 - 2 = 3
```

所以可以存：

```text
999.99
123.45
0.01
-999.99
```

但不能存：

```text
1000.00
```

因为 `1000.00` 的整数部分需要 4 位，超过了 `DECIMAL(5,2)` 的整数位上限 3 位。

### 3.2 `D` 是小数位数

`D` 表示小数点后最多保留多少位。

例如：

```sql
DECIMAL(10,4)
```

表示：

```text
总数字位数：10
小数位数：4
整数位数：10 - 4 = 6
```

所以大致范围可以理解为：

```text
-999999.9999 ~ 999999.9999
```

### 3.3 整数位数 = `M - D`

这是最重要的公式：

```text
整数部分最多位数 = M - D
```

几个例子：

| 类型 | 总位数 M | 小数位 D | 整数位 M-D | 最大正值大致为 |
| --- | ---: | ---: | ---: | --- |
| `DECIMAL(5,2)` | 5 | 2 | 3 | `999.99` |
| `DECIMAL(10,2)` | 10 | 2 | 8 | `99999999.99` |
| `DECIMAL(10,4)` | 10 | 4 | 6 | `999999.9999` |
| `DECIMAL(18,2)` | 18 | 2 | 16 | `9999999999999999.99` |
| `DECIMAL(20,8)` | 20 | 8 | 12 | `999999999999.99999999` |
| `DECIMAL(2,2)` | 2 | 2 | 0 | `0.99` |

### 3.4 `M` 可以等于 `D`

`D` 不能大于 `M`，但 `M` 可以等于 `D`。

例如：

```sql
rate DECIMAL(4,4)
```

这表示：

```text
总位数 4 位
小数位 4 位
整数位 0 位
```

它适合保存类似下面这种小于 1 的小数：

```text
0.1234
0.8500
```

但它不能保存：

```text
1.0000
```

因为整数部分已经需要 1 位。

所以 `DECIMAL(5,4)` 和 `DECIMAL(4,4)` 的差别很大：

| 类型 | 可表达含义 |
| --- | --- |
| `DECIMAL(4,4)` | 只能表达 `0.xxxx` 这类小于 1 的值 |
| `DECIMAL(5,4)` | 可以表达到 `9.9999` |
| `DECIMAL(6,4)` | 可以表达到 `99.9999` |

## 四、`DECIMAL` 的默认值与上限

### 4.1 不写 `M,D` 时的默认行为

如果写成：

```sql
amount DECIMAL
```

MySQL 中默认 `M` 为 10，`D` 为 0。

也就是说，它近似等同于：

```sql
amount DECIMAL(10,0)
```

这表示：

```text
总共 10 位数字
没有小数部分
```

所以，下面这种写法不适合金额：

```sql
price DECIMAL
```

因为它不会帮你自动变成两位小数金额。

更合理的是明确写出：

```sql
price DECIMAL(10,2)
```

### 4.2 `DECIMAL(M)` 等同于 `DECIMAL(M,0)`

例如：

```sql
amount DECIMAL(10)
```

可以理解为：

```sql
amount DECIMAL(10,0)
```

也就是只有整数，没有小数。

如果你希望保存两位小数，必须明确写成：

```sql
amount DECIMAL(10,2)
```

### 4.3 最大 precision 与最大 scale

MySQL 中：

- `DECIMAL` 最大总位数 `M` 是 65；
- 最大小数位数 `D` 是 30。

但这不表示建表时应该随便写成：

```sql
amount DECIMAL(65,30)
```

这通常是不合理的。

字段设计应该由业务范围决定，而不是盲目追求最大值。

例如：

| 场景 | 更合理的方向 |
| --- | --- |
| 普通商品价格 | `DECIMAL(10,2)` 通常够用 |
| 企业订单金额 | `DECIMAL(18,2)` 更保守 |
| 银行金额 | 依业务规模考虑 `DECIMAL(18,2)`、`DECIMAL(20,2)` 或更大 |
| 汇率 | 更关注小数位，例如 `DECIMAL(20,8)` |
| 利率 | 可能用 `DECIMAL(7,6)` 或 `DECIMAL(9,6)` |

## 五、`DECIMAL` 的范围怎么推

### 5.1 正数最大值

对于：

```sql
DECIMAL(M,D)
```

整数位数是：

```text
M - D
```

所以最大正值可以粗略理解为：

```text
整数部分全部是 9，小数部分全部是 9
```

例如：

```sql
DECIMAL(5,2)
```

整数部分 3 位，小数部分 2 位，所以最大正值是：

```text
999.99
```

### 5.2 负数范围

如果字段没有加非负约束，`DECIMAL` 默认可以保存负数。

例如：

```sql
amount DECIMAL(5,2)
```

可以保存：

```text
-999.99
```

这在某些业务里是合理的，例如：

- 退款金额；
- 调账差额；
- 损益金额；
- 应收应付差额；
- 财务修正值。

所以不要一看到金额就本能地禁止负数，要看业务语义。

### 5.3 `DECIMAL(5,2)` 的完整理解

```sql
CREATE TABLE decimal_demo (
    amount DECIMAL(5,2)
);
```

它可以保存：

```sql
INSERT INTO decimal_demo (amount)
VALUES
    (0.01),
    (123.45),
    (999.99),
    (-999.99);
```

但下面这个值会超出范围：

```sql
INSERT INTO decimal_demo (amount)
VALUES (1000.00);
```

原因是：

```text
DECIMAL(5,2) 的整数部分最多 3 位，而 1000.00 的整数部分是 4 位。
```

## 六、小数位超出时会发生什么

假设字段是：

```sql
amount DECIMAL(5,2)
```

如果插入：

```sql
INSERT INTO decimal_demo (amount)
VALUES (123.4567);
```

这个值的小数位超过了 `D = 2`。

此时 MySQL 会把值转换到目标 scale，也就是转换成两位小数可保存的形式。

但是笔记里不要简单写死：

```text
一定四舍五入。
```

更稳妥的理解是：

```text
当小数位超过 DECIMAL 指定的 scale 时，MySQL 会把值转换到该 scale；官方说明中也提醒具体行为可能受环境影响，通常不要把业务舍入规则完全交给字段类型自动处理。
```

### 6.1 实务建议：业务规则要明确

如果业务规定必须四舍五入，应明确处理：

```sql
INSERT INTO decimal_demo (amount)
VALUES (ROUND(123.4567, 2));
```

如果业务规定必须无条件截断，也应该明确处理，或在后端统一用 `BigDecimal` 的规则处理。

例如 Java 中常见写法是：

```java
BigDecimal amount = new BigDecimal("123.4567")
        .setScale(2, RoundingMode.HALF_UP);
```

或：

```java
BigDecimal amount = new BigDecimal("123.4567")
        .setScale(2, RoundingMode.DOWN);
```

重点是：

```text
DECIMAL 负责精确保存；业务层负责明确舍入规则。
```

### 6.2 为什么不要依赖隐式转换

如果你依赖数据库自动处理多余小数位，会出现几个问题：

- 新人不知道系统到底是四舍五入还是截断；
- 不同数据库、不同版本、不同 SQL mode 下可能有差异；
- 业务规则不透明；
- 对账时很难解释「为什么这笔金额变成这样」。

所以金融、会计、电商结算场景通常不应该把金额舍入规则藏在隐式转换里。

## 七、整数部分超出时会发生什么

小数位超出是一回事，整数部分超出是另一回事。

例如：

```sql
amount DECIMAL(5,2)
```

最多只能保存到：

```text
999.99
```

如果插入：

```sql
1000.00
```

这不是小数位问题，而是整数部分超出范围。

### 7.1 strict mode 下

在 strict SQL mode 下，MySQL 会拒绝超出范围的值，插入失败。

这通常是现代系统更希望看到的行为。

因为它可以让问题尽早暴露，而不是默默把错误数据写进去。

### 7.2 非 strict mode 下

如果没有启用严格限制，MySQL 可能会把超出范围的值裁剪到该字段能表示的端点，并产生 warning。

例如某个字段最大只能到 `999.99`，你插入更大的值，在非严格模式下可能被裁剪成最大值。

这在业务系统中很危险，因为：

```text
错误金额被静默改写，比插入失败更难发现。
```

### 7.3 实务建议

生产系统建议：

- 开启 strict mode；
- 字段范围按业务上限预留；
- 后端 DTO / Validator 提前校验范围；
- 数据库层用 `CHECK` 约束补一层保护；
- 不要让金额字段靠非 strict mode 自动裁剪。

## 八、金额字段应该怎么设计

金额字段不是简单写一个 `DECIMAL(10,2)` 就结束。

你至少要问四个问题：

1. 最大金额可能是多少？
2. 是否允许负数？
3. 小数位是多少？
4. 计算过程是否需要比最终显示更多的小数位？

### 8.1 商品价格

普通商品价格常见写法：

```sql
price DECIMAL(10,2) NOT NULL
```

含义：

```text
整数部分最多 8 位，小数部分 2 位
最大可到 99999999.99
```

对于多数零售商品，`DECIMAL(10,2)` 已经够用。

但如果是企业采购、大宗商品、金融资产，可能需要更大范围。

### 8.2 订单金额

订单金额通常比单价更需要预留空间：

```sql
total_amount DECIMAL(18,2) NOT NULL
```

因为订单总金额可能来自：

- 多个商品小计；
- 运费；
- 优惠；
- 税费；
- 手续费；
- 跨币别换算。

`DECIMAL(18,2)` 的整数位有 16 位，通常比 `DECIMAL(10,2)` 更适合订单级、账户级金额。

### 8.3 账户余额

账户余额常见写法：

```sql
balance DECIMAL(18,2) NOT NULL DEFAULT 0.00
```

如果业务中余额一定不能为负，建议明确加约束：

```sql
balance DECIMAL(18,2) NOT NULL DEFAULT 0.00,
CHECK (balance >= 0)
```

如果业务允许透支、欠款、调账，则不应该加这个限制。

### 8.4 交易金额

交易金额可以设计为：

```sql
transaction_amount DECIMAL(18,2) NOT NULL
```

但要注意：

```text
交易金额是否允许负数，取决于你是用正负数表达方向，还是用 transaction_type 表达方向。
```

两种设计都常见。

#### 设计一：金额永远为正，交易方向独立字段

```sql
amount DECIMAL(18,2) NOT NULL,
transaction_type VARCHAR(20) NOT NULL,
CHECK (amount > 0)
```

例如：

```text
DEPOSIT  100.00
WITHDRAW 100.00
```

#### 设计二：金额带正负号

```sql
amount DECIMAL(18,2) NOT NULL
```

例如：

```text
+100.00
-100.00
```

这两种没有绝对对错，要看系统的账务模型。

但不要混用：

```text
有时用 type 表达方向，有时又用 amount 正负表达方向。
```

这会让统计与对账变得混乱。

---

## 九、汇率、利率、税率怎么设计

金额通常是两位小数，但汇率、利率、税率不一定。

### 9.1 汇率

汇率常见需要 4～8 位甚至更多小数。

例如：

```sql
exchange_rate DECIMAL(20,8) NOT NULL
```

这表示：

```text
整数部分最多 12 位
小数部分 8 位
```

对于多数汇率保存，重点不是整数部分多大，而是小数部分够不够。

不建议写成：

```sql
exchange_rate DOUBLE
```

如果汇率参与金额换算与结算，`DOUBLE` 的近似误差可能造成后续金额差异。

### 9.2 利率

利率可以有两种表达方式。

#### 方式一：保存小数形式

```sql
annual_rate DECIMAL(9,6)
```

例如：

```text
0.035000 表示 3.5%
0.012500 表示 1.25%
```

这种方式适合计算。

#### 方式二：保存百分比数值

```sql
annual_rate_percent DECIMAL(7,4)
```

例如：

```text
3.5000 表示 3.5%
1.2500 表示 1.25%
```

这种方式比较接近展示。

两种都可以，但字段命名要清楚。

推荐：

```sql
annual_rate DECIMAL(9,6) COMMENT '年利率，小数形式，例如 0.035000 表示 3.5%'
```

不要只写：

```sql
rate DECIMAL(9,6)
```

因为别人不知道你存的是 `0.035` 还是 `3.5`。

### 9.3 税率

税率也要先决定表达方式。

如果保存小数形式：

```sql
tax_rate DECIMAL(7,6)
```

例如：

```text
0.050000 表示 5%
0.075000 表示 7.5%
```

如果保存百分比形式：

```sql
tax_rate_percent DECIMAL(5,2)
```

例如：

```text
5.00 表示 5%
7.50 表示 7.5%
```

实务中更重要的是：

```text
系统内统一一种表达方式。
```

否则计算公式很容易写错。

---

## 十、`DECIMAL` 与 `UNSIGNED`

你可能会看到旧系统这样写：

```sql
amount DECIMAL(18,2) UNSIGNED
```

直觉上这表示：

```text
金额不能是负数。
```

但在 MySQL 8.4 官方文件中，`UNSIGNED` 用在 `DECIMAL` 上已经被标记为 deprecated，官方建议可考虑使用简单的 `CHECK` 约束。

所以新系统更推荐：

```sql
amount DECIMAL(18,2) NOT NULL,
CHECK (amount >= 0)
```

### 10.1 为什么 `CHECK` 更清楚

`CHECK` 的好处是业务语义更明确。

例如：

```sql
CHECK (amount >= 0)
CHECK (discount_rate >= 0 AND discount_rate <= 1)
CHECK (tax_rate >= 0 AND tax_rate <= 1)
```

这些约束一看就知道业务含义。

而 `UNSIGNED` 只是类型属性，表达能力有限。

### 10.2 不是所有金额都应该非负

不要看到金额就加非负。

下面这些金额可能需要允许负数：

- 调账差额；
- 损益金额；
- 退款冲正；
- 应收应付余额；
- 授信额度调整差额；
- 会计分录借贷方向中的净额。

所以是否非负，要看字段语义。

---

## 十一、`DECIMAL` 与 `ZEROFILL`

旧系统也可能看到：

```sql
amount DECIMAL(10,2) ZEROFILL
```

这种写法不建议新系统继续使用。

原因是：

- `ZEROFILL` 偏显示层语义；
- 它容易让字段类型混入格式化需求；
- 现代系统更应该在前端、报表层或格式化函数中处理显示格式；
- `ZEROFILL` 相关旧式写法在 MySQL 新版本中也不鼓励继续依赖。

如果你想显示：

```text
00000123.45
```

这应该是显示层的责任，不是数据库字段类型的责任。

---

## 十二、`DECIMAL` 的存储成本

`DECIMAL` 比整数和浮点数更复杂。

MySQL 的 `DECIMAL` 存储不是固定 4 bytes 或 8 bytes，而是依照 precision 和 scale 决定。

官方文件说明，`DECIMAL` / `NUMERIC` 会把 9 个十进制数字打包进 4 bytes，并且整数部分和小数部分分别计算存储需求。

你不需要在初学阶段背完整计算公式，但要知道：

```text
DECIMAL 的 precision 越大，存储成本通常越高。
```

所以不要无脑写：

```sql
amount DECIMAL(65,30)
```

这会让字段显得「很安全」，但实际上可能带来：

- 不必要的存储成本；
- 更复杂的计算；
- 更难理解的业务语义；
- 后端字段精度处理更麻烦。

合理做法是：

```text
根据业务最大值和小数精度预留，而不是直接开到最大。
```

---

## 十三、`DECIMAL` 的计算结果与聚合

`DECIMAL` 的优势不只在存储，也体现在计算语义上。

MySQL 官方文件说明，`DECIMAL` 列参与基本运算时，会使用较高 precision 处理；聚合函数方面，`SUM()` 和 `AVG()` 对 exact-value 参数，例如整数或 `DECIMAL`，会返回 `DECIMAL`，而对 approximate-value 参数，例如 `FLOAT` / `DOUBLE`，会返回 `DOUBLE`。

这代表：

```text
如果底层字段是 DECIMAL，金额汇总更符合精确值语义；如果底层字段是 DOUBLE，汇总结果仍然是近似值。
```

### 13.1 金额汇总示例

```sql
CREATE TABLE order_item (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    unit_price DECIMAL(10,2) NOT NULL,
    quantity INT NOT NULL,
    subtotal DECIMAL(18,2) NOT NULL
);
```

查询订单总额：

```sql
SELECT order_id, SUM(subtotal) AS order_total
FROM order_item
GROUP BY order_id;
```

因为 `subtotal` 是 `DECIMAL`，所以 `SUM(subtotal)` 的语义更适合金额汇总。

### 13.2 不建议用浮点金额汇总

不要这样设计：

```sql
subtotal DOUBLE NOT NULL
```

然后再：

```sql
SELECT SUM(subtotal)
FROM order_item;
```

因为你会把金额汇总建立在近似值基础上。

即使某一次看起来结果正确，也不代表长期累计和对账一定可靠。

---

## 十四、Java 后端中如何对应 `DECIMAL`

如果你做 Java 后端，这点非常重要：

> MySQL 的 `DECIMAL` 金额字段，Java 中优先使用 `BigDecimal`，不要用 `double` / `Double`。

### 14.1 推荐写法

实体类：

```java
public class Order {
    private Long id;
    private BigDecimal totalAmount;
}
```

MyBatis / MyBatis-Plus 中通常可以自然映射：

```java
@TableField("total_amount")
private BigDecimal totalAmount;
```

### 14.2 不推荐写法

```java
private Double totalAmount;
```

问题是：

- `Double` 是二进制浮点近似值；
- 可能重新引入浮点误差；
- 和数据库 `DECIMAL` 的设计目标冲突；
- 金额比较、加减、汇总容易出问题。

### 14.3 `BigDecimal` 的构造也要注意

不要这样写：

```java
BigDecimal amount = new BigDecimal(0.1);
```

更推荐：

```java
BigDecimal amount = new BigDecimal("0.1");
```

或：

```java
BigDecimal amount = BigDecimal.valueOf(0.1);
```

因为 `new BigDecimal(0.1)` 会把 `double` 的近似值带进去。

### 14.4 金额比较不要直接用 `equals()`

```java
new BigDecimal("1.0").equals(new BigDecimal("1.00"))
```

结果是 `false`，因为 `equals()` 会比较 scale。

金额数值比较更常用：

```java
amount.compareTo(BigDecimal.ZERO) >= 0
```

判断金额是否相等：

```java
amount1.compareTo(amount2) == 0
```

这虽然是 Java 内容，但和 MySQL `DECIMAL` 的实务使用高度相关。

## 十五、完整建表示例

下面是一个较完整的订单表设计示例：

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    order_no VARCHAR(32) NOT NULL,

    currency_code CHAR(3) NOT NULL DEFAULT 'TWD',

    original_amount DECIMAL(18,2) NOT NULL COMMENT '商品原始总金额',
    discount_amount DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '优惠金额',
    tax_amount DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '税额',
    shipping_fee DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '运费',
    payable_amount DECIMAL(18,2) NOT NULL COMMENT '应付金额',

    exchange_rate DECIMAL(20,8) DEFAULT NULL COMMENT '汇率，需要时使用',

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CHECK (original_amount >= 0),
    CHECK (discount_amount >= 0),
    CHECK (tax_amount >= 0),
    CHECK (shipping_fee >= 0),
    CHECK (payable_amount >= 0),
    CHECK (exchange_rate IS NULL OR exchange_rate > 0)
);
```

这个例子的重点：

- 金额类字段使用 `DECIMAL(18,2)`；
- 汇率使用 `DECIMAL(20,8)`，比金额保留更多小数位；
- 订单编号使用 `VARCHAR`，不是数字类型；
- 非负约束使用 `CHECK` 表达；
- 币别使用 `CHAR(3)` 保存 ISO 货币代码，例如 `TWD`、`USD`、`JPY`。

### 15.1 为什么订单编号不用 `DECIMAL`

订单编号虽然可能长得像数字：

```text
2026050100012345
```

但它不是用来计算的数值。

它更适合用：

```sql
order_no VARCHAR(32)
```

原因：

- 可能有前导 0；
- 可能包含字母或分隔符；
- 不参与加减乘除；
- 是业务标识，不是数学数值。

## 十六、常见错误写法

### 错误 1：金额用 `DOUBLE`

```sql
price DOUBLE
```

问题：

```text
DOUBLE 是近似值，不适合金额。
```

更合理：

```sql
price DECIMAL(10,2)
```

### 错误 2：以为 `DECIMAL(10,2)` 有 10 位整数

错误理解：

```text
DECIMAL(10,2) = 10 位整数 + 2 位小数
```

正确理解：

```text
DECIMAL(10,2) = 总共 10 位数字，其中 2 位小数，整数部分最多 8 位。
```

### 错误 3：不写 `M,D`

```sql
amount DECIMAL
```

问题：

```text
这通常等同于 DECIMAL(10,0)，没有小数位。
```

更合理：

```sql
amount DECIMAL(18,2)
```

### 错误 4：所有金额都加 `UNSIGNED`

```sql
amount DECIMAL(18,2) UNSIGNED
```

问题：

- `DECIMAL UNSIGNED` 在新版本中不建议继续依赖；
- 有些金额字段本来就可能为负；
- 业务约束用 `CHECK` 表达更清楚。

更合理：

```sql
amount DECIMAL(18,2) NOT NULL,
CHECK (amount >= 0)
```

### 错误 5：把显示格式交给字段类型

```sql
amount DECIMAL(10,2) ZEROFILL
```

问题：

```text
ZEROFILL 是显示层味道很重的旧式写法，不建议新系统依赖。
```

更合理：

```text
数据库保存数值，前端或报表层负责格式化。
```

### 错误 6：金额计算时混入浮点数

```sql
SELECT price * 0.1
FROM product;
```

这类写法要小心，因为 `0.1` 的类型推断、表达式上下文可能影响计算语义。

更稳妥的是保持精确数值语义，并在业务层明确计算规则。

例如：

```sql
SELECT price * CAST('0.10' AS DECIMAL(4,2))
FROM product;
```

或在 Java 中用 `BigDecimal` 完成金额计算。

---

## 十七、`DECIMAL` 不是万能方案

`DECIMAL` 很适合金额，但它不是万能方案。

### 17.1 它不负责业务规则

例如：

```sql
amount DECIMAL(18,2)
```

只能保证：

```text
这个字段能保存最多 18 位数字，其中 2 位小数。
```

它不能保证：

- 订单金额等于明细金额加总；
- 折扣金额不超过原始金额；
- 税额计算符合税务规则；
- 退款金额不超过已付款金额；
- 币别换算使用正确汇率；
- 四舍五入规则符合财务规定。

这些仍需要：

- 后端业务逻辑；
- 数据库约束；
- 事务控制；
- 对账机制；
- 审计日志；
- 测试用例。

### 17.2 它也不一定适合所有小数

下面这些场景不一定优先用 `DECIMAL`：

| 场景 | 可考虑类型 | 原因 |
| --- | --- | --- |
| 传感器实时读数 | `DOUBLE` | 本身就是测量近似值 |
| 科学计算结果 | `DOUBLE` | 需要范围和计算效率 |
| 机器学习模型分数 | `DOUBLE` | 通常不是精确业务金额 |
| 经纬度空间计算 | `DOUBLE` / 空间类型 | 依计算方式决定 |
| 大量统计中间结果 | `DOUBLE` | 常可接受近似误差 |

所以不要把结论背成：

```text
小数一律用 DECIMAL。
```

更准确是：

```text
必须精确的十进制小数优先 DECIMAL；允许误差的近似值可考虑 FLOAT / DOUBLE。
```

## 十八、面试表达版

如果面试被问：

> MySQL 里的 `DECIMAL` 和 `FLOAT` / `DOUBLE` 有什么区别？

可以这样回答：

```text
DECIMAL 是定点数，属于 exact value，适合保存必须精确的十进制数值，例如金额、价格、余额、税额。

FLOAT 和 DOUBLE 是浮点数，属于 approximate value，适合保存允许一定误差的近似值，例如测量值、科学计算结果、统计分析结果。

DECIMAL(M,D) 中，M 是总位数，也叫 precision；D 是小数位数，也叫 scale；整数部分最多是 M - D 位。比如 DECIMAL(10,2) 不是 10 位整数加 2 位小数，而是总共 10 位数字，其中 2 位小数，整数部分最多 8 位。

实务上，金额字段在数据库中用 DECIMAL，Java 中通常对应 BigDecimal，而不应该用 double / Double。
```

如果进一步问：

> `DECIMAL` 的缺点是什么？

可以这样回答：

```text
DECIMAL 的存储和计算成本通常比 FLOAT / DOUBLE 高，而且 precision 和 scale 要根据业务设计，不能无脑开很大。它解决的是精确十进制表示问题，但不自动解决业务舍入、税额计算、对账规则等问题。
```

## 二十、一句话抓核心

`DECIMAL` 的核心价值不是「也能存小数」，而是「能按十进制精确语义保存固定小数位数值」；建表时要用 `M` 控制总位数、用 `D` 控制小数位，并让业务层明确金额、汇率、税率的舍入与约束规则。
