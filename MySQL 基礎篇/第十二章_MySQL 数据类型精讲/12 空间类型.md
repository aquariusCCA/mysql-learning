# 12 空间类型

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇要解决的问题是：

> 当字段要保存「位置、路线、区域、地理围栏」这类数据时，应该用普通的 `DECIMAL` 经度/纬度字段，还是使用 MySQL 的空间类型？如果使用空间类型，又该如何理解 `POINT`、`LINESTRING`、`POLYGON`、`SRID`、`SPATIAL INDEX` 和距离计算？

空间类型很容易被误解成：

- `POINT` 只是把两个数字合在一起保存。
- 经纬度坐标一定应该用 `POINT`，不能用普通数值列。
- `POINT(25.0330 121.5654)` 和 `POINT(121.5654 25.0330)` 差不多。
- `ST_Distance()` 算出来的结果默认就是米或公里。
- `SRID 4326` 可以简单理解成「投影坐标系」。
- 只要建了 `SPATIAL INDEX`，附近搜索就一定很快。
- `GEOMETRY` 是总类型，所以直接用它最灵活、最好。
- 空间类型只是冷门知识，普通业务系统完全不会碰到。

这些理解都不够准确。

真正要先抓住的是：

> MySQL 空间类型保存的是「几何值」，而不是普通字符串或普通数值；它的正确使用通常同时涉及几何类型、坐标顺序、SRID/SRS、空间函数和空间索引。

如果只能先记一句话：

> 一个位置用 `POINT`，一条路线用 `LINESTRING`，一个区域用 `POLYGON`；如果是经纬度，通常要明确 `SRID 4326`，并牢记 `POINT(x y)` 中 `x` 通常是 longitude，经度，`y` 通常是 latitude，纬度。

## 30 秒复习入口

- MySQL 空间类型用来保存几何对象，例如点、线、面、多个点、多个面。
- `GEOMETRY` 是空间类型的总类；实务中能用具体类型就优先用具体类型。
- `POINT` 表示一个点，常用于坐标位置。
- `LINESTRING` 表示由多个点连接成的线，常用于路线或轨迹。
- `POLYGON` 表示封闭区域，常用于行政区域、服务范围、地理围栏。
- `MULTIPOINT`、`MULTILINESTRING`、`MULTIPOLYGON` 表示同类几何对象的集合。
- `GEOMETRYCOLLECTION` 可以混合不同类型的几何对象，但业务表中不应轻易滥用。
- WKT 是文本格式，例如 `POINT(121.5654 25.0330)`。
- WKB 是二进制格式，更适合程序和数据库内部处理。
- `ST_GeomFromText()` 可以把 WKT 转成 MySQL 内部几何值。
- `ST_AsText()` 可以把几何值转成可读的 WKT。
- `POINT(x y)` 中 `x` 是横轴，`y` 是纵轴；经纬度场景下通常 `x = longitude`、`y = latitude`。
- 常见错误是把纬度和经度写反。
- `SRID` 是空间参考系统编号，不只是一个随便填的数字。
- 不指定 SRID 时，默认通常是 `SRID 0`，可理解成没有实际地球单位的平面坐标。
- 地理经纬度常见使用 `SRID 4326`，也就是 WGS 84。
- `ST_Distance()` 的单位和语义取决于空间参考系统。
- `ST_Distance_Sphere()` 会按球面距离计算，结果单位是米，常用于两个点之间的近似地球距离。
- `SPATIAL INDEX` 是空间索引，常用于点查、区域查、相交查等空间查询优化。
- 建空间索引的空间列通常需要 `NOT NULL`。
- 空间索引不是所有查询都会自动高效；查询条件、函数、SRID、版本和执行计划都会影响结果。
- 如果只是保存经纬度并展示地图，两个 `DECIMAL` 字段可能更简单。
- 如果需要距离计算、点在区域内、路线/区域建模、空间索引，就应该考虑空间类型。

## 一、先讲结论

MySQL 空间类型不是普通业务系统每天都会用到的类型，但它非常适合下面这些数据：

```text
分行位置
ATM 位置
店铺位置
仓库位置
车辆位置
设备定位
路线轨迹
配送路径
行政区域
服务范围
地理围栏
地图标注
```

最常用的三种是：

| 要保存的数据 | 推荐类型 | 示例 |
|---|---|---|
| 一个位置 | `POINT` | 店铺坐标、ATM 坐标、车辆当前位置 |
| 一条路线 | `LINESTRING` | 行驶轨迹、道路、配送路线 |
| 一块区域 | `POLYGON` | 服务区域、行政区域、园区范围、地理围栏 |

一句话：

```text
点 -> POINT
线 -> LINESTRING
面 -> POLYGON
```

如果只是要在页面上显示一个经纬度，不做空间查询，使用两个普通数值列也可以：

```sql
longitude DECIMAL(10, 7) NOT NULL,
latitude  DECIMAL(9, 7)  NOT NULL
```

但如果你要做下面这些事，就应该考虑空间类型：

```text
计算两点距离
查询附近的店铺
判断某个点是否在某个区域内
查询路线是否经过某区域
保存复杂边界
使用空间索引优化空间查询
```

也就是说：

> 普通经纬度字段解决「显示坐标」；空间类型解决「把坐标当成几何对象来计算和查询」。

## 二、空间类型解决的本质问题

普通字段只能表达：

```text
longitude = 121.5654
latitude  = 25.0330
```

这两个数字本身不会告诉数据库：

- 它们是一组坐标。
- 它们代表地球上的一个位置。
- 它们可以参与空间关系判断。
- 它们可以使用空间索引。
- 它们可以和区域、路线、点集合进行几何计算。

空间类型则可以把这些数据保存成几何对象：

```sql
POINT(121.5654 25.0330)
```

这时数据库知道它是一个点，可以搭配空间函数使用：

```sql
ST_Distance_Sphere(location, ST_GeomFromText('POINT(121.5000 25.0500)', 4326))
ST_Contains(boundary, location)
ST_Within(location, boundary)
ST_Intersects(route, boundary)
```

所以空间类型的核心不是「多了一种存法」，而是：

> 让数据库知道这是一份可以被几何模型理解、计算、比较、索引的数据。

## 三、MySQL 常见空间类型总览

MySQL 常见空间类型可以这样理解：

| 类型 | 中文理解 | 适合场景 |
|---|---|---|
| `GEOMETRY` | 空间类型总类 | 同一列可能保存不同几何类型时 |
| `POINT` | 点 | 经纬度位置、地图标记、设备坐标 |
| `LINESTRING` | 线 | 路线、轨迹、道路、边界线 |
| `POLYGON` | 面 | 区域、围栏、行政区、服务范围 |
| `MULTIPOINT` | 多个点 | 多个离散坐标点的集合 |
| `MULTILINESTRING` | 多条线 | 多段路线、多个线段集合 |
| `MULTIPOLYGON` | 多个面 | 多个区域组成的整体，例如岛屿、飞地 |
| `GEOMETRYCOLLECTION` | 混合几何集合 | 同时包含点、线、面的复杂集合 |

实务上最常见的是：

```text
POINT       最常用
POLYGON     次常用
LINESTRING  特定路线/轨迹业务会用
```

`GEOMETRY` 虽然灵活，但不建议默认使用。

原因是：

- 具体类型更能表达业务语义。
- 具体类型更容易被程序理解和约束。
- 具体类型减少误存其他几何对象的风险。
- 具体类型在维护和接口定义上更清楚。

例如店铺位置应该写：

```sql
location POINT NOT NULL SRID 4326
```

而不是：

```sql
location GEOMETRY NOT NULL
```

除非你的业务真的允许这个字段有时是点、有时是线、有时是面。

## 四、`POINT`：保存一个位置

`POINT` 表示一个点。

常见场景：

```text
店铺位置
银行分行位置
ATM 位置
仓库位置
车辆当前位置
手机定位点
IoT 设备位置
地图标注点
```

示例：

```sql
CREATE TABLE stores (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    location POINT NOT NULL SRID 4326,
    SPATIAL INDEX idx_location (location)
);
```

插入一个点：

```sql
INSERT INTO stores (name, location)
VALUES (
    '台北 101 附近店铺',
    ST_GeomFromText('POINT(121.5654 25.0330)', 4326)
);
```

查询可读格式：

```sql
SELECT
    id,
    name,
    ST_AsText(location) AS location_wkt,
    ST_X(location) AS longitude,
    ST_Y(location) AS latitude,
    ST_SRID(location) AS srid
FROM stores;
```

结果概念：

```text
location_wkt                 longitude   latitude   srid
POINT(121.5654 25.0330)      121.5654    25.0330    4326
```

这里最重要的是：

```text
POINT(x y)
x = 横轴
 y = 纵轴
```

在经纬度场景中，通常理解为：

```text
x = longitude = 经度
y = latitude  = 纬度
```

所以：

```sql
POINT(121.5654 25.0330)
```

表示：

```text
经度 121.5654
纬度 25.0330
```

不要写反成：

```sql
POINT(25.0330 121.5654)
```

这一点非常容易错。

---

## 五、经度和纬度为什么容易写反

很多地图 API、前端变量、接口字段会使用下面的命名：

```json
{
  "lat": 25.0330,
  "lng": 121.5654
}
```

也就是先 `lat`，再 `lng`。

但 WKT 的点是：

```text
POINT(x y)
```

在地理坐标常见习惯中：

```text
x = longitude / lng / 经度
y = latitude  / lat / 纬度
```

所以从 API 转成 MySQL `POINT` 时，经常会这样写：

```sql
ST_GeomFromText('POINT(121.5654 25.0330)', 4326)
```

而不是：

```sql
ST_GeomFromText('POINT(25.0330 121.5654)', 4326)
```

一个简单判断方式：

```text
台湾经度大约 120 ~ 122
台湾纬度大约 21 ~ 26
```

如果你看到台湾资料被写成：

```text
POINT(25.0330 121.5654)
```

大概率是经纬度顺序写反。

## 六、`LINESTRING`：保存路线或轨迹

`LINESTRING` 表示由多个点依序连接成的线。

常见场景：

```text
道路路线
车辆轨迹
配送路径
河流线段
捷运路线
运动轨迹
```

示例：

```sql
CREATE TABLE delivery_routes (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    route_name VARCHAR(100) NOT NULL,
    path LINESTRING NOT NULL SRID 4326,
    SPATIAL INDEX idx_path (path)
);
```

插入路线：

```sql
INSERT INTO delivery_routes (route_name, path)
VALUES (
    '路线 A',
    ST_GeomFromText(
        'LINESTRING(121.5000 25.0300, 121.5200 25.0400, 121.5654 25.0330)',
        4326
    )
);
```

查询：

```sql
SELECT
    id,
    route_name,
    ST_AsText(path) AS path_wkt
FROM delivery_routes;
```

概念上：

```text
LINESTRING(点1, 点2, 点3, ...)
```

注意：

- `LINESTRING` 是有顺序的。
- 点的顺序决定路线方向和形状。
- `LINESTRING` 不适合保存无序点集合；无序点集合更接近 `MULTIPOINT` 或另一张明细表。
- 如果轨迹点很多，而且每个点还要保存时间、速度、设备状态，通常应该拆成轨迹点明细表，而不是只存一条巨大 `LINESTRING`。

例如轨迹点如果有时间：

```text
车辆 ID
时间
经度
纬度
速度
方向
```

这类数据通常更适合：

```sql
CREATE TABLE vehicle_track_points (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    vehicle_id BIGINT UNSIGNED NOT NULL,
    recorded_at DATETIME(3) NOT NULL,
    location POINT NOT NULL SRID 4326,
    speed DECIMAL(8, 2),
    SPATIAL INDEX idx_location (location),
    INDEX idx_vehicle_time (vehicle_id, recorded_at)
);
```

也就是说：

> `LINESTRING` 适合表达路线几何形状；若每个点都有业务属性，通常要拆成明细表。

## 七、`POLYGON`：保存区域或围栏

`POLYGON` 表示一个封闭区域。

常见场景：

```text
行政区边界
商圈范围
配送范围
服务区域
禁行区域
地理围栏
园区边界
停车区域
```

示例：

```sql
CREATE TABLE service_areas (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    area_name VARCHAR(100) NOT NULL,
    boundary POLYGON NOT NULL SRID 4326,
    SPATIAL INDEX idx_boundary (boundary)
);
```

插入一个简单矩形区域：

```sql
INSERT INTO service_areas (area_name, boundary)
VALUES (
    '服务区域 A',
    ST_GeomFromText(
        'POLYGON((121.5000 25.0000, 121.6000 25.0000, 121.6000 25.1000, 121.5000 25.1000, 121.5000 25.0000))',
        4326
    )
);
```

`POLYGON` 最重要的规则：

```text
起点和终点要闭合
```

也就是：

```text
第一个点 = 最后一个点
```

例如：

```text
POLYGON((0 0, 10 0, 10 10, 0 10, 0 0))
```

最后回到 `0 0`。

如果多边形有洞，例如一个区域中间挖掉一块，可以写成：

```sql
POLYGON(
  (0 0, 10 0, 10 10, 0 10, 0 0),
  (3 3, 7 3, 7 7, 3 7, 3 3)
)
```

第一组通常是外圈，后面的组可以表示内圈。

判断某个点是否在区域内：

```sql
SELECT
    a.id,
    a.area_name
FROM service_areas a
WHERE ST_Contains(
    a.boundary,
    ST_GeomFromText('POINT(121.5654 25.0330)', 4326)
);
```

也可以反过来写：

```sql
SELECT
    a.id,
    a.area_name
FROM service_areas a
WHERE ST_Within(
    ST_GeomFromText('POINT(121.5654 25.0330)', 4326),
    a.boundary
);
```

语义上：

```text
ST_Contains(区域, 点) = 区域是否包含这个点
ST_Within(点, 区域)   = 点是否位于这个区域内
```

## 八、集合类型：`MULTI*` 和 `GEOMETRYCOLLECTION`

除了单个点、线、面，还有集合类型。

### 8.1 `MULTIPOINT`

表示多个点：

```sql
MULTIPOINT((121.5000 25.0000), (121.6000 25.1000))
```

适合：

```text
同一对象的一组离散点
多个采样点
多个候选位置
```

但如果每个点都有自己的时间、状态、说明，通常拆表更好。

---

### 8.2 `MULTILINESTRING`

表示多条线：

```sql
MULTILINESTRING(
  (121.5000 25.0000, 121.5100 25.0100),
  (121.5200 25.0200, 121.5300 25.0300)
)
```

适合：

```text
多段道路
多段路线
一个对象由多条线组成
```

---

### 8.3 `MULTIPOLYGON`

表示多个面：

```sql
MULTIPOLYGON(
  ((0 0, 10 0, 10 10, 0 10, 0 0)),
  ((20 20, 30 20, 30 30, 20 30, 20 20))
)
```

适合：

```text
一个行政区由多个不连续区域组成
一个服务范围由多个区域组成
岛屿、飞地、多园区边界
```

---

### 8.4 `GEOMETRYCOLLECTION`

`GEOMETRYCOLLECTION` 可以混合点、线、面：

```sql
GEOMETRYCOLLECTION(
  POINT(121.5654 25.0330),
  LINESTRING(121.5000 25.0000, 121.6000 25.1000),
  POLYGON((121.5000 25.0000, 121.6000 25.0000, 121.6000 25.1000, 121.5000 25.1000, 121.5000 25.0000))
)
```

但是普通业务表中不建议轻易用它。

原因是：

- 查询和处理更复杂。
- 后端对象映射更麻烦。
- 业务语义不够明确。
- 容易把不同概念硬塞进同一个字段。

只有当业务对象本身就是混合几何集合时，才考虑使用。

## 九、WKT 与 WKB

空间数据常见两种表示格式：

| 格式 | 全称 | 特点 |
|---|---|---|
| WKT | Well-Known Text | 文本格式，可读性强 |
| WKB | Well-Known Binary | 二进制格式，适合程序传输和内部处理 |

WKT 示例：

```text
POINT(121.5654 25.0330)
LINESTRING(121.5000 25.0000, 121.6000 25.1000)
POLYGON((0 0, 10 0, 10 10, 0 10, 0 0))
```

插入 WKT：

```sql
INSERT INTO stores (name, location)
VALUES ('店铺 A', ST_GeomFromText('POINT(121.5654 25.0330)', 4326));
```

读取 WKT：

```sql
SELECT ST_AsText(location) AS location_wkt
FROM stores;
```

WKB 示例通常是二进制，不适合人直接阅读：

```sql
SELECT ST_AsBinary(location)
FROM stores;
```

学习阶段建议先掌握 WKT。

实际后端程序中，可能会使用：

- WKT 字符串
- WKB 二进制
- GIS 类库对象
- 前端传来的 `lat` / `lng`
- GeoJSON，然后在应用层转换

不要把 WKT 当成普通字符串保存到 `VARCHAR` 或 `TEXT`。

错误示例：

```sql
location_text VARCHAR(100) NOT NULL
```

然后保存：

```text
POINT(121.5654 25.0330)
```

这样数据库并不知道它是几何值，也无法真正使用空间函数和空间索引。

## 十、SRID 与 SRS

这是空间类型最容易被跳过，但非常关键的概念。

### 10.1 SRS 是什么

`SRS` 是 Spatial Reference System，空间参考系统。

它描述的是：

```text
这些坐标要放在哪个空间参考系统中理解？
单位是什么？
坐标轴代表什么？
坐标范围是什么？
如何计算距离？
```

### 10.2 SRID 是什么

`SRID` 是 Spatial Reference Identifier，空间参考系统编号。

可以简单理解为：

```text
SRID 是 SRS 的编号
```

常见例子：

```text
SRID 0     默认平面坐标，轴没有实际单位
SRID 4326  WGS 84，经纬度坐标系统，常用于 GPS / 地图经纬度
```

注意：

> `SRID 4326` 通常是地理坐标系，不要简单说成「投影坐标系」。

如果你写：

```sql
POINT NOT NULL
```

没有指定 SRID，那么几何值常见会落在默认的 `SRID 0` 语义中。

如果你明确保存地球经纬度，建议写：

```sql
location POINT NOT NULL SRID 4326
```

并插入：

```sql
ST_GeomFromText('POINT(121.5654 25.0330)', 4326)
```

这样比只写一个普通 `POINT` 更明确。

---

## 十一、`SRID 0` 与 `SRID 4326` 的差异

### 11.1 `SRID 0`

`SRID 0` 可以先理解为：

```text
一个没有实际地球单位的无限平面坐标系
```

例如：

```sql
SELECT ST_Distance(
    ST_GeomFromText('POINT(1 1)'),
    ST_GeomFromText('POINT(2 2)')
) AS distance;
```

结果概念类似：

```text
sqrt((2 - 1)^2 + (2 - 1)^2) = 1.414...
```

这比较像数学平面上的距离。

如果你把经纬度用 `SRID 0` 存进去，再直接用 `ST_Distance()`，很容易得到一个「看起来有数字，但业务意义不清楚」的结果。

---

### 11.2 `SRID 4326`

`SRID 4326` 常用于 WGS 84 经纬度。

例如：

```sql
SELECT ST_Distance(
    ST_GeomFromText('POINT(121.5654 25.0330)', 4326),
    ST_GeomFromText('POINT(121.5000 25.0500)', 4326)
) AS distance;
```

在支持地理 SRS 的空间函数中，MySQL 可以依据 SRS 语义处理距离。

如果你只是要快速计算两个经纬度点之间的近似球面距离，也常见使用：

```sql
SELECT ST_Distance_Sphere(
    ST_GeomFromText('POINT(121.5654 25.0330)', 4326),
    ST_GeomFromText('POINT(121.5000 25.0500)', 4326)
) AS distance_m;
```

这里 `distance_m` 可以理解为以米为单位的球面距离近似值。

但要记住：

- `ST_Distance_Sphere()` 是球面近似。
- `ST_Distance()` 的语义取决于 SRS 与 MySQL 版本行为。
- 投影坐标、地理坐标、平面坐标不能混在一起随便算。
- 两个几何对象的 SRID 不一致时，空间函数通常会报错。

---

## 十二、距离计算：`ST_Distance()` vs `ST_Distance_Sphere()`

这是本篇最重要的避坑点之一。

### 12.1 `ST_Distance()`

`ST_Distance(g1, g2)` 计算两个几何对象之间的距离。

但是结果单位不能脱离 SRS 来解释。

如果是 `SRID 0` 平面坐标：

```sql
SELECT ST_Distance(
    ST_GeomFromText('POINT(1 1)'),
    ST_GeomFromText('POINT(2 2)')
) AS distance;
```

你可以把它理解成平面几何距离。

但如果你传的是经纬度，却没有指定正确 SRID，结果就不能直接当成米或公里。

---

### 12.2 `ST_Distance_Sphere()`

`ST_Distance_Sphere(g1, g2)` 会以球面模型计算距离，返回值单位是米。

常见用于：

```text
两个经纬度点之间的大致距离
附近门店
附近 ATM
附近设备
```

示例：

```sql
SET @center = ST_GeomFromText('POINT(121.5654 25.0330)', 4326);

SELECT
    id,
    name,
    ST_Distance_Sphere(location, @center) AS distance_m
FROM stores
ORDER BY distance_m
LIMIT 10;
```

注意：

- 它适合 `POINT` / `MULTIPOINT` 这类场景。
- 它不是所有几何类型的通用万能距离函数。
- 它是球面模型，不等于最精细的椭球测地线模型。
- 如果需要很严谨的 GIS 计算，应确认 MySQL 版本、SRS、函数语义，并考虑专业 GIS 系统。

实务规则：

```text
平面坐标距离 -> ST_Distance()
经纬度点距离的简单近似 -> ST_Distance_Sphere()
严谨地理空间分析 -> 确认 SRS + 版本 + 函数行为，必要时用专业 GIS 工具
```

---

## 十三、空间索引 `SPATIAL INDEX`

空间索引用来优化空间查询。

常见建法：

```sql
CREATE TABLE stores (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    location POINT NOT NULL SRID 4326,
    SPATIAL INDEX idx_location (location)
);
```

也可以后加：

```sql
ALTER TABLE stores ADD SPATIAL INDEX idx_location (location);
```

空间索引的核心理解：

```text
普通索引主要按大小或顺序查找
空间索引主要按空间范围、边界矩形、相交关系等方式辅助查找
```

MySQL 的 `SPATIAL INDEX` 通常可理解为基于 R-Tree 的空间索引。

它特别适合：

```text
点查询
区域查询
相交查询
包含关系查询的候选筛选
```

但不要误解成：

```text
只要建了 SPATIAL INDEX，所有距离排序都会自动很快
```

例如下面这种查询：

```sql
SELECT
    id,
    name,
    ST_Distance_Sphere(location, @center) AS distance_m
FROM stores
ORDER BY distance_m
LIMIT 10;
```

它要对很多点计算距离并排序，未必能只靠空间索引直接解决全部问题。

更常见的优化思路是：

1. 先用范围条件缩小候选数据。
2. 再计算精确距离。
3. 再排序和分页。

对于普通业务系统，如果附近搜索量不大，可以先用简单方案；如果数据量很大、空间查询复杂，再进一步设计空间索引、范围粗筛、缓存或专门搜索服务。

---

## 十四、空间索引和 `NOT NULL`

建立空间索引时，要特别注意 `NOT NULL`。

常见写法：

```sql
location POINT NOT NULL SRID 4326,
SPATIAL INDEX idx_location (location)
```

不建议写成：

```sql
location POINT NULL SRID 4326,
SPATIAL INDEX idx_location (location)
```

如果确实存在「还不知道位置」的业务，可以考虑：

```sql
location POINT NULL SRID 4326
```

但此时要重新确认：

- 是否仍要建立空间索引。
- 查询时是否要排除 `NULL`。
- 业务上未知位置是否应该用独立状态字段表达。

例如：

```sql
location_status TINYINT NOT NULL COMMENT '0=未知, 1=已定位',
location POINT NULL SRID 4326
```

不要为了凑 `NOT NULL`，随便塞一个假的坐标，例如：

```text
POINT(0 0)
```

因为 `POINT(0 0)` 是真实坐标，不是「未知」。

---

## 十五、该用 `POINT`，还是两个 `DECIMAL` 字段？

这是实务中最常见的问题。

### 15.1 只展示地图位置

如果你的需求只是：

```text
保存经度
保存纬度
前端地图展示
不做空间查询
不做距离计算
不做点在区域内判断
```

可以用普通字段：

```sql
longitude DECIMAL(10, 7) NOT NULL,
latitude  DECIMAL(9, 7)  NOT NULL
```

优点：

- 简单。
- 容易理解。
- 前后端传输方便。
- ORM / MyBatis 映射简单。
- 普通查询、导出 Excel、报表都容易处理。

缺点：

- 不是真正的空间对象。
- 不能直接用空间索引。
- 空间函数使用不自然。

---

### 15.2 需要空间计算或空间查询

如果你的需求是：

```text
附近搜索
距离排序
点是否在区域内
路线与区域是否相交
区域覆盖范围
空间索引优化
```

建议使用空间类型：

```sql
location POINT NOT NULL SRID 4326
```

优点：

- 语义明确。
- 可以使用空间函数。
- 可以使用空间索引。
- 更适合 GIS 场景。

缺点：

- 学习成本较高。
- 后端映射较复杂。
- SQL 可读性比普通数值列差。
- 对 SRID、坐标顺序、函数语义要求更高。

---

### 15.3 折中方案

有些系统会同时保存：

```sql
longitude DECIMAL(10, 7) NOT NULL,
latitude  DECIMAL(9, 7)  NOT NULL,
location  POINT NOT NULL SRID 4326
```

这样做的好处：

- 普通业务、报表、Excel 导出用 `longitude` / `latitude`。
- 空间查询用 `location`。

但坏处是：

- 数据会重复。
- 必须保证三者一致。
- 应用层或触发器要维护同步。

所以是否采用折中方案，要看团队能力与业务复杂度。

## 十六、常见字段选型速查

| 业务字段 | 推荐设计 | 理由 |
|---|---|---|
| 店铺位置 | `POINT SRID 4326` 或 `DECIMAL lng/lat` | 看是否需要空间查询 |
| 银行分行位置 | `POINT SRID 4326` | 后续可能做附近分行查询 |
| ATM 位置 | `POINT SRID 4326` | 常见附近查询场景 |
| 用户当前位置 | 通常不直接长期存在用户主表 | 可能涉及频繁更新、隐私、时效性 |
| 车辆当前位置 | `POINT SRID 4326` + 更新时间 | 常用于实时定位 |
| 车辆轨迹 | 轨迹点明细表，点用 `POINT` | 每个点通常有时间、速度等属性 |
| 配送路线模板 | `LINESTRING SRID 4326` | 路线形状比较固定 |
| 行政区域边界 | `POLYGON` / `MULTIPOLYGON` | 区域可能由多个面组成 |
| 服务范围 | `POLYGON` / `MULTIPOLYGON` | 常用点在区域内判断 |
| 地理围栏 | `POLYGON SRID 4326` | 判断设备是否进出区域 |
| 简单地址 | `VARCHAR` | 地址文字不是空间坐标 |
| 邮政编码 | `VARCHAR` | 不是数值计算字段 |
| 城市编号 | `VARCHAR` / `INT` 外键 | 行政区编码不是空间对象 |
| GeoJSON 原始内容 | `JSON` 或文本另存 | 若要空间查询，应转成空间类型 |

## 十七、完整示例：附近店铺

```sql
CREATE TABLE stores (
```

### 17.2 插入数据

```sql
INSERT INTO stores (name, address, location)
VALUES
(

```

### 17.3 查询坐标

### 17.4 查询距离某点最近的店铺

- 区域粗筛。
- 经纬度范围粗筛。
- 空间索引候选筛选。
- 缓存。
- 分片或专门地理搜索服务。

## 十八、完整示例：判断点是否在服务区域内

### 18.1 建表

```sql
CREATE TABLE service_areas (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    area_name VARCHAR(100) NOT NULL,
    boundary POLYGON NOT NULL SRID 4326,
    SPATIAL INDEX idx_boundary (boundary)
);
```

---

### 18.2 插入区域

```sql
INSERT INTO service_areas (area_name, boundary)
VALUES (
    '信义服务区',
    ST_GeomFromText(
        'POLYGON((121.5000 25.0000, 121.6000 25.0000, 121.6000 25.1000, 121.5000 25.1000, 121.5000 25.0000))',
        4326
    )
);
```

---

### 18.3 判断某个点是否在区域内

```sql
SET @p = ST_GeomFromText('POINT(121.5654 25.0330)', 4326);

SELECT
    id,
    area_name
FROM service_areas
WHERE ST_Contains(boundary, @p);
```

也可以写：

```sql
SELECT
    id,
    area_name
FROM service_areas
WHERE ST_Within(@p, boundary);
```

语义上：

```text
区域 contains 点
点 within 区域
```

## 十九、空间数据的有效性

空间数据不仅要语法正确，也要几何上有效。

例如下面的 WKT 在语法上看起来像多边形：

```text
POLYGON((0 0, 10 10, 10 0, 0 10, 0 0))
```

但它可能形成自相交的「蝴蝶形」多边形。

这种数据在空间分析时容易导致：

- 判断结果异常。
- 空间函数报错。
- 距离或包含关系不可靠。
- 索引筛选效果不符合预期。

可以使用：

```sql
SELECT ST_IsValid(
    ST_GeomFromText('POLYGON((0 0, 10 10, 10 0, 0 10, 0 0))')
) AS is_valid;
```

实务建议：

- 区域边界从地图或 GIS 系统导入前要先验证。
- 不要让用户随便画复杂多边形后直接入库。
- 导入行政区边界、商圈边界时，要记录来源和版本。
- 对复杂空间数据，要建立数据校验流程。

## 二十、`GEOMETRY` 不要滥用

`GEOMETRY` 是所有空间类型的父级类型。

它很灵活：

```sql
shape GEOMETRY NOT NULL SRID 4326
```

这个字段可以保存：

```text
POINT
LINESTRING
POLYGON
MULTIPOINT
MULTIPOLYGON
...
```

但普通业务表中，不建议因为它灵活就默认使用。

例如：

```sql
location GEOMETRY NOT NULL SRID 4326
```

不如：

```sql
location POINT NOT NULL SRID 4326
```

因为业务语义是「位置点」，不是任意几何对象。

适合使用 `GEOMETRY` 的情况：

- 地图标注表，同一张表允许点、线、面。
- GIS 编辑器保存用户绘制的不同几何对象。
- 通用空间数据仓库。

不适合使用 `GEOMETRY` 的情况：

- 店铺位置。
- ATM 位置。
- 车辆当前位置。
- 单一业务语义明确的字段。

规则：

```text
能用具体类型，就不要默认用 GEOMETRY。
```

---

## 二十一、不要把空间数据乱塞进字符串或 JSON

错误设计 1：用字符串保存点。

```sql
location VARCHAR(100) NOT NULL
```

保存：

```text
121.5654,25.0330
```

问题：

- 数据库不知道这是坐标。
- 无法使用空间索引。
- 经度纬度容易写反。
- 查询距离很麻烦。
- 数据格式容易不一致。

---

错误设计 2：用 JSON 保存核心坐标。

```sql
location JSON NOT NULL
```

保存：

```json
{
  "lat": 25.0330,
  "lng": 121.5654
}
```

如果只是保存第三方地图 API 回传的原始资料，可以接受。

但如果这是核心位置字段，而且要查询附近门店、判断区域、做距离排序，就不应该只塞进 JSON。

比较好的做法是：

```sql
location POINT NOT NULL SRID 4326
```

如果还要保留原始 API 响应，可以另设：

```sql
raw_map_payload JSON
```

也就是：

```text
核心位置 -> POINT
原始报文 -> JSON
展示地址 -> VARCHAR
```

## 二十二、空间类型和普通业务字段的边界

不是所有和「地点」有关的数据都应该用空间类型。

| 数据 | 是否适合空间类型 | 原因 |
|---|---|---|
| 经纬度坐标 | 适合 | 是空间位置 |
| 地址文字 | 不适合 | 是文本，不是坐标 |
| 邮政编码 | 不适合 | 是编码，不是几何对象 |
| 行政区代码 | 不适合 | 是业务编码，通常外键或字典 |
| 城市名称 | 不适合 | 是文本标签 |
| 区域边界 | 适合 | 是面 |
| 路线轨迹 | 适合 | 是线或点序列 |
| 坐标原始报文 | 看情况 | 可用 JSON 保存原始内容，但核心查询字段应结构化 |

例如分行表可以这样设计：

```sql
CREATE TABLE bank_branches (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    branch_code VARCHAR(20) NOT NULL UNIQUE,
    branch_name VARCHAR(100) NOT NULL,
    city_code VARCHAR(20) NOT NULL,
    district_code VARCHAR(20) NOT NULL,
    address VARCHAR(255) NOT NULL,
    location POINT NOT NULL SRID 4326,
    SPATIAL INDEX idx_location (location),
    INDEX idx_city_district (city_code, district_code)
);
```

这里：

```text
branch_code   业务编码
city_code     行政区编码
district_code 行政区编码
address       地址文本
location      空间位置
```

不要把它们混为一谈。

## 二十三、Java / MyBatis 实务提醒

空间类型在 Java / MyBatis 中不像 `VARCHAR`、`INT`、`DATETIME` 那么直接。

常见处理方式有三种。

### 23.1 插入时由 SQL 转换

应用层传经度、纬度：

```java
BigDecimal longitude = new BigDecimal("121.5654");
BigDecimal latitude = new BigDecimal("25.0330");
```

Mapper 中组织 WKT：

```sql
INSERT INTO stores (name, location)
VALUES (
    #{name},
    ST_GeomFromText(CONCAT('POINT(', #{longitude}, ' ', #{latitude}, ')'), 4326)
)
```

更严谨的做法是在应用层先校验：

```text
经度：(-180, 180]
纬度：[-90, 90]
```

再写入数据库。

---

### 23.2 查询时转成普通字段

不要直接把 `POINT` 硬映射成普通字符串。

更常见的是查询时拆出来：

```sql
SELECT
    id,
    name,
    ST_X(location) AS longitude,
    ST_Y(location) AS latitude,
    ST_AsText(location) AS locationWkt
FROM stores
WHERE id = #{id}
```

Java DTO：

```java
public class StoreLocationDTO {
    private Long id;
    private String name;
    private BigDecimal longitude;
    private BigDecimal latitude;
    private String locationWkt;
}
```

这样简单、清楚，也方便前端使用。

---

### 23.3 复杂 GIS 场景使用专门类库

如果你要处理复杂几何对象，例如：

```text
复杂区域
多区域
路线简化
空间相交
缓冲区
拓扑关系
GeoJSON 转换
```

可以考虑使用 Java GIS 类库，例如 JTS。

但对于一般业务系统，学习阶段不用一开始就引入复杂类库。

先掌握：

```text
POINT
SRID 4326
ST_GeomFromText
ST_AsText
ST_X / ST_Y
ST_Distance_Sphere
ST_Contains / ST_Within
SPATIAL INDEX
```

已经足够应对很多常见场景。

## 二十四、常见错误写法

### 错误 1：经纬度顺序写反

错误：

```sql
ST_GeomFromText('POINT(25.0330 121.5654)', 4326)
```

正确：

```sql
ST_GeomFromText('POINT(121.5654 25.0330)', 4326)
```

记法：

```text
POINT(lng lat)
POINT(经度 纬度)
```

---

### 错误 2：不指定 SRID，却拿来算现实地理距离

不推荐：

```sql
ST_GeomFromText('POINT(121.5654 25.0330)')
```

更明确：

```sql
ST_GeomFromText('POINT(121.5654 25.0330)', 4326)
```

---

### 错误 3：把 `ST_Distance()` 默认当成公里

错误理解：

```text
ST_Distance() 返回的就是公里
```

更准确：

```text
ST_Distance() 的单位和语义取决于 SRS；经纬度点的近似球面距离常用 ST_Distance_Sphere()，其结果单位是米。
```

---

### 错误 4：所有位置字段都用 `GEOMETRY`

不推荐：

```sql
location GEOMETRY NOT NULL
```

推荐：

```sql
location POINT NOT NULL SRID 4326
```

---

### 错误 5：用字符串保存 WKT

不推荐：

```sql
location VARCHAR(100) NOT NULL
```

推荐：

```sql
location POINT NOT NULL SRID 4326
```

---

### 错误 6：用 `POINT(0 0)` 表示未知位置

不推荐：

```text
未知位置 -> POINT(0 0)
```

原因：

```text
POINT(0 0) 是真实坐标，不是 NULL。
```

更合理：

```sql
location POINT NULL SRID 4326,
location_status TINYINT NOT NULL
```

---

### 错误 7：认为空间索引一定能优化所有距离排序

错误理解：

```text
只要建 SPATIAL INDEX，ORDER BY ST_Distance_Sphere() 就一定很快。
```

更准确：

```text
空间索引常用于空间范围、相交、包含等候选筛选；距离排序通常还需要先缩小候选范围，再计算距离。
```

## 二十五、面试和实务常问问题

### 问题 1：`POINT` 里面两个数字分别是什么？

答案：

`POINT(x y)` 中 `x` 是横轴，`y` 是纵轴。经纬度场景下，通常：

```text
x = longitude，经度
y = latitude，纬度
```

所以常见写法是：

```text
POINT(lng lat)
```

---

### 问题 2：`SRID 4326` 是什么？

答案：

`SRID 4326` 通常对应 WGS 84，经纬度坐标系统，常用于 GPS / 地图经纬度。

它不是随便填的数字，也不应该简单说成投影坐标系。

---

### 问题 3：`ST_Distance()` 和 `ST_Distance_Sphere()` 有什么区别？

答案：

`ST_Distance()` 是通用距离函数，结果单位和语义取决于几何对象所属的 SRS。

`ST_Distance_Sphere()` 用球面模型计算点之间的距离，返回值单位是米，常用于经纬度点之间的近似距离。

---

### 问题 4：经纬度一定要用 `POINT` 吗？

答案：

不一定。

如果只是保存和展示坐标，两个 `DECIMAL` 字段更简单。

如果要做距离、附近搜索、点在区域内、空间索引等功能，才更适合使用 `POINT`。

---

### 问题 5：为什么不建议直接用 `GEOMETRY` 保存店铺位置？

答案：

因为店铺位置的业务语义就是一个点，使用 `POINT` 更准确。

`GEOMETRY` 太宽泛，可能误存线、面或集合，降低约束和可读性。

---

### 问题 6：`POLYGON` 为什么首尾点要相同？

答案：

因为 `POLYGON` 表示封闭区域，外圈必须闭合。

例如：

```text
POLYGON((0 0, 10 0, 10 10, 0 10, 0 0))
```

第一个点和最后一个点都是 `0 0`。

---

### 问题 7：空间索引是什么？

答案：

空间索引用来优化空间列上的空间查询，例如点查、区域查、相交查等。

MySQL 的 `SPATIAL INDEX` 通常会建立 R-Tree 空间索引，而不是普通字段常见的 B-Tree 索引。

---

### 问题 8：可以把 GeoJSON 直接存在 `JSON` 字段吗？

答案：

可以保存原始 GeoJSON，但如果你需要数据库参与空间计算和空间索引，应该转换成 MySQL 空间类型。

比较好的拆法是：

```text
用于计算和查询的几何对象 -> 空间类型
用于留存原始报文       -> JSON
```

---

## 二十六、自测问题

### 问题 1

保存一个 ATM 的经纬度位置，最适合的空间类型是什么？

答案：

`POINT`。

如果需要空间查询，建议：

```sql
location POINT NOT NULL SRID 4326
```

---

### 问题 2

下面哪个写法更符合经纬度习惯？

```text
A. POINT(25.0330 121.5654)
B. POINT(121.5654 25.0330)
```

答案：

B。

经纬度场景通常是：

```text
POINT(longitude latitude)
POINT(经度 纬度)
```

---

### 问题 3

保存配送服务范围，应该优先考虑哪个空间类型？

答案：

`POLYGON` 或 `MULTIPOLYGON`。

如果服务范围是一个连续区域，用 `POLYGON`；如果由多个不连续区域组成，用 `MULTIPOLYGON`。

---

### 问题 4

`ST_Distance()` 的结果一定是米吗？

答案：

不一定。

`ST_Distance()` 的距离单位和语义取决于 SRS。经纬度点的近似球面距离可以考虑 `ST_Distance_Sphere()`，其返回值单位是米。

---

### 问题 5

空间列要建立 `SPATIAL INDEX`，通常应该注意什么？

答案：

空间索引列通常需要声明为 `NOT NULL`，并且建议明确 SRID，例如：

```sql
location POINT NOT NULL SRID 4326,
SPATIAL INDEX idx_location (location)
```

---

### 问题 6

如果只是保存地址文字，例如「台北市信义区市府路 45 号」，应该用 `POINT` 吗？

答案：

不应该。

地址文字是文本数据，适合用 `VARCHAR`。如果还需要地图位置，可以另外保存 `POINT`。

---

### 问题 7

为什么不建议用 `POINT(0 0)` 表示未知位置？

答案：

因为 `POINT(0 0)` 是一个真实坐标，不是未知值。

未知位置应该用 `NULL` 或状态字段表达。

---

## 二十七、本节总结

MySQL 空间类型的核心价值不是「可以把经纬度放进数据库」，而是：

> 让数据库把坐标当成几何对象，并通过空间函数和空间索引进行空间关系计算。

最重要的选型规则是：

```text
单个位置       -> POINT
路线 / 轨迹    -> LINESTRING，或轨迹点明细表
单个区域       -> POLYGON
多个区域       -> MULTIPOLYGON
混合几何对象   -> GEOMETRYCOLLECTION，谨慎使用
只展示经纬度   -> DECIMAL longitude + latitude 也可以
需要空间查询   -> 空间类型 + SRID + 空间函数 + 空间索引
```

再进一步：

- `POINT(x y)` 中，地理坐标通常是 `POINT(longitude latitude)`。
- `SRID 4326` 常用于 WGS 84 经纬度，不要简单说成投影坐标系。
- `SRID 0` 更像没有实际地球单位的平面坐标语义。
- `ST_Distance()` 不能脱离 SRS 解释结果单位。
- `ST_Distance_Sphere()` 常用于两个经纬度点之间的球面距离近似，结果单位是米。
- 空间索引可以优化部分空间查询，但不是所有距离排序的万能解。
- `GEOMETRY` 很灵活，但业务明确时优先使用 `POINT`、`LINESTRING`、`POLYGON` 等具体类型。
- 地址、行政区编码、邮政编码、城市名称不是空间对象，不要误用空间类型。
- 如果只是展示坐标，普通 `DECIMAL` 经度/纬度字段可能更简单；如果要做空间计算，再引入空间类型。

一句话抓核心：

> MySQL 空间类型的学习重点不是背类型名，而是分清楚「点、线、面」、明确 `SRID`，并知道什么时候该用空间函数和空间索引。
