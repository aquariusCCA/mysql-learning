# 7 文本字符串类型

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇要解决的问题是：

> MySQL 里存文字时，到底该选 `CHAR`、`VARCHAR`，还是 `TEXT`？为什么很多字段明明都是字符串，却不能无脑使用同一种类型？

字符串字段是业务系统里最常见的字段之一，例如：

- 用户名
- 昵称
- 邮箱
- 手机号
- 身份证号
- 国家代码
- 币种代码
- 商品名称
- 商品标题
- 地址
- 简短备注
- 文章正文
- 评论内容
- 富文本内容
- 日志原文

这些字段表面上都叫「字符串」，但它们背后的业务语义差异很大。

建表时真正要先分清的是：

1. 这个字段是固定长度，还是可变长度？
2. 这个字段是短字符串，还是大段文本？
3. 这个字段是否经常参与查询、排序、分组、唯一约束？
4. 这个字段是否需要前缀索引、全文索引，还是不应该建普通索引？
5. 这个字段是否需要区分大小写、重音、全半角，或二进位比较？
6. 这个字段的长度单位应该理解成字符，还是底层字节？
7. 这个字段是否可能保存中文、emoji、特殊符号或多语言内容？
8. 这个字段是否真的应该存成字符串，而不是数字、日期、JSON、枚举表或外键？

如果只用「能不能存下」来选字符串类型，很容易把数据表设计得过宽、语义不清、索引难做、查询变慢。

这一篇的目标不是让你死背每个类型的最大长度，而是建立一套实务判断：

> 先判断字符串的业务语义，再判断长度变化、字符集、查询方式和索引策略。

如果只能先记一句话：

> 固定短值用 `CHAR`，普通可变字符串优先用 `VARCHAR`，真正的大段内容再用 `TEXT`。

## 30 秒复习入口

- MySQL 常见文本字符串类型包括：`CHAR`、`VARCHAR`、`TINYTEXT`、`TEXT`、`MEDIUMTEXT`、`LONGTEXT`。
- `CHAR(M)`：固定长度字符串，`M` 表示最多字符数，范围通常是 `0 ~ 255`。
- `VARCHAR(M)`：可变长度字符串，`M` 表示最多字符数，理论上可到 `65535`，但实际受最大行大小、字符集和其他列影响。
- `TEXT` 系列：大段文本类型，适合文章正文、长评论、富文本、日志原文等内容。
- 大多数普通业务字符串字段，默认优先考虑 `VARCHAR`。
- 长度固定、值很短、语义明确的字段，可以考虑 `CHAR`，例如国家代码、币种代码、固定状态码。
- `TEXT` 不是「更高级的 `VARCHAR`」，而是面向大文本内容的类型。
- `VARCHAR(20)` 的 `20` 应从「最多 20 个字符」理解，不是固定 20 bytes。
- 底层实际占用多少 bytes，取决于实际内容和字符集，例如 `utf8mb4` 一个字符最多可能需要 4 bytes。
- `CHAR` 存储时会按固定长度补空格，取出时通常会移除尾部空格。
- `VARCHAR` 不会为了固定长度补空格，存储时会保存实际内容，并额外使用 1 或 2 bytes 记录长度。
- `TEXT` / `BLOB` 建普通索引时必须指定索引前缀长度，例如 `INDEX(content(100))`。
- `CHAR` / `VARCHAR` 建前缀索引是可选的，`TEXT` 建索引时 prefix length 是必需的。
- `TEXT` 字段不适合直接当主键、外键或高频精确匹配字段。
- `TEXT` 字段出现在查询结果、排序、分组、临时表中时，通常比普通短字段更需要谨慎。
- 需要长文本搜索时，不要简单依赖 `LIKE '%关键词%'`，应考虑 `FULLTEXT` 或搜索引擎方案。
- 字符串比较是否区分大小写，主要受 collation 影响，不是只由字段类型决定。
- 手机号、身份证号、银行卡号、订单展示号通常更适合用字符串，而不是数值类型。

## 一、先讲结论

文本字符串类型的选择，不是看哪个类型「容量最大」，而是看字段语义。

更合理的判断顺序是：

```text
先判断是否固定短值，
再判断是否普通可变字符串，
最后才判断是否属于大段文本。
```

### 1.1 最重要的选型表

| 需求 | 推荐类型 | 说明 |
| --- | --- | --- |
| 固定长度短代码 | `CHAR(M)` | 例如国家代码、币种代码、固定长度状态码 |
| 大多数普通字符串 | `VARCHAR(M)` | 例如姓名、邮箱、标题、地址、短备注 |
| 大段正文 | `TEXT` / `MEDIUMTEXT` | 例如文章正文、长评论、富文本 |
| 极短但长度不固定 | `VARCHAR(M)` | 例如昵称、标签名、短标题 |
| 可能保存 emoji / 多语言 | `VARCHAR` / `TEXT` + `utf8mb4` | 重点是字符集，而不只是类型 |
| 高频精确查询字段 | 优先 `VARCHAR` | 例如邮箱、用户名、业务编号 |
| 需要唯一约束字段 | 优先 `VARCHAR` / `CHAR` | 避免直接用 `TEXT` 做唯一标识 |
| 长文本搜索 | `TEXT` + `FULLTEXT` / 搜索引擎 | 不建议只依赖 `%keyword%` 模糊查询 |
| 二进位内容 | `BINARY` / `VARBINARY` / `BLOB` | 不属于本文主线，下一篇再讨论 |
| 固定可选值集合 | `ENUM` / 字典表 | 不要只从字符串角度思考 |
| 多选固定集合 | `SET` / 关联表 | `SET` 有限制，复杂业务更推荐关系表 |

### 1.2 一个简单选型流程

```text
这个字段是二进位数据吗？
  └─ 是：看 BINARY / VARBINARY / BLOB，不属于文本字符串主线

这个字段是固定可选值吗？
  └─ 是：考虑 ENUM、字典表、状态表，或 VARCHAR + CHECK

这个字段长度固定，而且很短吗？
  └─ 是：优先 CHAR(M)

这个字段是普通业务字符串吗？
  └─ 是：优先 VARCHAR(M)

这个字段是大段正文、富文本、日志原文吗？
  └─ 是：考虑 TEXT 系列

这个字段经常要精确查询、排序、唯一约束、外键关联吗？
  └─ 是：尽量不要直接用 TEXT，优先 VARCHAR / CHAR，或拆分字段

这个字段需要全文搜索吗？
  └─ 是：考虑 FULLTEXT 或专业搜索引擎
```

### 1.3 常见业务字段选型速查

| 字段 | 推荐类型示例 | 说明 |
| --- | --- | --- |
| `username` | `VARCHAR(50)` | 用户名长度变化明显，通常需要唯一索引 |
| `nickname` | `VARCHAR(50)` | 昵称可能含中文、emoji，注意字符集 |
| `email` | `VARCHAR(254)` | 邮箱是字符串，不是数字；是否大小写敏感要看业务和 collation |
| `phone` | `VARCHAR(20)` | 手机号不是用来计算的数字，可能有国家码、前导 0、`+` 号 |
| `id_no` | `VARCHAR(30)` | 身份证号可能含字母，不适合数值类型 |
| `bank_card_no` | `VARCHAR(32)` | 银行卡号不能用数值型，避免前导 0 和精度问题 |
| `order_no` | `VARCHAR(64)` | 展示编号通常是业务字符串，不等于自增主键 |
| `country_code` | `CHAR(2)` | ISO 国家代码通常固定 2 个字符 |
| `currency_code` | `CHAR(3)` | 例如 `TWD`、`USD`、`JPY` |
| `gender_code` | `CHAR(1)` / `TINYINT` / 字典表 | 看团队建模习惯和业务扩展性 |
| `status_code` | `VARCHAR(30)` / `TINYINT` / 字典表 | 如果状态会扩展，字典表或枚举值管理更清楚 |
| `product_name` | `VARCHAR(200)` | 商品名称属于普通字符串 |
| `title` | `VARCHAR(200)` | 标题通常仍适合 `VARCHAR` |
| `address` | `VARCHAR(255)` / `VARCHAR(500)` | 地址较长但仍通常是普通字段 |
| `remark` | `VARCHAR(500)` / `TEXT` | 短备注用 `VARCHAR`，长备注再考虑 `TEXT` |
| `article_content` | `TEXT` / `MEDIUMTEXT` | 正文属于大段文本 |
| `comment_content` | `TEXT` | 长评论可以用 `TEXT` |
| `html_content` | `MEDIUMTEXT` | 富文本、HTML 可能很长 |
| `log_message` | `TEXT` / `MEDIUMTEXT` | 日志原文通常不适合普通短字段 |

## 二、MySQL 文本字符串类型总览

MySQL 的字符串类型可以先粗略分成两类：

```text
文本字符串：CHAR、VARCHAR、TEXT、ENUM、SET
二进位字符串：BINARY、VARBINARY、BLOB
```

这一篇主要讨论文本字符串，也就是会受到字符集和排序规则影响的类型。

### 2.1 本篇主线类型

| 类型 | 类别 | 主要用途 |
| --- | --- | --- |
| `CHAR` | 固定长度文本字符串 | 固定短代码、固定短标识 |
| `VARCHAR` | 可变长度文本字符串 | 大多数普通业务字符串 |
| `TINYTEXT` | 小型大文本 | 很短的小段文本，实务中不如 `VARCHAR` 常用 |
| `TEXT` | 大文本 | 普通长正文、长评论 |
| `MEDIUMTEXT` | 更大文本 | 富文本、大文档、大日志 |
| `LONGTEXT` | 超大文本 | 极大文本内容，使用前应审慎评估 |

`ENUM` 和 `SET` 也是字符串相关类型，但它们更像「受限制的特殊字符串」，会在后续章节单独讨论。

### 2.2 文本字符串 vs 二进位字符串

文本字符串和二进位字符串最大的差异是：

| 对比项 | 文本字符串 | 二进位字符串 |
| --- | --- | --- |
| 常见类型 | `CHAR`、`VARCHAR`、`TEXT` | `BINARY`、`VARBINARY`、`BLOB` |
| 存储语义 | 字符 | bytes |
| 是否有字符集 | 有 | 没有一般意义上的字符集 |
| 是否受 collation 影响 | 是 | 否，按 byte 比较 |
| 适合内容 | 姓名、标题、正文 | hash、token、加密结果、文件二进位 |

例如：

```sql
name VARCHAR(50) CHARACTER SET utf8mb4
file_hash VARBINARY(32)
content TEXT CHARACTER SET utf8mb4
avatar BLOB
```

注意：

- 文字内容用文本字符串类型。
- 原始二进位内容用二进位字符串类型。
- 不要把图片、PDF、加密后的 bytes 当成 `TEXT` 存。

## 三、`CHAR`：固定长度字符串

`CHAR(M)` 表示固定长度字符串。

### 3.1 核心理解

```sql
code CHAR(5)
```

可以理解成：

> 这个字段最多保存 5 个字符，并且它在语义上更接近固定长度字段。

`CHAR` 适合字段长度固定、值很短、变化很小的场景。

### 3.2 `M` 的含义

在文本字符串类型中，`CHAR(M)` 的 `M` 表示字符数，不是 bytes。

例如：

```sql
name CHAR(5) CHARACTER SET utf8mb4
```

表示最多 5 个字符。

但是底层实际可能占多少 bytes，要看字符集和实际内容。

例如：

```sql
SELECT CHAR_LENGTH('abc') AS char_len, LENGTH('abc') AS byte_len;
SELECT CHAR_LENGTH('你好') AS char_len, LENGTH('你好') AS byte_len;
```

常见理解：

- `CHAR_LENGTH()` 看字符数。
- `LENGTH()` 看 bytes 数。

### 3.3 `CHAR` 的长度范围

`CHAR(M)` 的 `M` 通常范围是：

```text
0 ~ 255
```

实务中很少把 `CHAR` 定义得很长。

如果你想写：

```sql
description CHAR(500)
```

这通常就是设计味道不对。因为长文本或长度变化大的内容，本来就不适合用固定长度思维建模。

### 3.4 `CHAR` 的空格行为

`CHAR` 最容易踩坑的是尾部空格。

一般情况下：

- 存储时，`CHAR` 会向右补空格到指定长度。
- 查询取出时，尾部空格通常会被移除。
- 如果启用特殊 SQL mode，尾部空格行为可能有所不同。

示例：

```sql
CREATE TABLE char_space_demo (
    code CHAR(4)
);

INSERT INTO char_space_demo (code) VALUES ('ab');

SELECT code, CHAR_LENGTH(code), LENGTH(code)
FROM char_space_demo;
```

你不应该把 `CHAR` 当成「可以可靠保存尾部空格」的类型。

如果尾部空格本身有业务意义，应重新思考字段设计，甚至考虑 `VARCHAR` 或二进位类型。

### 3.5 适合 `CHAR` 的场景

`CHAR` 适合：

- 固定长度国家代码：`CHAR(2)`，例如 `TW`、`US`、`JP`
- 固定长度币种代码：`CHAR(3)`，例如 `TWD`、`USD`、`JPY`
- 固定长度性别代码：`CHAR(1)`，例如 `M`、`F`
- 固定长度短状态码：例如 `A`、`I`
- 固定长度校验码或短代码

示例：

```sql
CREATE TABLE country (
    country_code CHAR(2) NOT NULL,
    country_name VARCHAR(100) NOT NULL,
    PRIMARY KEY (country_code)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

### 3.6 不适合 `CHAR` 的场景

不建议用 `CHAR` 保存：

- 用户名
- 昵称
- 邮箱
- 地址
- 商品名称
- 文章标题
- 备注
- 长描述
- 富文本内容

这些字段长度变化明显，用 `VARCHAR` 或 `TEXT` 更自然。

## 四、`VARCHAR`：可变长度字符串

`VARCHAR(M)` 表示可变长度字符串，是业务建表中最常用的字符串类型。

### 4.1 核心理解

```sql
name VARCHAR(50)
```

可以理解成：

> 这个字段最多保存 50 个字符，但实际存储时只保存实际内容长度，再额外记录长度信息。

它适合大多数普通业务字符串。

### 4.2 `VARCHAR(M)` 的 `M` 是字符数

`VARCHAR(20)` 中的 `20` 应理解成最多 20 个字符，而不是固定 20 bytes。

例如：

```sql
CREATE TABLE varchar_len_demo (
    name VARCHAR(20) CHARACTER SET utf8mb4
);
```

这里的 `VARCHAR(20)` 表示最多 20 个字符。

但是实际占用 bytes 会受到内容和字符集影响：

```sql
SELECT
    CHAR_LENGTH('Hello') AS hello_chars,
    LENGTH('Hello') AS hello_bytes,
    CHAR_LENGTH('你好') AS cn_chars,
    LENGTH('你好') AS cn_bytes,
    CHAR_LENGTH('🙂') AS emoji_chars,
    LENGTH('🙂') AS emoji_bytes;
```

这也是为什么不能把 `VARCHAR(20)` 简单理解成「20 bytes」。

### 4.3 `VARCHAR` 的最大长度

`VARCHAR(M)` 理论上 `M` 可以到 `65535`，但这个值不是你可以随便使用的业务长度。

实际可用长度会受到几个因素影响：

1. MySQL 最大行大小限制。
2. 表中其他列也会占用行空间。
3. 字符集会影响每个字符可能需要的最大 bytes。
4. `VARCHAR` 自身还需要 1 或 2 bytes 保存长度。
5. 是否允许 `NULL`、行格式、存储引擎也会影响实际表现。

例如使用 `utf8mb4` 时，一个字符最多可能需要 4 bytes。此时如果只从最大 bytes 角度估算，`VARCHAR` 可声明的最大字符数会明显小于 `65535`。

所以实务上不要为了「保险」写：

```sql
name VARCHAR(10000)
```

更合理的是根据业务上限定义：

```sql
username VARCHAR(50)
email VARCHAR(254)
title VARCHAR(200)
address VARCHAR(500)
```

### 4.4 `VARCHAR` 的存储特点

`VARCHAR` 是可变长度类型。

可以简化理解为：

```text
实际内容 bytes + 长度前缀
```

长度前缀通常是：

- 内容最大长度不超过 255 bytes：额外 1 byte。
- 内容最大长度可能超过 255 bytes：额外 2 bytes。

注意这里说的是 bytes，不是字符数。

### 4.5 适合 `VARCHAR` 的场景

`VARCHAR` 适合：

- 用户名
- 昵称
- 邮箱
- 手机号
- 身份证号
- 银行卡号
- 订单编号
- 商品名称
- 商品标题
- 地址
- 短备注
- URL
- 标签名称
- 外部系统代码

示例：

```sql
CREATE TABLE user_profile (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    nickname VARCHAR(50) NULL,
    email VARCHAR(254) NOT NULL,
    phone VARCHAR(20) NULL,
    address VARCHAR(500) NULL,
    UNIQUE KEY uk_user_profile_username (username),
    UNIQUE KEY uk_user_profile_email (email)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

### 4.6 为什么大多数普通字段优先用 `VARCHAR`

因为真实业务中的文字字段通常长度变化明显：

- 不同用户的姓名长度不同。
- 不同商品的名称长度不同。
- 不同地址长度差异很大。
- 不同邮箱长度也不一样。

如果这些字段都用 `CHAR`，固定长度语义不自然。

如果这些字段都用 `TEXT`，又会让索引、默认值、查询、排序、外键等设计更麻烦。

所以：

> 普通业务字符串，优先从 `VARCHAR` 开始思考。

## 五、`CHAR` vs `VARCHAR` 怎么选

这是文本字符串类型的第一组核心比较。

### 5.1 对比表

| 对比项 | `CHAR` | `VARCHAR` |
| --- | --- | --- |
| 长度特性 | 固定长度 | 可变长度 |
| `M` 的单位 | 字符数 | 字符数 |
| 常见范围 | `0 ~ 255` | 理论可到 `65535`，实际受行大小和字符集影响 |
| 存储方式 | 固定长度语义，常涉及右侧补空格 | 实际内容 + 长度前缀 |
| 尾部空格 | 取出时通常会去掉尾部空格 | 尾部空格通常会保留 |
| 适合场景 | 固定短代码 | 大多数普通字符串 |
| 常见例子 | 国家代码、币种代码 | 用户名、邮箱、地址、标题 |

### 5.2 选型口诀

```text
固定、短、语义像代码：CHAR
不固定、常规业务字段：VARCHAR
```

### 5.3 典型例子

更适合 `CHAR`：

```sql
country_code CHAR(2)
currency_code CHAR(3)
gender_code CHAR(1)
```

更适合 `VARCHAR`：

```sql
username VARCHAR(50)
email VARCHAR(254)
product_name VARCHAR(200)
address VARCHAR(500)
```

### 5.4 不要过度迷信 `CHAR` 性能

有些资料会说：

> `CHAR` 固定长度，所以一定比 `VARCHAR` 快。

这个说法在现代业务系统里不能直接当作选型原则。

更合理的判断是：

1. 字段语义是否固定长度？
2. 字段是否很短？
3. 是否经常参与索引比较？
4. 数据量是否足够大到值得为了这个差异优化？
5. 使用的存储引擎、字符集、行格式是否真的让 `CHAR` 更有利？

多数业务表中，类型语义和查询模式比「理论性能」更重要。

## 六、字符数、字节数、字符集与排序规则

这是整篇最容易混淆的部分。

### 6.1 字符数和字节数不是一回事

在 MySQL 文本字符串类型中，`CHAR(M)` 和 `VARCHAR(M)` 的 `M` 是字符数。

但是底层存储要占多少 bytes，要看字符集和具体内容。

示例：

```sql
SELECT
    CHAR_LENGTH('A') AS a_chars,
    LENGTH('A') AS a_bytes,
    CHAR_LENGTH('你') AS ni_chars,
    LENGTH('你') AS ni_bytes,
    CHAR_LENGTH('🙂') AS emoji_chars,
    LENGTH('🙂') AS emoji_bytes;
```

常见判断：

| 函数 | 含义 |
| --- | --- |
| `CHAR_LENGTH(str)` | 返回字符数 |
| `LENGTH(str)` | 返回 bytes 数 |

所以：

```sql
VARCHAR(20)
```

更应该理解为：

```text
最多 20 个字符，但实际 bytes 占用取决于字符集和内容。
```

### 6.2 为什么推荐理解 `utf8mb4`

现代业务系统通常建议优先考虑 `utf8mb4`，因为它可以支持更完整的 Unicode 字符，包括很多 emoji。

例如：

```sql
CREATE TABLE article (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    content TEXT NOT NULL
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

注意：

- `utf8mb4` 一个字符最多可能需要 4 bytes。
- 中文通常不是 1 byte。
- emoji 往往需要更多 bytes。
- 字段能存多少字符，和底层最大 bytes 限制有关。

### 6.3 字符集和排序规则的差异

字符集决定：

```text
这个字段能保存哪些字符，以及这些字符如何编码。
```

排序规则决定：

```text
字符串如何比较、排序、是否区分大小写、是否区分重音等。
```

例如：

```sql
CREATE TABLE collation_demo (
    name VARCHAR(50)
        CHARACTER SET utf8mb4
        COLLATE utf8mb4_0900_ai_ci
);
```

`utf8mb4_0900_ai_ci` 可以粗略拆成：

| 部分 | 含义 |
| --- | --- |
| `utf8mb4` | 字符集 |
| `0900` | Unicode Collation Algorithm 版本相关命名 |
| `ai` | accent-insensitive，不区分重音 |
| `ci` | case-insensitive，不区分大小写 |

常见后缀：

| 后缀 | 大意 |
| --- | --- |
| `_ci` | case-insensitive，不区分大小写 |
| `_cs` | case-sensitive，区分大小写 |
| `_bin` | binary collation，按编码值比较 |

### 6.4 collation 会影响唯一约束

假设字段使用不区分大小写的 collation：

```sql
email VARCHAR(254) COLLATE utf8mb4_0900_ai_ci
```

那么在唯一索引下，下面两个值可能会被视为相同：

```text
Tom@example.com
tom@example.com
```

这不一定是坏事，很多业务本来就希望邮箱唯一时不区分大小写。

但重点是：

> 是否区分大小写，应该由业务决定，而不是无意识地沿用默认 collation。

如果你需要严格区分大小写，可以考虑：

```sql
username VARCHAR(50) COLLATE utf8mb4_0900_as_cs
```

或使用二进位比较规则、应用层规范化字段等方案。

## 七、`TEXT` 系列：大段文本

当字段不再是普通短字符串，而是大段内容时，就进入 `TEXT` 系列。

### 7.1 `TEXT` 系列类型

常见 `TEXT` 类型包括：

| 类型 | 最大长度级别 | 常见理解 | 典型场景 |
| --- | --- | --- | --- |
| `TINYTEXT` | 小 | 很短的小段文本 | 实务中较少使用，常被 `VARCHAR` 替代 |
| `TEXT` | 中 | 普通长文本 | 文章正文、评论、说明 |
| `MEDIUMTEXT` | 大 | 更大的文本 | 富文本、大文档、较长日志 |
| `LONGTEXT` | 极大 | 超大文本 | 极大内容，使用前应审慎评估 |

从存储上看，`TEXT` 系列是可变长度类型，会保存实际内容并额外保存长度信息。

### 7.2 `TEXT` 系列容量不要只按字符理解

`TEXT` 系列的容量限制更应该从 bytes 角度理解。

简化记忆：

| 类型 | 大致上限 |
| --- | --- |
| `TINYTEXT` | 约 255 bytes |
| `TEXT` | 约 64 KB |
| `MEDIUMTEXT` | 约 16 MB |
| `LONGTEXT` | 约 4 GB |

注意：

- 这些是 bytes 级别的上限，不是「保证可存这么多个字符」。
- 如果使用 `utf8mb4`，一个字符最多可能占 4 bytes。
- 实际能传输和写入多大的值，还会受到 `max_allowed_packet`、客户端、服务端内存等因素影响。

### 7.3 适合 `TEXT` 的场景

适合 `TEXT` 的字段通常是「内容型字段」：

- 文章正文
- 新闻正文
- 商品长描述
- 用户长评论
- 富文本 HTML
- Markdown 内容
- 错误日志原文
- 第三方接口原始响应文本
- 长说明文案

示例：

```sql
CREATE TABLE article (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    summary VARCHAR(500) NULL,
    content MEDIUMTEXT NOT NULL,
    created_at DATETIME(3) NOT NULL,
    KEY idx_article_created_at (created_at)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

这里：

- `title` 是标题，适合 `VARCHAR(200)`。
- `summary` 是摘要，适合 `VARCHAR(500)`。
- `content` 是正文，适合 `TEXT` 或 `MEDIUMTEXT`。

### 7.4 不要把所有字符串都写成 `TEXT`

错误倾向：

```sql
CREATE TABLE bad_user (
    username TEXT,
    email TEXT,
    phone TEXT,
    address TEXT
);
```

问题不在于「不能存」，而是：

1. 字段语义不清楚。
2. 长度约束不明确。
3. 不利于唯一索引和普通索引设计。
4. 查询、排序、临时表可能更重。
5. 外键、主键、默认值等设计会变得别扭。
6. 应用层和数据库层都更难判断字段合理性。

更好的设计：

```sql
CREATE TABLE good_user (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(254) NOT NULL,
    phone VARCHAR(20) NULL,
    address VARCHAR(500) NULL,
    UNIQUE KEY uk_good_user_username (username),
    UNIQUE KEY uk_good_user_email (email)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

## 八、`VARCHAR` vs `TEXT` 怎么选

这是文本字符串类型的第二组核心比较。

### 8.1 对比表

| 对比项 | `VARCHAR` | `TEXT` |
| --- | --- | --- |
| 定位 | 普通可变字符串 | 大段文本 |
| 长度限制 | 受 `M`、行大小、字符集影响 | 按 `TEXT` 系列类型决定大容量上限 |
| 是否适合短业务字段 | 适合 | 不适合当默认选择 |
| 是否适合长正文 | 不适合硬塞 | 适合 |
| 普通索引 | 可直接建，也可建前缀索引 | 建索引必须指定前缀长度 |
| 唯一约束 | 常用 | 不建议直接使用，除非非常明确 |
| 外键 | 可用 | 通常不可用 |
| 默认值 | 可用普通 literal default | 新版本可用表达式默认值，但实务上不建议依赖 |
| 查询成本 | 较轻 | 大字段查询、排序、临时表更需谨慎 |
| 典型字段 | 用户名、邮箱、标题、地址 | 正文、富文本、日志原文 |

### 8.2 什么时候用 `VARCHAR`

优先用 `VARCHAR` 的场景：

- 字段有明确最大长度。
- 字段是普通业务属性。
- 字段经常参与查询、排序、唯一约束。
- 字段可能会被当成外键或业务键。
- 字段通常不会非常大。

例如：

```sql
username VARCHAR(50)
email VARCHAR(254)
title VARCHAR(200)
address VARCHAR(500)
```

### 8.3 什么时候用 `TEXT`

考虑 `TEXT` 的场景：

- 内容明显是大段文本。
- 长度上限难以用普通 `VARCHAR` 合理表达。
- 不适合经常做精确匹配。
- 通常不会作为业务唯一标识。
- 查询时经常只是详情页才读取。

例如：

```sql
content TEXT
html_content MEDIUMTEXT
log_message TEXT
raw_response MEDIUMTEXT
```

### 8.4 边界判断

如果字段是：

```text
短备注、标题、摘要、地址
```

不要一看到「可能比较长」就立刻用 `TEXT`。

可以先考虑：

```sql
remark VARCHAR(500)
summary VARCHAR(1000)
address VARCHAR(500)
```

如果字段是：

```text
正文、富文本、大段日志、接口原文
```

再考虑：

```sql
content TEXT
content MEDIUMTEXT
```

一句话：

> 能合理定义业务最大长度、且会参与普通查询的字段，优先 `VARCHAR`；真正内容型的大段文本，才考虑 `TEXT`。

## 九、`TEXT` 的索引、查询与性能注意事项

`TEXT` 不是不能查，也不是不能建索引，但它的使用方式和普通短字符串不同。

### 9.1 `TEXT` 建普通索引必须指定前缀长度

错误写法：

```sql
CREATE TABLE article_bad_index (
    content TEXT,
    INDEX idx_content (content)
);
```

更合理的写法：

```sql
CREATE TABLE article_good_index (
    content TEXT,
    INDEX idx_content_prefix (content(100))
);
```

意思是：

```text
只对 content 前 100 个字符建立索引。
```

注意：

- 对 `TEXT` / `BLOB` 建索引时，必须指定 prefix length。
- 对 `CHAR` / `VARCHAR` 建前缀索引是可选的。
- SQL 中写的 prefix length 对非二进位字符串通常按字符解释。
- 存储引擎限制通常按 bytes 计算，所以多字节字符集下要特别注意。

### 9.2 前缀索引不是完整内容索引

前缀索引只索引前面一段。

例如：

```sql
INDEX idx_content_prefix (content(100))
```

代表索引只覆盖前 100 个字符。

如果查询条件区分度主要出现在第 100 个字符之后，这个索引帮助就有限。

所以前缀索引适合：

- 前缀区分度较高的字段。
- URL 前缀、路径前缀、标题前缀等。
- 只需要辅助过滤，而不是完整内容检索。

不适合：

- 任意关键词搜索。
- 全文内容检索。
- 需要严格按完整内容唯一的场景。

### 9.3 长文本搜索不要只靠 `LIKE '%keyword%'`

下面这种查询很常见：

```sql
SELECT *
FROM article
WHERE content LIKE '%MySQL%';
```

它的问题是：

- 前面有 `%`，普通 B-tree 索引通常难以有效利用。
- 内容字段很大时，扫描成本高。
- 数据量上来后性能容易恶化。

如果真的需要长文本搜索，应考虑：

1. MySQL `FULLTEXT` 索引。
2. Elasticsearch、OpenSearch、Meilisearch 等搜索引擎。
3. 额外建立关键词、倒排索引或搜索表。
4. 针对业务场景做摘要字段、标签字段、状态字段拆分。

### 9.4 避免无脑 `SELECT *`

如果表里有 `TEXT` 字段，不建议在列表页随手写：

```sql
SELECT * FROM article;
```

更好的做法是：

```sql
SELECT id, title, summary, created_at
FROM article
ORDER BY created_at DESC
LIMIT 20;
```

详情页再查正文：

```sql
SELECT id, title, content, created_at
FROM article
WHERE id = 1001;
```

这样做的好处：

- 列表页不用传输大量正文。
- 减少内存和网络开销。
- 避免大字段参与不必要的临时表处理。
- 查询意图更清楚。

### 9.5 `TEXT` 不适合做外键字段

在 InnoDB 这类常见场景中，外键字段需要索引支持。

但 `TEXT` 建索引必须使用 prefix length，而外键不支持前缀索引作为约束依据。

所以 `TEXT` 不适合当外键列。

如果你想用一段文字作为关联键，通常应该改成：

```sql
id BIGINT UNSIGNED PRIMARY KEY
```

或者：

```sql
code VARCHAR(64) NOT NULL UNIQUE
```

然后其他表引用这个 `id` 或 `code`。

## 十、默认值、空字符串与 `NULL`

字符串字段经常会遇到三个概念：

```text
NULL
空字符串 ''
默认值 DEFAULT
```

它们不是一回事。

### 10.1 `NULL` 和空字符串不同

```text
NULL：未知、没有值、不适用
''：已知为空字符串
```

例如：

```sql
middle_name VARCHAR(50) NULL
nickname VARCHAR(50) NULL
remark VARCHAR(500) NULL
```

如果用户没有填写昵称，你可以用 `NULL` 表示「没有提供」。

如果业务明确要求昵称不可为空：

```sql
nickname VARCHAR(50) NOT NULL
```

但要不要允许 `''`，还需要应用层或 `CHECK` 进一步约束。

### 10.2 `VARCHAR` 可以有普通默认值

例如：

```sql
status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'
remark VARCHAR(500) NOT NULL DEFAULT ''
```

但不要为了避免 `NULL` 就到处写 `DEFAULT ''`。

比较好的判断是：

- 字段业务上确实有默认值：可以设 `DEFAULT`。
- 字段只是用户没填写：考虑 `NULL`。
- 字段必须填写：`NOT NULL`，并在应用层验证。

### 10.3 `TEXT` 默认值不要想当然

现代 MySQL 对 `TEXT` / `BLOB` / `JSON` 等类型的默认值规则比较特殊：

- 普通 literal default 写法容易出错。
- 新版本允许表达式形式的默认值，例如 `DEFAULT ('')` 这种表达式写法。
- 但实务上，`TEXT` 字段通常不建议依赖默认值表达业务含义。

更推荐：

```sql
content TEXT NULL
```

或者：

```sql
content TEXT NOT NULL
```

并由应用层在插入前明确决定内容。

也就是说：

> 如果一个字段需要很自然地使用默认值，它通常更像普通业务字段，应该先思考是否用 `VARCHAR` 更合理。

## 十一、字符串字段与索引设计

字符串字段经常参与索引，但不同类型的索引策略不同。

### 11.1 精确匹配字段

例如：

- 用户名
- 邮箱
- 手机号
- 订单号
- 外部系统编号

适合：

```sql
username VARCHAR(50) NOT NULL,
email VARCHAR(254) NOT NULL,
order_no VARCHAR(64) NOT NULL,
UNIQUE KEY uk_username (username),
UNIQUE KEY uk_email (email),
UNIQUE KEY uk_order_no (order_no)
```

这类字段不适合用 `TEXT`。

### 11.2 前缀查询字段

如果经常这样查：

```sql
WHERE name LIKE 'Tom%'
```

普通索引可能有机会被使用。

例如：

```sql
KEY idx_name (name)
```

但如果是：

```sql
WHERE name LIKE '%Tom%'
```

前面有 `%`，普通 B-tree 索引通常难以有效利用。

### 11.3 前缀索引字段

如果字段较长，但前面一段已经有足够区分度，可以考虑前缀索引：

```sql
url VARCHAR(1000) NOT NULL,
KEY idx_url_prefix (url(191))
```

但要注意：

- 前缀索引不是完整索引。
- prefix length 太短，区分度可能不足。
- prefix length 太长，索引体积会变大。
- 多字节字符集下，索引限制按 bytes 计算时更容易踩到上限。

### 11.4 排序和分组字段

经常 `ORDER BY`、`GROUP BY` 的字段，最好不要轻易设计成 `TEXT`。

例如：

```sql
ORDER BY title
GROUP BY category_name
```

如果这些字段长度明确且不大，优先用：

```sql
title VARCHAR(200)
category_name VARCHAR(100)
```

不要写成：

```sql
title TEXT
category_name TEXT
```

### 11.5 唯一约束字段

如果字段要唯一，通常应优先考虑 `VARCHAR` 或 `CHAR`。

例如：

```sql
email VARCHAR(254) NOT NULL,
UNIQUE KEY uk_email (email)
```

如果你想对长文本做唯一约束，要非常小心，因为：

1. `TEXT` 普通索引需要 prefix length。
2. prefix unique 只能保证前缀唯一，不等于完整内容唯一。
3. 长文本完整唯一通常不适合直接靠字段本身建索引解决。

更常见的做法是保存 hash：

```sql
content MEDIUMTEXT NOT NULL,
content_sha256 BINARY(32) NOT NULL,
UNIQUE KEY uk_content_sha256 (content_sha256)
```

然后由应用层或生成列维护 hash。

## 十二、常见字段设计误区

### 12.1 手机号不要用整数类型

手机号看起来是数字，但它不是用来数学计算的数字。

不建议：

```sql
phone BIGINT
```

更建议：

```sql
phone VARCHAR(20)
```

原因：

- 可能有国家码，例如 `+886`。
- 可能有前导 `0`。
- 可能包含分隔符或扩展号。
- 不需要加减乘除。
- 作为字符串查询和展示更自然。

### 12.2 身份证号、银行卡号不要用数值类型

不建议：

```sql
id_no BIGINT
bank_card_no BIGINT
```

更建议：

```sql
id_no VARCHAR(30)
bank_card_no VARCHAR(32)
```

原因：

- 可能包含字母。
- 可能有前导 0。
- 长度可能超过数值类型安全范围。
- 不参与数学计算。
- 展示格式才是主要语义。

### 12.3 订单号要区分内部主键和展示编号

常见设计：

```sql
id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
order_no VARCHAR(64) NOT NULL UNIQUE
```

这里：

- `id` 是内部主键，用于关联和索引。
- `order_no` 是业务展示编号，用于给用户、客服、外部系统查看。

不要把两者混在一起。

### 12.4 状态字段不要无脑用字符串

状态字段可以有多种设计方式：

```sql
status TINYINT NOT NULL
status VARCHAR(30) NOT NULL
status_code VARCHAR(30) NOT NULL
status_id BIGINT UNSIGNED NOT NULL
```

怎么选要看业务：

| 场景 | 可能方案 |
| --- | --- |
| 状态很少、系统内部固定 | `TINYINT` + 代码枚举 |
| 状态需要可读性 | `VARCHAR(30)` |
| 状态需要后台维护、多语言、排序 | 字典表 / 状态表 |
| 状态只有固定几个且很少变化 | `ENUM` 也可考虑，但要理解维护成本 |

不要因为它「看起来像文字」就一定用 `VARCHAR`，也不要为了省空间就一律用数字。

### 12.5 URL 不一定用 `TEXT`

URL 有时很长，但多数业务中可以先考虑：

```sql
url VARCHAR(1000)
```

如果确实可能非常长，再考虑：

```sql
url TEXT
```

但如果要经常按 URL 精确查询或唯一约束，建议额外保存 hash：

```sql
url TEXT NOT NULL,
url_sha256 BINARY(32) NOT NULL,
UNIQUE KEY uk_url_sha256 (url_sha256)
```

## 十三、完整建表示例

下面是一个比较接近实际业务的文章表设计示例。

```sql
CREATE TABLE article (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,

    -- 普通短字符串：适合 VARCHAR
    title VARCHAR(200) NOT NULL,
    slug VARCHAR(200) NOT NULL,
    summary VARCHAR(500) NULL,

    -- 固定短代码：适合 CHAR
    language_code CHAR(5) NOT NULL DEFAULT 'zh-TW',

    -- 大段内容：适合 TEXT / MEDIUMTEXT
    content MEDIUMTEXT NOT NULL,

    -- 搜索或列表页常用字段，不要每次都依赖 content
    author_name VARCHAR(100) NOT NULL,
    category_code VARCHAR(50) NOT NULL,

    -- 时间字段
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,

    PRIMARY KEY (id),
    UNIQUE KEY uk_article_slug (slug),
    KEY idx_article_category_created (category_code, created_at),
    KEY idx_article_title_prefix (title(50)),
    FULLTEXT KEY ft_article_title_content (title, content)
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

这个例子里：

- `title`：标题，使用 `VARCHAR(200)`。
- `slug`：文章唯一别名，使用 `VARCHAR(200)` 并建立唯一索引。
- `summary`：摘要，使用 `VARCHAR(500)`。
- `language_code`：语言代码，长度相对固定，使用 `CHAR(5)`。
- `content`：正文，使用 `MEDIUMTEXT`。
- `author_name`：作者名，使用 `VARCHAR(100)`。
- `category_code`：分类代码，使用 `VARCHAR(50)`。
- `FULLTEXT`：用于全文搜索，而不是依赖普通 B-tree 索引搜索整篇正文。

## 十四、常见混淆点

### 14.1 `VARCHAR(20)` 不是 20 bytes

`VARCHAR(20)` 表示最多 20 个字符。

实际 bytes 取决于字符集和内容。

### 14.2 `TEXT` 不是更高级的 `VARCHAR`

`TEXT` 是大段文本类型，不是普通字符串字段的万能替代品。

用户名、邮箱、手机号、订单号、标题通常不应该随手写成 `TEXT`。

### 14.3 `CHAR` 不等于一定更快

`CHAR` 的意义是固定长度语义清楚。

不要为了「听说快」把长度变化明显的字段写成 `CHAR`。

### 14.4 字符集不等于排序规则

字符集决定能存什么字符。

排序规则决定怎么比较和排序。

例如，是否区分大小写，主要看 collation。

### 14.5 `LIKE '%keyword%'` 不是普通索引友好的查询

如果前面有 `%`，普通 B-tree 索引通常很难发挥作用。

长文本搜索应考虑 `FULLTEXT` 或搜索引擎。

### 14.6 `TEXT` 前缀索引不是完整内容索引

```sql
INDEX(content(100))
```

只索引前 100 个字符，不代表整段文本都有完整索引。

### 14.7 字符串字段不要和数字字段混着比

如果字段是字符串：

```sql
order_no VARCHAR(64)
```

查询时就不要写：

```sql
WHERE order_no = 123456
```

更应该写：

```sql
WHERE order_no = '123456'
```

因为字符串和数字混合比较可能触发隐式类型转换，影响语义和索引使用。

## 十六、一句话抓核心

文本字符串类型的选择，不是只看「能不能存下」，而是先分清这个字段是「固定短值」「普通可变字符串」还是「真正的大段文本」；再结合字符集、排序规则、索引方式和查询场景决定最终类型。
