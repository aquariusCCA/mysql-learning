# 3 浮点类型

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇要解决的问题是：

> 建表时，遇到带小数的字段，到底该用 `FLOAT`、`DOUBLE`，还是应该改用 `DECIMAL`？为什么明明只是存 `0.1`、`1.1` 这种简单小数，数据库里却可能出现精度误差？

浮点类型是 MySQL 数据类型里最容易「看起来懂了，实际建表时选错」的一类。因为很多人会直觉认为：

- 有小数点，就用 `FLOAT` 或 `DOUBLE`。
- `DOUBLE` 比 `FLOAT` 精度高，所以金额用 `DOUBLE` 应该也可以。
- 写成 `FLOAT(10,2)`，就能像 `DECIMAL(10,2)` 一样精确保存两位小数。
- 查询时直接用 `=` 比较浮点数，应该没有问题。

这些想法都很危险。

这一篇的重点不是死背 `FLOAT` 和 `DOUBLE` 的语法，而是建立一套判断流程：

1. 这个小数是「精确值」还是「近似值」？
2. 这个字段是否涉及金额、余额、价格、税额、汇率、会计或交易？
3. 查询时是否需要精确相等比较？
4. 聚合计算后是否必须得到稳定、精确的小数结果？
5. 这个字段只是测量值、统计值、科学计算值，还是业务结算值？

如果只能先记一句话：

> `FLOAT` / `DOUBLE` 适合存「近似值」，不适合存「必须精确的小数」；只要涉及金额、结算、会计、价格，优先考虑 `DECIMAL`。

## 30 秒复习入口

- MySQL 常见浮点类型主要是 `FLOAT` 和 `DOUBLE`。
- `FLOAT` 是单精度浮点数，通常占 4 bytes。
- `DOUBLE` 是双精度浮点数，通常占 8 bytes。
- `DOUBLE` 比 `FLOAT` 能保留更多有效数字，但两者本质上都是「近似数值类型」。
- 浮点数不能保证十进制小数被精确保存，例如 `0.1` 在二进制浮点中通常只能近似表示。
- 金额、价格、余额、税额、汇率、会计、交易字段，不应优先使用 `FLOAT` / `DOUBLE`，应优先考虑 `DECIMAL`。
- `FLOAT(M,D)`、`DOUBLE(M,D)` 是 MySQL 的非标准旧式扩展写法，已经不建议继续依赖。
- 浮点数比较不要直接依赖 `=`，更稳妥的做法是使用「容差范围」比较。
- 如果你要的是「精确到几位小数」，应该先想到 `DECIMAL(M,D)`，而不是 `FLOAT(M,D)`。

## 一、先讲结论

浮点类型选型可以先抓住一句话：

> 只要字段值允许存在微小误差，可以考虑 `FLOAT` / `DOUBLE`；只要字段值必须精确，尤其涉及钱，优先使用 `DECIMAL`。

### 1.1 最常用的实务判断

| 字段场景 | 是否建议用浮点 | 推荐类型 | 原因 |
| --- | --- | --- | --- |
| 商品价格 | 不建议 | `DECIMAL(10,2)` / `DECIMAL(18,2)` | 金额必须精确 |
| 账户余额 | 不建议 | `DECIMAL(18,2)` 或更大 | 交易与账务不能接受近似误差 |
| 税额、手续费 | 不建议 | `DECIMAL` | 涉及结算与对账 |
| 汇率 | 通常不建议用浮点 | `DECIMAL(18,6)` / `DECIMAL(20,8)` | 汇率虽然是小数，但业务上常要求固定精度 |
| 折扣率，例如 `0.85` | 视业务而定 | `DECIMAL(5,4)` 较常见 | 常需要精确表示几位小数 |
| 温度、湿度、传感器读数 | 可以 | `DOUBLE` / `FLOAT` | 本身通常就是测量近似值 |
| 科学计算结果 | 可以 | `DOUBLE` | 需要较高精度的近似计算 |
| 统计分析结果 | 可以 | `DOUBLE` | 比例、均值、模型分数通常可接受近似 |
| 经纬度 | 视场景而定 | `DECIMAL(10,7)` / `DOUBLE` / `POINT` | 只存坐标展示可用 `DECIMAL`；空间计算可考虑空间类型 |

### 1.2 一个简单决策流程

可以用下面的问题判断：

```text
这个字段是小数吗？
  ├─ 不是小数：回去考虑整数、字符串、日期等类型
  └─ 是小数：继续问
        │
        ├─ 是否涉及金额、价格、余额、税额、汇率、交易、会计？
        │     └─ 是：优先 DECIMAL
        │
        ├─ 是否要求精确到固定小数位，而且不能有近似误差？
        │     └─ 是：优先 DECIMAL
        │
        ├─ 是否只是测量值、统计值、科学计算值？
        │     └─ 是：可以考虑 DOUBLE / FLOAT
        │
        └─ 不确定：优先 DECIMAL，或回到业务语义确认
```

### 1.3 最容易犯的错误

不要用下面这种思路选型：

```sql
price DOUBLE
balance FLOAT
tax_rate FLOAT(5,2)
amount DOUBLE(10,2)
```

这些写法的问题是：

- `price`、`balance`、`amount` 这类字段通常必须精确，不适合浮点。
- `FLOAT(5,2)` / `DOUBLE(10,2)` 容易让人误解成精确小数。
- 浮点数即使显示成两位小数，内部也仍然是近似值。

更合理的方向通常是：

```sql
price DECIMAL(10,2)
balance DECIMAL(18,2)
tax_rate DECIMAL(7,6)
amount DECIMAL(18,2)
```

## 二、浮点类型是什么

浮点类型用来表示「近似数值」。

在 MySQL 中，常见浮点类型主要有：

| 类型 | 名称 | 存储大小 | 特点 |
| --- | --- | ---: | --- |
| `FLOAT` | 单精度浮点数 | 4 bytes | 占用较小，精度较低 |
| `DOUBLE` | 双精度浮点数 | 8 bytes | 占用较大，精度较高 |
| `REAL` | 实数类型别名 | 通常等同 `DOUBLE` | 受 `REAL_AS_FLOAT` SQL mode 影响 |

### 2.1 什么叫「近似数值」？

近似数值的意思是：

> 数据库保存的值，不一定和你写进 SQL 的十进制字面量完全一模一样。

例如你写：

```sql
INSERT INTO demo_float(value) VALUES (0.1);
```

你看到的是 `0.1`，但它在二进制浮点系统中可能只能保存成一个非常接近 `0.1` 的近似值。

这不是 MySQL 独有的问题，而是二进制浮点表示的通病。Java、JavaScript、C、Python 等语言在使用二进制浮点时也会遇到类似现象。

例如 JavaScript 中经典的：

```js
0.1 + 0.2 === 0.3 // false
```

本质原因和数据库浮点数误差类似：很多十进制小数无法被有限位数的二进制浮点精确表示。

### 2.2 浮点数适合表示什么？

浮点数适合表示本来就允许误差的值，例如：

- 温度：`36.678`
- 湿度：`65.4321`
- 传感器读数：`0.0000345`
- 机器学习模型分数：`0.873492`
- 科学计算结果：`6.022e23`
- 统计平均值：`78.345678`

这些值通常有一个共同点：

> 它们本身就来自测量、估算、统计或科学计算，不是业务结算凭证。

### 2.3 浮点数不适合表示什么？

浮点数不适合表示必须精确的小数，例如：

- 账户余额
- 商品价格
- 转账金额
- 税额
- 手续费
- 应收账款
- 应付账款
- 利息
- 交易金额
- 对账金额

这些数据的共同点是：

> 不能因为近似误差导致少一分钱、多一分钱，或对账不平。

## 三、`FLOAT` 和 `DOUBLE` 的区别

`FLOAT` 和 `DOUBLE` 的核心差别是：

> `DOUBLE` 比 `FLOAT` 占用更多空间，但能保留更多有效数字。

| 数据类型 | 存储大小 | 精度概念 | 适合场景 |
| --- | ---: | --- | --- |
| `FLOAT` | 4 bytes | 单精度，精度较低 | 大量测量值、对精度要求不高的近似数据 |
| `DOUBLE` | 8 bytes | 双精度，精度较高 | 科学计算、统计分析、对近似精度要求较高的场景 |

### 3.1 用一个例子感受差异

```sql
CREATE TABLE demo_float_double (
    value_float  FLOAT,
    value_double DOUBLE
);

INSERT INTO demo_float_double (value_float, value_double)
VALUES (12345.6789012345, 12345.6789012345);

SELECT value_float, value_double
FROM demo_float_double;
```

你可能看到类似结果：

```text
+-------------+-------------------+
| value_float | value_double      |
+-------------+-------------------+
| 12345.7     | 12345.6789012345  |
+-------------+-------------------+
```

这说明：

- `FLOAT` 因为精度较低，更早发生近似化。
- `DOUBLE` 能保留更多有效数字。
- 但 `DOUBLE` 仍然是近似类型，不是精确小数类型。

### 3.2 `DOUBLE` 精度更高，不等于没有误差

很多人会误以为：

> `FLOAT` 有误差，那我全部改成 `DOUBLE` 就好了。

这只对了一半。

`DOUBLE` 确实比 `FLOAT` 精度高，但它仍然使用二进制浮点表示。也就是说：

- 误差可能比较小；
- 能表示的有效数字比较多；
- 但它仍然不是精确十进制；
- 不适合拿来存金额、余额、价格。

可以这样记：

| 需求 | 是否该用 `DOUBLE` |
| --- | --- |
| 比 `FLOAT` 更高精度的近似计算 | 可以 |
| 精确金额计算 | 不应该 |
| 统计分析、科学计算 | 常见 |
| 对账、结算、会计 | 不应该 |

### 3.3 `FLOAT` 什么时候还能用？

在现代业务系统里，`FLOAT` 的使用场景其实比 `DOUBLE` 更少。

可以考虑 `FLOAT` 的情况包括：

- 数据量非常大，每行节省 4 bytes 有明显意义。
- 数据本身精度要求不高，例如粗略传感器读数。
- 后续不会用于财务结算、精确比较或严肃对账。
- 业务明确接受较低精度。

如果不确定，通常优先考虑：

```text
近似小数：DOUBLE
精确小数：DECIMAL
```

而不是盲目使用 `FLOAT`。

## 四、`REAL`、`DOUBLE PRECISION` 与 `FLOAT(p)`

除了 `FLOAT` 和 `DOUBLE`，旧系统或教材里还可能看到：

```sql
REAL
DOUBLE PRECISION
FLOAT(p)
```

### 4.1 `DOUBLE PRECISION`

`DOUBLE PRECISION` 可以理解为 `DOUBLE` 的另一种写法。

```sql
CREATE TABLE demo_double_precision (
    score DOUBLE PRECISION
);
```

实务上更常直接写：

```sql
score DOUBLE
```

### 4.2 `REAL`

在 MySQL 中，`REAL` 默认通常视为 `DOUBLE`。

但如果启用了 `REAL_AS_FLOAT` SQL mode，`REAL` 会被当成 `FLOAT`。

例如：

```sql
SET sql_mode = 'REAL_AS_FLOAT';

CREATE TABLE demo_real (
    value REAL
);
```

这时 `REAL` 会按 `FLOAT` 处理。

实务建议：

> 新表设计时，为了可读性和可维护性，直接写 `FLOAT` 或 `DOUBLE`，不要让团队成员去猜 `REAL` 当前到底代表什么。

### 4.3 `FLOAT(p)`

你可能也会看到：

```sql
FLOAT(10)
FLOAT(24)
FLOAT(53)
```

这里的 `p` 不是小数位数，也不是 `DECIMAL(M,D)` 里的总位数。

它表示的是「精度位数」概念，而且 MySQL 主要用它来决定最终采用单精度还是双精度存储。

实务上不建议在新系统里用 `FLOAT(p)` 表达业务含义，因为它会造成理解成本。更清楚的写法是：

```sql
-- 需要单精度近似值
value FLOAT

-- 需要双精度近似值
value DOUBLE
```

如果你真正想表达的是「总共几位、小数几位」，请考虑：

```sql
value DECIMAL(M, D)
```

## 五、`FLOAT(M,D)` 与 `DOUBLE(M,D)` 为什么不建议继续使用

旧系统中很常见下面这种写法：

```sql
FLOAT(7,4)
DOUBLE(10,2)
```

这类写法容易让人误会成：

> 只要写了 `(M,D)`，浮点数就会像 `DECIMAL(M,D)` 一样精确。

这是错误理解。

### 5.1 `M` 和 `D` 表面上是什么意思？

在这种旧式写法里：

- `M`：总位数
- `D`：小数位数

例如：

```sql
FLOAT(7,4)
```

可以粗略理解成：

```text
总共最多 7 位数字，其中小数点后最多 4 位
```

所以显示上可能像：

```text
-999.9999
```

### 5.2 插入时可能发生四舍五入

例如：

```sql
CREATE TABLE demo_float_md (
    value FLOAT(7,4)
);

INSERT INTO demo_float_md(value) VALUES (999.00009);

SELECT value FROM demo_float_md;
```

可能得到类似：

```text
999.0001
```

因为 MySQL 存储时会根据声明的小数位进行处理。

但关键是：

> 这仍然是浮点近似值，不会因为写了 `(M,D)` 就变成精确小数。

### 5.3 为什么不建议使用？

不建议继续依赖 `FLOAT(M,D)` / `DOUBLE(M,D)`，主要有四个原因：

1. 这是 MySQL 的非标准扩展，移植性差。
2. 官方已经标记为 deprecated，未来版本可能移除。
3. 它容易让人误解成精确小数。
4. 业务上真正需要固定小数位时，通常应该用 `DECIMAL(M,D)`。

所以新系统建议写成：

```sql
-- 近似值
temperature DOUBLE

-- 精确值
price DECIMAL(10,2)
```

不要写成：

```sql
price DOUBLE(10,2)
```

## 六、为什么浮点数会有精度误差

这一节是整篇最重要的核心。

浮点数误差不是因为 MySQL 算错，而是因为：

> 很多十进制小数无法被二进制浮点格式精确表示。

### 6.1 十进制小数不一定能被二进制精确表示

我们人类平常习惯使用十进制。

例如：

```text
0.1
0.2
0.47
0.44
0.19
```

这些在十进制里看起来很简单。

但计算机底层使用二进制，很多十进制小数转成二进制后会变成无限循环小数。计算机不可能存无限位，只能截断或近似保存。

所以数据库里实际保存的可能不是「精确的 0.1」，而是「非常接近 0.1 的一个值」。

### 6.2 误差会在计算时被放大或暴露出来

单个值显示时，你可能看不出问题。

例如：

```sql
SELECT 0.1;
```

显示结果可能就是：

```text
0.1
```

但当你做加总、平均、比较时，内部近似值就可能暴露出来。

例如：

```sql
CREATE TABLE demo_double_sum (
    value DOUBLE
);

INSERT INTO demo_double_sum(value)
VALUES (0.47), (0.44), (0.19);

SELECT SUM(value) AS total
FROM demo_double_sum;
```

理论上：

```text
0.47 + 0.44 + 0.19 = 1.10
```

但你可能看到类似：

```text
1.0999999999999999
```

这不是语法错误，而是浮点近似值参与计算后的自然结果。

### 6.3 `FLOAT` 的误差通常比 `DOUBLE` 更明显

如果改用 `FLOAT`：

```sql
CREATE TABLE demo_float_sum (
    value FLOAT
);

INSERT INTO demo_float_sum(value)
VALUES (0.47), (0.44), (0.19);

SELECT SUM(value) AS total
FROM demo_float_sum;
```

可能得到类似：

```text
1.0999999940395355
```

这是因为 `FLOAT` 可用精度较低，近似误差通常更容易显现。

## 七、为什么不要直接用 `=` 比较浮点数

如果字段是浮点类型，下面这种写法要特别小心：

```sql
SELECT *
FROM demo_double_sum
WHERE value = 1.1;
```

或者：

```sql
SELECT SUM(value) = 1.1
FROM demo_double_sum;
```

你以为它会判断「数学上是否等于 1.1」，但数据库比较的是内部保存或计算出来的数值。

如果 `SUM(value)` 实际结果接近：

```text
1.0999999999999999
```

那它和 `1.1` 就可能不相等。

### 7.1 错误示范

```sql
SELECT SUM(value) = 1.1 AS is_equal
FROM demo_double_sum;
```

可能得到：

```text
0
```

也就是 false。

### 7.2 正确思路：使用容差比较

更稳妥的方式是先定义可接受误差，例如：

```text
0.000001
```

然后这样比较：

```sql
SELECT ABS(SUM(value) - 1.1) < 0.000001 AS almost_equal
FROM demo_double_sum;
```

意思是：

> 不要求两个浮点数完全相等，只要求它们的差距小于可接受误差。

### 7.3 查询条件也可以用范围

例如不要写：

```sql
WHERE score = 0.8
```

可以改成：

```sql
WHERE score BETWEEN 0.8 - 0.000001
                AND 0.8 + 0.000001
```

或者：

```sql
WHERE ABS(score - 0.8) <= 0.000001
```

注意：

- `ABS(column - value)` 这种写法可能影响索引使用。
- 如果数据量很大，范围写法通常更容易被优化器利用。
- 但最根本的还是：如果你需要精确相等比较，应该重新确认字段是否应使用 `DECIMAL`。

## 八、什么时候应该改用 `DECIMAL`

只要你处理的是「精确十进制值」，就应该优先考虑 `DECIMAL`。

### 8.1 必须优先考虑 `DECIMAL` 的场景

| 场景 | 推荐类型 | 原因 |
| --- | --- | --- |
| 商品价格 | `DECIMAL(10,2)` | 价格必须精确到分 |
| 订单金额 | `DECIMAL(18,2)` | 金额需要对账 |
| 账户余额 | `DECIMAL(18,2)` / `DECIMAL(20,2)` | 余额不能出现近似误差 |
| 税率 | `DECIMAL(7,6)` | 税率常需要固定小数位 |
| 汇率 | `DECIMAL(18,6)` / `DECIMAL(20,8)` | 汇率涉及换算和结算 |
| 利率 | `DECIMAL(8,6)` / `DECIMAL(10,8)` | 利息计算需要稳定精度 |
| 手续费 | `DECIMAL(18,2)` | 涉及收付款 |

### 8.2 `DECIMAL(M,D)` 的语义更适合业务小数

例如：

```sql
price DECIMAL(10,2)
```

意思是：

- 总共最多 10 位数字；
- 小数点后最多 2 位；
- 整数部分最多 8 位；
- 可以表达从 `-99999999.99` 到 `99999999.99` 的范围。

如果价格不应为负数，可以加约束：

```sql
price DECIMAL(10,2) NOT NULL CHECK (price >= 0)
```

### 8.3 不要把「显示两位小数」和「精确两位小数」混在一起

有时候你只是想在前端显示两位小数：

```text
12.30
```

这属于显示格式问题。

有时候你是希望数据库精确保存两位小数：

```text
12.30 是业务值本身
```

这属于数据类型问题。

如果是金额、价格，应该在数据库层就用 `DECIMAL` 表达精确小数，而不是只靠前端格式化。

## 九、`UNSIGNED`、`ZEROFILL` 与浮点类型

浮点类型也可能看到这些属性：

```sql
FLOAT UNSIGNED
DOUBLE UNSIGNED
FLOAT ZEROFILL
```

但在现代设计中，不建议依赖它们。

### 9.1 `UNSIGNED` 对浮点数的意义

`UNSIGNED` 用在浮点或定点数上时，主要效果是：

> 不允许存负数。

例如：

```sql
CREATE TABLE demo_unsigned_float (
    temperature FLOAT UNSIGNED
);
```

这表示 `temperature` 不能存负数。

但问题是：

- 它不会让浮点数更精确。
- 它不会扩大浮点类型的上限范围。
- 官方已经不建议在 `FLOAT`、`DOUBLE`、`DECIMAL` 上继续使用 `UNSIGNED`。

更现代、更清楚的写法是使用 `CHECK` 约束：

```sql
CREATE TABLE demo_temperature (
    temperature DOUBLE NOT NULL,
    CHECK (temperature >= 0)
);
```

### 9.2 `ZEROFILL` 不应该用来做业务格式化

`ZEROFILL` 只是显示补零相关的旧式能力，不应该用来表达业务编号或格式。

例如不要为了显示：

```text
00012.30
```

就把字段设计成：

```sql
amount DOUBLE ZEROFILL
```

这类格式化应该交给：

- 前端显示层；
- 报表层；
- SQL 查询时临时格式化；
- 或专门的字符串字段。

不要让数值字段承担显示格式职责。

## 十、聚合函数与浮点结果

在实际项目中，浮点字段最常见的问题不是单笔存储，而是聚合计算。

例如：

```sql
SELECT SUM(score), AVG(score)
FROM model_score;
```

如果 `score` 是 `FLOAT` 或 `DOUBLE`，聚合结果也可能受到浮点近似误差影响。

### 10.1 `SUM()` / `AVG()` 的结果类型要注意

MySQL 对 `SUM()` / `AVG()` 的处理大方向是：

- 对整数、`DECIMAL` 这类 exact-value 参数，结果偏向 `DECIMAL`。
- 对 `FLOAT` / `DOUBLE` 这类 approximate-value 参数，结果偏向 `DOUBLE`。

这代表：

```sql
amount DECIMAL(18,2)
```

拿去加总，通常比：

```sql
amount DOUBLE
```

更适合金额汇总、报表统计、对账计算。

### 10.2 报表金额不要先存浮点再四舍五入

不要这样设计：

```sql
CREATE TABLE order_report_bad (
    amount DOUBLE NOT NULL
);

SELECT ROUND(SUM(amount), 2)
FROM order_report_bad;
```

这只是把显示结果四舍五入，不代表底层资料和中间计算完全精确。

更好的设计是：

```sql
CREATE TABLE order_report_good (
    amount DECIMAL(18,2) NOT NULL
);

SELECT SUM(amount)
FROM order_report_good;
```

如果业务规则需要四舍五入，也应该明确规定：

- 在哪一步四舍五入；
- 使用什么舍入规则；
- 保留几位小数；
- 是每笔先四舍五入，还是汇总后再四舍五入。

## 十一、Java 后端开发中的对应关系

如果你用 Java 连接 MySQL，建议建立下面的直觉：

| MySQL 类型 | Java 常见类型 | 使用建议 |
| --- | --- | --- |
| `FLOAT` | `Float` / `float` | 少用，除非明确接受较低精度 |
| `DOUBLE` | `Double` / `double` | 用于近似计算、统计值、科学值 |
| `DECIMAL` | `BigDecimal` | 金额、价格、余额、汇率、利率 |

### 11.1 金额不要在 Java 用 `double` 接

即使数据库用了 `DECIMAL`，Java 端也不应该随手用 `double` 接金额。

不建议：

```java
private Double amount;
```

更建议：

```java
private BigDecimal amount;
```

原因是：

- `double` 仍然是二进制浮点。
- `BigDecimal` 更适合表达精确十进制。
- 金额计算通常需要明确的舍入模式，例如 `RoundingMode.HALF_UP`。

### 11.2 MyBatis / JPA 映射时也要保持一致

例如金额字段：

```sql
amount DECIMAL(18,2) NOT NULL
```

Java 实体类建议：

```java
private BigDecimal amount;
```

不要数据库用 `DECIMAL`，Java 却用 `Double`，否则你会在应用层重新引入浮点误差。

## 十二、实务建表示例

### 12.1 错误示例：金额与评分都随便用浮点

```sql
CREATE TABLE product_bad (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    price DOUBLE NOT NULL,
    discount FLOAT,
    rating FLOAT
);
```

问题：

- `price` 是价格，不应该用 `DOUBLE`。
- `discount` 如果是固定折扣率，通常也应考虑 `DECIMAL`。
- `rating` 如果只是统计评分，可以使用 `DOUBLE` 或 `DECIMAL`，要看业务是否要求固定精度。

### 12.2 较合理示例：精确值与近似值分开

```sql
CREATE TABLE product_good (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,

    -- 精确业务小数
    price DECIMAL(10,2) NOT NULL CHECK (price >= 0),
    discount_rate DECIMAL(5,4) NOT NULL DEFAULT 1.0000,

    -- 统计或模型结果，可接受近似
    rating_score DOUBLE,
    recommendation_score DOUBLE,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

这个设计表达得更清楚：

- `price` 是金额，使用 `DECIMAL`。
- `discount_rate` 是固定精度业务小数，使用 `DECIMAL`。
- `rating_score`、`recommendation_score` 是统计或模型分数，允许近似，使用 `DOUBLE`。

### 12.3 传感器资料示例

```sql
CREATE TABLE sensor_reading (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    device_id BIGINT UNSIGNED NOT NULL,
    temperature DOUBLE NOT NULL,
    humidity DOUBLE NOT NULL,
    voltage DOUBLE,
    recorded_at DATETIME NOT NULL,

    INDEX idx_device_time (device_id, recorded_at)
);
```

这里使用 `DOUBLE` 是合理的，因为：

- 温度、湿度、电压本来就是测量值。
- 测量值通常允许误差。
- 后续常见操作是统计趋势、平均值、最大值、最小值。

如果设备精度很低，也可以考虑 `FLOAT`，但除非数据量极大，否则 `DOUBLE` 通常更稳。

## 十四、常见混淆点

### 14.1 有小数点，不代表应该用浮点

错误直觉：

```text
小数 = FLOAT / DOUBLE
```

更正确的判断是：

```text
小数 = 先判断精确值还是近似值
```

| 小数类型 | 推荐方向 |
| --- | --- |
| 精确小数 | `DECIMAL` |
| 近似小数 | `FLOAT` / `DOUBLE` |

### 14.2 `DOUBLE` 不是金额字段的保险解

`DOUBLE` 的精度比 `FLOAT` 高，但仍然是近似数。

所以：

```sql
amount DOUBLE
```

不应该因为「比 `FLOAT` 精度高」就被用于金额。

金额字段应该优先：

```sql
amount DECIMAL(18,2)
```

### 14.3 `FLOAT(M,D)` 不等于 `DECIMAL(M,D)`

这点非常重要。

```sql
FLOAT(10,2)
```

和：

```sql
DECIMAL(10,2)
```

不是同一回事。

| 写法 | 本质 | 是否适合精确金额 |
| --- | --- | --- |
| `FLOAT(10,2)` | 旧式浮点扩展，仍是近似值 | 不适合 |
| `DOUBLE(10,2)` | 旧式浮点扩展，仍是近似值 | 不适合 |
| `DECIMAL(10,2)` | 精确十进制 | 适合 |

### 14.4 显示结果看起来正确，不代表内部没有误差

例如你看到：

```text
1.1
```

不代表内部一定是精确的 `1.1`。

它可能只是显示层做了格式化，或者客户端只显示了有限位数。

### 14.5 可以用 `ROUND()`，但不要把它当成根本解决方案

`ROUND()` 可以控制显示或某一步计算结果：

```sql
SELECT ROUND(SUM(score), 4)
FROM model_score;
```

但它不能改变字段本身是浮点近似值的事实。

如果底层数据需要精确，应该从字段类型就选 `DECIMAL`。

## 十六、面试表达版

如果面试被问：

> MySQL 里的 `FLOAT`、`DOUBLE`、`DECIMAL` 有什么区别？

可以这样回答：

```text
FLOAT 和 DOUBLE 都是浮点类型，属于 approximate value，也就是近似数值。
FLOAT 通常占 4 bytes，DOUBLE 通常占 8 bytes，DOUBLE 能保留更多有效数字，但两者都可能有二进制浮点误差。

DECIMAL 是定点数，属于 exact value，适合保存必须精确的小数，例如金额、价格、余额、税额。

所以如果是科学计算、统计值、传感器读数，可以考虑 DOUBLE；如果是金额和财务数据，应该优先用 DECIMAL，而不是 FLOAT 或 DOUBLE。
另外，浮点数比较时不应该直接依赖 =，通常要使用容差比较。
```

---

## 十七、一句话抓核心

浮点类型适合存「允许误差的近似小数」，不适合存「必须精确的业务小数」；遇到金额、价格、余额、税额、汇率时，先考虑 `DECIMAL`，不要被 `DOUBLE` 的高精度表象误导。
