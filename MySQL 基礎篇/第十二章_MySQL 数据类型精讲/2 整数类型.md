# 2 整数类型

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇要解决的问题是：

> 建表时，遇到整数类字段，到底该用 `TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT` 还是 `BIGINT`？什么时候要加 `UNSIGNED`？旧系统里常见的 `INT(11)`、`TINYINT(1)`、`ZEROFILL` 又该怎么理解？

整数类型看起来简单，但在真实项目里很容易踩坑。常见问题包括：

- 把 `INT(11)` 误解成“最多只能存 11 位数字”。
- 把 `TINYINT(1)` 误解成“只能存 0 或 1”。
- 给订单号、手机号、身份证号这类“看起来是数字”的字段使用整数类型。
- 主键范围估得太小，后期资料量成长后出现范围不够。
- 随手加 `UNSIGNED`，后面做减法或差值计算时产生意料外的结果。
- 继续依赖 `ZEROFILL` 做编号格式化，但它已经不适合作为新系统设计方案。

所以这一篇的重点不是死背五种整数类型，而是建立一套判断流程：

1. 这个字段本质上是不是真的“整数”？
2. 它会不会出现负数？
3. 它未来最大可能到多少？
4. 它是否会作为主键、外键、状态码、计数器或业务编号？
5. 它的显示格式是否应该交给数据库类型来处理？

## 30 秒复习入口

- MySQL 常见整数类型有五种：`TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT` / `INTEGER`、`BIGINT`。
- 它们的核心差异是：**占用字节数不同，所以可表示的整数范围不同**。
- 整数类型默认是 `SIGNED`，也就是允许负数。
- `UNSIGNED` 表示无符号，会禁止负数，并把可表示范围整体移到非负数区间。
- `INT(11)` 里的 `11` 是旧式显示宽度概念，不会限制实际可存范围。
- `TINYINT(1)` 不等于只能存 `0` 和 `1`；如果要严格限制布尔值，应加约束或由应用层校验。
- `BOOL` / `BOOLEAN` 在 MySQL 中是 `TINYINT(1)` 的同义词。
- `ZEROFILL` 只影响显示补零，并且会隐含 `UNSIGNED`；新系统不建议继续依赖。
- 主键 ID 不要只看当前资料量，要预估系统生命周期内的增长空间。

## 一、先讲结论

整数类型选型可以先抓住一句话：

> 先确认这个字段是不是“真正用于数值运算、比较或计数的整数”，再根据是否允许负数和最大可能范围选择类型。

### 1.1 最常用的实务判断

| 字段类型 | 常见建议 | 理由 |
| --- | --- | --- |
| 小型状态码 | `TINYINT` / `TINYINT UNSIGNED` | 状态值范围通常很小，例如 0、1、2、3 |
| 布尔标记 | `TINYINT(1)` / `BOOLEAN`，并搭配约束或应用层校验 | MySQL 没有真正独立的 Boolean 存储类型 |
| 年龄、月份、星期、等级 | `TINYINT UNSIGNED` | 范围很小且不应为负数 |
| 分类编号、小型代码 | `SMALLINT UNSIGNED` | 比 `TINYINT` 大，但仍比 `INT` 节省 |
| 一般计数、库存、浏览数 | `INT UNSIGNED` | 范围通常够大，且不应为负数 |
| 普通业务表自增主键 | `BIGINT UNSIGNED` 或 `INT UNSIGNED` | 看系统规模；无法预估长期增长时，`BIGINT UNSIGNED` 更稳 |
| 大型流水号、日志 ID、分布式 ID | `BIGINT UNSIGNED` | 需要非常大的整数空间 |
| 手机号、身份证号、订单编号 | 通常用 `VARCHAR` | 它们是“编码”，不是拿来加减乘除的数值 |

### 1.2 一个容易记住的原则

如果字段满足下面条件，才优先考虑整数类型：

- 它需要进行大小比较、范围查询、排序、加减运算或计数。
- 它没有必须保留的前导零。
- 它不是电话号码、身份证号、银行卡号、订单展示编号这类业务编码。
- 它的值域可以被清楚估计。

例如：

| 需求 | 不建议 | 较合理 |
| --- | --- | --- |
| 用户年龄 | `VARCHAR(3)` | `TINYINT UNSIGNED` |
| 手机号 `0912345678` | `INT` | `VARCHAR(20)` |
| 订单展示编号 `00001234` | `INT(8) ZEROFILL` | 内部 ID 用整数，展示编号用格式化或 `VARCHAR` |
| 商品库存 | `VARCHAR(10)` | `INT UNSIGNED NOT NULL DEFAULT 0` |
| 是否删除 | `VARCHAR(1)` | `TINYINT(1) NOT NULL DEFAULT 0` |
| 大型系统用户 ID | `INT` | `BIGINT UNSIGNED` |

## 二、整数类型总览

MySQL 支持的常见整数类型如下：

| 数据类型 | 存储大小 | 有符号范围 `SIGNED` | 无符号范围 `UNSIGNED` | 常见用途 |
| --- | ---: | ---: | ---: | --- |
| `TINYINT` | 1 byte | -128 ~ 127 | 0 ~ 255 | 布尔标记、小型状态码、年龄、等级 |
| `SMALLINT` | 2 bytes | -32,768 ~ 32,767 | 0 ~ 65,535 | 小型分类编号、小范围计数 |
| `MEDIUMINT` | 3 bytes | -8,388,608 ~ 8,388,607 | 0 ~ 16,777,215 | 中等范围编号或计数，实务较少见 |
| `INT` / `INTEGER` | 4 bytes | -2,147,483,648 ~ 2,147,483,647 | 0 ~ 4,294,967,295 | 最常用的通用整数、计数、普通 ID |
| `BIGINT` | 8 bytes | -9,223,372,036,854,775,808 ~ 9,223,372,036,854,775,807 | 0 ~ 18,446,744,073,709,551,615 | 大型主键、流水号、超大计数 |

### 2.1 字节数为什么会影响范围？

可以粗略这样理解：

- 1 byte = 8 bit，所以能表示的组合数是 `2^8 = 256`。
- `TINYINT SIGNED` 要同时表示负数和正数，所以范围是 `-128 ~ 127`。
- `TINYINT UNSIGNED` 不需要表示负数，所以范围是 `0 ~ 255`。

同理：

| 类型 | 位数 | `UNSIGNED` 最大值 |
| --- | ---: | ---: |
| `TINYINT` | 8 bit | `2^8 - 1 = 255` |
| `SMALLINT` | 16 bit | `2^16 - 1 = 65,535` |
| `MEDIUMINT` | 24 bit | `2^24 - 1 = 16,777,215` |
| `INT` | 32 bit | `2^32 - 1 = 4,294,967,295` |
| `BIGINT` | 64 bit | `2^64 - 1 = 18,446,744,073,709,551,615` |

这个表不一定要死背，但要记住：

> 类型越大，不是“显示得越长”，而是“能表示的范围越大”。

### 2.2 `INT` 和 `INTEGER` 有差别吗？

在 MySQL 中，`INTEGER` 是 `INT` 的同义词。

也就是说下面两种写法语义相同：

```sql
CREATE TABLE demo_int_alias (
    a INT,
    b INTEGER
);
```

实务上更常看到 `INT`。

## 三、`SIGNED` 与 `UNSIGNED`

整数类型默认是 `SIGNED`，也就是允许负数。

```sql
CREATE TABLE demo_signed_default (
    score INT
);
```

上面的 `score INT` 等价于：

```sql
score INT SIGNED
```

### 3.1 `UNSIGNED` 的作用

`UNSIGNED` 表示无符号。它的效果是：

1. 不允许存负数。
2. 把原本分给负数的范围，移动到非负数区间。

例如：

| 定义 | 可存范围 |
| --- | ---: |
| `INT` | -2,147,483,648 ~ 2,147,483,647 |
| `INT UNSIGNED` | 0 ~ 4,294,967,295 |

所以 `UNSIGNED` 不是“让容量变成两倍”，更准确地说是：

> 总组合数不变，但范围从「负数 + 正数」移动成「纯非负整数」。

### 3.2 适合使用 `UNSIGNED` 的字段

通常适合用在“业务上不应该出现负数”的字段：

| 字段 | 建议示例 | 原因 |
| --- | --- | --- |
| 自增主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | ID 通常不为负数 |
| 年龄 | `TINYINT UNSIGNED` | 年龄不应为负数 |
| 库存 | `INT UNSIGNED` | 库存数量通常不应为负数 |
| 浏览数 | `INT UNSIGNED` / `BIGINT UNSIGNED` | 浏览次数不应为负数 |
| 点赞数 | `INT UNSIGNED` | 次数不应为负数 |
| 金币、积分 | `INT UNSIGNED` / `BIGINT UNSIGNED` | 看业务是否允许负积分 |

示例：

```sql
CREATE TABLE product_stock (
    product_id BIGINT UNSIGNED NOT NULL,
    stock_qty INT UNSIGNED NOT NULL DEFAULT 0,
    sold_qty INT UNSIGNED NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id)
);
```

### 3.3 不要无脑使用 `UNSIGNED`

`UNSIGNED` 虽然可以扩大非负范围，但也会影响表达式计算。

例如，两个库存字段都是 `UNSIGNED`：

```sql
stock_qty INT UNSIGNED,
locked_qty INT UNSIGNED
```

如果你做类似计算：

```sql
stock_qty - locked_qty
```

当 `locked_qty` 大于 `stock_qty` 时，结果本来应该是负数，但因为参与运算的值可能带有无符号属性，结果可能出现报错或不符合直觉的行为。

所以实际开发时要注意：

- 只是“单纯存储非负数”，`UNSIGNED` 很适合。
- 如果字段经常参与差值计算，特别是可能产生负数，要更谨慎。
- 可以在 SQL 中明确转换，或在业务层先处理边界。

示例：

```sql
SELECT CAST(stock_qty AS SIGNED) - CAST(locked_qty AS SIGNED) AS available_diff
FROM product_stock;
```

## 四、`INT(M)`、显示宽度与旧系统遗留写法

很多旧系统会看到这种字段定义：

```sql
id INT(11)
status TINYINT(1)
amount BIGINT(20)
```

初学时最容易误解成：

- `INT(11)` 最多只能存 11 位数字。
- `TINYINT(1)` 最多只能存 1 位数字。
- `BIGINT(20)` 最多只能存 20 位数字。

这些理解都是错的。

### 4.1 `M` 是显示宽度，不是取值范围

`INT(M)` 里的 `M` 是旧式显示宽度概念，不决定实际可存范围。

例如：

```sql
CREATE TABLE demo_int_width (
    id INT(5)
);

INSERT INTO demo_int_width (id) VALUES (1), (12345), (123456);

SELECT * FROM demo_int_width;
```

结果中 `123456` 仍然可以存进去，只要它没有超过 `INT` 的真实范围。

真正决定 `INT` 可存范围的是：

```text
-2,147,483,648 ~ 2,147,483,647
```

而不是括号里的 `5`。

### 4.2 那为什么旧系统常看到 `INT(11)`？

这是历史遗留写法。

过去很多工具、ORM 或建表习惯会默认生成：

```sql
id INT(11) NOT NULL AUTO_INCREMENT
```

但在现代 MySQL 中，整数显示宽度已经不建议继续依赖。新系统建表时直接写：

```sql
id INT NOT NULL AUTO_INCREMENT
```

或：

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT
```

会更清楚。

### 4.3 `TINYINT(1)` 也不是只能存 0 和 1

`TINYINT(1)` 的真实范围仍然是：

```text
SIGNED:   -128 ~ 127
UNSIGNED: 0 ~ 255
```

所以这个字段：

```sql
is_deleted TINYINT(1)
```

理论上仍然可以存 `2`、`3`、`100`，除非你另外加约束或由应用层校验。

如果业务上只允许 `0` 和 `1`，可以写成：

```sql
CREATE TABLE demo_boolean_flag (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    is_deleted TINYINT(1) NOT NULL DEFAULT 0,
    CONSTRAINT chk_demo_boolean_flag_deleted CHECK (is_deleted IN (0, 1))
);
```

如果你的 MySQL 版本或团队规范不依赖 `CHECK`，那就要在应用层或写入逻辑中保证只写入 `0` / `1`。

## 五、`BOOLEAN`、`BOOL` 与 `TINYINT(1)`

MySQL 中的：

```sql
BOOLEAN
BOOL
```

本质上是：

```sql
TINYINT(1)
```

例如：

```sql
CREATE TABLE user_flags (
    user_id BIGINT UNSIGNED NOT NULL PRIMARY KEY,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    is_deleted BOOL NOT NULL DEFAULT FALSE
);
```

你可以把它理解成一种语义化写法：

- `BOOLEAN` 让读表结构的人知道这是布尔标记。
- 但底层仍然不是只能存 `TRUE` / `FALSE` 的严格布尔类型。

### 5.1 `TRUE` 和 `FALSE` 的实际含义

在 MySQL 中：

```sql
TRUE  = 1
FALSE = 0
```

所以：

```sql
SELECT TRUE, FALSE;
```

可以理解为：

```text
1, 0
```

### 5.2 一个容易忽略的细节

在条件判断中，非 0 值通常会被视为真：

```sql
SELECT IF(2, 'true', 'false');
```

结果是：

```text
true
```

但是如果你写：

```sql
SELECT 2 = TRUE;
```

结果不是 true，因为 `TRUE` 本质上是 `1`，而 `2 = 1` 不成立。

所以如果你希望一个布尔字段只有 `0` 和 `1`，不要只靠 `BOOLEAN` 这个类型名称，最好搭配：

- `NOT NULL DEFAULT 0`
- `CHECK (field IN (0, 1))`
- 应用层 enum / boolean 映射
- 写入前校验

## 六、`ZEROFILL`：前导零显示，不是存储设计

`ZEROFILL` 的作用是：查询显示时用前导零补足显示宽度。

例如：

```sql
CREATE TABLE demo_zerofill (
    order_seq INT(5) ZEROFILL NOT NULL
);

INSERT INTO demo_zerofill (order_seq) VALUES (1), (23), (456), (123456);

SELECT order_seq FROM demo_zerofill;
```

可能看到：

```text
00001
00023
00456
123456
```

重点是：

- `ZEROFILL` 改变的是显示效果，不是实际存储值。
- 超过显示宽度的值不会因为 `INT(5)` 被截断。
- `ZEROFILL` 会隐含 `UNSIGNED`。
- `ZEROFILL` 和整数显示宽度都属于不建议新系统继续依赖的旧式设计。

### 6.1 新系统怎么做前导零？

如果只是查询时想显示成固定长度，可以用：

```sql
SELECT LPAD(order_seq, 5, '0') AS display_order_seq
FROM demo_zerofill;
```

如果这是一个真正的业务编号，例如：

```text
ORD-20260501-000001
```

更建议把它当成“业务编号字符串”处理，而不是试图用 `ZEROFILL` 解决。

常见设计是：

```sql
CREATE TABLE orders (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    order_no VARCHAR(40) NOT NULL UNIQUE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

其中：

- `id` 是数据库内部主键。
- `order_no` 是给业务、客户、报表使用的展示编号。

## 七、`AUTO_INCREMENT` 与整数主键选型

`AUTO_INCREMENT` 常和整数主键一起使用。

典型写法：

```sql
CREATE TABLE users (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    PRIMARY KEY (id)
);
```

### 7.1 `AUTO_INCREMENT` 负责什么？

`AUTO_INCREMENT` 负责在插入资料时自动产生递增值。

例如：

```sql
INSERT INTO users (username) VALUES ('Alice'), ('Bob');

SELECT id, username FROM users;
```

可能得到：

```text
1 Alice
2 Bob
```

这里要分清楚：

| 设计 | 作用 |
| --- | --- |
| `BIGINT` | 决定可存范围 |
| `UNSIGNED` | 决定是否允许负数，并扩大非负上限 |
| `AUTO_INCREMENT` | 决定是否自动递增 |
| `PRIMARY KEY` | 决定是否作为主键唯一识别资料 |

`AUTO_INCREMENT` 不会改变类型范围。范围不够时，仍然会出问题。

### 7.2 主键用 `INT` 还是 `BIGINT`？

可以这样判断：

| 场景 | 建议 |
| --- | --- |
| 小型练习项目、内部工具、资料量确定很小 | `INT UNSIGNED` 通常够用 |
| 一般业务系统，长期资料量不确定 | `BIGINT UNSIGNED` 更稳 |
| 日志表、交易流水、消息表、行为记录表 | 优先考虑 `BIGINT UNSIGNED` |
| 分布式 ID、雪花算法 ID | 通常使用 `BIGINT` / `BIGINT UNSIGNED` |

### 7.3 不要为了省空间过度压缩主键范围

例如：

```sql
id SMALLINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
```

最大只能到 `65,535`。

如果这个表只是系统参数表，可能没问题；但如果是用户表、订单表、日志表，风险就很高。

实务上主键类型要考虑：

- 现在资料量。
- 未来几年资料量。
- 是否会导入历史资料。
- 是否会分表、分库或迁移。
- 是否会作为其他表的外键。
- 是否有大量二级索引。

结论：

> 主键选型不要只看今天有几笔资料，而要看系统生命周期内的增长空间。

## 八、超出范围时会怎样？

整数类型真正会失败的地方，不是超过 `INT(11)` 的 `11`，而是超过该类型的真实范围。

例如：

```sql
CREATE TABLE demo_out_of_range (
    a TINYINT,
    b TINYINT UNSIGNED
);
```

`TINYINT` 范围是：

```text
SIGNED:   -128 ~ 127
UNSIGNED: 0 ~ 255
```

所以：

```sql
INSERT INTO demo_out_of_range (a, b) VALUES (128, 256);
```

在 strict SQL mode 下通常会报错：

```text
ERROR 1264 (22003): Out of range value for column ...
```

### 8.1 strict mode 与非 strict mode 的差异

| SQL mode | 超出范围时的行为 |
| --- | --- |
| strict mode | 直接报错，插入或更新失败 |
| 非 strict mode | 可能截断成该类型边界值，并产生 warning |

例如非 strict mode 下，`TINYINT UNSIGNED` 插入 `256`，可能被截成 `255`。

但这不是正常设计应该依赖的行为。

实务上应该：

- 选择足够大的整数类型。
- 在应用层做范围校验。
- 必要时加 `CHECK` 约束。
- 不要依赖非 strict mode 的截断行为。

## 九、整数类型的业务选型速查表

| 业务字段 | 推荐类型 | 说明 |
| --- | --- | --- |
| 是否删除 | `TINYINT(1) NOT NULL DEFAULT 0` | 搭配 `0/1` 语义，最好加约束 |
| 是否启用 | `TINYINT(1) NOT NULL DEFAULT 1` | `1` 启用，`0` 停用 |
| 状态码 | `TINYINT UNSIGNED` / `SMALLINT UNSIGNED` | 状态很多时可用 `SMALLINT` |
| 性别代码 | `TINYINT UNSIGNED` 或字典表 | 视业务复杂度决定 |
| 年龄 | `TINYINT UNSIGNED` | 可搭配 `CHECK (age BETWEEN 0 AND 150)` |
| 月份 | `TINYINT UNSIGNED` | 可搭配 `CHECK (month BETWEEN 1 AND 12)` |
| 排序号 | `INT` / `INT UNSIGNED` | 若允许负数排序，就不要用 `UNSIGNED` |
| 库存数量 | `INT UNSIGNED NOT NULL DEFAULT 0` | 不应为负数 |
| 销售数量 | `INT UNSIGNED NOT NULL DEFAULT 0` | 不应为负数 |
| 浏览次数 | `INT UNSIGNED` / `BIGINT UNSIGNED` | 高流量系统可用 `BIGINT` |
| 点赞数 | `INT UNSIGNED` | 若规模巨大可改 `BIGINT` |
| 用户 ID | `BIGINT UNSIGNED` | 长期系统较稳 |
| 订单 ID | `BIGINT UNSIGNED` | 订单资料成长快 |
| 日志 ID | `BIGINT UNSIGNED` | 日志量通常很大 |
| 外部平台 ID | `VARCHAR` 或 `BIGINT` | 若平台保证纯数值且不会超范围才用整数 |
| 手机号 | `VARCHAR(20)` | 不要用整数 |
| 身份证号 | `VARCHAR(30)` | 可能含字母或前导零 |
| 银行账号 | `VARCHAR(30)` | 编码，不是数值 |
| 展示订单号 | `VARCHAR(40)` | 可能有前缀、日期、前导零 |

## 十、字段选型流程

遇到一个疑似整数的字段，可以照这个流程判断。

### 第一步：它是不是“真正的数值”？

如果只是由数字组成的编码，不一定该用整数。

| 字段 | 是否适合整数 | 原因 |
| --- | --- | --- |
| 年龄 | 适合 | 可比较、可范围查询 |
| 库存 | 适合 | 可计算 |
| 手机号 | 不适合 | 有前导零、不是拿来计算 |
| 身份证号 | 不适合 | 可能含字母，属于编码 |
| 订单展示编号 | 不适合 | 可能需要前缀、日期、固定格式 |
| 用户内部 ID | 适合 | 用于关联和识别资料 |

### 第二步：会不会出现负数？

| 情况 | 建议 |
| --- | --- |
| 不可能为负 | 考虑 `UNSIGNED` |
| 可能为负 | 保持默认 `SIGNED` |
| 差值计算可能为负 | 谨慎使用 `UNSIGNED` |
| 业务上不应为负，但计算中可能暂时为负 | 可用 `SIGNED` + 业务约束，或计算时转换 |

### 第三步：最大值可能到多少？

| 最大值预估 | 可以考虑 |
| ---: | --- |
| 0 ~ 255 | `TINYINT UNSIGNED` |
| 0 ~ 65,535 | `SMALLINT UNSIGNED` |
| 0 ~ 16,777,215 | `MEDIUMINT UNSIGNED` |
| 0 ~ 4,294,967,295 | `INT UNSIGNED` |
| 超过 42 亿或难以预估 | `BIGINT UNSIGNED` |

### 第四步：是否是主键或长期增长字段？

如果是主键、日志 ID、流水号、订单 ID，通常不要只看眼前范围。

更推荐问：

- 这个表是否会长期增长？
- 是否可能导入历史数据？
- 是否会因为业务扩张而暴增？
- 是否会作为其他表的外键长期传播？

不确定时，主键倾向保守一些，使用 `BIGINT UNSIGNED`。

## 十一、完整建表示例

下面是一张比较贴近实务的用户表：

```sql
CREATE TABLE app_user (
    user_id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    age TINYINT UNSIGNED DEFAULT NULL COMMENT '年龄',
    status TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '状态：0停用，1正常，2锁定',
    login_count INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '登录次数',
    is_deleted TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否删除：0否，1是',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    PRIMARY KEY (user_id),
    UNIQUE KEY uk_app_user_username (username),
    CONSTRAINT chk_app_user_age CHECK (age IS NULL OR age BETWEEN 0 AND 150),
    CONSTRAINT chk_app_user_status CHECK (status IN (0, 1, 2)),
    CONSTRAINT chk_app_user_deleted CHECK (is_deleted IN (0, 1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

这个例子里面，整数类型的设计思路是：

| 字段 | 类型 | 理由 |
| --- | --- | --- |
| `user_id` | `BIGINT UNSIGNED` | 主键长期增长，不需要负数 |
| `age` | `TINYINT UNSIGNED` | 年龄范围小，不应为负数 |
| `status` | `TINYINT UNSIGNED` | 状态码范围小 |
| `login_count` | `INT UNSIGNED` | 次数不应为负，范围比 `TINYINT` 大很多 |
| `is_deleted` | `TINYINT(1)` | 布尔标记，但用约束限制只能为 0 或 1 |

## 十二、常见错误与修正

### 错误 1：把 `INT(11)` 当成 11 位限制

错误理解：

```text
INT(11) 最多只能存 11 位数字。
```

正确理解：

```text
INT 的范围固定，括号里的 11 是旧式显示宽度概念，不限制存储范围。
```

---

### 错误 2：认为 `TINYINT(1)` 只能存 0 和 1

错误理解：

```text
TINYINT(1) 是布尔类型，所以只能存 0 或 1。
```

正确理解：

```text
TINYINT(1) 仍然是 TINYINT，SIGNED 范围是 -128 ~ 127。
```

如果要限制只存 `0` 和 `1`，要加约束或校验。

---

### 错误 3：手机号使用 `INT`

错误写法：

```sql
phone INT
```

问题：

- 手机号可能有前导零。
- 手机号不是拿来做数学运算的数字。
- 不同国家号码长度不同，也可能有 `+886` 这类格式。

较合理写法：

```sql
phone VARCHAR(20)
```

---

### 错误 4：订单号使用 `INT(8) ZEROFILL`

错误写法：

```sql
order_no INT(8) ZEROFILL
```

问题：

- `ZEROFILL` 不建议新系统继续依赖。
- 订单号通常是业务编号，未来可能加前缀、日期、渠道码。
- 展示格式不应该强绑在整数类型上。

较合理写法：

```sql
id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
order_no VARCHAR(40) NOT NULL UNIQUE
```

---

### 错误 5：状态字段直接用 `INT`

可以用，但不够精确。

```sql
status INT NOT NULL DEFAULT 1
```

如果状态值只有几个，用 `INT` 有点过大。

较合理写法：

```sql
status TINYINT UNSIGNED NOT NULL DEFAULT 1
```

并搭配注释、字典表、枚举类或约束说明状态含义。

---

### 错误 6：所有 ID 都无脑 `BIGINT`

`BIGINT` 很稳，但不是任何字段都要无脑使用。

例如状态码、年龄、月份、星期、是否删除，用 `BIGINT` 就没有必要。

比较合理的原则是：

- 主键、流水号、日志 ID：可以偏保守，常用 `BIGINT UNSIGNED`。
- 小范围业务值：用更贴近语义的小类型。
- 不确定未来增长的关键字段：宁可给足范围。
- 非关键、小范围、非常明确的字段：不要无脑放大。

## 十三、面试与实务常问问题

### 13.1 `INT(11)` 和 `BIGINT(20)` 里的数字是什么意思？

是旧式显示宽度，不是取值范围，也不是位数限制。

### 13.2 `INT` 和 `BIGINT` 怎么选？

看最大值预估与系统生命周期。

- 资料量确定不大，`INT UNSIGNED` 通常够用。
- 主键、订单、日志、流水号这类长期增长字段，`BIGINT UNSIGNED` 更稳。

### 13.3 `UNSIGNED` 是不是一定比较好？

不是。

它适合业务上绝不为负的字段，但如果经常参与可能得到负数的计算，要小心表达式行为。

### 13.4 MySQL 的 `BOOLEAN` 是真正的布尔类型吗？

不是独立存储类型。`BOOLEAN` / `BOOL` 是 `TINYINT(1)` 的同义词。

### 13.5 `TINYINT(1)` 是否只能存 0 和 1？

不是。它仍然可以存 `TINYINT` 范围内的整数。要限制 `0/1`，需要约束或应用层校验。

### 13.6 为什么不建议用 `ZEROFILL`？

因为它只是旧式显示补零方案，而且会隐含 `UNSIGNED`。现代做法更推荐在查询层、应用层格式化，或把真正的业务编号存为字符串。

## 十五、一句话抓核心

整数类型的选择，本质上不是看括号里的显示宽度，而是看字段是否真的是数值、是否允许负数、最大范围是否足够，以及这个字段在业务中是主键、计数、状态码还是单纯的展示编号。
