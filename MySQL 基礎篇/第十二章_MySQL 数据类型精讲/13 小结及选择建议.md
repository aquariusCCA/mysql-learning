# 13 小结及选择建议

所属章节：[第十二章_MySQL 数据类型精讲](./README.md)

## 本节导读

这一篇不再介绍新的 MySQL 数据类型，而是把前面 12 篇内容收束成一套可以在建表时直接使用的「字段选型流程」。

你真正要解决的问题不是：

```text
MySQL 有哪些数据类型？
```

而是：

```text
当我面对一个真实业务字段时，应该怎么判断它到底该用哪种类型？
```

很多初学者建表时会下意识使用几个「万能默认值」：

```text
数字      -> INT
小数      -> DOUBLE
金额      -> FLOAT / DOUBLE
字符串    -> VARCHAR(255)
长字符串  -> TEXT
时间      -> DATETIME
状态      -> INT 或 VARCHAR
复杂数据  -> JSON
经纬度    -> VARCHAR 或两个 DOUBLE
```

这些写法不一定全部错误，但它们都太粗。真正的字段选型应该先看业务语义，再看范围、精度、长度、是否可变、是否需要索引、是否参与比较、是否会被频繁查询。

如果只能先记一句话：

> 字段类型不是根据「看起来像什么」来选，而是根据「它表达什么业务语义、需要什么计算规则、未来怎么查询维护」来选。

## 建议回查情境

遇到下面情况时，可以回到这一篇：

- 准备设计一张新表，但不知道字段类型怎么选。
- 不确定一个字段该用 `INT` 还是 `BIGINT`。
- 不确定金额该用 `DECIMAL` 还是 `DOUBLE`。
- 不确定 `created_at` / `updated_at` 该用 `DATETIME` 还是 `TIMESTAMP`。
- 不确定短字符串该用 `CHAR` 还是 `VARCHAR`。
- 不确定文章正文、日志、备注该用 `VARCHAR` 还是 `TEXT`。
- 不确定状态字段该用 `ENUM`、`VARCHAR`、`TINYINT` 还是字典表。
- 不确定多选标签该用 `SET`、JSON array 还是中间表。
- 不确定扩展字段该用普通列还是 `JSON`。
- 不确定经纬度该用两个 `DECIMAL` 字段还是 `POINT`。
- 想检查自己建表时有没有把「能存」误当成「设计合理」。
- 想在面试或工作中说明字段选型的理由。

## 30 秒复习入口

- 选字段类型的第一步不是背类型名，而是判断字段语义。
- 整数先看范围，再决定 `TINYINT`、`SMALLINT`、`INT`、`BIGINT`。
- 非负整数可以考虑 `UNSIGNED`，但不要机械套用。
- 自增主键中小系统常见 `BIGINT UNSIGNED`，避免未来容量焦虑。
- 金额、价格、余额、税额、利率等精确十进制数据，通常用 `DECIMAL`。
- `FLOAT` / `DOUBLE` 是近似值，不适合保存金额。
- `BIT` 适合底层位值或 bitmask，不适合普通布尔业务字段。
- 只存日期用 `DATE`，只存年份用 `YEAR`。
- 表示时长可以考虑 `TIME`，但要知道它不只是一天内时间。
- 业务上的固定日期时间通常用 `DATETIME`。
- 系统记录的时间点可以用 `TIMESTAMP`，但要理解时区转换。
- 普通短文本大多用 `VARCHAR`。
- 固定长度短代码可以考虑 `CHAR`。
- 大段文本再考虑 `TEXT`，不要把 `TEXT` 当成更大的 `VARCHAR`。
- `ENUM` 适合稳定、小规模、单选的候选值。
- `SET` 适合稳定、小规模、多选的候选值，但多数多对多关系更适合中间表。
- 二进制原始字节用 `BINARY` / `VARBINARY` / `BLOB`，不要和普通文本混用。
- 半结构化、低频查询、扩展属性可以考虑 `JSON`。
- 高频查询、排序、统计、关联的字段不应该藏在 `JSON` 里。
- 空间位置、路线、区域可以考虑空间类型，单点位置常用 `POINT`。
- 字段类型只解决「怎么存」，还要配合 `NOT NULL`、`DEFAULT`、`CHECK`、索引和业务规则。
- 好的字段设计应该让后端代码、SQL 查询、数据校验和未来维护都更简单。

## 一、先讲结论：字段选型的总流程

建表时可以按下面顺序判断。

```text
第一步：判断字段表达什么业务语义
第二步：判断属于哪一大类数据
第三步：判断范围、长度、精度、是否固定
第四步：判断是否需要索引、排序、比较、聚合、关联
第五步：判断是否需要约束，例如 NOT NULL、DEFAULT、CHECK、UNIQUE
第六步：判断是否有未来扩展或历史兼容问题
第七步：最后才考虑存储空间和性能细节
```

更具体地说：

| 判断问题 | 影响选择 |
| --- | --- |
| 是数字还是编号？ | 决定用数值类型还是字符串类型 |
| 是精确小数还是允许误差？ | 决定用 `DECIMAL` 还是 `FLOAT` / `DOUBLE` |
| 是日期、时长、业务时间还是系统时间点？ | 决定用 `DATE`、`TIME`、`DATETIME`、`TIMESTAMP` |
| 是普通短字符串还是大文本？ | 决定用 `VARCHAR` 还是 `TEXT` |
| 候选值是否稳定？ | 决定是否使用 `ENUM` / `SET` |
| 字段是否会被频繁查询？ | 决定是否拆成普通列并建立索引 |
| 是否是结构化扩展信息？ | 决定是否使用 `JSON` |
| 是否是几何对象？ | 决定是否使用空间类型 |
| 是否是原始 bytes？ | 决定是否使用二进制字符串类型 |

一句话：

> 先判断语义，再判断类型；先保证正确性，再考虑优化。

## 二、字段选型时最重要的 7 个问题

### 问题 1：这个字段是用来计算，还是用来展示？

很多字段虽然看起来是数字，但本质上不是数值。

例如：

```text
手机号
身份证号
银行卡号
邮政编码
订单展示编号
客户编号
合同编号
```

这些字段通常不应该用 `INT` 或 `BIGINT`，因为它们不是拿来做加减乘除的数值，而是业务标识或展示编号。

更合理的选择通常是：

```sql
phone        VARCHAR(20)
id_card_no   VARCHAR(30)
bank_card_no VARCHAR(32)
postal_code  VARCHAR(20)
order_no     VARCHAR(64)
```

判断标准：

```text
会不会参与数学计算？
会不会保留前导 0？
长度是否可能超过整数范围？
是否可能包含字母、横线、地区码、校验码？
```

只要答案偏向「展示、标识、匹配」，通常就应该考虑字符串。

---

### 问题 2：这个数字是否需要精确？

如果是下面这些字段，通常要求精确：

```text
金额
价格
余额
利息
税额
汇率
手续费率
折扣率
本金
```

应优先考虑：

```sql
DECIMAL(M, D)
```

例如：

```sql
amount DECIMAL(18, 2) NOT NULL DEFAULT 0.00
rate   DECIMAL(10, 6) NOT NULL
```

`FLOAT` / `DOUBLE` 适合的是允许近似误差的场景，例如：

```text
科学测量
传感器数据
模型评分
统计估算
地图距离近似值
```

判断标准：

```text
这个字段的小数误差是否会造成业务问题？
是否要参与对账、扣款、计费、结算？
是否要和 Java BigDecimal 对接？
```

如果是，优先 `DECIMAL`。

---

### 问题 3：这个时间是业务时间，还是系统记录时间？

常见判断：

| 字段语义 | 推荐类型 |
| --- | --- |
| 生日 | `DATE` |
| 入职日期 | `DATE` |
| 账单日期 | `DATE` |
| 年份 | `YEAR` 或 `SMALLINT`，看业务需求 |
| 会议开始时间 | `DATETIME` |
| 预约时间 | `DATETIME` |
| 订单创建时间 | `DATETIME` 或 `TIMESTAMP` |
| 资料更新时间 | `DATETIME` 或 `TIMESTAMP` |
| 音视频时长 | `TIME` 或整数秒数 |

一个简单判断：

```text
如果它是用户或业务约定的日历时间，通常偏 DATETIME。
如果它是系统记录事件发生的时间点，可以考虑 TIMESTAMP。
```

但不能机械认为：

```text
created_at 一定用 TIMESTAMP
业务时间一定不能用 TIMESTAMP
```

真正要看团队是否统一时区策略、是否跨时区部署、是否需要记录全球统一时间点。

---

### 问题 4：这个字符串长度是否固定？是否会很长？

常见判断：

| 字段语义 | 推荐类型 |
| --- | --- |
| 国家代码 `TW`、`US` | `CHAR(2)` |
| 币别 `TWD`、`USD` | `CHAR(3)` |
| 用户名 | `VARCHAR(50)` |
| 邮箱 | `VARCHAR(255)` |
| 标题 | `VARCHAR(100)` / `VARCHAR(200)` |
| 地址 | `VARCHAR(255)` / `VARCHAR(500)` |
| 文章正文 | `TEXT` |
| 长评论 | `TEXT` |
| 日志原文 | `TEXT` / 外部日志系统 |

判断标准：

```text
长度是否固定？
是否多数行都很短？
是否会频繁作为查询条件？
是否需要完整建立索引？
是否只是展示大段内容？
```

普通业务字符串先考虑 `VARCHAR`。只有当内容确实可能很长，并且语义上就是大文本时，再考虑 `TEXT`。

---

### 问题 5：这个字段是否是固定候选值？候选值会不会变化？

例如订单状态：

```text
pending
paid
shipped
finished
cancelled
```

可以选择：

```sql
status ENUM('pending', 'paid', 'shipped', 'finished', 'cancelled')
```

也可以选择：

```sql
status VARCHAR(20) NOT NULL
CHECK (status IN ('pending', 'paid', 'shipped', 'finished', 'cancelled'))
```

还可以选择：

```sql
status_code TINYINT NOT NULL
```

再配合代码枚举或字典表。

判断标准：

```text
候选值是否很少？
是否稳定？
是否需要后台维护？
是否需要多语言显示？
是否需要排序权重、启用状态、说明文字？
是否有外部系统对接编码？
```

如果候选值稳定、小规模、不会经常变，`ENUM` 可以考虑。

如果候选值会运营配置、需要后台维护或经常扩展，通常更适合字典表。

---

### 问题 6：这个字段是否会被频繁查询、排序、统计或关联？

这是决定是否使用 `JSON`、`TEXT`、`BLOB`、空间类型的重要问题。

例如：

```sql
profile JSON
```

如果 `profile` 只是保存低频展示的扩展信息，可以接受。

但如果经常要查询：

```sql
profile->>'$.level'
profile->>'$.city'
profile->>'$.riskScore'
```

那就应该考虑把这些字段拆出来：

```sql
level      TINYINT
city_code  VARCHAR(20)
risk_score DECIMAL(10, 4)
```

判断标准：

```text
是否会出现在 WHERE？
是否会出现在 ORDER BY？
是否会出现在 GROUP BY？
是否会建立索引？
是否会和其他表 JOIN？
是否会被报表频繁统计？
```

如果会，优先普通列。

---

### 问题 7：这个字段的数据库约束是否表达清楚？

字段类型只是第一层，约束才让数据更接近业务规则。

例如金额字段：

```sql
amount DECIMAL(18, 2) NOT NULL DEFAULT 0.00 CHECK (amount >= 0)
```

状态字段：

```sql
status VARCHAR(20) NOT NULL CHECK (status IN ('draft', 'active', 'disabled'))
```

邮箱字段：

```sql
email VARCHAR(255) NOT NULL UNIQUE
```

创建时间字段：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

不要只想「用什么类型能存进去」，还要想：

```text
可不可以为空？
默认值是什么？
是否唯一？
是否不能为负？
是否只能在固定范围？
是否需要索引？
是否需要自动更新？
```

| 业务字段 | 推荐类型 | 说明 |
| --- | --- | --- |
| 自增主键 | `BIGINT UNSIGNED` | 中长期系统更稳，避免 `INT` 容量焦虑 |
| 小表主键 | `INT UNSIGNED` | 数据量确定很小也可以使用 |
| 年龄 | `TINYINT UNSIGNED` | 但年龄通常也可以从生日计算，不一定要存 |
| 数量 | `INT UNSIGNED` / `BIGINT UNSIGNED` | 看最大数量范围 |
| 库存 | `INT` 或 `INT UNSIGNED` | 若允许扣成负数表示预占，要谨慎使用 `UNSIGNED` |
| 状态码 | `TINYINT` / `SMALLINT` / `ENUM` / `VARCHAR + CHECK` | 看团队编码规范 |
| 手机号 | `VARCHAR(20)` | 不是数值，可能有国家码、前导 0 |
| 身份证号 | `VARCHAR(30)` | 可能包含字母或校验码 |
| 银行卡号 | `VARCHAR(32)` | 不做数学计算，可能超出整数安全范围 |
| 订单号 | `VARCHAR(64)` | 展示编号通常不是数值 |
| 金额 | `DECIMAL(18,2)` | 金融、订单、付款常见选择 |
| 汇率 | `DECIMAL(18,8)` 或按业务决定 | 小数位通常比金额更多 |
| 利率 | `DECIMAL(10,6)` 或按业务决定 | 注意百分比和小数表示法 |
| 模型分数 | `DOUBLE` / `DECIMAL` | 若只是近似评分可用 `DOUBLE` |
| 生日 | `DATE` | 不需要时间部分 |
| 创建时间 | `DATETIME(3)` / `TIMESTAMP(3)` | 看时区策略和团队规范 |
| 更新时间 | `DATETIME(3)` / `TIMESTAMP(3)` | 常配合 `ON UPDATE` |
| 预约时间 | `DATETIME` | 通常是业务日历时间 |
| 登录时间 | `DATETIME` / `TIMESTAMP` | 看是否要全球统一时间点 |
| 音视频时长 | `INT UNSIGNED` 秒数 / `TIME` | 秒数常更好计算 |
| 用户名 | `VARCHAR(50)` | 长度按产品规则决定 |
| 邮箱 | `VARCHAR(255)` | 常见做法，并考虑唯一索引 |
| 标题 | `VARCHAR(100)` / `VARCHAR(200)` | 按业务限制 |
| 地址 | `VARCHAR(255)` / `VARCHAR(500)` | 如果很长再评估 `TEXT` |
| 文章正文 | `TEXT` / `MEDIUMTEXT` | 大文本语义 |
| 备注 | `VARCHAR(500)` / `TEXT` | 看长度上限和查询方式 |
| 头像 URL | `VARCHAR(500)` | 存地址，不是图片 bytes |
| 图片文件 | 存 object key / URL，必要时 `BLOB` | 大文件通常不直接放 MySQL |
| 密码 hash | `VARCHAR` 或 `VARBINARY` | 看 hash 输出格式 |
| SHA-256 原始值 | `BINARY(32)` | 32 bytes 原始二进制 |
| UUID 文本 | `CHAR(36)` | 可读性好 |
| UUID bytes | `BINARY(16)` | 空间更省，程序处理稍复杂 |
| 扩展配置 | `JSON` | 低频查询、结构可变时适合 |
| 经纬度展示 | `DECIMAL(10,7)` 经度 + 纬度 | 简单展示和普通查询足够 |
| 经纬度空间查询 | `POINT SRID 4326` | 需要空间函数和空间索引时考虑 |
| 标签多对多 | 中间表 | 不建议默认用 `SET` 或 JSON array |
| 角色权限 | 中间表 / 权限表 | 需要扩展、查询、授权管理 |

## 五、数值类型选择建议

### 1. 整数类型

整数类型选择时，最重要的是范围。

| 类型 | 适合场景 |
| --- | --- |
| `TINYINT` | 小状态码、开关、等级、很小范围数字 |
| `SMALLINT` | 中小范围编号、分数、分类序号 |
| `MEDIUMINT` | MySQL 特有类型，较少用，除非明确需要 |
| `INT` | 普通数量、普通编号、中等规模表主键 |
| `BIGINT` | 大表主键、流水号、计数器、可能长期增长的数据 |

常见建议：

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT
```

适合中长期业务系统，尤其是你无法确定未来数据量时。

但也不要把 `BIGINT` 机械套用到所有字段。例如：

```sql
status BIGINT
age BIGINT
is_deleted BIGINT
```

这种设计就太粗。

---

### 2. `UNSIGNED` 的判断

`UNSIGNED` 表示不允许负数，并扩大非负范围。

适合：

```text
自增 ID
数量
次数
浏览量
点赞数
库存数量，前提是不允许负库存
```

不一定适合：

```text
余额变动值
库存变动值
温度
差额
盈亏
可正可负的统计值
```

例如：

```sql
change_amount DECIMAL(18,2) NOT NULL
```

这里不要用非负约束，因为变动金额可能是正数，也可能是负数。

---

### 3. 精确小数优先 `DECIMAL`

金额字段示例：

```sql
amount DECIMAL(18,2) NOT NULL DEFAULT 0.00 CHECK (amount >= 0)
```

汇率字段示例：

```sql
exchange_rate DECIMAL(18,8) NOT NULL
```

利率字段示例：

```sql
annual_rate DECIMAL(10,6) NOT NULL
```

关键不是「有小数就一定 `DECIMAL`」，而是：

```text
需要十进制精确 -> DECIMAL
允许近似误差   -> FLOAT / DOUBLE
```

---

### 4. 浮点类型谨慎用于业务金额

不建议：

```sql
price DOUBLE
balance FLOAT
```

因为 `FLOAT` / `DOUBLE` 是近似值。

可以考虑：

```sql
temperature DOUBLE
model_score DOUBLE
sensor_value DOUBLE
```

前提是业务接受误差。

---

### 5. `BIT` 不等于普通布尔字段首选

普通布尔字段更常见：

```sql
is_deleted TINYINT(1) NOT NULL DEFAULT 0
```

`BIT` 更适合：

```text
底层位标记
bitmask
协议字段
权限位压缩表示
```

但如果权限要经常扩展、查询、维护，通常应该设计权限表，而不是强行使用 bitmask。

---

## 六、日期与时间类型选择建议

### 1. 只存日期：`DATE`

适合：

```text
生日
账单日期
入职日期
交易日期
```

示例：

```sql
birth_date DATE
```

不要为了省事写成：

```sql
birth_date DATETIME
```

如果时间部分没有意义，就不要存时间部分。

---

### 2. 表示时长：`TIME` 或整数秒数

`TIME` 可以表示时长，但后端系统中也常用整数秒数。

例如：

```sql
duration_seconds INT UNSIGNED NOT NULL
```

优点是计算简单。

如果需要显示 `HH:MM:SS` 或使用 MySQL 时间函数，也可以考虑：

```sql
duration TIME
```

---

### 3. 业务固定时间：常用 `DATETIME`

适合：

```text
预约时间
会议时间
活动开始时间
课程上课时间
```

示例：

```sql
appointment_at DATETIME NOT NULL
```

这类时间通常表达的是业务日历上的某个时间，不一定希望因为 session time_zone 改变而显示不同结果。

---

### 4. 系统记录时间：`DATETIME` 或 `TIMESTAMP`

常见写法一：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

常见写法二：

```sql
created_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

选择重点：

```text
是否需要 UTC 转换？
是否跨时区部署？
是否有历史日期超过 TIMESTAMP 范围？
团队 ORM 和数据库连接时区是否统一？
```

不要只背「创建时间用 `TIMESTAMP`」或「所有时间用 `DATETIME`」。

---

### 5. 日期范围查询建议使用半开区间

推荐：

```sql
WHERE created_at >= '2026-05-01 00:00:00'
  AND created_at <  '2026-05-02 00:00:00'
```

不推荐：

```sql
WHERE DATE(created_at) = '2026-05-01'
```

原因是对字段套函数通常不利于普通索引使用。

---

## 七、字符串类型选择建议

### 1. `CHAR` 适合固定长度短字符串

适合：

```text
国家代码：TW、US、JP
币别代码：TWD、USD、JPY
固定长度 hash 片段
固定长度性别代码或类型代码，视规范而定
```

示例：

```sql
currency CHAR(3) NOT NULL
country_code CHAR(2) NOT NULL
```

---

### 2. `VARCHAR` 是普通业务字符串主力

适合：

```text
姓名
邮箱
标题
地址
URL
订单号
客户编号
```

示例：

```sql
username VARCHAR(50) NOT NULL,
email    VARCHAR(255) NOT NULL,
address  VARCHAR(255)
```

注意：

```text
VARCHAR(M) 的 M 是字符数，不是 bytes。
实际存储和最大可用长度会受字符集、行大小、索引长度等影响。
```

---

### 3. `TEXT` 适合大文本，但不是万能字符串

适合：

```text
文章正文
长评论
说明文档
日志原文
```

不适合：

```text
用户名
邮箱
订单号
状态
高频查询条件
外键字段
需要完整唯一约束的字段
```

示例：

```sql
content TEXT NOT NULL
```

如果要对 `TEXT` 建索引，通常需要考虑前缀索引或全文索引，而不是当成普通 `VARCHAR` 使用。

---

### 4. 字符集优先统一为 `utf8mb4`

现代项目通常建议统一：

```sql
CHARACTER SET utf8mb4
COLLATE utf8mb4_0900_ai_ci
```

或使用团队统一的 `utf8mb4` collation。

重点是：

```text
不要同一个库、同一个系统里混用一堆字符集和排序规则。
```

否则比较、排序、关联、唯一约束都可能出现不易察觉的问题。

---

## 八、`ENUM` / `SET` / 字典表选择建议

### 1. `ENUM` 适合稳定单选值

适合：

```text
性别枚举，前提是业务定义稳定
订单状态，前提是流程稳定且不需要后台配置
审核状态，前提是候选值很少且稳定
```

示例：

```sql
status ENUM('draft', 'active', 'disabled') NOT NULL DEFAULT 'draft'
```

注意：

```text
ENUM 的排序默认与定义顺序有关，不是单纯字典序。
ENUM 的内部编号不是数据库索引。
不建议使用 ENUM('0','1','2') 这类看起来像数字的值。
```

---

### 2. `SET` 适合稳定多选值，但使用面更窄

适合：

```text
非常稳定的小规模多选开关
固定能力标记
固定特性标签
```

不适合：

```text
用户标签
商品标签
角色权限
文章分类
任何需要扩展、统计、维护、关联的多对多关系
```

这些更适合中间表：

```sql
user_tag (
  user_id BIGINT UNSIGNED NOT NULL,
  tag_id  BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (user_id, tag_id)
)
```

---

### 3. 字典表适合可维护、可扩展候选值

如果候选值需要：

```text
后台新增
显示名称
排序权重
启用 / 禁用
多语言
说明文字
外部系统映射码
```

就优先考虑字典表。

示例：

```sql
status_dict (
  code        VARCHAR(30) PRIMARY KEY,
  name        VARCHAR(100) NOT NULL,
  sort_order  INT NOT NULL DEFAULT 0,
  enabled     TINYINT(1) NOT NULL DEFAULT 1
)
```

---

## 九、二进制、JSON、空间类型选择建议

### 1. 二进制字符串保存 bytes，不保存普通文字

适合：

```text
UUID 原始 bytes
hash 原始 bytes
加密后的二进制内容
文件小对象
协议 payload
```

常见：

```sql
uuid_bin BINARY(16)
sha256   BINARY(32)
```

如果是普通文字，不应该用二进制类型。

---

### 2. 大文件通常不建议直接塞 MySQL

图片、PDF、Excel、视频等文件，可以直接用 `BLOB` 存，但并不代表一定应该这么做。

多数业务系统更常见：

```text
文件存 object storage / 文件服务器
MySQL 只存 file_id、url、object_key、metadata
```

示例：

```sql
file_key VARCHAR(500) NOT NULL,
file_name VARCHAR(255) NOT NULL,
file_size BIGINT UNSIGNED NOT NULL
```

除非有事务一致性、审计、部署条件等明确需求，否则不要默认把大文件内容塞进数据库。

---

### 3. JSON 适合扩展属性，不适合核心字段逃避设计

适合：

```text
扩展配置
第三方接口原始响应摘要
低频展示属性
不稳定结构的补充信息
```

不适合：

```text
金额
状态
用户 ID
订单 ID
创建时间
高频查询条件
报表统计字段
关系数据
```

合理示例：

```sql
extra JSON
```

但如果你经常这样查：

```sql
WHERE extra->>'$.status' = 'active'
ORDER BY extra->>'$.score'
```

就应该认真考虑拆字段或建立生成列 / 函数索引。

---

### 4. 空间类型适合几何对象，不适合普通地址文本

适合：

```text
店铺位置
ATM 位置
路线轨迹
服务区域
地理围栏
```

示例：

```sql
location POINT NOT NULL SRID 4326
```

如果只是保存地址：

```sql
address VARCHAR(255)
```

如果只是展示经纬度：

```sql
longitude DECIMAL(10,7)
latitude  DECIMAL(10,7)
```

如果要做点在区域内、附近查询、空间关系判断，再考虑空间类型和空间索引。

---

## 十、字段属性和类型要一起设计

### 1. `NOT NULL`

不要默认所有字段都允许 `NULL`。

适合 `NOT NULL` 的字段：

```text
主键
业务必填字段
状态
创建时间
金额，若业务上可用 0 表示
数量，若业务上可用 0 表示
```

但不要滥用默认值掩盖未知状态。

例如未知生日：

```sql
birth_date DATE NULL
```

比下面这种更合理：

```sql
birth_date DATE NOT NULL DEFAULT '0000-00-00'
```

---

### 2. `DEFAULT`

默认值应该表达业务默认，而不是为了省掉后端判断。

适合：

```sql
status TINYINT NOT NULL DEFAULT 0
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
is_deleted TINYINT(1) NOT NULL DEFAULT 0
```

不适合：

```sql
email VARCHAR(255) NOT NULL DEFAULT ''
id_card_no VARCHAR(30) NOT NULL DEFAULT ''
```

空字符串不是所有未知值的合理替代品。

---

### 3. `CHECK`

`CHECK` 可以表达简单业务约束。

示例：

```sql
amount DECIMAL(18,2) NOT NULL CHECK (amount >= 0),
score  TINYINT UNSIGNED NOT NULL CHECK (score <= 100)
```

但复杂规则仍然应放在应用层或业务流程中。

---

### 4. `UNIQUE`

唯一约束适合真正业务唯一的字段。

示例：

```sql
email VARCHAR(255) NOT NULL UNIQUE,
order_no VARCHAR(64) NOT NULL UNIQUE
```

不要只在后端检查唯一，数据库层也应该保护关键唯一性。

---

### 5. 索引设计要配合字段类型

字段是否适合索引，要看：

```text
字段长度
选择性
查询频率
排序需求
是否参与 JOIN
是否经常范围查询
```

典型不佳设计：

```sql
content TEXT
```

然后频繁：

```sql
WHERE content = '...'
ORDER BY content
```

这说明字段类型或查询模型本身可能需要重设。

---

## 十一、常见错误选型与修正

### 错误 1：所有整数都用 `INT`

不够精细。

修正：

```text
小状态、小等级、小范围 -> TINYINT / SMALLINT
普通数量、普通编号     -> INT
大表主键、长期流水号   -> BIGINT
```

---

### 错误 2：金额用 `DOUBLE`

不建议。

修正：

```sql
amount DECIMAL(18,2) NOT NULL
```

如果是汇率或利率，再按业务精度增加小数位。

---

### 错误 3：手机号用 `BIGINT`

不建议。

修正：

```sql
phone VARCHAR(20)
```

手机号是标识，不是数值。

---

### 错误 4：所有字符串都用 `VARCHAR(255)`

不够具体。

修正：

```sql
username VARCHAR(50)
title    VARCHAR(200)
email    VARCHAR(255)
```

字段长度应该来自业务规则，而不是盲目复制。

---

### 错误 5：所有时间都用 `DATETIME`

太粗。

修正：

```text
只要日期 -> DATE
时长     -> TIME 或整数秒
业务时间 -> DATETIME
系统时间 -> DATETIME / TIMESTAMP，看时区策略
```

---

### 错误 6：用 `TEXT` 保存所有可能变长的字段

不建议。

修正：

```text
普通业务字符串 -> VARCHAR
大段正文       -> TEXT
```

---

### 错误 7：为了灵活，把字段都塞进 `JSON`

短期省事，长期可能很痛。

修正：

```text
高频查询字段 -> 普通列
低频扩展字段 -> JSON
多对多关系   -> 中间表
```

---

### 错误 8：用 `SET` 做用户标签

不建议。

修正：

```sql
user_tag (
  user_id BIGINT UNSIGNED NOT NULL,
  tag_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (user_id, tag_id)
)
```

---

### 错误 9：经纬度存在 `VARCHAR`

不建议。

修正：

简单场景：

```sql
longitude DECIMAL(10,7),
latitude  DECIMAL(10,7)
```

空间查询场景：

```sql
location POINT NOT NULL SRID 4326
```

---

### 错误 10：用默认值掩盖未知值

不建议：

```sql
birth_date DATE NOT NULL DEFAULT '0000-00-00'
email VARCHAR(255) NOT NULL DEFAULT ''
```

修正：

```sql
birth_date DATE NULL
email VARCHAR(255) NULL
```

如果业务上确实必填，就在流程中保证它真实存在。

---

## 十二、建表示例：用户表

下面是一个偏实务的用户表例子。

```sql
CREATE TABLE user_account (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键 ID',
  user_no VARCHAR(64) NOT NULL COMMENT '用户展示编号',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  email VARCHAR(255) NULL COMMENT '邮箱',
  phone VARCHAR(20) NULL COMMENT '手机号',
  password_hash VARCHAR(255) NOT NULL COMMENT '密码 hash',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1=启用，2=停用，3=锁定',
  birth_date DATE NULL COMMENT '生日',
  balance DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '账户余额',
  profile_extra JSON NULL COMMENT '低频扩展资料',
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  deleted TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_no (user_no),
  UNIQUE KEY uk_email (email),
  KEY idx_phone (phone),
  KEY idx_status_created_at (status, created_at),
  CHECK (balance >= 0),
  CHECK (status IN (1, 2, 3))
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  COMMENT='用户账户表';
```

这个例子体现了几个原则：

- 主键用 `BIGINT UNSIGNED`，适合长期增长。
- 展示编号 `user_no` 用 `VARCHAR`，不是数值。
- 手机号用 `VARCHAR`，不是 `BIGINT`。
- 余额用 `DECIMAL`，不是 `DOUBLE`。
- 生日用 `DATE`，不是 `DATETIME`。
- 状态用小整数，并用 `CHECK` 表达范围。
- 扩展资料放 `JSON`，但核心字段没有藏进 JSON。
- 时间字段使用 `DATETIME(3)`，精度和默认值明确。
- 字符集和 collation 明确。

## 十三、建表示例：订单表

```sql
CREATE TABLE orders (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键 ID',
  order_no VARCHAR(64) NOT NULL COMMENT '订单号',
  user_id BIGINT UNSIGNED NOT NULL COMMENT '用户 ID',
  total_amount DECIMAL(18,2) NOT NULL COMMENT '订单总金额',
  paid_amount DECIMAL(18,2) NOT NULL DEFAULT 0.00 COMMENT '已支付金额',
  currency CHAR(3) NOT NULL DEFAULT 'TWD' COMMENT '币别',
  status VARCHAR(20) NOT NULL DEFAULT 'pending' COMMENT '订单状态',
  paid_at DATETIME(3) NULL COMMENT '支付时间',
  remark VARCHAR(500) NULL COMMENT '备注',
  snapshot JSON NULL COMMENT '低频订单快照',
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_created_at (user_id, created_at),
  KEY idx_status_created_at (status, created_at),
  CHECK (total_amount >= 0),
  CHECK (paid_amount >= 0),
  CHECK (status IN ('pending', 'paid', 'cancelled', 'refunded', 'finished'))
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  COMMENT='订单表';
```

这里的重点：

- `order_no` 是业务编号，用 `VARCHAR`。
- 金额全部用 `DECIMAL`。
- 币别是固定 3 字符代码，用 `CHAR(3)`。
- 状态用 `VARCHAR + CHECK`，比 `ENUM` 更容易和应用层枚举保持可读性。
- 订单快照可以用 `JSON`，因为它更多是历史展示和低频读取。
- 高频查询字段 `user_id`、`status`、`created_at` 没有放进 JSON。

## 十四、从 Java / MyBatis 角度看字段选型

你目前往 Java 全端方向走，字段类型还要考虑 Java 映射。

| MySQL 类型 | Java 常见类型 | 注意事项 |
| --- | --- | --- |
| `TINYINT` / `SMALLINT` / `INT` | `Integer` | 注意是否可能为 `NULL` |
| `BIGINT` | `Long` | ID 常用 `Long` |
| `DECIMAL` | `BigDecimal` | 金额不要用 `Double` |
| `FLOAT` / `DOUBLE` | `Float` / `Double` | 不适合精确金额 |
| `DATE` | `LocalDate` | 只含日期 |
| `TIME` | `LocalTime` / `Duration` | 表示时长时可能用 `Duration` 更清楚 |
| `DATETIME` / `TIMESTAMP` | `LocalDateTime` / `Instant` / `OffsetDateTime` | 视时区策略决定 |
| `CHAR` / `VARCHAR` / `TEXT` | `String` | 注意长度和字符集 |
| `JSON` | `String` / `JsonNode` / DTO | 注意序列化和类型处理器 |
| `BINARY` / `VARBINARY` | `byte[]` | 注意十六进制显示和传输 |
| `BLOB` | `byte[]` / `InputStream` | 大对象不要随便 `SELECT *` |
| `POINT` 等空间类型 | WKT String / 专门几何类 | 通常需要转换或 TypeHandler |

几个关键习惯：

```text
金额：MySQL DECIMAL <-> Java BigDecimal
ID：MySQL BIGINT <-> Java Long
日期：MySQL DATE <-> Java LocalDate
普通日期时间：MySQL DATETIME <-> Java LocalDateTime
真正时间点：可考虑 Instant / OffsetDateTime，但要统一时区策略
```

---

## 十五、字段选型检查清单

建表前可以逐项检查：

```text
[ ] 这个字段的业务语义是否清楚？
[ ] 它是数值、文本、时间、二进制、JSON，还是空间数据？
[ ] 如果是数字，是否需要数学计算？是否允许负数？范围多大？
[ ] 如果是小数，是否要求精确？
[ ] 如果是时间，具体是日期、时长、业务时间，还是系统时间点？
[ ] 如果是字符串，长度是否固定？最大长度是否有业务规则？
[ ] 如果是大文本，是否真的需要 TEXT？是否会被频繁查询？
[ ] 如果是状态，候选值是否稳定？是否需要后台维护？
[ ] 如果是多选，是否其实是多对多关系？
[ ] 如果是 JSON，里面的字段是否会被频繁 WHERE / ORDER BY / GROUP BY？
[ ] 如果是文件，是否应该只存 URL / object key？
[ ] 如果是经纬度，是否需要空间查询？
[ ] 是否需要 NOT NULL？
[ ] 是否需要 DEFAULT？默认值是否有业务意义？
[ ] 是否需要 UNIQUE？
[ ] 是否需要 CHECK？
[ ] 是否需要索引？索引字段长度是否合适？
[ ] Java 类型映射是否清楚？
[ ] 未来扩展时是否容易维护？
```

如果这些问题都能回答，字段选型通常不会太差。

---

## 十六、面试或工作中可以怎么表达字段选型理由

### 问：为什么金额不用 `DOUBLE`？

可以答：

```text
金额属于精确十进制数据，不能接受二进制浮点近似误差。
所以 MySQL 用 DECIMAL(M,D)，Java 用 BigDecimal。
DOUBLE 更适合允许误差的测量值、统计值或科学计算。
```

---

### 问：为什么手机号不用 `BIGINT`？

可以答：

```text
手机号是业务标识，不是数值。
它不需要加减乘除，而且可能有国家码、前导 0、格式符号。
所以应该用 VARCHAR，而不是整数类型。
```

---

### 问：`DATETIME` 和 `TIMESTAMP` 怎么选？

可以答：

```text
DATETIME 更像保存业务日历上的日期时间，不会因为 session time_zone 改变而自动转换。
TIMESTAMP 更适合记录实际时间点，会按时区和 UTC 做转换。
如果是 created_at / updated_at，两者都可能使用，关键是团队时区策略必须统一。
```

---

### 问：为什么不用 JSON 保存所有扩展字段？

可以答：

```text
JSON 适合低频、半结构化、变化较快的扩展属性。
但如果某个字段会高频查询、排序、分组、统计、关联或建立索引，就应该拆成普通列。
否则 SQL 可读性、索引设计、数据约束和维护都会变差。
```

---

### 问：`ENUM` 和字典表怎么选？

可以答：

```text
ENUM 适合稳定、小规模、不会频繁变化的单选值。
如果候选值要后台维护、需要显示名称、排序、多语言、启用停用或外部编码映射，就更适合字典表。
```

## 十七、自测题

### 问题 1

订单金额应该用 `DOUBLE` 还是 `DECIMAL`？为什么？

答案：

应使用 `DECIMAL`。

因为订单金额要求精确十进制计算，不能接受浮点近似误差。

---

### 问题 2

手机号应该用 `BIGINT` 吗？

答案：

通常不应该。

手机号是标识符，不是用于数学计算的数值。应使用 `VARCHAR(20)` 或按业务规则设定长度。

---

### 问题 3

`created_at` 一定要用 `TIMESTAMP` 吗？

答案：

不一定。

`DATETIME` 和 `TIMESTAMP` 都可以用于系统记录时间。重点是团队是否统一时区策略、是否需要 UTC 转换、是否受 `TIMESTAMP` 范围限制。

---

### 问题 4

文章正文应该用 `VARCHAR(5000)` 还是 `TEXT`？

答案：

如果确实是大段正文，通常应考虑 `TEXT`。

但如果是摘要、标题、短备注，应该优先 `VARCHAR`，并根据业务限制设置长度。

---

### 问题 5

商品标签可以用 `SET` 吗？

答案：

技术上可以，但多数情况下不建议。

商品标签通常会扩展、统计、筛选、关联和后台维护，更适合标签表 + 商品标签中间表。

---

### 问题 6

扩展信息用 `JSON` 是否一定比较好？

答案：

不一定。

如果只是低频展示的扩展属性，`JSON` 可以考虑。如果其中字段经常被查询、排序、统计、关联，就应该拆成普通列或建立合适的索引策略。

---

### 问题 7

经纬度一定要用 `POINT` 吗？

答案：

不一定。

如果只是展示位置，两个 `DECIMAL` 字段更简单。如果需要空间关系判断、附近查询、区域判断，再考虑 `POINT`、`SRID`、空间函数和空间索引。

---

### 问题 8

为什么不能用 `0000-00-00` 表示未知生日？

答案：

因为这不是一个真实日期，而且容易受 SQL mode 影响，也会污染业务语义。

未知值应该用 `NULL`，或者用额外状态字段表达。

---

## 十八、本章最终总结

第十二章的核心不是背完 MySQL 所有数据类型，而是建立下面这套思维：

```text
字段语义 -> 数据大类 -> 范围 / 精度 / 长度 -> 查询方式 -> 约束与索引 -> 可维护性
```

可以把整章压缩成下面这张表：

| 字段语义 | 优先考虑 |
| --- | --- |
| 小范围整数 | `TINYINT` / `SMALLINT` |
| 普通整数 | `INT` |
| 大量增长 ID / 流水号 | `BIGINT` |
| 精确金额 / 价格 / 利率 | `DECIMAL` |
| 允许误差的测量值 | `FLOAT` / `DOUBLE` |
| 普通布尔字段 | `TINYINT(1)` |
| 底层位标记 | `BIT` |
| 日期 | `DATE` |
| 时长 | `TIME` 或整数秒数 |
| 业务日期时间 | `DATETIME` |
| 系统时间点 | `DATETIME` / `TIMESTAMP`，看时区策略 |
| 固定短代码 | `CHAR` |
| 普通字符串 | `VARCHAR` |
| 大段文本 | `TEXT` |
| 稳定单选值 | `ENUM` 或 `VARCHAR + CHECK` |
| 稳定小规模多选值 | `SET`，谨慎使用 |
| 多对多关系 | 中间表 |
| 原始 bytes | `BINARY` / `VARBINARY` / `BLOB` |
| 半结构化扩展属性 | `JSON` |
| 坐标、路线、区域 | 空间类型 |

最后再记住这几条：

- `INT`、`VARCHAR(255)`、`DATETIME` 不是万能三件套。
- 金额不要用浮点数。
- 业务编号通常用字符串，不要因为它长得像数字就用整数。
- `TEXT`、`JSON`、`BLOB` 不应该成为逃避字段设计的工具。
- 高频查询字段尽量设计成普通列。
- 字段类型要和 `NOT NULL`、`DEFAULT`、`CHECK`、`UNIQUE`、索引一起看。
- 表结构设计的目标不是「能存进去」，而是「语义清楚、约束明确、查询友好、长期可维护」。

一句话抓核心：

> 好的 MySQL 字段选型，是把业务语义、数据范围、计算精度、查询方式和维护成本一起考虑后的结果，而不是套用某个万能默认类型。
